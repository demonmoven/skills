# Gloop 前端视觉改版执行方案·纯方案增量版 v0.2.1

> 用途：这是一份可直接交给代码 Agent 的增量执行方案。
> 特点：仍然不限定具体文件路径，但必须建立在仓库现状之上，禁止平行发明 token、主题、组件和数据流。

---

## 1. 文档定位

`v0.1` 的问题不是方向错，而是缺少现状基线，导致执行时容易：

1. 重复定义 token
2. 和现有 6 套主题打架
3. 重复造已有组件
4. 误判 SSE 的现状能力
5. 和已有 spec 重叠

因此，`v0.2` 的目标不是重写设计方向，而是把方案改成一份**面向现有仓库的增量执行稿**。

---

## 2. 现状基线

## A. token 基线

当前样式系统已经存在完整 token 体系，至少包括：

1. `--slime-*`
2. `--brand-*`
3. `--warrior-gold`
4. `--mage-violet`
5. `--ink-*`
6. 语义色
7. radius / shadow / spacing scale

### 约束

1. 本方案**不新增平行品牌 token 命名**。
2. 禁止新造 `--gloop-cyan`、`--primary-gloop` 这类与现有 token 平行的变量。
3. 本轮只允许：
   - 沿用现有 token
   - 补充使用规则
   - 收敛局部组件的使用方式

### 使用规则

1. `--brand-*`
   - 继续作为主题主色来源。
   - 主按钮、激活态、主选择态默认跟随 `--brand-*`。

2. `--slime-*`
   - 保持为跨主题稳定常量。
   - 只用于 Gloop 焦点强调、品牌提示、局部识别位。
   - 不替代主题主色。

3. `--warrior-gold` / `--mage-violet`
   - 继续作为角色 / phase 语义色。
   - 仅用于轻量角色提示，不升级为页面主色。

## B. 主题基线

当前已有 6 套主题：

1. `obsidian`
2. `bili`
3. `teal`
4. `emerald`
5. `violet`
6. `sakura`

### 约束

1. 本方案**不重做主题系统**。
2. 本方案**不收敛主题数量**。
3. 本轮必须兼容现有 6 套主题。

### 执行规则

1. 主按钮、激活态、选中态继续跟随当前主题的 `--brand-*`。
2. `--slime-*` 只作为跨主题一致的焦点强调，不替代 `--brand-*`。
3. `warrior / mage` 语义色只用于角色感知，不允许抢过主题主色。

## C. 组件基线

当前仓库已经存在一批与本方案高度相关的组件或视图能力：

1. `EventTimeline`
2. `ExecutionTrace`
3. `PhaseProgressBar`
4. `StatusBadge`
5. `QuestSummary`
6. `MageReviewBand`
7. `DesignPlanCard`
8. `FinalVerdictCard`
9. 首页已有 `attentionSections / pipeline / primaryStatus / primaryTone` 这类指挥中心雏形

### 约束

1. 本方案默认采用**改造优先，新增次之**。
2. 在没有明确缺口前，不新建与上述组件平行的新组件。
3. 每一项改动都应先回答：
   - 现状由哪个组件承担？
   - 本轮是复用、改造，还是补一个小壳层？

## D. 数据流基线

当前流能力要按真实现状处理：

1. SSE 已存在
2. `useGlobalQuestStream` 目前主要承担“刷新触发器”角色
3. 详情页已有事件 / 轨迹能力
4. 原始 JSON / trace 已可用于调试和证据展示

### 关键事实

当前 SSE 不应被假设为“现成的详情页展示数据源”。  
在现状下，它更接近：

1. 触发刷新
2. 表示有更新发生
3. 驱动重新拉取

而不是直接提供完整的人类可读工作摘要。

### 约束

1. 本方案 `P0` **不把 SSE 升级为新的展示架构**。
2. 本方案 `P0` **不要求后端新增 API**。
3. 若要把 SSE 升级为真正的“正在发生什么”数据源，必须作为 `P1` 之后的专项能力推进。

## E. 现有 spec 基线

仓库内已存在多份相关 spec，至少包括：

1. `homepage-optimization-spec-v0.2.1`
2. `homepage-optimization-spec-v0.2`
3. `platform-optimization-spec-v0.1`
4. 其他已落地的首页优化 / 平台改造 / 重构类 spec

### 约束

1. 本方案不是对已有 spec 的重复改写。
2. 已在旧 spec 落地的内容，本方案只允许：
   - 补充视觉规则
   - 收敛优先级
   - 修正文案与默认展示策略
3. 不允许把已落地组件重新设计成平行版本。

### 边界定义

1. 首页相关：以既有首页优化成果为基线，本方案只补“风格收敛与优先级强化”。
2. 详情页相关：以既有 Phase、timeline、trace、review 等能力为基线，本方案只补“首屏信息重排与默认展示层次”。
3. 平台页相关：以现有平台优化成果为基线，本方案只补统一视觉节奏，不重做信息架构。

## 3. 本轮目标

本轮不是全量视觉翻新，而是做一个能落地验证的最小闭环。

### 本轮必须达成

1. 详情页从“功能堆叠页 / 调试页”升级为“任务处置中心”。
2. 用户能在首屏快速知道：
   - 当前状态
   - 当前阶段
   - 当前处理者
   - 是否需要自己介入
3. 默认轨迹层变得可理解，原始流和调试细节下沉。
4. 所有改动不破坏现有 token、主题、组件体系。

### 本轮暂不追求

1. 全站彻底风格统一
2. 首页指挥中心完全重构
3. 6 套主题体系重做
4. 新的实时展示架构
5. 样式文件大拆分

---

## 4. 设计原则

## A. 视觉原则

1. 克制
2. 专业
3. 有品牌感
4. 高密度但不压迫

## B. RPG 语义边界

本方案中的“轻 RPG 语义”仅限于：

1. 角色命名
2. phase 语义
3. 局部轻量角色提示

明确禁止：

1. RPG 图腾
2. 游戏纹理
3. 游戏式大面积配色
4. 夸张视觉符号

换句话说：

**RPG 只保留在语义层，不升级为视觉主风格。**

## C. role 颜色权重

`warrior / mage` 颜色可以保留，但必须是轻量载体。

推荐载体：

1. 小圆点
2. 细边线
3. 轻量 badge
4. 标题旁的小型 phase 标识

明确禁止：

1. 同屏大面积角色底色
2. 把 role 色做成模块主背景
3. 用 role 色抢过当前主题品牌色

---

## 5. P0 最小闭环

## A. P0 范围

`P0` 只做 4 件事：

1. 详情页首屏信息重排
2. 收敛并补齐“当前工作情况”首屏模块
3. 轨迹区做默认摘要层 / 调试层分离
4. 收敛详情页卡片、按钮、section 的节奏

首页、Stats、Skills、Automations 的大改全部不进入本轮 `P0`。

## B. P0 为什么先做详情页

因为详情页最接近用户真实决策点，也是最容易验证“三层展示模型”是否成立的地方。

如果详情页都不能把 agent 的工作解释清楚，那么把这套模型铺到首页和全站没有意义。

---

## 6. 详情页增量方案

## A. 现状

当前详情页已经有：

1. phase 相关能力
2. 事件 / 轨迹展示
3. review / design / final verdict 等块级组件
4. 结构化 trace 建模能力

问题不在“没有内容”，而在：

1. 首屏优先级不够清楚
2. 任务状态、阶段、处理者、主操作没有被压到第一阅读层
3. 默认视图偏工程视角
4. 原始轨迹表达过重

## B. 本轮只改什么

本轮不重做详情页信息架构，只做以下增量：

1. 重新排序首屏阅读层
2. 将现有 `header + info-section + alert-box` 分散承担的首屏状态信息，收敛为单一“当前工作情况”总览容器
3. 默认轨迹只展示摘要版工作流
4. 把原始 trace / 原始 JSON / 工具细节降级到调试层

### 边界约束

1. 这里的“当前工作情况”是**收敛改造**，不是在现有首屏结构之上再叠一个平行 summary 模块。
2. 若现有信息已由 `header`、`info-section`、`alert-box` 等区域承担，本轮优先通过重组、合并、提级完成，而不是新增重复块。

## C. 首屏必须回答的 4 个问题

用户进入详情页首屏时，必须能直接看懂：

1. 这是什么委托
2. 当前卡在哪
3. 谁在处理
4. 我下一步能做什么

## D. 首屏必备元素

首屏必须可见以下四类信息：

1. 当前状态
2. 当前阶段
3. 当前处理者
4. 主操作入口

### 验收方式

无论桌面还是常规笔记本视口，以上四类信息不得全部落到首屏以下。

## 7. agent 工作情况展示规范

## A. 三层展示模型

详情页与 agent 工作情况相关的信息，统一拆成三层：

### 第一层：当前工作情况

默认展示，位于首屏靠前区域。

至少包含：

1. 当前状态
2. 当前阶段
3. 当前处理者
4. 最近一次可解释进展
5. 最后更新时间
6. 是否等待人工

### 第二层：摘要版工作轨迹

默认展开，但只展示关键节点。

只展示：

1. 状态变化
2. 关键动作
3. 评审切换
4. 等待输入
5. 阻塞 / 失败

### 第三层：原始调试层

默认折叠或置于次级 tab。

放置：

1. 原始事件流
2. 原始 JSON
3. 工具参数
4. tool result 细节
5. 完整 trace

## B. 数据来源边界

### P0 数据来源

`P0` 不新增后端接口，默认使用：

1. 现有 quest / phase / status 等结构化字段
2. 现有 REST 拉取结果
3. 现有 trace / events 中可稳定提取的结构化信息
4. SSE 只作为刷新和新鲜度提示

### P0 对 SSE 的允许改动

`P0` 允许对现有 `useEventStream` 状态机做**轻量扩展**，但仅限于表达连接状态与数据新鲜度提示。

这类扩展包括但不限于：

1. 在 `connecting / open / reconnecting` 之外增加更明确的连接失败或放弃重连状态
2. 增加“数据可能非最新”的新鲜度提示
3. 为首屏“当前工作情况”提供连接状态文案

### 约束

1. 这类扩展**不等于**把 SSE 升级为详情页主展示数据源。
2. `P0` 仍然不允许让 SSE 直接承载完整的工作流语义内容。
3. 首屏主信息仍应来自现有结构化字段、REST 拉取结果和可稳定提取的 trace 信息。

### P1 才能做的事

以下能力不进入 `P0`：

1. 让 SSE 直接承载完整展示语义
2. 把实时事件直接变成主叙事数据源
3. 要求后端补全新的自然语言摘要字段

## C. “一句话总结”的合法来源

`P0` 中允许出现“当前工作情况”的一句话摘要，但来源必须明确。

仅允许 3 种来源之一：

1. 后端已有摘要字段
2. 前端规则映射表
3. 已有结构化 trace 的固定模板拼装

### P0 采用建议

本轮建议采用：

**前端规则映射表 + 固定模板拼装**

例如：

1. `phase=review` -> `法师正在评审当前结果`
2. `intensity=quick` 且无评审 -> `快速模式，本轮无评审`
2. `waiting_input=true` -> `等待你补充信息后继续`
3. `apply_failed=true` -> `应用失败，等待处理`

### 约束

1. 不允许在 `P0` 中假设前端能自由生成高语义自然语言总结。
2. 不允许在没有稳定数据来源时写出“生成实现方案中”这类过细语义。

## 8. 轨迹区改造规则

## A. 现状

当前已经有：

1. `ExecutionTrace`
2. `EventTimeline`
3. trace 归并、筛选、分组能力

### 结论

本轮不新造平行轨迹组件，而是在现有轨迹能力上做“默认层次重构”。

## B. 默认轨迹层规则

默认轨迹层只展示摘要版关键节点：

1. 初始默认展开节点数建议为 `5`，允许根据真实 quest 密度微调；经验目标区间可控制在 `3-8`
2. 关键节点 = 语义事件 ∪ 决策事件 ∪ 错误事件 ∪ 状态切换事件
3. 关键节点按时间倒序选取最近 `N` 个
4. 连续工具调用应聚合，不按原始粒度平铺
5. 次要噪音默认折叠

### 说明

1. `3-8` 不是硬编码指标，而是经验区间。
2. 验收应优先关注“默认轨迹是否足以解释当前状态”，而不是机械追求节点数。

## C. 调试轨迹层规则

原始轨迹默认不进入主正文阅读流。

要求：

1. 原始 JSON 默认折叠
2. 原始事件默认折叠
3. 工具调用参数默认折叠
4. 原始结果文本默认折叠

## 9. 首页与其他页面的边界

## A. 首页

首页方向仍然成立，但不进入 `P0` 全量改造。

本轮只保留两条约束：

1. 不推翻既有首页优化成果
2. 后续若继续改首页，只能做“风格收敛与信息优先级强化”，不能重造平行指挥中心结构

## B. Automations / Skills / Stats

本轮不作为主战场。

只允许在 `P0` 里做：

1. 局部按钮 / 卡片 / 标题节奏收敛
2. 不破坏现有页面结构的小幅统一

不允许在 `P0` 里做：

1. 整页重构
2. 重新设计信息架构
3. 额外增加新交互流

## 10. 响应式、灰度与回滚

## A. 响应式约束

详情页改版必须覆盖中小屏阅读。

至少要满足：

1. 小屏下右侧辅助区允许下沉，但“当前状态 / 当前阶段 / 当前处理者 / 主操作”仍需保持首屏可见
2. 首屏信息模块不能因为布局变化被挤到首屏以下
3. 调试层在小屏下优先折叠，不与主叙事竞争

## B. 灰度策略

视觉改版按页面灰度推进：

1. 先详情页
2. 验证通过后再考虑首页
3. 再考虑其他核心页面

## C. 回滚策略

本轮必须保证：

1. 新增规则优先覆盖默认展示顺序，不破坏底层数据结构
2. 原始轨迹能力继续保留
3. 若新首屏模块体验不佳，应可以退回到旧展示顺序，而不是影响数据链路

## D. SSE 断连状态

“当前工作情况”模块必须覆盖以下状态：

1. 同步中
2. 重连中
3. 连接断开
4. 数据可能非最新

不允许在 SSE 断连时继续假装“实时中”。

### P0 实施说明

1. 若当前实现只能稳定提供 `connecting / open / reconnecting` 三态，则至少先在 `P0` 中完整展示这三态。
2. 若执行者选择扩展 `useEventStream` 状态机，则允许在 `P0` 中补上“连接断开 / 数据可能非最新”两态。
3. 无论是否扩展状态机，都不得把 SSE 直接升级为详情页主叙事数据源。

## 11. 可量化验收标准

## A. token / 主题

1. 不新增平行品牌 token 命名。
2. 主按钮与主激活态继续跟随 `--brand-*`。
3. `--slime-*` 只作为跨主题焦点强调，不替代主题主色。
4. 改动后 6 套主题均可用。

## B. 详情页首屏

1. 首屏默认可见：
   - 当前状态
   - 当前阶段
   - 当前处理者
   - 主操作入口
2. `当前工作情况` 模块默认展开。
3. 用户无需展开调试层即可判断是否需要自己介入。

## C. 轨迹层

1. 默认轨迹节点初始值建议为 `5`，可根据真实 quest 密度微调，经验目标区间为 `3-8`。
2. 单屏默认不展示完整原始 JSON。
3. 连续工具调用默认聚合。
4. 原始调试层默认折叠或置于次级 tab。
5. 关键节点选择规则必须显式实现：语义事件 ∪ 决策事件 ∪ 错误事件 ∪ 状态切换事件，按时间取最近 `N` 个。

## D. 信息密度

1. 单卡默认标签数不超过 `3` 个。
2. role 语义标签不得抢过主状态。
3. 原始调试信息不进入首屏主阅读流。

### 标签计数口径

这里的“标签”默认指同一信息卡内并列出现的 badge / chip / phase label / role label / risk label / output label 等显式标签元素。

不强制把以下元素计入该上限：

1. 卡片主标题
2. 正文摘要
3. 独立主状态区中的单一 `StatusBadge`

## E. 风险控制

1. 不新增平行主题机制。
2. 不新增平行轨迹组件。
3. 不要求后端新增 API 才能完成 `P0`。

## 12. 执行入口

这份文档不再提供失真压缩版指令。

执行方式为：

1. 先通读全文
2. 严格遵守“现状基线”
3. 从 `P0` 第 1 项开始
4. 如遇到 token、主题、组件、数据来源冲突，以“增量复用优先”原则决策

一句话执行原则：

**先承认现状，再做增量，不造平行系统。**

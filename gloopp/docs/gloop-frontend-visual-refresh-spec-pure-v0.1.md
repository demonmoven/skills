# Gloop 前端视觉改版执行方案·纯方案版 v0.1

> 用途：这是一份偏产品 / 设计导向的执行方案，可直接交给代码 Agent 或设计实现 Agent 使用。
> 特点：只描述目标、原则、页面改版方向和验收标准，不约束具体文件路径与代码结构。

---

## 1. 改版目标

本轮改版不是重构产品，而是在保留现有产品结构和核心交互方式的前提下，完成一次高收益的视觉升级。

需要达成 4 个结果：

1. 让界面更像 `Gloop`，而不是通用后台。
2. 让首页更快回答“现在该看什么、该处理什么”。
3. 让详情页更像“任务处置中心”，并能清楚表达 agent 的工作情况。
4. 让 `Quests / Quest Detail / Automations / Skills / Stats` 形成统一的产品视觉语言。

---

## 2. 本轮边界

### 要做

1. 调整视觉层级、间距、字体、卡片、按钮、状态标签和页面节奏。
2. 强化首页 `Focus` 视图的“指挥中心”表达。
3. 升级详情页，让它更像“处置任务”的地方，而不是日志页或调试页。
4. 建立一套更稳定的品牌色使用规则。
5. 重构默认信息呈现方式，让用户先看到“解释过的工作情况”，再看到底层细节。

### 不做

1. 不改后端 API 契约。
2. 不新增复杂产品流程或额外业务功能。
3. 不推翻现有核心页面结构。
4. 不做游戏化界面，不引入重装饰、重渐变或炫技型视觉。
5. 不把页面改成“终端日志查看器”。

---

## 3. 设计原则

### 3.1 视觉关键词

- 克制
- 专业
- 有品牌感
- 高密度但不压迫
- 轻 RPG 语义，不游戏化

### 3.2 产品表达原则

1. 整体仍然是专业工具界面，而不是游戏 UI。
2. 品牌表达只出现在关键识别位，不全局泛滥。
3. 首页负责“发现问题”，详情页负责“理解问题并完成决策”。
4. 默认主视图展示解释过的信息，原始流和调试细节下沉。
5. 所有主要页面共享同一套节奏：页头、容器、标题、卡片、辅助信息。

---

## 4. 品牌与颜色策略

### 4.1 颜色角色分工

建立清晰的颜色分工：

1. **Brand / Gloop Cyan**
   - 用于主按钮、当前激活态、首页主视觉强调、关键焦点线。
   - 不大面积铺满页面。

2. **Warrior Gold**
   - 用于执行相关语义。
   - 只用于 role / phase / 轻量标识。

3. **Mage Violet**
   - 用于评审、设计任务、法师相关语义。
   - 只用于 badge、phase label、细线和小面积强调。

4. **Amber / Red**
   - Amber：等待人工、等待输入、审核关注。
   - Red：阻塞、失败、应用失败。
   - 仅用于风险提示。

### 4.2 背景层级

建议统一为 4 层：

1. 页面底色：浅灰，不用纯白。
2. 一级容器：白底。
3. 二级容器：弱染色白或极浅灰。
4. hover / active：轻微亮度变化和边框强化，不做重阴影漂浮。

## 5. 首页改版方案

## A. `Focus` 视图

### 目标

把首页从“做得不错的任务面板”升级为“产品级指挥中心”。

### 改动要求

1. 顶部总览区不再像普通三栏卡片，要更像一块完整的指挥横幅。
2. 左侧主状态表达更强，用户一眼能知道当前最值得关注的事情。
3. 中间品牌区域保留角色语义，但要更像产品识别符号，而不是装饰图。
4. 右侧流程状态更精致，像系统状态刻度，而不是普通圆角标签。
5. 整体更宽松，主次更明确，减少“一个大卡片里又塞三块”的感觉。

### 预期结果

用户打开首页后，应能迅速理解：

1. 当前整体状态如何
2. 主要瓶颈在哪里
3. 现在是否需要人工介入

## B. 注意事项区

### 目标

把“关注事项”做成真正的“决策区”。

### 改动要求

1. 每个分区首先表达“为什么这些任务在这里”。
2. 分区标题、原因说明、数量之间拉开层级。
3. 卡片只强调一个核心判断，其他 meta 降级。
4. 限制同一卡片同时出现的标签数量，避免徽章墙。

## C. `Board` 视图

### 目标

提升扫读效率，把它从“普通看板”升级成“流程看板”。

### 改动要求

1. 列头更清晰，能直接表达该列的意义和数量。
2. 卡片更轻、更短，优先服务浏览而不是阅读。
3. phase 分组更像流程泳道，而不是简单区块。
4. role 语义只做轻量表达，不做大面积染色。

## D. `List` 视图

### 目标

保留高密度，但提升行级可扫读性。

### 改动要求

1. 每一行要有更明确的主次结构。
2. 先看懂“为什么值得处理”，再看次级字段。
3. attention 行和普通行要克制地区分开。
4. 让列表更像运营台列表，而不是技术表格。

## 6. 详情页改版方案

## A. 详情页角色定位

详情页应该从“功能堆叠页 / 调试页”升级为“任务处置中心”。

用户点进详情页后，第一屏应该先回答 4 个问题：

1. 这是什么委托
2. 当前卡在哪
3. 谁在处理
4. 我下一步能做什么

## B. 首屏结构

### 改动要求

1. 顶部总览区强化标题、状态、阶段、主操作之间的层级关系。
2. 当前状态、阻塞原因、评审意见等“当前最重要信息”必须首屏优先可见。
3. 页面内容按优先级重排：
   - 总览
   - 当前问题
   - 推荐动作
   - 过程证据
   - 历史细节
4. 右侧侧栏更像辅助决策区，而不是随意堆放次要信息。

## C. 时间线与证据区

### 改动要求

1. 时间线更像叙事流，而不是原始日志堆叠。
2. 重要节点更突出，次要日志降噪。
3. diff、产物、评论、阶段信息必须视觉分段明确。
4. 长内容区保留工程信息，但整体阅读感不能像调试控制台。

---

## 7. 详情页 agent 工作情况展示规范

## A. 总体原则

详情页必须展示 agent 的工作情况，而且应该成为“看 agent 正在怎么干活”的主场。

但默认展示的必须是：

1. 解释过的工作情况
2. 结构化的进展信息
3. 与当前决策直接相关的内容

而不是默认把原始 SSE 事件、原始 JSON 或终端式日志直接铺给用户。

## B. 三层展示模型

### 第一层：当前工作情况

这是首屏必须默认可见的区域。

应当展示：

1. 当前状态：执行中 / 评审中 / 等待输入 / 阻塞 / 已完成
2. 当前阶段：例如战士执行、法师评审、应用中
3. 当前处理者：哪个角色或 agent 正在工作
4. 最近一次进展：一句人话总结
5. 最后更新时间
6. 实时连接状态：同步中 / 重连中
7. 是否需要人工介入

### 第二层：最近工作流

这是详情页上半部分推荐默认展开的“工作叙事层”。

应当展示：

1. 最近 3 到 8 个关键节点
2. 每个节点的时间
3. 每个节点的一句摘要
4. 必要时的轻量展开

节点类型可以包括：

1. 已加载上下文
2. 已开始执行
3. 正在调用工具
4. 已生成阶段结论
5. 法师开始评审
6. 等待用户输入
7. apply 失败并暂停

要求：

1. 这层更像任务进展流，不像终端输出。
2. 只展示关键动作和状态变化，不展示所有噪音。

### 第三层：深入调试视图

这层保留给高级用户和调试场景，默认折叠或放在次级 tab。

适合放：

1. 原始 SSE 事件流
2. 原始 JSON 输出
3. 工具调用参数
4. tool result 原始文本
5. 完整 trace 细节

要求：

1. 不要默认展开。
2. 不要放在首屏主要阅读区。
3. 命名要明确告诉用户这是“原始轨迹 / 调试信息”。

## C. 如何使用现有流能力

### SSE 的职责

用于构建“上层状态”：

1. 当前状态
2. 当前阶段
3. 最近一步动作
4. 最新 agent 输出摘要
5. 等待输入 / 阻塞 / 评审切换
6. 实时同步状态

### JSON / trace 的职责

用于构建“下层细节”：

1. 结构化工作轨迹
2. 证据层
3. 工具结果详情
4. 调试层
5. 原始事件与原始输出展开

核心原则：

**用 SSE 做“正在发生什么”**

**用 JSON 做“具体发生了什么”**

不要反过来。

## D. 首屏模块建议

建议在详情页首屏新增一个固定模块：

### 当前工作情况

该模块至少包含：

1. 当前阶段
2. 当前角色
3. 最近进展一句话
4. 最后更新时间
5. 是否等待人工
6. 跳转到工作轨迹按钮

文案风格应当是人话表达，例如：

- `战士正在执行第 2 阶段：生成实现方案`
- `法师正在评审最新结果`
- `等待你回答一个问题后继续`
- `因 apply 失败已暂停，等待处理`

要求：

1. 不直接展示底层事件类型名。
2. 不直接暴露内部事件命名。
3. 一句话必须能帮助用户判断是否需要介入。

## 8. 其他页面改版方向

## A. `Automations`

### 目标

从“配置后台”升级为“自动化控制台”。

### 改动要求

1. 左侧列表更突出状态和类型。
2. 详情页头部更像“自动化概览区”。
3. 标签体系统一，减少散乱的小字描述。
4. 表单区更整洁，减少“长表单铺到底”的感觉。

## B. `Skills`

### 目标

从“技能文档查看器”升级为“能力浏览页”。

### 改动要求

1. 左侧更像能力目录。
2. 右侧顶部强化 skill identity。
3. 内容区更像产品内知识页，不像原始文档。
4. 原始视图保留，但不应成为默认表达方式。

## C. `Stats`

### 目标

从普通 dashboard 提升为“诊断中心”。

### 改动要求

1. 顶部健康区更像系统报告。
2. 统计卡片更理性、更克制，减少模板味。
3. 与首页共享设计语言，但整体更冷静。
4. 风险色只在真正异常区域使用。

## 9. 组件层规范

## A. 卡片系统

统一成 3 级：

1. 一级卡片：页面级大区块
2. 二级卡片：常规信息卡
3. 三级条目卡：列表、动态、结果项

原则：

1. 优先通过边框、背景明度、内边距区分层级。
2. 不靠重阴影制造“高级感”。

## B. 按钮系统

目标是把整体按钮质感提升一档。

要求：

1. 主按钮更稳重。
2. 工具按钮不显得过小。
3. segmented 控件 active 对比更清晰。

## C. 状态标签系统

统一 4 类标签优先级：

1. 状态标签
2. 角色标签
3. 风险标签
4. 产物标签

要求：

1. 同一张卡不要堆太多标签。
2. 风险标签优先级高于产物标签。
3. role 语义标签要轻，不要抢主状态。

## 10. 实施优先级

## P0：必须做

1. 首页 `Focus` 视图升级。
2. Quest 卡片信息减负和层级重排。
3. 详情页总览区和主内容层级升级。
4. 详情页新增“当前工作情况”模块。
5. 详情页轨迹默认展示摘要版工作流，原始流下沉到调试层。
6. 全站统一页头、按钮、容器和 section 节奏。

## P1：建议做

1. `Board` 视图列头和 phase lane 优化。
2. `List` 视图行级节奏优化。
3. 详情页时间线、diff、评论区细节精修。
4. `Automations / Skills / Stats` 的骨架拉齐。

## P2：可选

1. 微动效微调。
2. 更细的 role / design 视觉区分。
3. 更完整的颜色 token 收敛。

## 11. 验收标准

### 首页

1. `Focus` 页一眼能看出主状态、关注区、系统动态区。
2. 注意事项卡片不再显得拥挤。
3. `Focus / Board / List / Detail` 四种任务相关页面视觉语言统一，但各自功能侧重点明确。

### 详情页

1. 首屏能快速看懂当前状态、阶段、负责人和下一步动作。
2. 信息块有明显主次，不再像均质化的功能堆叠。
3. 用户能一眼看懂 agent 当前在做什么，以及是否需要自己介入。
4. 时间线、diff、评论、产物区更易读，不像原始日志页。
5. 原始流和调试信息保留，但不会挤占默认主视图。

### 全站

1. `Quests / Quest Detail / Automations / Skills / Stats` 看起来像同一个产品。
2. 页头、卡片、按钮、section 节奏明显统一。
3. 品牌色使用稳定，不零散、不滥用。
4. agent 工作情况以“解释过的状态 + 工作流摘要”呈现，而不是默认直接暴露原始流输出。

### 视觉质量

1. 没有过重阴影、过度渐变、游戏化装饰。
2. 没有明显“为了改而改”的结构扰动。
3. 信息密度仍然高，但比现在更好读。

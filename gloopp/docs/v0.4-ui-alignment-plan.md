# Gloop v0.4 UI Alignment Plan

> Status: Draft
> Target: align the existing dashboard with Gloop v0.4 as a Loop Engineering System.
> Scope: frontend information architecture, page hierarchy, shared components, and verifiable implementation slices.

## 1. Why This Exists

Gloop v0.4 changed the backend from a Quest Runner into a Loop Engineering System. The UI now needs to expose that system honestly.

The user problem is not "the page looks old". The problem is:

- after a delegation starts, the user needs to know whether the agent session exists, whether the process started, whether output appeared, and whether the system is waiting for a phase signal;
- when the loop needs a human, the user needs one actionable queue, not scattered status names;
- when a maker/checker loop finishes, the user needs structured delivery, structured review, and evidence before raw trace;
- when automation runs, the user needs triage quality and no-finding behavior, not just "more quests were created";
- when choosing agents, the user needs capability tier and observability, not only whether a binary exists.

Therefore v0.4 UI alignment is an information architecture pass, not a visual rewrite.

## 2. Design Principles

### 2.1 System Objects First

Every page should use the same v0.4 nouns:

| UI Object | Source |
|---|---|
| Task / Quest | `QuestMeta` |
| Run / Phase | `QuestMeta.phases`, `pipeline_def`, `current_phase_idx` |
| Agent Session | `agent_sessions` |
| MakerReport | `reports.maker_reports` |
| ReviewReport | `reports.review_reports` |
| Evidence | `reports.review_reports[].evidence_refs`, trace evidence |
| Loop State | `loop_state_spine` |
| Human Exception | `human_exception`, `/api/human-exceptions` |
| Activity Snapshot | `context dim activity_snapshot` |

Legacy words can remain only as compatibility labels where the code still has them, such as `user_review`. The visible workflow should say "Human Exception" / "人工处理" rather than implying every success requires user review.

### 2.2 One Primary Question Per Surface

Each page must answer one primary question:

| Page | Primary Question |
|---|---|
| Feed / Home | What is happening now, and what needs me? |
| Quest Detail | What is the current loop state, what was delivered, what was checked, and what evidence backs it? |
| Inbox | What human decisions or automation candidates are waiting? |
| Automations | Which loops create useful work, which create no-finding noise, and what policy gates them? |
| Adventurers / Agents | Which agents are fit for which loops? |
| Stats | Is the loop system getting healthier? |
| Settings | What policies govern runtime, automation, connectors, and safety? |

### 2.3 Evidence Before Trace

Trace is forensic detail. It should not be the first thing a user reads.

Quest Detail order should be:

1. Current Work Status
2. Human Exception / Action
3. MakerReport
4. ReviewReport
5. Evidence
6. Loop State
7. Trace

### 2.4 Dense But Calm

Keep the current high-density workbench style. Do not add marketing sections, hero layouts, decorative cards, or "AI dashboard" visual noise.

## 4. First-principles User Tasks

The UI plan starts from Gloop users, not from an external framework. Addy's Loop Engineering primitives are used later as a checklist. The primary user task is:

> When a delegation is stuck or slow, the user can tell what happened and what to do next without reading raw trace.

### 4.1 Priority Order

| Priority | User Task | Why It Matters | Cut If Needed? |
|---|---|---|---|
| P0 | Diagnose and resolve a stuck quest. | This is the pain that triggered v0.4: late failures and unknown agent state. | No |
| P0 | Understand current running state. | If the user cannot see session/process/output/protocol health, the loop feels dead. | No |
| P1 | Read structured maker/checker outcome. | Reports/evidence are what make the loop reviewable. | No |
| P1 | Triage Human Exceptions and automation candidates. | Keeps HOTL as exception governance rather than final approval. | No |
| P2 | Compare agent capability and automation quality. | Important for long-term governance, less urgent than stuck-quest resolution. | Yes |
| P2 | Polish shared visual components. | Engineering debt reduction; must be usage-driven. | Yes |

### 4.2 Minimum Viable Validation

The first UI slice succeeds only if this scenario works:

```text
Given a quest is blocked, waiting_input, apply_failed, idle, or protocol-warning,
when the user opens the dashboard,
then within 3 clicks they can answer:
  1. where it is stuck,
  2. why it is stuck,
  3. what action is recommended,
  4. what evidence or runtime signal supports that recommendation.
```

Concrete click budget:

| Start | Path | Max Clicks |
|---|---|---|
| Feed first viewport | exception item -> Quest Detail -> action/evidence section | 2 |
| Inbox | Human Exception card -> Quest Detail -> action/evidence section | 2 |
| Quest Detail direct link | status/action card -> evidence/trace jump | 1 |

Baseline today:

- Feed shows attention in a sidebar/mobile drawer, but not as the primary cockpit.
- Quest Detail has runtime, reports, and loop state, but no dedicated evidence panel and no clear stuck-quest spine.
- Inbox has Human Exception cards and automation candidates, but not as two explicit lanes.

Target:

- A stuck quest is visible from the first screen.
- The recommended action is visible before raw trace.
- Evidence and runtime health are one jump away.

### 4.3 Success Metrics

These metrics anchor the implementation. The headline click-count metric starts as a manual fixture check in Slice 1 and becomes instrumented in Slice 7.

| Metric | Baseline | Target | Verification |
|---|---|---|---|
| Stuck quest diagnosis clicks | Not measured; current flow often requires opening detail and scanning trace/panels. | <= 3 clicks from Feed or Inbox. | Slice 1 manual fixture walkthrough; Slice 7 adds lightweight UI event instrumentation. |
| First output visibility | Runtime event exists; not visible outside detail consistently. | Running quest shows first-output state in cockpit/detail. | UI fixture or manual running quest. |
| Human Exception actionability | API exists; UI split is partial. | 100% exception cards show reason, recommended action, action tokens, risk. | `/api/human-exceptions` fixture + UI check. |
| Evidence before trace | No dedicated Evidence panel. | Evidence section appears before Trace when evidence refs exist. | Quest with ReviewReport evidence refs. |
| Report visibility | Reports render inline in detail. | Maker and Checker reports have stable cards and labels. | Completed quest with reports. |
| Automation candidate clarity | Candidate/direct exists in data; not central in UI. | Candidate/direct is visible on automation and candidate cards. | Automation run fixture. |

Instrumentation plan for the click metric:

- event name: `ui.stuck_diagnosis_path`;
- fields: `entry_surface`, `quest_id`, `exception_kind`, `click_count`, `resolved_surface`, `has_recommended_action`, `has_evidence_jump`;
- storage: local event/stat store first, no network telemetry;
- emit owner: Slice 1, because Feed / Inbox / Quest Detail are where the click path happens;
- likely emit files: `web/src/pages/FeedView.tsx`, `web/src/pages/Inbox.tsx`, `web/src/pages/QuestDetail.tsx`, plus a small helper such as `web/src/features/quest/stuckDiagnosisMetrics.ts`;
- aggregation owner: Slice 7, after Slice 1 defines the manual path and Slice 2/3/4 stabilize surfaces.

## 5. Addy Primitive Cross-check

This section cross-checks the user-task plan against Addy Osmani's Loop Engineering article, which frames the loop around five building blocks plus one memory layer:

1. Automations: discovery and triage on a schedule.
2. Worktrees: isolation so parallel agents do not step on each other.
3. Skills: project knowledge and methods the agent can load instead of guessing.
4. Plugins / Connectors: bridges into real tools.
5. Sub-agents: separate maker and checker roles.
6. Memory: durable state outside a single conversation.

Earlier drafts used the broader AI engineering vocabulary of Prompt / Skills / Evals / Metrics / Plugins / State. That vocabulary is useful for internal quality gates, but the UI alignment plan should not be driven by it. Prompt, evals, and metrics are support systems that make the user-task slices measurable.

### 5.0 Support Systems: Prompt, Evals, Metrics

These are not Addy's six primitives, but they are needed to make the primitives operable in Gloop.

Prompt current capability:

- System prompt is deliberately lean: role, permission boundary, and skill manifest.
- Phase prompts are increasingly ABI-like rather than methodology-heavy.
- Context packs can include Loop State Spine and other structured blocks.

Prompt needs strengthening:

- Remove stale v0.3 phrasing that implies user review is the default success gate.
- Make prompt/template version drift visible in Quest Detail when relevant.
- Show which context blocks were injected for a phase without forcing users into raw trace.
- Keep protocol text short; move detailed operating method into skills.

Eval current capability:

- Go unit/integration tests cover orchestrator, fsstore, executor, reports, evidence, runtime health, and API contracts.
- Web tests cover mage review, quest answer API, and display semantics.
- Doctor e2e exists for agent compatibility checks.

Eval needs strengthening:

- Define explicit Loop Engineering evals rather than only code-level tests:
  - first output coverage;
  - runtime error classification latency;
  - MakerReport coverage;
  - ReviewReport coverage;
  - evidence-backed pass coverage;
  - Human Exception actionability;
  - automation no-finding rate;
  - Tier C usage rate.
- Add regression fixtures for real user pain: "delegation started, no visible progress, fails late".
- Separate "build works" from "loop is healthy".

Metric current capability:

- Runtime health events exist.
- AgentSession state is persisted.
- Automation trust and personal stats exist.
- Connector audit events exist.

Metric needs strengthening:

- Add v0.4 metrics to stats API:
  - `runtime_first_output_coverage`;
  - `runtime_idle_warning_count`;
  - `protocol_warning_count`;
  - `maker_report_coverage`;
  - `review_report_coverage`;
  - `evidence_backed_review_coverage`;
  - `human_exception_open_count`;
  - `human_exception_resolution_latency_ms`;
  - `automation_no_finding_count`;
  - `tier_c_quest_count`.
- Make metrics drill down to quests.
- Avoid treating turn budget as progress.

UI alignment for support systems:

- Quest Detail should show a compact "Prompt / Context Pack" diagnostic row under Loop State or Trace.
- Settings / Prompts should mark platform ABI templates separately from style/custom prompt templates.
- Prompt-related warnings should be diagnostic, not a normal user workflow.
- Stats should have a Loop Health section backed by eval-like metrics.
- Doctor output should link agent capability and runtime-health evidence.

Acceptance criteria:

- A user can tell whether a quest used base prompts or overrides.
- A user can inspect injected context blocks without reading full raw trace.
- No page implies prompt text is the main way to operate the loop.
- Stats can show report/evidence/runtime coverage even when counts are zero.
- A failed quest has a visible failure category and whether it was early or late.
- Doctor and Settings use the same capability tier labels.

### 5.4 Plugins / Connectors

Current capability:

- Connector framework exists.
- Git connector exists.
- Connector audit events exist: `connector.started`, `connector.skipped`, `connector.done`, `connector.failed`.
- Automation and quest creation can carry connector intent.

Needs strengthening:

- Expose connector side-effect tier:
  - read-only;
  - local reversible;
  - external side effect.
- Show connector audit trail in Quest Detail.
- Warn when connector intent exists but global connector is disabled.
- Make connector policy explicit in Automation and Settings.
- Ensure external side effects route through connector contracts rather than hidden agent behavior.

Connector side-effect tier source:

- Tier is a connector-declared contract, not an agent self-report.
- Each connector implementation should expose a static side-effect class in code/config.
- Settings may display and enable/disable connector classes, but should not let users arbitrarily relabel a connector as safer than its implementation declares.
- Runtime inference can add warnings, but it cannot downgrade an external side effect to local/reversible.

UI alignment:

- Automation page should show connector policy summary before save/run.
- Settings should show connector enabled state, side-effect class, and audit behavior.
- Quest Detail should include connector audit events in Evidence or Timeline.

Acceptance criteria:

- A user can see whether a quest intended to touch external systems.
- Connector failures appear as actionable Human Exceptions or visible audit events.
- No connector is silently skipped without an audit event.

Owner slices:

- Slice 5 owns connector tier display, disabled warnings, and audit placement.
- Slice 5 owns the backend connector side-effect class contract because that contract is consumed by Automation Governance.
- Slice 7 owns connector metrics.

### 5.5 Sub-agents

Current capability:

- Gloop models maker/checker roles as Warrior and Mage.
- Pipeline phases exist and can represent execute/review phases.
- MakerReport and ReviewReport are persisted.
- Review phases can use EvidenceRef and structured review.

Needs strengthening:

- Make maker/checker separation visible on every active quest.
- Show which agent produced the MakerReport and which checked it.
- Expose low-confidence checker states and missing evidence.
- Support future multi-agent fanout without flattening all agents into one "assignee".

UI alignment:

- Quest Detail should show Maker and Checker as distinct phase actors.
- Feed running bar should distinguish execution and review.
- Adventurers page should show role fitness and capability tier.
- ReviewReportCard should make checker verdict separate from final system state.

Acceptance criteria:

- A user can tell whether work is in maker phase or checker phase from the first screen.
- Maker and checker reports cannot visually collapse into one generic summary.
- Tier C checker/maker usage is visible as risk.

Owner slices:

- Slice 1 owns maker/checker current-state visibility for stuck quests.
- Slice 2 owns MakerReport/ReviewReport separation in Quest Detail.
- Slice 6 owns capability-tier and role-fitness surfacing.

### 5.6 Memory

Current capability:

- Event log, session rows, reports, evidence refs, AgentSession state, context dims, and LoopStateSpine exist.
- Old global `loop_state` has been renamed to `activity_snapshot`.
- Per-task `loop_state_spine` exists and request_changes can write next expected action.

Needs strengthening:

- Expand LoopStateSpine beyond request_changes:
  - blocked;
  - waiting_input;
  - apply_failed;
  - runtime protocol warning;
  - human exception creation/resolution.
- Add confirmed facts and failed paths from MakerReport/ReviewReport/EvidenceRef.
- Keep Activity Snapshot as global projection, not task memory.
- Make Loop State visible as agent-readable state and human-readable summary.

LoopStateSpine write/clear contract:

| Event / State | Writer | Write Timing | Clear / Update Timing | Interaction With Phase State |
|---|---|---|---|---|
| `request_changes` | orchestrator review outcome handler | before rework phase is enqueued | superseded by next review or success/failure | `current_phase` becomes maker rework target; `current_phase_idx` remains source of truth for execution. |
| `blocked` | quest service / orchestrator block wrapper | when quest enters blocked | when blocked is resolved, cancelled, or moved to user review | does not change phase index; records why current phase cannot progress. |
| `waiting_input` | question/ask handler | when quest enters waiting_input | when answer is injected or timeout action fires | phase index pauses; `next_expected_action` points to user answer. |
| `apply_failed` | apply failure recorder | when apply fails | when apply succeeds or changes are discarded | phase already completed; records externalization failure, not maker/checker failure. |
| `runtime.protocol_warning` | micro loop runtime watchdog | when agent returns without phase signal | when a valid signal arrives or quest blocks | phase remains active; marks protocol risk. |
| Human Exception created | human exception projector | when an actionable exception appears | when source status changes out of exception state | mirrors source status; never becomes independent source of truth. |

Rule: `current_phase_idx` and phase status remain execution source of truth. LoopStateSpine is recoverable memory and next-action context; it must not drive state transitions by itself.

UI alignment:

- Quest Detail should show LoopStateCard near reports and evidence.
- Feed should use Activity Snapshot-style summary, not raw context dimension UI.
- Inbox should write or display Human Exception linkage to Loop State.

Acceptance criteria:

- After request_changes, the next maker phase shows previous failed path and expected action.
- Blocked and waiting-input quests have human exceptions reflected in LoopStateSpine.
- Users can distinguish Activity Snapshot from Loop State Spine.

Owner slices:

- Slice 1 owns blocked/waiting/apply-failed/runtime-warning visibility and readiness audit.
- Slice 0 only audits backend writer coverage and routes gaps.
- Small missing writers may be fixed inside the consuming slice; wide lifecycle gaps must become explicit backend sub-slices.
- Slice 2 owns LoopStateCard placement.
- Slice 7 owns metrics for memory/actionability coverage.

## 6. Target Page Designs

### 6.1 Feed: Loop Cockpit

The first viewport should answer:

- what is running;
- what needs human action;
- what finished recently;
- whether the system is healthy.

Target layout:

```text
[Composer]

[Loop Cockpit]
  Running Sessions | Human Exceptions | Recent Deliveries | Automation Candidates

[Need You Queue]    [Live Activity Feed]
```

Required changes:

- Promote Human Exceptions above the feed list on desktop and mobile.
- Group attention by `human_exception.priority`, not only status.
- Show compact runtime health for running quests: `created / started / first output / idle / protocol warning / exited`.
- Keep Activity Feed as chronological event projection, not as the main control surface.

Acceptance criteria:

- A blocked/auth/config quest is visible in first viewport without opening Inbox.
- Running quests show whether first output has appeared.
- Empty state remains compact and invites delegation, not onboarding text.

### 6.2 Quest Detail: Loop Narrative

Quest Detail should have a stable vertical spine:

```text
Current Work Status
Human Exception / Current Action
Maker Delivery
Checker Review
Evidence
Loop State
Artifacts
Timeline
Trace
Side Metadata
```

Required changes:

- Merge current `冒险者结论` and MakerReport into a `Maker Delivery` component.
- Convert ReviewReport panel into a `Checker Review` component with confidence, verdict, evidence count, required changes, and residual risk.
- Add a dedicated Evidence section before trace:
  - T0 platform evidence first;
  - agent evidence second;
  - trace fallback last.
- Move Loop State near reports, not below unrelated panels.
- Human Exception action block should show:
  - reason;
  - recommended action;
  - available actions;
  - audit reference;
  - risk level.

Acceptance criteria:

- A user can understand "what happened and what to do next" without opening raw trace.
- Report/evidence/loop state sections render empty states only when relevant, not as blank panels.
- Human Exception action text matches `/api/human-exceptions`.

### 6.3 Inbox: Human Exceptions + Automation Candidates

Inbox should become a two-lane work queue:

```text
Human Exceptions
  blocked / waiting_input / user_review / apply_failed

Automation Candidates
  pending automation-created quests
```

Required changes:

- Rename visible section titles:
  - "Human Exceptions" / "需要你处理"
  - "Automation Candidates" / "待确认自动化委托"
- Keep the navigation label `收件箱` for now if desired, but page title should clarify the two lanes.
- Human Exception cards should show recommended action and exact action tokens mapped to UI buttons.
- Automation candidates should show `triage_mode`, source automation, and why it did not auto-start.

Acceptance criteria:

- Human Exception and automation candidate items are visually distinct.
- Search filters both lanes.
- A `no_finding` automation should not create a candidate; it should archive to discovery history.

### 6.4 Automations: Triage And Governance

Automation page should answer:

- does this automation create useful work;
- does it go direct or candidate;
- what trust tier/policy applies;
- what connectors can create side effects;
- what no-finding archive says.

Required changes:

- Surface `triage_mode` as a first-class segmented control:
  - `candidate`: propose first;
  - `direct`: run immediately.
- Add a "Discovery Archive" section showing `no_finding` records.
- Add "Policy" row: trust tier, auto_start, auto_apply, allow_l2, connectors.
- Warn when connectors are selected but global connector is disabled.
- Warn when automation is direct but agent capability tier is low observability.

Acceptance criteria:

- A user can tell whether an automation will create a candidate or run directly.
- No-finding records are visible without inspecting files.
- Connector side-effect intent is visible before save/run.

### 6.5 Adventurers / Agents: Capability Matrix

Agent selection should be based on fitness, not only availability.

Required changes:

- Add an Agent Capability Matrix view:
  - agent;
  - capability tier;
  - streaming;
  - interrupt;
  - tool visibility;
  - recommended task risk.
- In create quest/recruit flows, show why Tier C is lower confidence.
- Prefer non-Tier-C default recommendations when available.

Acceptance criteria:

0. Backend Readiness.

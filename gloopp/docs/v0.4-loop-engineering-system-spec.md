# Gloop v0.4 方案：本地优先的 Loop Engineering System

> 版本：v0.4 draft
> 定位：把 Gloop 从单次 Quest Runner 升级为本地优先的 Loop Engineering System。
> 核心：Agent Runtime Health、Typed Reports、Evidence-first Checker、Loop State Spine、Human Exception Queue。

---

## 0. 命名与定位

Gloop 对外应该是 **Loop Engineering System**，不是「Loop OS」。

「Loop OS」可以作为内部架构隐喻，强调它像工作操作系统一样管理运行时、状态、证据和例外；但产品定义必须回到更准确的边界：

**Gloop 是一个本地优先的 Loop Engineering System。用户不是持续提示 Agent 的人，而是设计、观察和治理循环的人。**

从第一性原理看，Gloop 不应该只是：

- Agent UI
- Cron + Prompt
- Maker/Checker demo
- Quest 状态机
- 自动化任务列表

Gloop 应该是一套能持续运行的 loop 系统：

1. 自动发现值得做的工作。
2. 安全隔离工作区。
3. 把工作分派给 Maker。
4. 自动收集证据。
5. 交给 Checker 审查。
6. 由 Policy 决定是否自动闭环。
7. 只把例外交给人。
8. 把 loop 状态持久化，供下一轮继续。

一句话：

**系统做机制，Agent 做判断，人类处理例外和授权。**

## 1. 背景：为什么 v0.4 需要重定方向

### 1.1 当前代码事实与 v0.4 的关系

本文档是 **v0.4 目标方案与实现对照**。写实现时必须先对照现有代码，不能把目标态当已落地事实；完成实现后，本节记录当前 checkout 的落地状态。

当前 checkout 的关键事实：

- `internal/model/model.go` 仍保留顶层 `reviewing` / `user_review` / `blocked` / `waiting_input` 兼容状态；v0.4 通过 `needs_human.created` 事件和 `human_exception` API/UI 投影落地目标语义，底层枚举暂不破坏迁移。
- 旧 `internal/orchestrator/loop_state.go` 已被 `activity_snapshot.go` 取代，写入 `context/dim_activity_snapshot`；它是全局活动快照，不是本文 §9 定义的 per-task Loop State Spine。
- `internal/fsstore/loop_state_spine.go` 已新增 per-task Loop State Spine；request_changes 会写入 attempts / failed paths / next_expected_action，返工上下文会注入 `loop_state_spine` block。
- `internal/fsstore/reports.go` 已新增 MakerReport / ReviewReport / EvidenceRef；旧 phase done / review 入口会生成最小 typed report。
- `internal/orchestrator/evidence_injection.go` 已升级为 L0 EvidenceRef producer；ReviewReport 会引用 `checked_against` / `evidence_refs`。
- `internal/orchestrator/macro_loop.go`、`micro_loop.go` 仍是当前核心执行链路；v0.4 以增量迁移方式把 runtime health、reports、evidence、loop state、human exception 接入现有链路。

因此，v0.4 的第一步不是直接新建一堆概念，而是建立现有实现和目标模型之间的迁移桥。

### 1.2 当前真实痛点

用户的核心抱怨不是「没有 Feed」，也不是「没有 Maker/Checker」。

真实痛点是：

> 发出委托后，不知道 Agent 和平台之间到底发生了什么；过了很久才发现失败。

这说明系统缺的不是一个更漂亮的 Dashboard，而是以下三类健康信号：

- Runtime Health：Agent 进程是不是活着？有没有输出？是不是卡在工具/网络/认证？
- Contract Health：Agent 是否知道当前阶段必须提交什么协议？是否忘记调用 phase/review signal？
- Progress Health：Agent 是否真的朝目标推进？还是只在输出无意义文本？

### 1.3 Addy Osmani Loop Engineering 的启发

Addy Osmani 的 Loop Engineering 文章强调：Loop Engineering 是把你从「提示 Agent 的人」替换成「设计提示 Agent 的系统的人」。

一个 loop 不是单次对话，而是六类 primitive 的组合：

| Primitive | 作用 |
|---|---|
| Automations | 定时发现和 triage 工作 |
| Worktrees | 隔离并行工作，避免文件冲突 |
| Skills | 固化项目知识和方法论 |
| Plugins / Connectors | 连接真实工具和外部系统 |
| Sub-agents | Maker / Checker 分离 |
| State / Memory | 记录完成了什么、失败了什么、下一步是什么 |

对照 Gloop，Maker/Checker 只是其中一个部件。v0.4 不能继续把「剑士/法师」当成系统本体。系统本体应该是持续运行、可恢复、可治理的 loop。

### 1.4 六个 Loop Engineering 关键组件在 Gloop 中的落点

v0.4 必须把六个组件落到明确模块，而不是停留在概念映射。

| Loop 组件 | Gloop 现有能力 | v0.4 全局最优落点 | 需要剔除 / 降级的旧设计 |
|---|---|---|---|
| Automations | `automation` 配置、cron、manual run、Inbox | 从“定时创建 Quest”升级为 **Discovery + Candidate Triage**。Automation 先产出 Candidate，no-finding 自动归档，值得做的再 promote 成 Task/Quest。 | 剔除“automation=直接造 Quest”的默认心智。保留直接运行能力作为显式高信任模式，而不是默认路径。 |
| Worktrees | `worktree/copy/readonly` workspace mode、apply/backup | 继续作为并行隔离和 ChangeSetRef 的事实来源；v0.4 要把 workspace health、base drift、apply readiness 变成 EvidenceRef。 | 剔除把 workspace diff 当 UI 附属物的设计。diff/change set 是 loop 的核心事实，不是详情页小工具。 |
| Skills | 内置 skill、用户 skill、prompt 注入 | Always-injected prompt 只保留短 ABI；项目知识、方法论、发布规范、review 方法都进入按需 Skills。 | 剔除巨型 prompt 和“每个任务重新解释项目”的做法。 |
| Plugins / Connectors | connector 框架、Git connector、外部产出引用 | Connector 统一变成权限分层能力：read-only / local reversible / external side-effect。所有外部副作用要有 Connector audit event 和 Policy gate。 | 剔除“Agent 自己随便碰外部系统”的隐式能力；外部世界必须走 connector contract。 |
| Sub-agents | Warrior/Mage、fan-out、spawn-execute | Maker/Checker 是默认子 Agent 拓扑；后续可扩展 Explorer / Verifier / Security Reviewer，但都必须提交 typed report。 | 剔除“角色越多越强”的幻觉。v0.4 只保留能提供明确 contract 的角色。 |
| State / Memory | events.jsonl、sessions、reviews、context、stats | 新增 **Loop State Spine**：Task/Run/Phase 的当前目标、尝试历史、失败路径、已确认事实、下一步预期。它是平台、Agent、人类共同读取的状态脊柱。 | 剔除把 Trace、Context、Feed 任意一个误当 Memory 的做法。Trace 是证据，Context 是环境，Feed 是投影，Loop State 才是脊柱。 |

结论：Gloop v0.4 的关键不是“补一个 runtime health 功能”，而是让六个组件在同一套 loop contract 下协同。否则仍然是几个好功能并排摆着，不是 Loop Engineering System。

### 1.5 现有实现对照表

| v0.4 概念 | 当前最接近实现 | 当前问题 | v0.4 处理 |
|---|---|---|---|
| Loop State Spine | `internal/fsstore/loop_state_spine.go` + `pipeline.go` 注入 block | 旧全局快照已迁到 `activity_snapshot`；per-task spine 已新增，但后续还可扩展 confirmed_facts。 | v0.4 已落地最小 per-task spine；不复用旧 dim name。 |
| ReviewReport | `internal/fsstore/reports.go` + `structured_review.go` | 现有 structured review 是 Mage 审查细项，不是完整 review settlement report。 | 已复用 structured review 作为 `ReviewReport.findings` 子结构；ReviewReport 作为外层报告，承载 verdict/score/confidence/evidence refs。 |
| Evidence Pack | `internal/orchestrator/evidence_injection.go` + `EvidenceRef` | 旧实现只做 L0 命令文本注入。 | 已升级为 EvidenceRef producer，输出结构化 evidence refs 并挂到 ReviewReport。 |

## 2. v0.4 目标

### 2.1 产品目标

把 Gloop 从 **Quest Runner** 升级为 **Loop Engineering System**。

用户打开 Gloop 时，应该能回答：

1. 我设计的 loop 现在有没有在健康运行？
2. 哪些 Agent 正在工作？是否卡住？
3. 哪些工作已经自主闭环？影响是什么？
4. 哪些例外需要我处理？为什么？
5. 哪些自动化发现了候选工作？是否值得推进？
6. 下一轮 loop 会接着做什么？

### 2.2 工程目标

v0.4 要建立五个地基：

1. Agent Runtime Health Layer
2. Typed MakerReport / ReviewReport
3. Evidence-first Checker Pipeline
4. Loop State Spine
5. Human Exception Queue

### 2.3 非目标

v0.4 不做这些事：

- 不做平台替 Checker 改 verdict。
- 不做所有任务都等人终审。
- 不把 token delta 当用户进度。
- 不把黑盒 CLI Agent 当一等可编排 Agent。
- 不继续堆巨型 prompt。
- 不让 Automation 直接制造无限 Quest 噪音。
- 不把 Feed 当 source of truth。

### 2.4 奥卡姆剃刀：v0.4 应剔除的旧心智

v0.4 需要主动剔除不再服务 Loop Engineering System 的设计。剃刀原则：**凡是不帮助 loop 更可观测、更可恢复、更可治理的东西，都降级或移除。**

| 旧设计 / 旧心智 | 问题 | v0.4 处理 |
|---|---|---|
| 顶层 `reviewing` 状态 | 把 phase 进度混进 Task 生命周期，导致用户和系统都误判状态。 | 只在运行时迁移边界保留。新热路径用 Phase 状态表达评审进度。 |
| `user_review` 作为默认闭环状态 | 与 HOTL 冲突，把人变成每轮 gatekeeper。 | v0.4 已先落地 `needs_human.created` 事件与 Human Exception Queue 投影；底层状态枚举保留兼容，待零引用后再删除。 |
| FocusView “状态快照”首页心智 | 只能看切面，看不到 loop 怎么转。 | 用 Loop Control Feed + Live Status Card 替代。 |
| Automation 直接创建 Quest | 自动化越多，噪音越多；发现和执行混在一起。 | 默认改为 Candidate Triage；直接创建 Quest 仅保留给高信任/显式配置。 |
| 巨型 prompt 承载项目知识 | 每次任务重复注入，污染上下文，难以版本化。 | 短 ABI + 按需 Skills + Loop State + Evidence Pack。 |
| Feed 当事实来源 | Feed 是给人看的投影，不适合恢复、审计和 agent 继续执行。 | Event log + Loop State 是 source of truth，Feed 只是 projection。 |
| Token delta 当进度 | token 活跃不等于工作推进。 | 用 runtime health + phase contract + evidence progress 替代。 |
| 黑盒 CLI agent 默认一等 | 不可观测、不可中断、失败晚暴露。 | 按 capability tier 分级，低可观测 agent 只跑低风险任务或显式选择。 |
| 平台替 Checker 重写 verdict | 破坏 Maker/Checker 分工，平台变成劣质语义裁判。 | 平台只记录 risk signal，不改写 verdict。 |

### 2.5 迁移纪律

剔除旧设计不能破坏本地存量数据。迁移策略：

1. 先建新模型和投影。
2. 旧字段只在 load/API boundary 归一化。
3. UI 只展示新语义。
4. 统计和自动化逐步切到新事件。
5. 有确认的零活跃引用后再删除兼容常量和 alias。

### 2.6 needs_human 当前状态

`needs_human` 是 v0.4 的目标语义；当前 checkout 已完成事件/API/UI 投影，底层状态枚举仍兼容旧值。

当前代码仍以 `user_review` 表达人工终审，以 `blocked` 表达异常阻塞，以 `waiting_input` 表达用户回答。v0.4 的处理是：

1. 新增 `needs_human.created` 事件。
2. 在 API boundary 将 `user_review` / `blocked` / `waiting_input` / apply_failed 归一化为 `human_exception` 投影。
3. UI 先用 Human Exception Queue 展示推荐动作和原因。
4. 存量数据可读、可自动回写后，再删除旧热路径。

当前不得声称底层状态机已完全统一到 `needs_human`；可以声称 v0.4 人工处理语义已通过事件和投影落地。

## 3. 第一性原则

### 3.1 System Does Mechanism, Agent Does Judgment

平台负责：

- 状态机
- 运行时健康
- 工作区隔离
- 预算和恢复
- 证据采集
- 权限和策略
- 持久化和审计

Agent 负责：

- 理解任务
- 产出方案或改动
- 判断质量
- 提交结构化报告

人类负责：

- 设定目标
- 授权高风险动作
- 处理例外
- 调整 loop 设计

平台不能替 Agent 做语义判断；Agent 不能绕过平台机制；人类不应该处理低价值机械确认。

### 3.2 HOTL Is Exception Governance, Not Final Approval

HOTL 不是「每个结果都等人点通过」。

正确路径：

1. Maker 产出。
2. 平台采集 evidence。
3. Checker 审查。
4. Checker pass + policy allow → 自动 apply / success。
5. 人类收到影响通知。
6. 只有异常进入目标态 `needs_human`（当前代码仍需从 `user_review` 迁移）。

进入目标态 `needs_human` 的条件必须明确：

- Checker request_changes 超过返工上限。
- apply 冲突。
- 外部副作用需要授权。
- Agent runtime health 异常且不可自动恢复。
- 验收条件不明确，需要用户回答。
- Policy 判定风险超过自动闭环边界。

### 3.3 State Must Outlive Conversations

单次 Agent conversation 会忘，Loop State 不能忘。

Gloop 的长期状态不能散落在聊天记录里，也不能只藏在 event log 里。必须有一个 agent 可读、平台可验证、人类可扫的 Loop State。

### 3.4 Observability Is a Contract

如果用户不知道 Agent 是否还活着，这不是 UI 问题，是 runtime contract 问题。

Agent 编排器必须能在运行中回答：

- 进程是否启动？
- 何时有第一字节输出？
- 最近一次输出是什么时候？
- 是否观察到工具调用？
- 是否观察到 phase signal？
- 是否进入协议风险？
- 是否进入恢复策略？

所有决策都要有来源。

## 5. Agent Capability Tier

现有 SOTA Agent 不能被一视同仁地当黑盒 CLI 编排。可编排性取决于能力接口，不只取决于模型智商。

### 5.0 当前 Executor 能力盘点（Phase 0 必做）

当前代码里 executor 适配器平铺在 `internal/executor` 下，注册入口在 `internal/orchestrator/executor_registration.go`。v0.4 在实现 Runtime Health 之前，必须先给现有适配器定级，否则 watchdog 会建在沙地上。

| Executor | 当前实现 | 初始分级 | 依据 | v0.4 处理 |
|---|---|---|---|---|
| ACP | `internal/executor/acp.go` | Phase 0 必须定级 | 协议式会话、可中断、可结构化交互；但 tool event 透出质量必须实测确认，不能停留在“候选”。 | Phase 0 输出 ACP tool event 验证报告；确认后定为 Tier A，否则降为 Tier B 并记录缺口。 |
| TraeX CLI | `traex exec --json` | Tier B | 有 JSONL/stream 输出，能解析 assistant 内容；native tool event 需要继续增强 parser。 | Phase 1 接 runtime health；Phase 0 标注能力缺口。 |
| Relay / Claude CLI | `--output-format=stream-json` | Tier B | 有 stream-json，错误解析已有基础；tool event 可见性仍不完整。 | Phase 1 接 runtime health；后续解析 tool start/end。 |
| Codex CLI | `codex exec --json` | Tier B | JSONL 与 TraeX 类似；可中断，tool 事件需验证。 | Phase 1 接 runtime health；后续解析 tool event。 |
| Aiden CLI | stream-json 变体 | Phase 0 必须定级 | wrapper 形态多，`x claude` / `x codex` 参数不同，稳定性取决于子模式。 | Phase 0 必须按 variant 给出确定 tier；无法确认的 variant 不纳入 v0.4 默认编排。 |
| Pi CLI | JSON 模式 | Phase 0 必须定级 | 输出能力较弱，工具事件不确定。 | Phase 0 必须给出确定 tier；若无法确认，默认 Tier C 且不纳入高风险任务。 |
| Mock | 内置测试 executor | Test-only | 不代表真实 agent 能力。 | 只用于测试，不参与产品推荐。 |

分级必须出现在配置/Settings/doctor 结果中。默认 Agent 选择不能只看“可用”，还要看 `capability_tier`。

### 5.1 Tier A：原生可编排 Agent

能力：

- structured event stream
- native tool start/end
- interrupt
- stable exit code
- cwd/env
- structured output
- protocol tool call

默认用于高价值任务。

### 5.2 Tier B：流式 CLI Agent

能力：

- JSONL / stream-json
- assistant output parsing
- partial error parsing
- interrupt

限制：

- 工具事件可能不完整
- 协议只能通过 CLI syscall 或文件 signal

可用于中风险任务。

### 5.3 Tier C：黑盒 CLI Agent

能力：

- `cmd.Wait()` 后拿 stdout/stderr

限制：

- 运行中不可观测
- 工具调用不可见
- 卡住时只能等超时

默认只用于低风险任务，且必须显示「低可观测性」。

## 6. Agent Runtime Health Layer

这是 v0.4 的 P0。

### 6.1 Runtime Events

每个 AgentSession 必须写入：

- `runtime.session.created`
- `runtime.process.started`
- `runtime.output.first_seen`
- `runtime.output.heartbeat`
- `runtime.tool.started`
- `runtime.tool.finished`
- `runtime.protocol.signal_seen`
- `runtime.idle_warning`
- `runtime.protocol_warning`
- `runtime.process.exited`
- `runtime.error.classified`

### 6.2 Health State

AgentSession 的 health state：

- `starting`
- `active`
- `idle`
- `waiting_signal`
- `protocol_risk`
- `recovering`
- `blocked`
- `exited`

### 6.3 Watchdogs

每个 phase 配置 watchdog：

| Watchdog | 触发条件 | 动作 |
|---|---|---|
| First output watchdog | 进程启动后 N 秒无输出 | runtime warning |
| Idle watchdog | N 秒无 stdout/tool/signal | idle warning |
| Tool watchdog | 单个工具运行超时 | interrupt / mark risk |
| Protocol watchdog | 长时间无 phase signal | 注入协议提醒 |
| Recovery watchdog | retry 超过上限 | blocked / needs_human |

### 6.4 用户可见解释

用户不看原始 runtime log，而看 Live Status：

```text
正在执行 · Maker phase
Agent: TraeX · 健康
最近进展: 运行测试，已观察到 3 个 tool event
等待: MakerReport signal
已用: 6m / 30m, 4 / 10 turns
风险: 无
```

风险态：

```text
运行健康风险
Agent 进程还在，但 60 秒无可见输出。
可能原因：长工具调用、网络等待、Agent 卡死。
系统动作：已注入协议提醒，下一步将尝试 interrupt/retry。
```

## 7. Typed MakerReport / ReviewReport

### 7.1 MakerReport

Maker 完成阶段时必须提交：

```json
{
  "schema_version": "maker_report.v1",
  "verdict": "done",
  "summary": "做了什么",
  "artifacts": ["art_..."],
  "changeset": "chg_...",
  "evidence": ["ev_..."],
  "impact": {
    "changed": [],
    "affected": [],
    "not_touched": [],
    "risks": []
  },
  "open_questions": []
}
```

`summary` 是人类可扫的一段话，不是文件路径流水账。

### 7.2 ReviewReport

Checker 完成阶段时必须提交：

```json
{
  "schema_version": "review_report.v1",
  "verdict": "pass",
  "score": 8,
  "checked_against": ["goal", "acceptance", "changeset", "evidence"],
  "findings": {
    "disagreements": [],
    "risks_extra": [],
    "endorsements": [],
    "referenced_checks": []
  },
  "required_changes": [],
  "residual_risks": [],
  "confidence": "high",
  "transition_note": ""
}
```

`findings` 是对象形态，复用现有 `internal/domain/quest/structured_review.go` 中的分桶结构：

- `MageDisagreement` → `findings.disagreements`
- `MageExtraRisk` → `findings.risks_extra`
- `MageEndorsement` → `findings.endorsements`
- `MageCheckReference` → `findings.referenced_checks`

因此 ReviewReport 是外层 settlement report；现有 `structured_review` 不是废弃物，而是 ReviewReport 的 typed findings 子结构。

`transition_note` 是可选字段，仅用于迁移期或能力缺失时解释低置信度原因；稳定态为空或省略。

### 7.3 兼容策略

旧 `gloop phase done --summary` 映射成最小 MakerReport。

旧 `gloop review pass/request_changes/reject` 映射成最小 ReviewReport。

兼容只存在于 API boundary，内部存储和 UI 读新 report。

### 7.4 Phase 2 过渡态

Phase 2 先解决“聊天不是唯一交付事实”，但 Evidence Pack 在 Phase 3 才完整落地。因此 Phase 2 允许出现 `checked_against=[]` 的最小 ReviewReport，但必须显式标注：

```json
{
  "confidence": "low",
  "checked_against": [],
  "transition_note": "evidence pack not available in phase 2"
}
```

这不是最终质量目标，只是迁移过渡态。Phase 3 完成后，Checker pass 必须有 evidence refs 或明确说明无可用 evidence。

## 8. Evidence-first Checker Pipeline

Checker 不审 Maker 的自述，Checker 审 evidence。

### 8.1 Evidence Pack

Checker phase 前，平台自动构造 Evidence Pack：

- Task goal
- Acceptance criteria
- MakerReport
- ChangeSetRef
- diff stat
- changed files
- L0 command outputs
- build/test/lint evidence
- workspace dirty state
- side-effect declaration
- previous rework history

### 8.2 Trust Tier

| Tier | 来源 | 信任级别 |
---|---|---|
| T0 | Platform evidence | 最高 |
| T1 | Checker observation | 高 |
| T2 | Maker claim | 中 |
| T3 | User input | 目标来源，不是执行事实 |

### 8.3 Checker Verdict

Checker verdict 必须引用 evidence：

- `checked_against`
- `evidence_refs`
- `finding_refs`

没有 evidence 的 pass 是低置信度 pass，平台记录 risk signal，但不改写 verdict。

## 9. Loop State Spine

Loop State 是 v0.4 的脊柱。

### 9.1 为什么需要 Loop State

Event log 是事实流水；Trace 是调试视图；Feed 是用户投影；Context 是环境信息。

这些都不能替代 Loop State。

Loop State 回答：

- 当前目标是什么？
- 已尝试什么？
- 哪些证据已确认？
- 哪些路径失败了？
- 为什么返工？
- 下一轮要做什么？
- 哪些需要人处理？

### 9.2 Loop State 内容

```json
{
  "task_id": "task_...",
  "current_goal": "...",
  "current_phase": "maker",
  "attempts": [
    {
      "run_id": "run_...",
      "summary": "...",
      "result": "request_changes",
      "reason": "..."
    }
  ],
  "confirmed_facts": [],
  "failed_paths": [],
  "open_blockers": [],
  "next_expected_action": "...",
  "human_exceptions": []
}
```

### 9.3 三方共享

Loop State 必须同时服务：

- 平台：恢复和决策。
- Agent：下一轮上下文。
- 人类：扫描和理解。

## 10. Human Exception Queue

目标态 `needs_human` 应投影成行动队列，而不是只展示状态名。

每条 Human Exception 必须有：

- 为什么需要你
- 推荐动作
- 证据摘要
- 风险等级
- 可选动作
- 审计链接

示例：

```text
Apply 失败：base 文件已变更
建议：查看冲突并重试 apply
证据：2 个冲突文件，patch 已保存
按钮：查看冲突 / 重新执行 / 丢弃
```

队列排序原则：

1. 安全/权限风险
2. apply 失败
3. waiting_input
4. runtime blocked
5. checker reject / max rework

## 12. Automation Triage

Automation 不应该只是「定时创建 Quest」。

它应该先发现候选工作：

1. scheduled discovery run
2. 读取 CI / issue / commit / context / monitor
3. 生成 Candidate
4. no-finding 自动归档
5. candidate 进入 Triage Inbox
6. 用户或 policy promote 成 Task/Quest

Candidate 字段：

- `source`
- `finding`
- `evidence`
- `suggested_task`
- `risk`
- `priority`
- `dedupe_key`

这样 automation 不会制造任务噪音。

## 15. v0.4 迭代计划

### 15.0 依赖图

v0.4 不能按“能力列表”硬线性推进。真实依赖如下：

```text
Phase 0: 现状盘点与迁移地基
  ├─ Capability Tier 盘点
  │    └─ Phase 1 Runtime Health watchdog 策略
  ├─ Task/Run/Phase/AgentSession 映射
  │    ├─ Phase 2 Typed Reports 挂载点
  │    └─ Phase 4 Loop State Spine
  ├─ structured_review 兼容策略
  │    └─ Phase 2 ReviewReport
  ├─ evidence_injection 兼容策略
  │    └─ Phase 3 Evidence Pack
  └─ needs_human 迁移计划
       └─ Human Exception Queue / UI / notification

Phase 1 Runtime Health
  └─ Live Status Card

Phase 2 Typed Reports
  └─ Phase 3 Evidence-first Checker

Phase 3 Evidence-first Checker
  └─ Phase 4 Loop State Spine

Phase 4 Loop State Spine
  ├─ Phase 5 Automation Triage
  └─ Feed projection

Phase 5 Automation Triage
  └─ Phase 6 Connectors + Capability policy
```

任何实现任务如果跨过依赖边界，必须说明临时桥接策略和回滚方式。

### Phase 0：现状盘点与迁移地基 P0

目标：先把现有实现和目标模型对齐，并浇筑最小数据地基，避免“新概念重名旧实现”和“领域大手术无迁移路径”。

任务：

- Loop State 命名迁移方案：现有 `loop_state` context dim 改名为 `activity_snapshot` 或 `global_activity_state`，新 Loop State Spine 使用 per-task 命名。
- Capability Tier 盘点：给 ACP / TraeX / Relay / Codex / Aiden / Pi / Mock 定级，并暴露到 doctor/settings。
- Task/Run/Phase/AgentSession 数据映射：定义当前 `QuestMeta` 到未来 `Task + Run + Phase + AgentSession` 的 backfill 规则。
- AgentSession 最小落库：至少持久化 `session_id / quest_id / phase / agent_id / capability_tier / health_status / started_at / first_output_at / last_output_at / exit_code`，供 Phase 1 Runtime Health 写入。
- AgentSession schema 演进策略：后续 Phase 可以 additive 方式增加 `process_id / cwd / env_hash / model / last_tool_event_at / last_signal_at` 等字段；新增字段必须 defaultable，不破坏 Phase 0 已落库数据。
- ReviewReport 兼容策略：明确 `structured_review.go` 是 ReviewReport 的 findings 子结构，还是被上层报告包裹。
- Evidence Pack 兼容策略：明确 `evidence_injection.go` 升级为 EvidenceRef producer。
- `needs_human` 迁移计划：新增状态/事件/API 投影的具体顺序。

验收：

- 输出一张“当前实现 → v0.4 模型”的字段映射表。
- 七种 executor 都有初始 capability tier。
- Aiden/Pi 这类待定项必须在 Phase 0 给出确定 tier，或明确标注“不纳入 v0.4 默认编排”。
- ACP tool event 透出质量完成实测，明确 Tier A 或降级 Tier B。
- AgentSession 最小存储可被创建、读取、按 quest 查询。
- 文档中不再出现目标态冒充当前实现的表述。
- `loop_state` 命名冲突有明确处理结论。

### Phase 1：Runtime Health P0

目标：发出委托后 5 秒内知道系统有没有真的跑起来。

任务：

- AgentSession runtime events
- executor stdout/stderr heartbeat
- process lifecycle event
- idle warning
- protocol watchdog
- UI Live Status Card

验收：

- 新建委托启动后，5 秒内 `runtime.session.created` 或明确失败原因出现率 ≥ 95%。
- 支持 Tier B 以上 executor 时，进程启动后 10 秒内 `runtime.process.started` 或启动失败事件出现率 ≥ 95%。
- 首个 stdout/stderr 出现时，`runtime.output.first_seen` 可在 SSE 中被前端收到。
- 60 秒无输出/无 signal 时，Live Status 显示 runtime warning。

### Phase 2：Typed Reports P0

目标：聊天不再是唯一交付事实。

任务：

- MakerReport schema
- ReviewReport schema
- CLI/API submit path
- validation + persistence
- 旧 phase done / review 兼容映射
- Final Delivery Card 改读 report

验收：

- 标准 execute 成功任务中，MakerReport 覆盖率 ≥ 95%。
- 带 Checker 的成功任务中，ReviewReport 覆盖率 ≥ 95%。
- 旧 `phase done/review` 提交路径能生成最小 report，且不破坏旧 API。
- Final Delivery Card 不再直接依赖聊天文本作为唯一交付事实。

### Phase 3：Evidence-first Checker P0/P1

目标：Checker 审证据，不审自述。

任务：

- EvidenceRef schema
- L0 command evidence pipeline
- diff/effect/side-effect evidence
- Evidence Pack injection
- ReviewReport `checked_against`

验收：

- Checker verdict 中 `checked_against` 非空比例 ≥ 95%。
- 每条 ReviewReport 至少引用 1 个 platform evidence 或明确说明无可用 evidence。
- `evidence_injection.go` 产出的 L0 命令结果可通过 EvidenceRef 追溯到原始命令和输出。

### Phase 4：Loop State Spine P1

目标：loop 可以跨轮继续，不靠聊天记忆。

任务：

- LoopState projection
- attempts / failed paths / next step
- agent-readable Loop State pack
- human-readable Loop State summary

验收：

- 每次 request_changes 后，Loop State 中有上一轮 summary、失败原因、下一轮 expected action。
- 返工启动时，Agent context 中包含 Loop State 摘要。
- 现有 `context/dim_loop_state` 已重命名为 `context/dim_activity_snapshot`，旧文件迁移保留备份。

### Phase 5：Automation Triage P1

目标：automation 从自动创建 Quest 升级为发现候选工作。

任务：

- discovery run
- candidate item
- triage inbox
- no-finding archive
- promote candidate to task
- scheduled Loop State refresh

验收：

- Triage discovery run 产出 no-finding 时自动归档，不创建 Quest。
- Candidate 进入 Triage Inbox 后可 promote / dismiss。
- 直接创建 Quest 的 automation 需要显式高信任配置。
- 无法量化历史基线时使用绝对指标：triage no-finding 0 创建 Quest。

### Phase 6：Connector + Agent Capability Matrix P2

目标：选择真正适合编排的 Agent 和外部系统。

任务：

- agent capability matrix
- default agent recommendation by capability tier
- connector permission model
- connector audit events
- external side-effect gating

验收：

- Settings / doctor 中展示每个 Agent 的 capability tier、可观测性、可中断性。
- 外部副作用 connector 默认要求 policy/human gate。
- Connector 调用有 `connector.*` 审计事件。
- 低可观测 Tier C Agent 不会被默认推荐给高风险任务。

## 16. 成功标准

v0.4 的成功标准必须可测。定性描述只能作为解释，不能作为验收。

| 指标 | 当前基线 | 目标 |
|---|---|---|
| 启动可见性 | v0.4 已新增 runtime session/process 事件。 | 新建并启动委托后 5 秒内出现 `workspace.created` + `runtime.session.created` 或明确失败原因，覆盖率 ≥ 95%。 |

| Human Exception 可行动性 | v0.4 已新增 Human Exception Queue 投影和推荐动作。 | needs_human / blocked / waiting_input item 中，推荐动作和原因展示覆盖率 ≥ 95%。 |

| 低可观测 Agent 风险标注 | v0.4 已在 Settings / doctor / Agent 选择中展示 capability tier。 | Tier C Agent 任务在 UI/doctor 中显示低可观测性标识，覆盖率 100%。 |

这些指标应进入 Stats/doctor，而不是只写在文档里。

## 17. 最终结论

Gloop v0.4 的目标不是更好看的 Agent Dashboard，也不是更复杂的 Maker/Checker。

**v0.4 要把 Gloop 从 Quest Runner 升级为本地优先的 Loop Engineering System：Runtime Health 保证可见，Typed Reports 保证可判，Evidence 保证可信，Loop State 保证可持续，Human Exception Queue 保证人只处理值得处理的事。**

不要再往单次任务编排里加糖。v0.4 要把 loop 的脊柱做出来。

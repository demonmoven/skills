# Gloop v0.6 — Thread as Default Surface

## 目标

把 Thread 设为 Feed 点进去的默认阅读面，把 QuestDetail 收敛为管理/调试面。确立三本账分离：

| 账本 | 职责 | 载体 | 消费者 |
|---|---|---|---|
| **Narrative Ledger** | 人类可读的委托叙事和决策记录 | `ThreadPost` (durable, append-only) | ThreadView（默认阅读面） |
| **Observation Ledger** | 运行观测、排障、审计 | `ExecutionTrace` / agent session events | QuestDetail → ExecutionTrace（调试面） |
| **Action Authority** | 操作权威、状态机、权限 | `QuestMeta` + action API + `HumanException` | QuestDetail（管理面） |

三本账不互相冒充。ThreadView 不能偷拿操作权威；ExecutionTrace 不能倒进叙事流。

---

## 背景与问题

v0.5 确立了"一种 Post"和"三视图合一"的产品原则，但前端 IA 没有兑现：

1. **Feed → QuestDetail 的认知断裂**：用户从 agent 社区信息流点进一个委托，看到的是塞满 20+ 面板的"工单仪表盘"。ThreadLedgerPanel 只是其中一个区域，还排在 maker report、impact summary、diff 后面。
2. **叙事面不是一等公民**：ThreadPost 数据模型已经完整（parent_reply_id、causal_refs、artifact_refs），但没有独立的阅读视图来消费它。
3. **操作权威分散**：comment、review、start/stop 等操作按钮散落在 detail 页各处，ThreadView 如果复制一套就会出现双权威。
4. **Fanout 叙事缺失**：fanout group 的生命周期（opened → leaf spawned → leaf terminal → merge）没有 durable ThreadPost，只在 Feed/Activity 里做派生视图。

---

## 设计原则（继承 v0.5 + 新增约束）

继承 v0.5 八条原则。新增：

9. **统一 Post envelope**：所有 ThreadPost 在 ThreadView 中渲染为同一种卡片外壳。`post_kind` 只影响左侧图标、accent color、evidence chips 默认展开策略，不决定完全不同的卡片形态。
10. **Durable narrative first, derived status separate**：Feed 和 ThreadView 消费的叙事事实必须来自 durable ThreadPost。但"需要人处理"的可行动状态（attention items）的权威仍然在 `QuestMeta` / `HumanException` / action API，不从 ThreadPost 反推。Attention items 可以引用 durable post 作为 evidence，但 authority 不迁移。
11. **Action authority singular**：start/stop/review/blocked retry/waiting input/spawn fanout 等主操作只能在管理面（QuestDetail）执行。ThreadView 最多放 deep link 跳管理面，不复制第二套按钮。`action_entrypoints` 是导航提示，不是授权执行。**ThreadView 可调用 narrative append APIs（comment / future reply），但禁止调用管理 state-transition APIs（start/stop/review/resolve/apply/spawn）。**
12. **Projection provenance required**：每个 system-generated ThreadPost 必须有 `causal_refs`，优先有 `SourceEventID`。没有溯源的投影不可信。
13. **Fanout lifecycle facts ≠ fanout summary snapshot**：先有 group opened / leaf spawned / leaf terminal / merge decision / group terminal 这些 durable lifecycle nodes，再有 summary 快照引用这些节点。不要把所有事实塞进一个 summary post。

### Fanout Root Identity 模型（P0b 前置定义）

**问题**：当前 fanout 只有共享 `GroupID`，没有显式 parent/root 概念。`SpawnQuest` 签名无 `parent_quest_id`，automation fanout 直接用 `CreateQuest` 批量创建。这导致 lifecycle posts 无法定位 root thread。更关键的是：normal quest 第一次触发 fanout 时，parent 还没有 `GroupID`，不能靠 `GroupID != "" && FanoutLeafID == ""` 反推 root。

**拍板方案**：

1. **Fanout Root 定义**：`GroupID != "" && FanoutLeafID == ""` 的 quest 是该 group 的 canonical fanout root（orchestration thread）。

2. **First Spawn Promotes Parent to Root**：`SpawnQuest` 内部逻辑：
   - 拿到 `parent_quest_id`，加载 parent quest
   - 如果 parent 已有 `GroupID` 且 `FanoutLeafID == ""`：它已经是 root，直接用
   - 如果 parent 有 `GroupID` 但 `FanoutLeafID != ""`：parent 是 leaf，用 `FindFanoutRoot(parent.GroupID)` 找 root
   - **如果 parent 无 `GroupID`（normal quest 首次 spawn）：promote parent 为 root** — 给 parent 设 `GroupID = groupID`（auto-generated or caller-provided），`FanoutLeafID` 保持空，`SaveQuest(parent)`，然后写 `fanout_group_opened` post
   - 如果找不到 root（automation fanout 无 parent）：跳过 root thread 通知

3. **`SpawnQuest` 签名变更**：加 `parent_quest_id string` 参数。

4. **Leaf quest 存 `ParentQuestID`**：在 `QuestMeta` 中加 `ParentQuestID` 字段。leaf terminal 时通过此字段定位 root thread 写通知。

5. **Automation fanout 无 root 场景**：automation.go 直接 `CreateQuest` 批量创建的 fanout 没有自然 root。处理方式：
   - 每个 leaf 独立 thread，lifecycle posts 写在各自 leaf thread
   - Group summary 完全由 `/api/quests/:id/thread` 的 `fanout_summary` view model 派生
   - 不创建 synthetic root quest，不写 merge_decision post

6. **Root 查找 helper**：`FindFanoutRoot(groupID string) (questID string, found bool)` — 遍历同 GroupID 的 quests，找 `FanoutLeafID == ""` 的那个。

7. **测试覆盖**：
   - `TestFirstSpawn_PromotesParentToRoot`：normal quest 首次 spawn → parent 被设 GroupID + FanoutLeafID 为空
   - `TestSecondSpawn_ReusesSameRoot`：同 group 第二次 spawn → 复用同一 root，不重复 promote
   - `TestLeafTerminal_NotifiesRootThread`：leaf terminal → root thread 收到 leaf_done post
   - `TestAutomationFanout_NoRootNoLifecyclePosts`：automation fanout → 无 root thread 通知

### Feed Attention Items 口径

| attention_kind | authority | 当前实现 | 与 durable thread 的关系 | P0b_action |
|---|---|---|---|---|
| blocked quest | `HumanExceptionFromQuest` (QuestMeta derived) | Feed 纯计算投影 | **不从 ThreadPost 派生 authority**；可以引用 `system_escalation` post 作为 evidence | 保持 authority 在 QuestMeta/HumanException；Feed item 可携带 `evidence_post_id` 指向 escalation post |
| waiting_input quest | 同上 | Feed 纯计算投影 | 同上；可引用 `system_waiting_input` post | 同上 |
| user_review quest | 同上 | Feed 纯计算投影 | 可引用 `review_report` post | 同上 |
| apply_failed quest | 同上 | Feed 纯计算投影 | 可引用 `decision_note` post | 同上 |

**原则**：Feed attention item must reference durable narrative evidence when available, but its authority remains `QuestMeta` / `HumanException` / action API。ThreadView 不偷拿操作权威。

## Thread API Contract

### `GET /api/quests/:id/thread`

返回 ThreadView 所需的全部数据。**不返回** ExecutionTrace、workspace diff、完整 artifact 内容等管理/调试面数据。

```typescript
interface ThreadViewModel {
  // === Durable facts ===
  quest: {
    id: string
    short_id: string
    query: string
    status: QuestStatus           // from QuestMeta (authoritative)
    workflow_mode: WorkflowMode   // from QuestMeta
    intensity: Intensity
    created_at_ms: number
    updated_at_ms: number
  }
  posts: ThreadPost[]             // durable narrative facts from thread_posts.jsonl
  actors: Record<string, {        // adventurer / user identity map
    name: string
    role: "maker" | "checker" | "system" | "human" | "automation"
    avatar_url?: string
  }>

  // === View model derived (NOT durable facts) ===
  // These are computed at read time and should not be treated as ledger truth.

  fanout_summary?: {              // 从 quest meta + group quests 实时派生
    group_id: string
    leaves: Array<{
      quest_id: string
      short_id: string
      status: QuestStatus         // from leaf QuestMeta
      latest_post_preview?: string // from leaf's latest ThreadPost
    }>
    merge_owner_leaf_id?: string
    merge_strategy?: string
  }

  action_entrypoints: Array<{     // 从 quest meta + 用户权限派生；导航提示，不授权执行
    action_type: "review" | "start" | "stop" | "blocked_resolve" | "waiting_input" | "apply" | "spawn_execute"
    label: string                 // e.g. "去审核", "处理阻塞"
    target_section: string        // QuestDetail 内的锚点 section id
    priority: "primary" | "secondary"
    evidence_post_id?: string     // 引用相关 durable post 作为 evidence
  }>

  reply_count: number             // derived: posts.filter(p => p.kind !== "root").length
}
```

**字段权威分层**：

| 字段 | 权威来源 | 是 durable fact? |
|---|---|---|
| `quest.status` | QuestMeta | ✅ (但不是 ThreadPost) |
| `posts[]` | thread_posts.jsonl | ✅ durable narrative |
| `actors` | adventurer configs | ✅ durable identity |
| `fanout_summary` | QuestMeta group + leaf ThreadPosts previews | ❌ view model derived |
| `action_entrypoints` | QuestMeta + permissions + action API | ❌ view model derived (navigation hint only) |
| `reply_count` | posts array length | ❌ derived count |

### ThreadPost 模型（storage schema 不变）

```go
type ThreadPost struct {
    PostID         string
    ThreadID       string                 // = quest_id
    ParentReplyID  string                 // empty = reply to root
    RootPostID     string                 // always "root_<qid>"
    CausalRefs     []string               // post IDs or event IDs
    AuthorIdentity string                 // adventurer ID or user ID
    AuthorRole     PostAuthorRole         // maker/checker/system/human/automation
    ArtifactRefs   []ThreadArtifactRef    // attached artifacts
    SourceEventID  int64                  // event that produced this post (provenance)
    Kind           string                 // root/maker_report/review_report/system_*/human_comment/fanout_*/...
    Content        string                 // markdown body (human-readable conclusion)
    CreatedAtMs    int64
}
```

### 统一 Post Envelope 规范

所有 post（包括 root、reply、system、fanout lifecycle）使用同一外壳：

```
┌─────────────────────────────────────┐
│ [icon] [author] [time] [kind badge] │
│                                     │
│ [content markdown]                  │
│                                     │
│ [evidence chips / artifact refs]    │
│ [reply context: "回复了 XXX"]       │
└─────────────────────────────────────┘
```

- **icon**：由 `author_role` 决定（maker=⚔️, checker=🔮, system=⚙️, human=👤, automation=🤖）
- **accent color**：由 `author_role` 决定（maker=橙, checker=蓝, system=灰, human=绿）
- **kind badge**：仅 system / fanout lifecycle posts 显示文字标签（如 "返工" "升级" "阻塞" "分支创建" "分支完成" "合并决策"）
- **evidence chips**：artifact_refs 渲染为可点击 chip，点击展开预览或下载
- **reply context**：当 `parent_reply_id` 非空且不是 root 时，显示"回复了 [author] 的帖子"

**关键约束**：`post_kind` 不决定卡片形态。fanout lifecycle posts（leaf_spawned, leaf_done, merge_decision）也是同一种 envelope，只是 kind badge 文字不同。fanout_summary snapshot post 同理。

### Fanout 在 ThreadView 中的呈现

当 quest 是 fanout root 时：

1. Root post 下方显示 **fanout group status panel**（由 `fanout_summary` view model 驱动，**不是 ThreadPost**，是 read-time derived UI）
2. Group status panel 显示 leaf 列表：每个 leaf 一行（short_id + status badge + latest post preview）
3. 点击 leaf → 跳 leaf 的 ThreadView
4. Fanout lifecycle posts（group_opened, leaf_spawned, leaf_done, merge_decision）作为正常 thread reply 出现在时间线中
5. Fanout summary snapshot post（如果有）也作为正常 reply 出现在时间线中，body 是结论性文本

**分层**：
- Durable facts: lifecycle posts in thread timeline
- Derived view: group status panel (from `fanout_summary` view model)

## 验收标准

### ThreadView Acceptance Criteria

用户 3 次点击内能回答：
1. "这个委托现在到哪了？" → root post 下方的 status badge + 最新 system/lifecycle post
2. "谁说了什么？" → chronological reply chain，每个 post 有 author + role + time
3. "有什么产物？" → post 的 artifact/evidence chips
4. "是否需要我处理？" → `action_entrypoints` 区域（从 QuestMeta 派生的导航提示）
5. "要处理去哪？" → `action_entrypoints` deep link 跳管理面对应 section

### Performance

- ThreadView 首屏加载 < 500ms（因为只拉 thread view model，不拉 execution trace 和 diff）
- Thread API response size < 50KB for typical quest（10-20 posts）

### Durability & Authority

- 所有语义事件（human comment、fanout lifecycle、waiting input）都有 durable ThreadPost projection
- 每个 system post 有 `SourceEventID > 0` 或非空 `causal_refs`（provenance）
- Feed attention items 的 authority 保持在 `QuestMeta` / `HumanException`，不从 ThreadPost 反推
- ThreadView 可调用 narrative append APIs（comment / future reply-to-post），但**禁止**调用管理 state-transition APIs（start/stop/review/resolve/apply/spawn）
- `action_entrypoints` 是导航提示，不授权执行（ThreadView 不直接调用 management action APIs）
- Fanout lifecycle facts 和 fanout summary snapshot 分离：lifecycle 是 append-only durable nodes，summary 是引用这些节点的快照

## 风险与未决

1. **Legacy quests 迁移**：v0.5 之前创建的 quest 可能缺少 ThreadPost。需要 `thread_audit.go` repair path 覆盖所有 gap types（human comment backfill 可能做不到，因为原始 event 可能已丢失；至少保证 system posts 的 causal_refs backfill）。
2. **Fanout leaf terminal parent notification 的幂等**：leaf 可能多次 SaveQuest，需要 dedup by post_id `fanout_leaf_done_{leaf_qid}`。
3. **Comment 实时性**：用户在 ThreadView 发评论后，agent 需要能及时感知。当前 `AppendUserComment` 已发 event bus，确认 micro loop 订阅了即可。
4. **Mobile 适配**：ThreadView 的时间线布局在窄屏下需要调整（post card 全宽，icon 缩小）。
5. **fanout_summary seq 并发**：多个 leaf 同时 terminal 可能触发并发 summary 写入。用 AppendThreadPost 的 post_id dedup + optimistic write 处理。
6. **`e.publish` → `publishRecorded` 迁移风险**：human_comment / waiting_input / human_answer 三处 producer 需要把 `e.publish`（void）替换为 `e.publishRecorded`（returns ev）。确认下游 subscriber 不依赖 publish 的 fire-and-forget 时序。`publishRecorded` 先写 event store 再 publish，语义更严格但可能微秒级延迟。

| 评审维度数 | 5 类 × 6 关键词 | 5 类 × 6 维度 × 3-5 检查项 | **+300%+** |

## 三、自治闭环就绪度评估

从 Loop Engineering 视角（红蓝对抗代替人的 push/yes/continue）评估当前体系：

### 已具备的自治基础 ✅

1. **Maker-Checker 分离**：剑士做、法师审，避免自审自判偏差
2. **结构化评审协议**：verdict/comment/hints/score 四字段，机器可解析
3. **返工闭环**：request_changes → hints → 剑士返工 → 法师复审，最多 N 轮
4. **预算机制**：按强度分级的 turn 数、返工次数、时间预算，防止无限循环
5. **终态明确**：pass / request_changes(max) / reject 三态驱动状态机

### 自治闭环的关键缺口 ⚠️

| 缺口 | 影响 | 严重度 |
|------|------|--------|
| 剑士交付物格式不规范 | 法师难以结构化解析，评审质量不稳定 | 高 |
| 法师 hints 质量参差 | 返工效率低，轮次耗尽后仍未达标 | 高 |
| 缺少自动证据收集 | 法师需要手动查文件/跑命令，浪费预算 | 中 |
| 缺少质量阈值校准 | 什么任务给几分通过，没有统一标准 | 中 |
| 命令白名单太窄 | 法师可执行的验证手段有限（仅 3 个测试命令） | 高 |
| 没有返工效果追踪 | 不知道返工是不是真的解决了问题 | 中 |
| 没有降级策略 | 红蓝僵持时没人拍板，只能等用户介入 | 高 |

### 自治度评分

- **当前自治度：约 40%** — 框架有了，但实际运行中人还需要频繁介入（终审、解决僵局、处理返工失败）
- **本次增强后预计自治度：约 55-60%** — 法师发现问题能力提升 → 返工更有效 → 最终交付质量更高 → 用户终审更放心 → 更少介入
- **完全自治目标：85%+** — 需要机制级改进（见下一章）

## 四、机制级改进建议（Loop Engineering 视角）

### 优先级 P0（自治闭环的必选项）

1. **剑士交付结构化强制化**
   - 剑士交付必须遵循固定模板（task_type / actions / artifacts / verification / risks）
   - 不结构化的交付，法师可以直接 request_changes
   - 为什么：结构化输入是自动化评审的基础，也是减少理解偏差的关键

2. **扩大法师命令白名单**
   - 当前只有 3 个测试命令，几乎只能做最浅的验证
   - 建议增加：lint 命令、静态检查、安全扫描、依赖审计、格式检查
   - 为什么：对抗式验证需要工具支持，手眼通天的法师不如一把好用的锤子

3. **自动证据注入**
   - 平台在评审阶段自动注入：diff 统计、文件变更列表、测试结果、构建状态
   - 法师不需要手动查，直接基于证据做判断
   - 为什么：减少法师「找证据」的 token 消耗，把预算用在「分析」上

### 优先级 P1（提升自治效率）

4. **返工效果追踪**
   - 每次返工后，法师需要明确标注「上一轮提出的 N 个问题，修复了 M 个」
   - 平台追踪修复率，低于阈值自动升级
   - 为什么：防止「越修越糟」的恶性循环（Loop Engineering 文章明确警告的风险）

5. **质量分阈值化**
   - 不同强度的 quest 设置不同的通过分数阈值
   - adversarial 强度任务，score < 7 一律 request_changes
   - 为什么：让质量标准可量化，减少「法师放水」

6. **僵局检测与降级**
   - 如果连续 2 轮返工后 score 提升 < 1 分，判定为僵局
   - 自动触发：升级任务强度 / 请求用户介入 / 接受当前状态
   - 为什么：红蓝对抗不能无限打下去，需要退出机制

### 优先级 P2（长期优化）

7. **法师技能专精化**
   - 不同 task_type 配不同的法师专精（安全法师 / 性能法师 / 代码质量法师）
   - 高价值任务可以召唤多个法师联合评审
   - 为什么：单一法师有限的上下文窗口装不下所有领域知识

8. **评审质量回标**
   - 用户终审结果回喂给法师，调整评审严格度
   - 形成「法师评审 → 用户终审 → 校准法师」的元循环
   - 为什么：自治系统需要自我校准能力

## 五、结论

1. **Prompt 增强效果显著**：预计地雷发现率从 ~37% 提升到 ~76%，相对提升约 100%
2. **但 prompt 层面有天花板**：76% 的发现率还不够支撑完全自治，需要机制级改进配合
3. **Loop Engineering 视角下的核心洞察**：
   - 红蓝对抗是自治闭环的必要条件，但不是充分条件
   - 真正的自治需要：结构化输入 + 工具化验证 + 自动证据 + 质量阈值 + 降级策略
   - 人不会完全退出循环，但会从「驱动器」变成「校准器」—— 从每轮都要 push，变成偶尔调一下参数
4. **建议路径**：先落地 prompt 增强（已完成）→ 再做 P0 级机制改进 → 达到 70%+ 自治度 → 再考虑 P1/P2

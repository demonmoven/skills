# Gloop v0.3 设计方案：循环运行反馈首页 + Summary 汇报密度重构

> 版本：v0.3.0（大版本）
> 定位：把首页从"状态快照"升级为"循环运行反馈流"，同时根治 summary 信息密度，让 agent 的阶段汇报天然服务 HOTL 感知。

---

## 0. 框架定位：Loop Engineering

Gloop 不是"自治系统"（那暗示 agent 自己决定干什么、人是旁观者）。Gloop 是 **loop engineering**——用户不是在写提示词发委托，而是在设计循环（automation / quest 扇出 / 事件触发都是循环机制）。agent 在人设计的循环里执行，循环本身是人的工程产物。

这个框架下：
- **HOTL**：人在循环之上感知和介入
- **Loop Engineering**：人设计循环

Feed 同时服务两者——让人感知循环运行（loop engineering 可观测性）+ 让人知道哪里要介入（HOTL）。Feed 不是"agent 干了啥的监控屏"，是"我设计的循环转得怎么样"的运行反馈。

真实数据印证：71 个 quest 中 50 个（71%）来自 automation，7 种自动化在自主派活，3 个 quest 已有 parent_quest_id（扇出已发生）。用户打开 gloop 不是看 agent 自治，是看自己设计的循环在怎么转。

## 1. 问题定义

### 1.1 HOTL 的感知缺口

Gloop 的 HOTL（human-on-the-loop）协作模式下，用户打开 dashboard 的核心诉求有两个，优先级不同：

| 诉求 | 优先级 | 频率 | 当前承载 |
|------|--------|------|----------|
| 介入异常（不处理会阻塞 agent） | 高 | 低频 | FocusView「需要介入」区块 |
| 感知变化（工作区发生了什么） | 中 | 高频（每次开都想看） | ❌ 缺失 |

当前首页 FocusView 是"当前状态快照"——执行循环/近期异常/影响日志都是静态切片，没有时间维度的"变化流"。用户每次打开看到的是切面，感知不到工作区脉搏。

### 1.2 信息源的 0% 覆盖陷阱

Gloop 早已设计 `--impact` 影响声明机制（`warrior_execution_instruction.md:23` 明确写"完成阶段时**必须**用 --impact 声明"），生产数据却显示：

- 26 个 `phase_checkpoint` 事件，payload 100% 只有 `{summary, tool, verdict}`，没有一个带 impact
- 71 个 meta.json，`impact_summary` 字段覆盖率 0%
- agent 一次都没执行过 --impact

**第一性原理**：必填字段（summary）→ 100% 覆盖；可选字段（--impact）→ 0% 覆盖。核心信息载体必须走必填字段，不能押注可选字段。prompt 说"必须"都没用，可选字段天然会被跳过。

### 1.3 Summary 密度错位

现有 summary 是"工作清单/IDE 密度"——文件路径、行数、函数名、Schema 编号。真实样例：

> `byteio 上报器实现 (internal/context/runtime/telemetry_byteio.go, 249 行)... 遵循设计文档 §3.2 JSON Schema... 批处理+超时+失败落盘(pending_byteio.jsonl)...`

但 gloop 不是 IDE。代码级细节本就在 diff/workspace 里，法师评审有自己的白名单验证命令（`gloop command list/run`），不靠 summary 的代码坐标核对。summary 对所有消费者都该是"方案/影响"密度。

## 2. 第一性原理推导

### 2.1 信息该写一次还是多次？

→ 一次。summary 是唯一必填字段（100% 覆盖），有三个消费者：法师评审、quest 历史、HOTL 汇报。不能为每个消费者让 agent 写不同版本。**单源多消费**是唯一解。

### 2.2 Summary 该承载什么密度？

→ 方案/影响密度，不是 IDE 密度。法师评审不靠 summary 的代码级细节（有白名单验证命令）；代码级细节在 diff/workspace 里。所以 summary 对所有消费者都该是"做了什么(功能级) + 怎么考虑(方案思路) + 产品形态 + 技术风险"，禁止文件路径/行数/函数名/diff 流水账。

### 2.3 HOTL 感知该用什么形态？

→ Feed 流（动态），不是 Changelog（变更日志），不是委托列表。

- **Changelog 心智**：版本回顾式，强日期分块，回顾性太重
- **Feed/Twitter 心智**：实时流，持续滚动，"正在发生什么"，匹配 HOTL"随时感知"的本质
- **委托列表**：当前状态快照，承载不了"变化流"

用户要的是"随时扫一眼在发生什么"，正是 Feed 心智。

### 2.4 Feed 该放哪？

→ 首页。变化感知是高频诉求（每次打开都想看），放首页 ROI 最高。但不能丢掉"需要介入"（高优先级低频）——用紧凑异常提醒条置顶，不抢 Feed 视觉重心。

### 2.5 Feed 的颗粒度？

→ 阶段闭环级（phase checkpoint），不是委托级，不是事件级。

**委托级的问题**：委托可能跑几小时甚至几天，中间是黑的，闭环才出一条动态。这恰恰是 FocusView 影响日志的毛病——只能看闭环的，感知不到"正在发生什么"。等于换皮没解决本质。

**事件级的问题**：token delta / command run 太碎，没有汇报密度。

**阶段级**：agent 完成 phase checkpoint 带着汇报，这是工作区里"值得发一条动态"的颗粒度。一个委托多阶段就多条动态，流是"活的"，能感知 agent 在推进。

**不刷屏**：真实数据——55 个 quest，88% 只有 1 个阶段，最多 3 个，平均每委托 1.2 条动态。阶段级 ≈ 委托级，但多阶段的那 12% 反而更丰富。

**阶段级让 Feed 更像 Twitter**：每条动态像一条推文，承载多维信息：
- 冒险者 = 作者（有名字如"蔻德艾克斯"、"测试剑士喵"，不只 ID）
- 委托 = 话题
- 阶段汇报 = 推文正文
- 项目 = 频道/话题标签
- 评审结论 = 互动（法师 pass/request_changes 像评论）
- verdict = 状态徽标

### 2.6 怎么组织多项目？

→ Feed 流内项目标签 + 可点击过滤。项目信息藏在 `base_working_dir` 里（提取末段目录名）。真实分布：gloop 64 / douyin-cli 3 / agent-workspace 3。不强分天块，Twitter 也不分天。

### 2.7 Feed 承载哪些动态类型？

→ 不只 phase_checkpoint，4 类动态都要进 Feed。这是 loop engineering 的可观测性——每种动态对应循环的一个环节：

| 动态类型 | 事件来源 | 循环意义 |
|----------|----------|----------|
| 委托诞生 | quest.created | 触发循环在工作（automation/扇出/事件触发/user） |
| 阶段闭环 | micro.tool_end / phase_checkpoint | 执行循环的产出 |
| 返工 | quest.review_submitted (verdict=request_changes) | 评审循环在把关 |
| 终态 | quest.success / failed / blocked | 循环结束态 |

每条动态带**来源标签**：user 手动 / automation:xxx / 父委托扇出 / 事件触发。看 Feed 就知道循环怎么转——哪些是自动派的、哪些是扇出的、哪些是你在等的。

只展示 phase_checkpoint 会漏掉最重要的变化："gloop 又自动派了新委托"——在 loop engineering 里，委托诞生是触发循环在工作的核心信号。

### 2.8 待办要钉住，不能进 Feed

waiting_input / blocked / user_review 这种"卡住等你操作"的状态，性质和"循环运行反馈"完全不同——一个是待办，一个是动态。混在 Feed 里按时间排，一个 blocked 3 天的 quest 早沉底了，但它才是最高优先级。

→ 异常提醒条不只显示数量，要**钉住待办列表**，不被 Feed 冲走。Feed 是"过去发生了什么"，置顶待办是"现在等你做什么"，两者分层。

### 2.9 关注/搜索定位单个委托

刷 Twitter 是无目的浏览，但 HOTL 打开 gloop 往往有具体目的——"昨天那个埋点 quest 怎么样了"。纯时间线不支持定位单个委托。

→ 项目过滤之外，加搜索框直接搜委托标题过滤 Feed。轻量方案，不做"关注"持久化（后续迭代）。

## 3. 方案总览

### 3.1 两条改动线

| 改动线 | 内容 | 根治点 |
|--------|------|--------|
| 信息源 | 改 warrior prompt summary 密度 | 把影响密度从 0% 覆盖的可选字段，迁移到 100% 覆盖的必填字段 |
| 展示层 | 首页 FocusView → FeedView | 从"状态快照"升级为"循环运行反馈流" |

### 3.2 信息流

```
循环运转（automation/扇出/事件触发/user）
        │
        ├── quest.created ─────────────┐
        ├── phase_checkpoint (summary)─┤
        ├── review_submitted (返工) ───┤
        └── quest.success/failed ──────┘
                                        │
                                        ▼
                        events.jsonl / global.jsonl
                                        │
                    ┌───────────────────┼───────────────────┐
                    ▼                   ▼                   ▼
              法师评审            quest 历史         /api/activity
                              (QuestDetail)      (4 类动态聚合)
                                                        │
                                                        ▼
                                                FeedView 首页
                                  (Feed 流 + 待办钉住 + 项目过滤 + 搜索)
```

单源（事件流一次写入）→ 三消费者各取所需，agent 零新增字段负担。

## 4. 信息源：Summary 密度重构

### 4.1 密度定义

**必须写**：
- 做了什么（功能级，不是文件级）
- 怎么考虑的（方案思路、设计决策）
- 产品形态（用户/系统侧的可见形态）
- 技术风险（潜在副作用、未验证假设）

**可选写**：
- 不用你管的（明确告知无需介入的部分）
- 潜在副作用

**禁止写**：
- 文件路径
- 行数
- 函数名
- diff 流水账（"改了 X 行，新增 Y 个函数"）
- Schema 编号、章节号等 IDE/文档坐标

### 4.2 好坏例子

**坏（IDE 密度，agent 当前实际写的）**：
> byteio 上报器实现 (internal/context/runtime/telemetry_byteio.go, 249 行)，遵循设计文档 §3.2 JSON Schema，批处理+超时+失败落盘(pending_byteio.jsonl)+下次启动异步补发...

**好（HOTL 汇报密度）**：
> 给 douyin-cli 落地 byteio 埋点，KR2 三指标（覆盖度/调用次数/渗透率）现在可测。
> 新增 byteio 作为第三路上报通道，与现有 TEA 对称，两平台可交叉验证数据一致性。KR2 三指标的计算逻辑落地：覆盖度按 12 个内置域统计，调用次数按域拆分，渗透率按去重用户算。
> 零重依赖纯标准库实现，endpoint 为空时整个通道 nil-safe 不影响现有链路。失败落盘+下次启动补发，不丢数据。
> 产品形态：CLI stats 命令直接输出 KR2 字段，本地可查；真实渗透率依赖 byteio/TEA 服务端数据，本地因隐私无 user_id 返回 n/a。
> 技术风险：本地无 user_id，渗透率只能服务端算，本地验证不了真实值。批处理+落盘是新增机制，已加测试覆盖但生产未验证。

### 4.3 --impact 降级

`--impact` 从"必须"降级为"可选结构化补充"：
- 有则前端展示为卡片侧栏（affected/not_touched/caveats）
- 无则降级到纯 summary 文本
- 不押注它（0% 覆盖率的事实证明靠不住），但不拒绝它

### 4.4 改动文件

`prompts/warrior_execution_instruction.md`：
- summary 指令从"你的摘要"改为"HOTL 汇报"，附密度定义 + 好坏例子
- `--impact` 段落从"必须用"改为"建议用，作为结构化补充"
- 保持 `gloop phase done --summary` 的 ABI 不变（只改写作要求，不改调用方式）

## 5. 后端：GET /api/activity 聚合接口

### 5.1 接口契约

```
GET /api/activity?project=<name>&limit=<N>
```

响应：
```json
{
  "items": [
    {
      "ts": 1782389659886,
      "quest_id": "qst_2606253040",
      "short_id": "2606253040",
      "query": "结合当前现状给 douyin-cli 落地 byteio 埋点...",
      "project": "douyin-cli",
      "warrior_id": "adv_warrior_001",
      "warrior_name": "剑士·格雷",
      "warrior_level": 8,
      "warrior_title": "新兵",
      "warrior_class": "warrior",
      "warrior_exp": 3570,
      "status": "success",
      "verdict": "done",
      "phase_idx": 0,
      "phase_count": 3,
      "summary": "给 douyin-cli 落地 byteio 埋点...",
      "review_verdict": "pass",
      "review_score": 9,
      "impact": null
    }
  ],
  "projects": ["gloop", "douyin-cli", "agent-workspace"]
}
```

### 5.2 数据来源

- `root.ReadGlobalEvents(n)` 读取全局事件流
- 过滤 `type == "micro.tool_end"` && `payload.tool == "phase_checkpoint"`
- 关联 `meta.json` 取 `query` / `status` / `base_working_dir`（提项目名 = 末段目录名，排除 `work` 等无意义名）/ `warrior_id` / `phase_count`
- 关联 adventurers 目录（`~/.gloop/adventurers/<id>.json`）取 `warrior_name` / `warrior_level` / `warrior_title`（称号）/ `warrior_class`（warrior/mage 职业）/ `warrior_exp`（经验值）
- 评审信息从 meta.json 的 `final_verdict` / `final_comment` 取（quest 闭环后才有）
- 时间倒序

### 5.3 项目名提取规则

```
base_working_dir = "/data00/.../agent-workspace/douyin-cli"  → project = "douyin-cli"
base_working_dir = "/data00/.../agent-workspace/gloop"        → project = "gloop"
base_working_dir 缺失或末段为 "work"                           → project = "(未分类)"
```

### 5.4 性能

- `ReadGlobalEvents` 读全局 `events/global.jsonl`，按 n 条限制
- 默认 limit=50，最大 200
- 每条 event 关联 meta.json 是一次小文件读，50 条可接受；后续若性能问题再缓存

### 5.5 改动文件

- 新建 `internal/server/api_activity.go`：handler + 聚合逻辑
- `internal/server/server.go`：路由表注册 `GET /api/activity`
- 新建 `internal/server/api_activity_test.go`：覆盖空数据/过滤/项目提取/分页

## 6. 前端：FeedView 首页

### 6.1 布局

```
┌─────────────────────────────────────────────┐
│  异常提醒条（紧凑横条，无异常时隐藏）          │
│  ⚠ 2 个需介入 → 处理                         │
├─────────────────────────────────────────────┤
│  [全部] [gloop] [douyin-cli] [agent-workspace] │  ← 项目过滤标签
├─────────────────────────────────────────────┤
│  ┌───────────────────────────────────────┐  │
│  │ 14:32 · [douyin-cli] · 给 douyin-cli…  │  │  ← Feed 卡片（收起态）
│  │ → 完成 byteio 埋点方案，定位 3 个 P0   │  │
│  └───────────────────────────────────────┘  │
│  ┌───────────────────────────────────────┐  │
│  │ 11:20 · [gloop] · 分析 Skill 轨迹…     │  │
│  │ → 635 样本分析，Overall 2.5/5...       │  │
│  └───────────────────────────────────────┘  │
│  ...                                         │
└─────────────────────────────────────────────┘
```

### 6.2 Feed 卡片两态

**收起态**（默认）：
- 冒险者头像 + 名字 + 等级称号（作者，像 Twitter 作者，如「剑士·格雷 Lv.8 · 新兵」）
- 时间（relativeTime）
- 项目标签（彩色 tag）
- 委托标题（query 截断）
- summary 首句钩子（一行，`→` 前缀）
- 点击展开

**展开态**：
- 冒险者头像 + 名字 + 等级称号 + 职业 + 经验（完整作者 profile，如「剑士·格雷 Lv.8 战士 · 3570 EXP」）
- 阶段信息（执行阶段 N/M · verdict）
- 完整 summary 汇报正文（保留换行）
- 若有 impact：展示 affected/not_touched/caveats 小卡片
- 若有法师评审：展示评审结论（法师 ✅ Pass 9/10 / ⚠ Request Changes）
- 状态徽标（success/blocked/failed）
- 点击跳转 QuestDetail

### 6.3 项目过滤

- 顶部标签栏：`[全部]` + 各项目名
- 点击某项目只显示该项目的动态
- 默认「全部」

### 6.4 异常提醒条

- 复用 `buildAttentionSections` 逻辑统计需介入数
- 有异常：`⚠ N 个需介入 → 处理`（点击跳委托列表或展开异常）
- 无异常：隐藏（不显示"风平浪静"，避免占空间）
- 紧凑横条，不是 FocusView 的整块面板

### 6.5 实时性

- 首次进入 fetch 全量
- 后续定时轮询（30s）或 SSE 推送新动态
- MVP 先做定时轮询，SSE 后续迭代

### 6.6 改动文件

- 新建 `web/src/pages/FeedView.tsx`：首页主体
- 新建 `web/src/components/FeedCard.tsx`：Feed 卡片（收起/展开）
- 新建 `web/src/components/AlertBar.tsx`：异常提醒条
- `web/src/api/client.ts`：加 `fetchActivity(project?, limit?)`
- `web/src/api/types.ts`：加 `ActivityItem` 类型
- `web/src/styles.css`：Feed 相关样式

## 8. 回落与兼容

### 8.1 旧 quest 的 summary

旧 quest 的 summary 是 IDE 密度——前端原样展示，不强求格式。新 quest 自然是新密度。prompt 改动只影响新 quest，不追溯旧数据。

### 8.2 impact 字段

- 有 impact：展示结构化卡片
- 无 impact：降级到纯 summary 文本
- 0% 覆盖率下，Feed 主要靠 summary，impact 是锦上添花

### 8.3 项目名缺失

`base_working_dir` 缺失的旧 quest → project = "(未分类)"，归到「全部」但不归到任何项目标签。

### 8.4 版本迁移

- 无 config schema 变更（prompt 改动不影响 config）
- 无数据迁移（events.jsonl / meta.json 结构不变）
- 前端 view 默认值变化通过 localStorage 兼容（旧用户存了 'focus' 的话 fallback 到 'feed'）

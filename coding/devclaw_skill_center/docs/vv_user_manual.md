# VV 用户手册

## 一句话介绍

VV（Verification & Validation）是一个**代码质量验证工具**——在你提交代码前，帮你自动检查代码规范、安全隐患、需求合规性等问题，告诉你能不能合入。

---

## 它能帮你做什么

| 能力 | 说明 |
|------|------|
| 代码规则检查 | go vet/build 预检、密钥扫描、禁用依赖检测、代码质量审查 |
| 结构与可维护性检查 | 代码结构是否合理、是否容易维护和测试 |
| 需求合规验证 | 代码是否满足需求文档的要求 |
| 回归检测 | 是否引入了回归问题 |
| Mock/取巧检测 | 是否用 mock 或其他取巧方式绕过了真正的实现 |
| 综合审查汇总 | 汇总多个审查报告，生成统一的问题清单 |

---

## 两种模式

VV 有两种工作模式，根据场景选择：

| 模式 | 命令 | 适合什么时候用 |
|------|------|---------------|
| **Gate（门禁）** | `/vv gate <代码路径>` | 提交 PR 前、夜间构建、发版前——检查代码能不能过 |
| **Review（审查）** | `/vv review <代码路径>` | E2E 迭代修复完成后——汇总所有审查意见 |

---

## Gate 模式

### 工作流程

```
你提供: 代码路径
        │
        ▼
  1. 规则检查
     go vet/build、密钥扫描、代码规范...
        │
        ▼
  2. 结构测试（nightly/release 级）
     可维护性、性能检查...
        │
        ▼
  3. 需求验证（nightly/release 级，需提供需求文档）
     代码是否满足需求...
        │
        ▼
  4. 回归检测
     是否引入回归问题...
        │
        ▼
  5. 综合评分 → 输出裁决
     PASS ✅ / FAIL ❌ / SOFT_FAIL ⚠️
```

### 三级门禁

根据场景选择严格程度：

| 级别 | 用途 | 检查范围 | 通过条件 |
|------|------|---------|---------|
| `pr`（默认） | PR 提交前快速检查 | 规则检查 + 回归检测 | 得分 ≥ 70，无严重问题 |
| `nightly` | 每夜全量检查 | 全部检查项 | 得分 ≥ 80，无严重/高危问题 |
| `release` | 发版前最严格检查 | 全部 + 版本号/CHANGELOG 等 | 得分 ≥ 90，仅允许提示级问题 |

### 参数说明

**必填：**

| 参数 | 说明 | 示例 |
|------|------|------|
| `gate` | 固定写 `gate` | `gate` |
| `<代码路径>` | 要检查的代码目录 | `./backend` |

**可选：**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `--gate-level` | `pr` | 门禁级别：`pr` / `nightly` / `release` |
| `--subsystems` | `all` | 指定执行哪些子系统，逗号分隔：`rule`, `structural`, `task`, `trace`, `regression` |
| `--spec-dir` | 无 | 需求文档目录，需求验证时需要 |
| `--trace-file` | 无 | Agent 执行轨迹文件，轨迹评分时需要 |
| `--base-sha` | `HEAD~1` | 基准 commit，用于计算代码 diff |
| `--output-dir` | `.vv-output` | 报告输出目录 |

### 使用示例

**PR 提交前快速检查（最常用）：**

```
/vv gate ./backend
```

**夜间全量检查：**

```
/vv gate ./backend --gate-level nightly --spec-dir ./specs
```

**发版前最严格检查：**

```
/vv gate ./backend --gate-level release --spec-dir ./specs
```

**只跑规则检查（最快）：**

```
/vv gate ./backend --subsystems rule
```

## Review 模式

### 工作流程

```
前提: 9 个 Review Agent 的报告已生成在输出目录下
        │
        ▼
  1. 汇总所有审查报告
     提取问题，按严重程度分类
        │
        ▼
  2. 综合代码审查
     Go 规范、API 规范、代码质量
        │
        ▼
  3. 输出审查结论
     完整版 + 精简版（供修复 Agent 使用）
```

### 参数说明

**必填：**

| 参数 | 说明 | 示例 |
|------|------|------|
| `review` | 固定写 `review` | `review` |
| `<代码路径>` | 要审查的代码目录 | `./backend` |

**可选：**

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `--spec-dir` | 无 | 需求文档目录，综合审查时参考 |
| `--base-sha` | `HEAD~1` | 基准 commit |
| `--output-dir` | `.vv-output` | 报告输出目录 |

### 使用示例

```
/vv review ./backend
/vv review ./backend --spec-dir ./specs --output-dir ./review-output
```

---

## 裁决结果怎么看

Gate 模式完成后会给出一个裁决：

| 裁决 | 含义 | 你需要做什么 |
|------|------|-------------|
| **PASS** | 全部通过 | 可以放心提交 |
| **FAIL** | 存在严重问题 | 必须修复后重新检查 |
| **SOFT_FAIL** | 有小问题但不致命 | 建议修复，也可以酌情提交 |
| **NEEDS_APPROVAL** | 涉及安全问题 | 需要人工审批 |

详细的问题清单和修复建议在输出目录的报告中查看。

## 常见问题

**Q: gate 和 review 该用哪个？**
日常提交代码用 `gate`，E2E 迭代修复完成后用 `review` 汇总审查意见。

**Q: 我只想快速检查，不想等太久？**
用默认的 `pr` 级别，或者 `--subsystems rule` 只跑规则检查，最快。

**Q: nightly 级别没检查需求合规怎么回事？**
需要通过 `--spec-dir` 提供需求文档目录，否则需求验证会自动跳过。

**Q: 报告在哪看？**
默认在 `.vv-output/` 目录下，`final-report.md` 是人可读的完整报告，`verdict.json` 是机器可读的裁决结果。

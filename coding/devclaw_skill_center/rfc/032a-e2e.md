# 3.2.1 E2E

> **本节目标**：理解端到端测试和代码质量门禁在 Agent 工作流中的位置——代码写完不等于功能正确，需要自动化验证、修复闭环和质量审查。

---

## 概念

### E2E 测试

**E2E（End-to-End）测试**从用户视角验证整个功能链路：启动应用 → 模拟用户操作 → 验证结果。

| 维度 | 单元测试 | E2E 测试 |
|------|----------|----------|
| 范围 | 单个函数/模块 | 完整功能链路 |
| 速度 | 快(毫秒级) | 慢(秒级) |
| 信心 | 局部正确 | 全局正确 |
| 脆弱性 | 低 | 较高(依赖环境) |

### 代码质量门禁

**V&V（Verification & Validation）** 通过多 Agent 协作完成结构化的代码质量审查——不是简单 code review，而是 5 个子系统、14+ 检查项的系统化门禁。

---

## 工具体系

xdev 提供 3 个 Post Task Completion 工具，覆盖后端 E2E、前端 E2E、代码门禁三个维度：

| 工具 | 定位 | 适用场景 |
|------|------|----------|
| **fixloop** | SPEC 驱动的全链路测试修复循环 | 后端服务的集成测试 + 自动修复 |
| **e2e-fe** | 前端 E2E 测试引擎 | 前端功能的端到端验证 |
| **vv** | V&V 验证与确认系统 | 代码质量门禁 + 多 Agent 审查 |

> UI 还原工具（`x-ui-workflow`）见 [3.2.2 UI 还原](032b-ui.md)。

## 1. fixloop（全链路测试修复循环）

> **核心思想**：SPEC 驱动的闭环——从需求文档自动生成测试用例，部署到泳道环境，跑测试，分析失败，修复代码，循环到全部通过。

### Slash Command

| 命令 | 说明 | 产物 |
|------|------|------|
| `/xdev:fixloop` | **主入口**——零参数启动交互式引导，自动推断上下文 | `.costudio/` 下全部产物 |
| `/xdev:fixloop [KEY=VALUE ...]` | 带参数启动，跳过交互引导 | 同上 |

**参数表**：

| 参数 | 必填 | 默认值 | 说明 |
|------|------|--------|------|
| `PSM` | 是 | — | TCE 服务标识 |
| `BRANCH` | 是 | — | 业务仓库分支 |
| `BUSINESS_REPO` | 是 | — | 业务代码仓库路径 |
| `TEST_REPO` | 是 | — | 测试代码仓库路径 |
| `SPEC_DIR` | 是 | — | 需求文档目录 |
| `IDL_REPO` | 是 | — | IDL 仓库路径 |
| `IDL_BRANCH` | 是 | — | IDL 变更分支 |
| `MAX_ITERATIONS` | 否 | `10` | 最大迭代轮次 |
| `GENERATE_TESTS` | 否 | `true` | 是否自动生成测试 |
| `SINGLE_TEST_RUN` | 否 | `false` | 只跑一次不修复 |
| `TCE_LANE` | 否 | 自动创建 | 复用已有泳道 |
| `SKIP_DEPLOY` | 否 | `false` | 跳过部署 |

> 必填参数会自动从对话上下文推断（如之前用过 speckit），推断不到的才交互式询问。

### 工作流

```text
前置：SPEC 文档（来自 speckit / openspec / exec-plan 等 SDD 工具的产物）
                        ↓
Stage 0: 测试生成（GENERATE_TESTS=true 时）
  → 从 SPEC 提取用户旅程 → 覆盖度分析 → 生成 E2E 测试 + 单元测试
                        ↓
Stage 1: 部署到 TCE 泳道
                        ↓
Stage 2: 运行集成测试（E2E + 单元），解析 go test -json 结果
                        ↓
Stage 3: Judge 角色——失败根因分析（读代码、日志、SPEC）
                        ↓
Stage 4: Fixer 角色——修复代码，commit + push
                        ↓
Stage 5: 迭代总结
                        ↓
        全部通过？──→ 完成
        仍有失败？──→ 回到 Stage 1（循环，直到 MAX_ITERATIONS）
```

> 每个 Stage 在独立 SubAgent 中执行，避免上下文窗口耗尽。

### 中间产物

> **核心思想**：fixloop 的产物分两层——Stage 0 的测试生成产物（一次性）和每轮迭代的修复产物（循环累积）。

```text
.costudio/
├── craft/                           # Stage 0 测试生成产物
│   ├── user_journeys.md             # 从 SPEC 提取的用户旅程
│   ├── e2e_work_copy/               # 生成的 E2E 测试代码
│   ├── unit_tests/                  # 生成的单元测试代码
│   ├── generated_test_cases.jsonl   # E2E 用例清单
│   ├── generated_unit_test_cases.jsonl
│   ├── test_dirs.txt                # E2E 测试目录列表
│   ├── unit_test_dirs.txt           # 单元测试目录列表
│   ├── stage1_to_stage2_coverage.md # 覆盖度分析报告（Stage1→2）
│   └── stage2_to_stage3_coverage.md # 覆盖度分析报告（Stage2→3）
├── iteration_1/                     # 第 1 轮迭代
│   ├── failed_cases.jsonl           # 失败用例
│   ├── test_stats.json              # 测试统计
│   ├── analysis_report.md           # Judge 的根因分析报告
│   ├── fix_summary.md               # Fixer 的修复摘要
│   └── iteration_summary.md         # 迭代总结
├── iteration_2/                     # 第 2 轮迭代
│   └── ...
└── iteration_N/
```

#### user_journeys.md 模板

> **核心思想**：从 SPEC 文档自动提取的用户旅程——作为测试用例生成的输入。

```markdown
# User Journeys

## Journey 1: {旅程名}
- **Actor**: {角色}
- **Precondition**: {前置条件}
- **Steps**:
  1. {操作步骤}
  2. {操作步骤}
- **Expected Result**: {预期结果}
```

#### analysis_report.md 模板

> **核心思想**：Judge 角色的根因分析——不只说"什么测试挂了"，还要分析"为什么挂"和"怎么修"。

```markdown
# Iteration {N} Analysis Report

## Failed Cases Summary
| Case | Error Type | Root Cause |
|------|-----------|------------|
| {用例名} | {错误类型} | {根因分析} |

## Recommended Fixes
### Fix 1: {修复描述}
- **File**: {文件路径}
- **Change**: {具体修改}
- **Rationale**: {修复理由}
```

## 2. e2e-fe（前端 E2E 测试引擎）

> **核心思想**：从 Feature Spec 自动生成前端 E2E 用例（YAML 格式），通过 Chrome DevTools Protocol 在真实浏览器中执行验证。

### Slash Command

| 命令 | 说明 | 产物 |
|------|------|------|
| `/xdev:e2e-fe gen-test-case <FeatureSpecPath> [Priority]` | 从 feature spec 生成 E2E 测试用例 | YAML 测试用例文件 |
| `/xdev:e2e-fe run <TestCases> [Options]` | 通过 Chrome DevTools 执行 E2E 测试 | 测试执行结果报告 |

**Priority 参数**：`p0`（仅 P0 用例）/ 默认（P0 + P1）

### 工作流

```text
前置：feature_spec.md（来自 SDD 工具的 spec 产物）
                ↓
/e2e-fe gen-test-case feature_spec.md
  → 读取 feature spec → 提取测试场景 → 生成 YAML 格式用例
                ↓
/e2e-fe run ./test-cases/
  → 启动 Chrome DevTools → 逐个执行用例 → 输出结果
```

### 中间产物：YAML 测试用例

> **核心思想**：声明式的测试用例格式——描述"做什么"和"验什么"，不关心"怎么做"。

```yaml
# 生成的 E2E 测试用例
- name: {用例名}
  priority: P0
  steps:
    - action: navigate
      url: {目标页面}
    - action: click
      selector: {元素选择器}
    - action: assert
      selector: {元素选择器}
      expected: {预期值}
```

## 3. vv（V&V 验证与确认）

> **核心思想**：不是简单 code review，而是 5 个子系统、14+ 检查项的系统化质量门禁——多 Agent 协作，交叉验证去伪。

### Slash Command

| 命令 | 说明 | 产物 |
|------|------|------|
| `/xdev:vv gate <target_path>` | **自动化门禁**——5 个子系统并行检查，输出 Pass/Fail 判定 | `.vv-output/` 下门禁报告 |
| `/xdev:vv review <target_path>` | **E2E 迭代审查**——9 个独立 Review Agent + 去伪验证 + 最终判定 | `.vv-output/` 下审查报告 |

**参数**：

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `--gate-level` | 门禁级别：`pr` / `nightly` / `release` | `pr` |
| `--subsystems` | 子系统选择：`rule,structural,task,trace,regression` 或 `all` | `all` |
| `--spec-dir` | SPEC 文档目录 | — |
| `--trace-file` | Agent trace 文件路径 | — |
| `--base-sha` | 基线 commit | `HEAD~1` |
| `--output-dir` | 输出目录 | `.vv-output` |

### 工作流

#### vv gate（门禁检查）

```text
/vv gate <path> --gate-level pr
  → 5 个子系统并行检查：
      1. rule-checker：规则预检、作用域边界、mock 检测
      2. structural-tester：代码质量、可维护性、性能一致性
      3. task-evaluator：需求合规性（需要 --spec-dir）
      4. trace-grader：Agent trace 评分（需要 --trace-file）
      5. regression-gater：回归检测
  → 汇总生成最终 Pass/Fail 判定 + 报告
```

#### vv review（多 Agent 审查）

```text
/vv review <path>
  → 9 个独立 Review Agent 并行审查
  → 汇总生成 issue 清单
  → 验证步骤：回到源码交叉验证每个发现的有效性，去重 + 过滤误报
  → 综合 code review
  → 最终 Pass/Fail 结论
```

### 5 个子系统

| 子系统 | 检查项 | 说明 |
|--------|--------|------|
| **rule-checker** | rule-precheck / scope-boundary / mock-detection / cozeloop-standards / data-api-compliance | 规则类静态检查 |
| **structural-tester** | code-quality / maintainability / performance-consistency | 结构类代码质量 |
| **task-evaluator** | requirements-compliance | 需求合规性 |
| **trace-grader** | trace-grading | Agent 行为 trace 评分 |
| **regression-gater** | regression-detection / bug-detection / failure-classifier | 回归和 bug 检测 |

---

## 工具选型

```text
"后端功能开发完了"           → /xdev:fixloop（SPEC 驱动，生成测试 + 部署 + 修复循环）
"前端功能开发完了"           → /xdev:e2e-fe gen-test-case + run（生成用例 + 浏览器验证）
"提 PR 前跑一下质量门禁"      → /xdev:vv gate .（5 子系统自动检查）
"想做一次深度 code review"   → /xdev:vv review .（9 Agent 交叉审查）
```

## 第一代：前 AI 时代（1978-2019）

### 概念

软件工程的"手工时代"。代码质量依赖人类经验和基于规则的工具链。

### 关键技术


| 技术                                | 年代          | 作用           |
| --------------------------------- | ----------- | ------------ |
| Lint（`lint` for C）                | 1978        | 最早的静态分析工具    |
| IDE（Eclipse / IntelliJ / VS Code） | 1990s-2010s | 语法高亮、自动补全、重构 |
| 静态分析（SonarQube / ESLint）          | 2000s       | 规则引擎驱动的代码检查  |
| CI/CD（Jenkins / GitHub Actions）   | 2010s       | 自动化构建、测试、部署  |


### 特征

- 所有"智能"都是**基于规则**的：AST 匹配、正则模式、手写规则
- 工具辅助开发者，但**不生成代码**
- 质量门禁依赖人工 Code Review

### 优势

- 确定性强：规则明确，结果可预测
- 成熟稳定：数十年积累的工具链和最佳实践

### 局限

- 人力瓶颈：所有代码都由人编写，速度受限于人的产能
- 规则僵化：只能检查已知模式，无法处理未见过的问题

## 第二代：Chat 时代（2020-2022）

### 概念

LLM 首次进入开发者工作流，但交互模式停留在"对话-复制-粘贴"。

### 关键事件


| 事件                | 时间      | 意义              |
| ----------------- | ------- | --------------- |
| GitHub Copilot 发布 | 2021.06 | 首个大规模 AI 代码补全产品 |
| ChatGPT 发布        | 2022.11 | 对话式编程的起点        |


### 典型工作流

```
开发者提问 → ChatGPT/Copilot Chat 回答 → 手动复制粘贴到 IDE → 手动调试
```

### 特征

- AI 是**顾问角色**：回答问题，但不直接操作代码库
- **无上下文**：模型看不到你的项目结构、依赖关系、编码规范
- **无工具调用**：不能读写文件、运行命令、执行测试
- 成果取决于 Prompt 质量和开发者的"翻译"能力

### 优势

- 快速原型：用 ChatGPT 生成一段算法实现，粘贴到项目中
- 学习提效：对话式学习比翻文档更高效，降低新技术上手门槛

### 局限

- 上下文缺失：多轮对话后上下文丢失，AI 开始"幻觉"
- 人工搬运：所有代码都需要人手动复制粘贴、适配、调试
- 无法处理大型项目：AI 看不到项目全貌，生成的代码不符合项目规范

---

## 第三代：MaaS 时代（2023）

### 概念

Model-as-a-Service，模型能力通过 IDE 插件深度集成到开发环境中。

### 关键技术


| 技术       | 代表产品                       | 能力                |
| -------- | -------------------------- | ----------------- |
| IDE 内联补全 | Copilot / Mars Code / Trae | 基于上下文的实时代码补全      |
| IDE Chat | Cursor / Trae Chat         | 在 IDE 内对话，可引用当前文件 |
| Diff 审查  | Copilot for PRs            | AI 辅助 Code Review |
| API 集成   | OpenAI API / Claude API    | 自定义 AI 工作流        |


### 特征

- AI **嵌入 IDE**，有了部分项目上下文（当前文件、相邻文件）
- 仍然是**人驱动**：人决定何时调用 AI、如何使用 AI 的输出
- 补全是主要范式：行级/块级/函数级代码生成
- 推广指标常以"AI 代码采纳率""补全接受率"衡量

### 优势

- 单文件内的重复模式（CRUD、测试用例）补全效率极高
- 无缝集成：AI 嵌入开发者已有的工作流，几乎零学习成本
- 对熟悉的项目做增量修改，补全上下文足够

### 局限

- 视野局限：跨文件/跨模块的重构，补全模型缺乏全局视野
- 无上下文管理概念：模型注意力分散时，开发者只能新开会话
- 被动模式：AI 只在被调用时才工作，不会主动发现和解决问题

## 第四代：Agent 时代（2024-2026）

### 概念

从"AI 补全代码"进化到"AI 自主编排工作流"。Agent 可以读写文件、执行命令、运行测试、发起 PR，以 ReAct（Reasoning + Acting）模式自主完成复杂任务。

### 关键产品


| 产品           | 类型            | 特点                        |
| ------------ | ------------- | ------------------------- |
| Claude Code  | CLI Agent     | Anthropic 官方，终端原生，上下文控制最强 |
| Codex CLI    | CLI Agent     | OpenAI 的命令行 Agent         |
| Cursor Agent | IDE Agent     | 在 IDE 中运行的 Agent 模式       |
| Trae / CoCo  | IDE/CLI Agent | 字节内部，IDE + CLI 双形态        |
| Windsurf     | IDE Agent     | 自动工作流编排                   |


### Agent 时代的演进路径

Agent 时代内部也有明显的演进路径，从即兴编程到工程化文档驱动：

#### 阶段一：Vibe Coding

直觉驱动、快速迭代的编码方式，是进入 Agent 时代的第一步：

- **Write Mode**：直接下达编码指令，Agent 自主执行并落地代码
- **Plan Mode**：先描述诉求 → Agent 生成计划 → 确认后执行编码

```
Write Mode:  "帮我加一个用户登录功能"  → Agent 直接写代码
Plan Mode:   "帮我加一个用户登录功能"  → Agent 出 plan → 人确认 → Agent 写代码
```

#### 阶段二：文档驱动（Spec-Driven）

工程化、可追溯的研发范式，Vibe Coding 成熟后的自然演进：

- **Pre Task Completion**：从需求到代码落地的完整交付（需求构建 → 调研 → 技术方案 → 任务拆解 → 编码/单测）
  - SDD（Spec-Driven Development）：需求规格 → 实现 → 验证
  - TDD（Test-Driven Development）：测试先行 → 实现 → 通过
- **Post Task Completion**：任务完成后，闭环收敛
  - E2E：用例生成 → loop(集成部署 → test → fix)
  - UI 还原：设计稿 → 代码 → 还原度校验 → 自动修复
  - Compound 复利工程：每次迭代让下一次更快更好

### 优势

- 自主执行：Agent 能独立完成"读代码 → 写代码 → 跑测试 → 修问题"的完整循环
- 项目级上下文：通过 AGENTS.md / MCP / Skill 等机制获取全局视野
- 工程化范式：SDD/TDD 让 Agent 的产出可预测、可验收
- 效率跃迁：复杂功能从"人写几天"变为"Agent 写几小时 + 人审几十分钟"

### 局限

- 上下文窗口有限：长对话或超大项目仍需精细的上下文管理
- 一致性挑战：同一个 prompt 多次执行可能得到不同结果
- 需要工程化投入：Harness（文档、hooks、约束）的搭建本身需要前期投入
- 调试难度：Agent 的推理过程是黑箱，出错时定位根因比人写的代码更难

## 第五代：AI Native 时代（2026-）

### 概念

软件工程的范式根本性转变。AI 不再是"辅助工具"，而是**系统的核心运行时**。

### 核心类比

```text
传统计算机                         AI Native
─────────────                     ──────────────
CPU       = 处理器                 Model   = 处理器（推理引擎）
RAM       = 内存                   Context = 内存（上下文窗口）
OS        = 操作系统               Harness = 操作系统（约束+反馈）
应用程序  = 服务                   Skill   = 服务/应用（可复用能力包）
```

### 特征

- **工程师的核心工作**从"写代码"变为"设计 Harness"——搭建环境、说清意图、建立反馈闭环
- **代码仓库本身**成为 AI 的运行时环境：文档是内存，hooks 是中断，lint 是硬件约束
- **Skill 生态**形成：可复用的 Agent 能力包取代传统的函数库/框架

### 优势

- 系统级协同：Agent 能力不再是散装工具，而是完整的"操作系统"级体验
- 自我进化：Compound 机制让系统越用越快

### 局限

- 仍在早期探索阶段，标准和规范尚未统一
- Agent 的可靠性和一致性仍需约束系统保障
- 团队协作模式尚在探索中

## 代际对比总结


| 维度    | 前 AI      | Chat      | MaaS         | Agent    | AI Native  |
| ----- | --------- | --------- | ------------ | -------- | ---------- |
| AI 角色 | 无         | 顾问        | 助手           | 执行者      | 运行时        |
| 交互方式  | 规则配置      | 对话复制      | IDE 内补全      | 指令/Spec  | Harness 设计 |
| 上下文   | 无         | 无         | 单文件          | 项目级      | 仓库级        |
| 自主性   | 0         | 0         | 低            | 高        | 极高         |
| 人的角色  | 编码者       | 提问者       | 操作者          | 指挥者      | 架构师        |
| 质量保障  | 人工 Review | 人工 Review | 人工+AI Review | Hooks+测试 | Harness 闭环 |

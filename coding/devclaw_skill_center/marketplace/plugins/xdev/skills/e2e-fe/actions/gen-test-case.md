# Gen E2E Test Case

根据 feature_spec.md 功能规格说明书，自动解析验收场景和功能需求，按用户故事维度生成结构化的 E2E 测试用例（YAML 格式）。

---

## 输入参数

### 必需参数

| 参数 | 说明 | 示例 |
|------|------|------|
| `feature_spec_path` | feature_spec.md 文件的绝对路径 | `/path/to/feature_spec.md` |

### 可选参数

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `priority` | 需要生成用例的优先级范围，可选值：`p0`（仅 P0）、`p0p1`（P0 和 P1） | `p0` |

---

## 输出格式

### 目录结构

所有生成的测试用例目录位于 `feature_spec.md` 同级目录下：

```
<feature_spec_dir>/
├── feature_spec.md
├── us-1/                          # 用户故事 1 的测试用例
│   ├── 01_默认加载模板列表.yaml
│   ├── 02_空列表状态.yaml
│   └── ...
├── us-2/                          # 用户故事 2 的测试用例
│   ├── 01_完整三步创建模板.yaml
│   └── ...
├── ...
└── us-N/                          # 用户故事 N 的测试用例
```

### YAML 用例格式

每个 YAML 文件代表一个验收场景，格式如下：

```yaml
name: 用例名称（来自验收场景的场景列）
url: "{url}/推断的路径"
actions: |
  自然语言描述的操作步骤，来自验收场景的"前置条件"和"操作步骤"列
checkpoints:
  - 检查点 1（来自验收场景的"预期结果"列中的 ✅ 项）
  - 检查点 2
  - 检查点 3
```

## 执行流程

### Phase 1: 参数解析与验证

1. **解析必需参数**：
   - 读取 `feature_spec_path`，确认文件存在且可读取
   - 如果用户未提供 `feature_spec_path`，通过 `AskUserQuestion` 询问

2. **解析可选参数**：
   - 确认 `priority` 参数，默认为 `p0p1`
   - 如果用户指定了优先级筛选条件，使用用户指定的值

3. **确定输出目录**：
   - 输出目录为 `feature_spec_path` 所在的同级目录

### Phase 2: 文档解析

1. **读取 feature_spec.md**：
   - 使用 `Read` 工具读取完整的 feature_spec.md 文件

2. **提取用户故事列表**：
   - 识别所有 `### 用户故事 N - {标题}（优先级：{PX}）` 格式的章节
   - 记录每个用户故事的编号、标题和优先级

3. **按优先级筛选**：
   - 根据 `priority` 参数筛选需要处理的用户故事
   - `p0p1`：保留 P0 和 P1 优先级的用户故事
   - `p0`：仅保留 P0 优先级的用户故事

4. **提取验收场景**：
   - 对每个通过筛选的用户故事，提取其「验收场景」表格
   - 解析表格中的每一行：场景名称、前置条件、操作步骤、预期结果

### Phase 3: 用例生成

对每个通过筛选的用户故事：

1. **创建用户故事目录**：
   - 在输出目录下创建 `us-{N}` 目录（N 为用户故事编号）

2. **为每个验收场景生成 YAML 文件**：
   - 文件命名：`{序号}_{场景名称}.yaml`（序号两位数补零，场景名称中的空格替换为下划线）
   - 根据验收场景内容生成 YAML：
     - `name`：场景名称
     - `url`：使用 `{url}` 变量作为域名前缀 + 推断的路径（如 `{url}/dashboard`），由 `e2e-fe run` 执行时填入实际地址
     - `actions`：将"前置条件"和"操作步骤"合并为自然语言操作描述
     - `checkpoints`：从"预期结果"列中提取所有 ✅ 标记的验证点

3. **YAML 生成规则**：
   - `actions` 字段用自然语言描述，不需要精确到 CSS 选择器
   - `checkpoints` 每一条独立为一个列表项
   - 预期结果中 ❌ 标记的项转化为反向检查点（如"不允许提交" → "提交按钮不可点击或点击后无响应"）
   - URL 使用 `{url}` 变量格式，由 `e2e-fe run` 执行时替换为实际地址

### Phase 4: 生成结果汇总

1. **输出生成摘要**：
   - 统计各用户故事生成的用例数量
   - 列出完整的目录结构
   - 提示用户后续可使用 `e2e-fe run` 执行这些用例

---

## 用例质量规则

1. **场景粒度**：每个验收场景对应一个独立的 YAML 文件，保持用例原子性
2. **操作描述**：使用自然语言，描述清晰的操作路径，包含必要的上下文（如"当前工作空间下存在多个实验模板"）
3. **检查点独立**：每个检查点验证一个具体的预期行为，避免将多个检查合并
4. **URL 推断**：根据用户故事描述的页面位置推断 URL 路径，使用 `{url}` 作为域名前缀变量（如 `{url}/templates`），由 `e2e-fe run` 执行时填入实际地址
5. **前置条件融入**：将验收场景的"前置条件"自然地融入到 `actions` 的开头描述中

---

## 执行准则

1. **必须提供 feature_spec_path**：这是唯一的必需参数，无此参数无法执行
2. **优先级筛选严格遵守**：仅生成指定优先级范围内的用例
3. **目录结构规范**：严格按 `us-{N}` 格式命名，N 与 feature_spec 中的用户故事编号一致
4. **YAML 格式正确**：生成的 YAML 必须是合法可解析的格式
5. **不遗漏场景**：目标优先级范围内的每个验收场景都必须生成对应用例
6. **文件命名可读**：文件名应直观反映场景内容

# E2E Run

使用 Chrome DevTools MCP 工具执行端到端测试用例，支持并发执行、登录态自动检测与用户辅助登录、失败时自动收集日志、最终输出总结报告。

---

## 输入参数

### 必需参数

| 参数 | 说明 | 示例 |
|------|------|------|
| `TestCases` | 测试用例列表，支持自然语言描述。每个用例必须包含：URL、操作步骤（Action List）、检查点（Checkpoints） | 见下方用例格式 |

### 可选参数

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `BackendMode` | 后端模式：`local`（本地启动）或 `remote`（提供 API Host+端口） | 需询问用户选择 |
| `BackendStartCmd` | 后端本地启动命令（BackendMode=local 时需要） | 无 |
| `ApiHost` | 远程 API 地址（BackendMode=remote 时需要） | 无 |
| `NeedMockServer` | 是否需要 Mock Server 能力 | 需询问用户选择 |
| `ApiDocPath` | API 文档路径（NeedMockServer=true 时需要） | 无 |
| `MaxRetries` | 单个用例最大重试修复次数 | 3 |
| `MaxConcurrency` | 最大并发执行用例数 | 3 |

## URL 变量替换

当用例中的 URL 使用 `{url}` 变量格式（如 `{url}/dashboard`）时，verify 执行前需要确定实际的 base URL：

1. 如果用户在参数中提供了实际 URL（如 `http://localhost:3000`），直接替换 `{url}` 为该值
2. 如果未提供，通过 `AskUserQuestion` 询问用户实际的 base URL
3. 将所有用例中的 `{url}` 替换为实际地址后再执行

## 用例格式

用例使用**自然语言描述**，每个用例包含三要素：**URL**、**操作描述（actions）**、**检查点（checkpoints）**。

操作描述不需要精确到具体的 CSS 选择器或 DOM 元素，只需用自然语言说明要做什么，skill 执行时会通过 `take_snapshot` 获取页面快照自动定位元素。

### 示例：YAML 格式

```yaml
name: 百度新闻跳转验证
url: https://www.baidu.com
actions: 进入百度首页后，点击顶部导航栏中的"新闻"链接
checkpoints:
  - 页面成功跳转到百度新闻站点
  - 新页面的 URL 包含 news.baidu.com
  - 新闻页面正常加载，能看到新闻标题列表
```

## 执行流程

### Phase 0: 用例读取与环境就绪检查

**核心原则**：不要求用户提供前端启动命令，而是先读取所有用例 URL，自动判断环境是否就绪，仅在必要时提示用户手动启动。

#### 0.1 Chrome MCP 可用性预检

在执行任何操作之前，必须先确认 Chrome DevTools MCP 连接正常，避免后续流程中才发现浏览器实例冲突导致整个流程中断。

**执行步骤**：

1. 调用 `list_pages` 测试 MCP 连接是否正常
2. 根据返回结果分类处理：

| 返回结果 | 处理方式 |
|---------|---------|
| 正常返回页面列表 | MCP 连接正常，继续执行 |
| `browser already running` 错误 | 提示用户手动关闭已有的 Chrome 实例后重试（见下方提示模板） |
| `MCP tool is not found` 错误 | 提示用户检查 MCP server 是否已启动并正确配置 |
| 其他连接错误 | 提示用户检查 MCP server 状态 |

3. 如果 MCP 连接异常，**必须**通过 `AskUserQuestion` 通知用户：

```
Chrome DevTools MCP 连接异常：{错误信息}

请按以下步骤处理后重试：
1. 手动关闭所有 Chrome 浏览器窗口
2. 确认 MCP server 已正确启动
3. 回复我继续执行

A. 已处理，继续执行
B. 中止测试
```

4. 用户回复后重新执行 `list_pages` 验证，确认正常后才继续

> **重要**：禁止使用 `pkill`/`kill` 等命令强制杀死 Chrome 或 MCP server 进程。强杀进程会导致 MCP 连接不可恢复，只能由用户手动重启。

#### 0.2 创建迭代输出目录

在用例所在目录下，按递增编号创建本次运行的输出目录，用于存放截图和总结报告。

**执行步骤**：

1. 确定用例所在目录（即用户提供用例文件的目录，或用户当前工作目录）
2. 使用 `LS` 工具列出该目录下已有的 `iteration-*` 文件夹
3. 解析已有编号，计算 `max(N) + 1` 作为本次编号；若不存在则从 `1` 开始
4. 使用 `RunCommand` 创建新目录：`mkdir -p <case_dir>/iteration-{N}`
5. 记录本次迭代目录路径 `ITERATION_DIR`，后续所有截图和报告均写入该目录

**目录结构示例**：
```
<case_dir>/
├── iteration-1/                          # 第 1 次运行
│   ├── report.md                         # 总结报告
│   ├── case1_success.png                 # 用例 1 成功截图
│   ├── case2_failure_1679000000.png      # 用例 2 失败截图
│   ├── case2_fix-advice.md               # 用例 2 失败现场还原文档
│   └── ...
├── iteration-2/                          # 第 2 次运行
│   ├── report.md
│   ├── case1_success.png
│   └── ...
└── ...
```

#### 0.3 URL 变量替换

如果用例中包含 `{url}` 变量格式的 URL：

1. 检查用户是否在参数中提供了 base URL
2. 如果未提供，通过 `AskUserQuestion` 询问实际的 base URL（如 `http://localhost:3000`）
3. 将所有用例中的 `{url}` 替换为实际地址

#### 0.4 读取并解析用例 URL

解析用户提供的所有测试用例，提取出所有涉及的 URL 列表，然后对每个 URL 进行分类：

| URL 类型 | 判断规则 | 示例 | 处理方式 |
|---------|---------|------|---------|
| **公网地址** | host 为已知公网域名（如 `*.baidu.com`、`*.douyin.com`、`*.taobao.com` 等），或 host 不是 `localhost` / `127.0.0.1` / 内网 IP 段 | `https://www.baidu.com` | 无需检查，直接可用 |
| **本地地址** | host 为 `localhost`、`127.0.0.1`、`0.0.0.0`，或端口形式的本地服务 | `http://localhost:3000` | 需要探测可达性 |
| **内网地址** | host 为内网 IP 段（`10.*`、`172.16-31.*`、`192.168.*`）或自定义内网域名 | `http://192.168.1.100:8080` | 需要探测可达性 |

#### 0.5 自动探测环境可达性

对所有**本地地址**和**内网地址**，使用 `RunCommand` 执行 `curl` 探测其可达性：

```bash
curl -sS -o /dev/null -w "%{http_code}" --connect-timeout 5 <url>
```

根据探测结果分为两类：
- **可达**（HTTP 状态码为 2xx/3xx）：标记为就绪，无需用户操作
- **不可达**（连接超时/拒绝/4xx/5xx）：标记为未就绪，需要用户手动启动

> **并发探测**：当存在多个需要探测的 URL 时，在同一个 assistant message 中发起多个 `RunCommand` 调用实现并发探测。

#### 0.6 处理不可达的环境

如果存在不可达的本地/内网 URL，**必须**通过 `AskUserQuestion` 通知用户：

```
检测到以下测试用例的目标环境尚未启动，无法访问：

- http://localhost:3000 （用例：XXX）
- http://localhost:8080 （用例：YYY）

请先手动启动对应的服务环境，确认可访问后回复我继续执行。

A. 环境已启动，继续执行
B. 跳过这些不可达的用例，只执行其他用例
```

用户回复后：
- 若选择 **A**：重新探测一次，确认可达后继续
- 若选择 **B**：将不可达用例标记为 `SKIPPED`，仅执行可达用例

#### 0.7 后端与 Mock Server 配置（可选）

仅当用例中涉及 API 调用且用户主动提出需要时，才询问以下配置：

**后端服务配置**（用户主动提出时才询问）：
```
后端服务如何提供？
A. 本地启动 — 提供启动命令和目录
B. 远程服务 — 提供 API Host + 端口
C. 不需要后端（纯静态页面或已内嵌）
```

**Mock Server**（用户主动提出时才询问）：
```
是否需要 Mock Server 能力？
A. 需要 — 请提供 API 文档路径，我会基于文档搭建 Mock Server
B. 不需要
```

#### 0.8 启动辅助服务（如需要）

根据用户选择，按以下顺序启动服务（使用 `RunCommand` 工具，设置 `blocking: false`）：

1. **Mock Server**（如需要）：
   - 读取 API 文档，初始化 Mock Server
   - 在新终端中启动 Mock Server
   - 验证 Mock Server 健康检查通过

2. **后端服务**（如需要本地启动）：
   - 在新终端中执行后端启动命令
   - 等待后端服务就绪

#### 0.9 最终确认所有 URL 可达

在进入测试执行前，对所有用例 URL（包括公网地址）做一次最终可达性确认，确保网络环境正常。

#### 0.10 登录态检测与用户辅助登录

**核心原则**：在正式执行测试用例之前，主动检测目标页面是否需要登录认证。如果检测到登录页面，暂停执行并请求用户在当前浏览器 session 中手动完成登录，确保后续测试用例在已认证的会话中运行。

**检测时机**：在 0.9 URL 可达性确认通过后、Phase 1 用例解析之前执行。

**执行步骤**：

1. **对用例 URL 去重**，提取出所有不同 origin（协议+域名+端口）的 URL。对于同一 origin 下的多个路径，只需检测一次登录态即可（因为同 origin 共享 Cookie/Session）。

2. **逐个 origin 打开探测页面**：
   - 使用 `new_page` 打开该 origin 下的第一个用例 URL
   - 等待页面加载完成（`wait_for` 或适当延时）
   - 执行登录态检测（见下方检测策略）

3. **登录态检测策略**（按优先级依次执行，任一命中即判定为需要登录）：

   | 检测方法 | 工具 | 判定规则 |
   |---------|------|---------|
   | **URL 重定向检测** | `evaluate_script`: `() => window.location.href` | 当前 URL 包含 `login`、`signin`、`sign-in`、`auth`、`sso`、`cas`、`oauth`、`passport` 等关键词（不区分大小写），说明被重定向到了登录页 |
   | **页面快照关键词检测** | `take_snapshot` | 快照中包含典型登录页面元素：密码输入框（`type="password"`）、"登录"/"Sign in"/"Log in" 按钮、用户名/邮箱输入框等 |
   | **HTTP 状态码检测** | `list_network_requests` | 页面主文档请求返回 401 Unauthorized 或 403 Forbidden |
   | **页面标题检测** | `evaluate_script`: `() => document.title` | 页面标题包含"登录"、"Login"、"Sign in"、"认证"、"Authentication" 等关键词（不区分大小写） |

4. **如果检测到需要登录**，**必须**通过 `AskUserQuestion` 暂停并通知用户：

   先截图当前页面状态以便用户了解情况：
   ```
   take_screenshot → 保存为 {ITERATION_DIR}/login_detection_{origin_host}.png
   ```

   然后通过 `AskUserQuestion` 提示用户：
   ```
   检测到访问 {origin} 时需要登录认证。

   当前页面已被重定向到登录页（{current_url}），请在该浏览器窗口中手动完成登录。

   操作步骤：
   1. 切换到测试浏览器窗口（Chrome DevTools MCP 控制的浏览器）
   2. 在登录页面中输入您的账号密码完成登录
   3. 确认登录成功后（页面跳转到目标页面或首页）回复我继续执行

   A. 已完成登录，继续执行
   B. 该站点无需登录，跳过检测继续执行
   C. 中止测试
   ```

5. **用户完成登录后验证**：
   - 用户选择 **A** 后，重新执行登录态检测（步骤 3），确认登录成功
   - 如果仍然检测到登录页面，再次提示用户，最多重试 3 次
   - 验证通过后，记录该 origin 为「已认证」，后续同 origin 的用例无需再次检测
   - 用户选择 **B**：标记该 origin 为「已认证」，跳过检测
   - 用户选择 **C**：中止整个测试流程

6. **关闭探测页面**：
   - 登录验证完成后，使用 `close_page` 关闭探测用的页面（如果不是最后一个页面）
   - 已认证的 session（Cookie/LocalStorage）会在同一浏览器实例的后续页面中自动保持

> **重要**：登录检测是在整个测试流程开始前的预检阶段完成的，确保后续 Phase 2 并发执行时所有页面都已具备登录态。同一浏览器实例内的所有标签页共享 Cookie 和 Session Storage，因此只需在探测页面中登录一次，同 origin 的所有用例即可共享认证状态。

### Phase 1: 用例解析

将用户提供的自然语言用例解析为可执行的测试计划：

1. **提取三要素**：
   - `url`: 测试目标 URL
   - `actions`: 自然语言操作描述（如"点击新闻链接"、"在搜索框输入手机壳"）
   - `checkpoints`: 检查点列表（如"页面跳转到新闻站点"、"搜索结果展示商品列表"）

2. **将自然语言 actions 拆解为执行步骤**：
   - 不依赖用户提供 CSS 选择器或 DOM 结构
   - 每一步操作前先通过 `take_snapshot` 获取页面 a11y tree
   - 根据自然语言描述，从快照中智能匹配目标元素的 `uid`
   - 例如：用户说"点击新闻链接" → 在快照中找到文本为"新闻"的 link 元素 → 获取其 uid → 执行 click

3. **对每个用例生成执行计划**，包括：
   - 打开页面（`new_page`）
   - 获取页面快照（`take_snapshot`），理解页面结构
   - 根据自然语言描述定位元素并执行操作（`fill` / `click` / `press_key`）
   - 验证检查点（`wait_for` / `evaluate_script` / `take_snapshot`）
   - 截图保存到 `ITERATION_DIR`（`take_screenshot`）

---

### Phase 2: 并发执行测试用例

#### 重要规则：当用例数量 >= 2 时，必须使用并发方式执行，但最大并发数不超过 `MaxConcurrency`（默认 3）

**并发执行策略**：

1. **分批并发打开测试页面**：
   - 将所有用例按 `MaxConcurrency`（默认 3）分批
   - 每批内使用 `new_page` 工具同时为每个用例打开独立的浏览器标签页
   - 在同一个 assistant message 中发起同一批内的多个 `new_page` 调用实现并发
   - 当前批次的所有用例执行完毕后，再开始下一批
   - 记录每个用例对应的 `pageId`

2. **按页面分别执行测试步骤**（在当前批次内）：
   - 对每个用例，使用 `select_page` 切换到对应页面
   - 依次执行该用例的操作步骤
   - 每完成一个用例的步骤，立即切换到下一个用例

3. **具体执行步骤映射**：

   | 用例操作 | Chrome DevTools MCP 工具 | 说明 |
   |---------|-------------------------|------|
   | 导航到 URL | `navigate_page` / `new_page` | 打开目标页面 |
   | 等待元素 | `wait_for` | 等待特定文本或元素出现 |
   | 获取页面结构 | `take_snapshot` | 获取页面 a11y tree 快照，定位元素 uid |
   | 填写输入框 | `fill` | 根据快照中的 uid 填写表单 |
   | 点击元素 | `click` | 根据快照中的 uid 点击按钮/链接 |
   | 按键 | `press_key` | 模拟键盘操作（如 Enter） |
   | 验证标题 | `evaluate_script` | `() => document.title` 检查标题 |
   | 验证文本 | `wait_for` | 等待指定文本出现在页面 |
   | 截图 | `take_screenshot` | 保存当前页面截图 |
   | 悬停 | `hover` | 悬停到指定元素 |
   | 拖拽 | `drag` | 拖拽元素到目标位置 |

4. **元素定位策略**：
   - **优先使用 `take_snapshot`** 获取页面 a11y tree，通过文本内容/角色/属性匹配元素 `uid`
   - 快照中的 `uid` 是与 Chrome DevTools MCP 交互的唯一元素标识符
   - 不要假设元素的 uid，每次操作前必须获取最新快照
   - 如果快照中找不到目标元素，可尝试滚动页面或等待加载

5. **运行时登录态检测**：

   在每个用例的页面打开后（`new_page` / `navigate_page` 之后），以及执行操作过程中发生页面跳转后，都需要进行登录态检测。这是对 Phase 0.10 预检的补充——因为某些页面路径可能需要额外的权限，或者 session 可能在测试过程中过期。

   **检测触发时机**：
   - 每个用例首次打开目标页面后，获取 `take_snapshot` 前
   - 操作过程中如果检测到 URL 发生了非预期跳转（跳到了登录页）
   - `navigate_page` 导航到新 URL 后

   **检测方法**：复用 Phase 0.10 的登录态检测策略（URL 重定向检测、页面快照关键词检测、HTTP 状态码检测、页面标题检测）。

   **检测到需要登录时的处理**：

   1. 暂停当前用例的执行
   2. 截图保存当前页面状态：`take_screenshot → {ITERATION_DIR}/{case_name}_login_required.png`
   3. 通过 `AskUserQuestion` 通知用户：

      ```
      执行用例「{case_name}」时检测到页面需要登录。

      当前页面 URL: {current_url}
      目标 URL: {expected_url}

      请切换到测试浏览器窗口，在当前页面完成登录后回复我。

      A. 已完成登录，继续执行当前用例
      B. 跳过当前用例，继续执行其他用例
      C. 中止测试
      ```

   4. 用户回复后：
      - **A**：验证登录成功后，从当前步骤重新开始执行（导航回目标 URL）
      - **B**：标记当前用例为 `SKIPPED (需要登录)`，继续执行其他用例
      - **C**：中止整个测试流程

   > **注意**：运行时检测不应过度干扰测试流程。如果某个 origin 在 Phase 0.10 中已标记为「已认证」且当前用例的 URL 并未重定向到登录页，则跳过检测，直接执行操作步骤。

### Phase 3: 检查点验证 & 失败日志收集

对每个用例的每个检查点进行验证：

#### 3.1 检查点验证方法

| 检查类型 | 验证方法 | 工具 |
|---------|---------|------|
| 标题包含特定文本 | `evaluate_script`: `() => document.title` | `evaluate_script` |
| 页面包含特定文本 | `wait_for` with text array | `wait_for` |
| 元素存在 | `take_snapshot` 后搜索元素 | `take_snapshot` |
| URL 包含特定内容 | `evaluate_script`: `() => window.location.href` | `evaluate_script` |
| 页面无报错 | 检查控制台消息 | `list_console_messages` |
| API 请求成功 | 检查网络请求 | `list_network_requests` + `get_network_request` |

#### 3.2 操作链路同步日志收集（核心能力）

**核心原则**：日志收集不是事后行为，而是与操作链路**同步进行**的。在执行用例的每一步操作时，都需要实时感知当前操作是否触发了错误或异常请求，确保失败现场的日志是**操作发生时**的真实记录，而非事后补采。

**同步收集策略**：

1. **每一步操作后立即检查控制台**：
   - 每执行一个 action（如 click、fill、press_key）后，立即调用 `list_console_messages` 检查是否产生了新的 `error` / `warn` 日志
   - 记录每一步操作关联的控制台输出，建立「操作 → 日志」的对应关系

2. **操作触发请求时同步收集 API 日志**：
   - 当操作步骤涉及**提交表单、点击发送/保存/确认按钮**等可能触发 API 请求的动作时，操作完成后必须立即调用 `list_network_requests`（过滤 `resourceTypes: ["xhr", "fetch"]`）检查新产生的请求
   - 对于状态码为 4xx/5xx 的失败请求，立即调用 `get_network_request` 获取完整的请求体和响应体
   - 记录请求的 URL、Method、Status、Request Headers/Body、Response Headers/Body

3. **操作链路上下文绑定**：
   - 所有收集到的日志必须绑定到触发它的具体操作步骤上，例如："步骤 3: 点击提交按钮 → 触发 POST /api/submit → 返回 500"
   - 这种绑定关系将在失败报告中完整还原操作链路

**当检查点验证失败时，在同步收集的基础上，额外执行以下完整的现场采集**：

1. **截图当前页面状态**：
   ```
   take_screenshot → 保存为 {ITERATION_DIR}/{case_name}_failure_{timestamp}.png
   ```

2. **收集完整控制台日志**：
   ```
   list_console_messages → 筛选 error 和 warn 类型
   get_console_message → 获取关键错误消息的详细内容（包含完整堆栈信息）
   ```

3. **收集完整网络请求日志**：
   ```
   list_network_requests → 获取所有请求列表（重点关注 xhr/fetch 类型）
   get_network_request → 对失败的请求(4xx/5xx)获取详细请求体和响应体
   ```
   重点关注：
   - 状态码为 4xx/5xx 的请求
   - XHR/Fetch 类型的 API 请求
   - 请求和响应的 headers、body
   - 请求的时间线顺序（用于还原操作链路）

4. **获取页面快照**：
   ```
   take_snapshot → 保存完整的页面 a11y tree 结构
   ```

5. **检查 JavaScript 错误**：
   ```
   evaluate_script: () => {
     return window.__ERROR_LOG__ || 'No errors captured';
   }
   ```

6. **收集页面 DOM 状态**：
   ```
   evaluate_script: () => {
     return {
       url: window.location.href,
       title: document.title,
       readyState: document.readyState,
       bodyText: document.body?.innerText?.substring(0, 2000)
     };
   }
   ```

#### 3.3 失败重试机制

当用例失败时：

1. 收集完所有日志后，分析失败原因
2. 如果是页面加载问题（超时/网络错误），尝试刷新页面重试
3. 如果是元素定位问题，重新获取快照并尝试其他定位方式
4. 每个用例最多重试 `MaxRetries` 次（默认 3 次）
5. 超过最大重试次数后标记为失败，继续执行其他用例

#### 3.4 数据缺失导致的用例无效判定

**核心原则**：当用例失败的根本原因是**页面缺少必要的业务数据**（而非代码 bug 或环境问题）时，该用例应被判定为「无效（缺少数据）」而非「失败」。这类用例的失败不是代码问题，重试也不会成功，需要用户先补充数据后再执行。

**检测时机**：在检查点验证失败后、进入失败重试机制之前执行数据缺失判定。如果判定为数据缺失，**跳过重试机制**，直接标记为无效。

**数据缺失判定策略**（满足以下任一条件即判定为数据缺失）：

| 判定方法 | 检测方式 | 典型场景 |
|---------|---------|---------|
| **空列表/空表格检测** | `take_snapshot` 快照中存在空状态占位符：如"暂无数据"、"No data"、"No results"、"空空如也"、"Empty"等文案；或表格/列表容器存在但内容行数为 0 | 用例需要操作列表项，但列表为空 |
| **操作目标不存在** | 用例操作描述中需要点击/选择某个数据项（如"点击第一条模板"、"选择某个评估器"），但页面快照中完全找不到可操作的数据项元素 | 用例依赖已有数据进行操作，但系统中没有相关数据 |
| **空状态组件检测** | `take_snapshot` 快照中出现典型的空状态 UI 组件：空状态插图、"创建第一个 XXX"引导按钮、"暂无 XXX"提示文案 | 功能模块本身正常，但没有任何业务数据 |
| **API 返回空数据** | `list_network_requests` + `get_network_request` 检查数据查询接口返回的列表为空数组 `[]` 或 `total: 0`，且 HTTP 状态码为 200（接口正常但数据为空） | 后端正常响应，但确实没有数据 |
| **级联数据缺失** | 前置操作步骤因数据为空而无法继续，导致后续所有操作步骤和检查点都无法执行 | 第一步"选择模板"就因为模板列表为空而失败，后续步骤全部无法进行 |

**判定流程**：

1. 检查点验证失败后，在已收集的现场日志（快照、网络请求、页面文本）中检索上述数据缺失信号
2. 如果命中任一判定条件：
   - 将该用例标记为 `INVALID (缺少数据)`，而非 `FAIL`
   - **跳过失败重试机制**（数据缺失不是偶发错误，重试不会改变结果）
   - 生成专用的简化版 fix-advice 文档（见 Phase 4.3）
3. 如果未命中任何数据缺失条件，按原有逻辑进入失败重试机制（3.3）

> **重要**：数据缺失判定必须与代码 bug 区分开。例如：如果列表 API 返回 500 错误导致列表为空，这是代码/后端问题，不是数据缺失；只有当 API 正常返回 200 但数据为空时，才判定为数据缺失。

## 技术规范

### Chrome DevTools MCP 工具使用规范

1. **页面管理**：
   - 每个测试用例使用独立的浏览器标签页（`new_page`）
   - 通过 `select_page` + `pageId` 切换用例上下文
   - 测试完成后必须使用 `close_page` 关闭所有测试页面（Phase 5）
   - 最后一个页面导航到 `about:blank` 释放资源

2. **元素交互**：
   - 所有元素操作必须基于 `take_snapshot` 返回的 `uid`
   - 操作前获取最新快照，不缓存旧的 uid
   - 对于动态页面，操作后等待适当时间再获取新快照

3. **并发控制**：
   - 同一 message 内可以并发调用多个独立的工具
   - `new_page` 可以并发创建多个页面，但同一批次最多并发 `MaxConcurrency`（默认 3）个用例
   - 用例数超过 `MaxConcurrency` 时，按批次依次执行，每批最多 `MaxConcurrency` 个
   - 但同一页面上的操作必须串行执行
   - 页面切换（`select_page`）后的操作必须按顺序进行

4. **超时处理**：
   - `wait_for` 默认超时 10000ms
   - 页面导航默认超时使用工具默认值
   - 超时后自动触发失败日志收集

5. **日志收集工具映射**：

   | 日志类型 | 工具 | 参数 |
   |---------|------|------|
   | 控制台消息 | `list_console_messages` | `types: ["error", "warn"]` |
   | 控制台详情 | `get_console_message` | `msgid: {id}` |
   | 网络请求列表 | `list_network_requests` | `resourceTypes: ["xhr", "fetch"]` |
   | 网络请求详情 | `get_network_request` | `reqid: {id}` |
   | 页面截图 | `take_screenshot` | `filePath: {ITERATION_DIR}/{name}.png` |
   | 页面快照 | `take_snapshot` | - |
   | 执行脚本 | `evaluate_script` | `function: () => {...}` |

## 执行准则

1. **Chrome MCP 预检优先**：在执行任何操作之前，必须先验证 Chrome DevTools MCP 连接正常
2. **并发优先**：两个及以上用例时必须使用并发执行，但最大并发数不超过 `MaxConcurrency`（默认 3），超出时分批执行
3. **同步日志收集**：操作链路中每一步操作后同步检查控制台错误和 API 请求日志，不依赖事后补采
4. **日志优先**：失败时必须尽可能多地收集日志（控制台、网络、截图、DOM 状态），确保现场完整可回溯
5. **不修改用例**：不允许修改用户提供的测试用例内容
6. **快照定位**：所有元素交互必须基于 `take_snapshot` 的 uid，不要猜测或硬编码
7. **错误不中断**：单个用例失败不应阻塞其他用例的执行
8. **完整报告**：无论成功或失败，都必须输出完整的总结报告 `report.md`
9. **失败现场还原**：每个失败用例必须单独输出 `{case_name}_fix-advice.md`，仅做现场还原（原始用例 + 失败现象 + 日志），不包含修复猜想
10. **截图保存**：每个用例执行完毕后必须截图，失败时额外截取失败现场，所有截图存入 `ITERATION_DIR`
11. **Chrome 清理**：所有用例执行完毕且报告输出后，必须关闭所有测试页面并尽力销毁 Chrome 实例
12. **服务清理**：测试完成后清理所有由 skill 启动的辅助服务进程（如 Mock Server、后端服务）
13. **环境自检优先**：不要求用户提供前端启动命令，先自动探测用例 URL 可达性，仅在不可达时提示用户手动启动
14. **迭代目录管理**：每次运行必须在用例目录下创建递增的 `iteration-N` 目录，所有产出物（截图、报告、fix-advice）均写入该目录
15. **Chrome 进程安全**：禁止使用 `pkill`/`kill`/`killall` 等命令直接杀死 Chrome 浏览器或 MCP server 进程。如果遇到 Chrome 实例冲突（如 `browser already running` 错误），必须通过 `AskUserQuestion` 提示用户手动关闭浏览器后重试。直接杀进程会导致 MCP 连接不可恢复，整个测试流程将无法继续
16. **登录态检测**：在 Phase 0 预检阶段和 Phase 2 运行时，自动检测目标页面是否需要登录。检测到登录页时，截图并通过 `AskUserQuestion` 请求用户在浏览器 session 中手动完成登录。同一 origin 只需登录一次，同浏览器实例内的标签页共享 Cookie/Session。不要尝试自动填写登录表单
17. **数据缺失判定**：当用例失败的根因是页面缺少业务数据（空列表、空表格、无可操作数据项）而非代码 bug 时，将用例标记为 `INVALID (缺少数据)` 而非 `FAIL`，跳过重试机制，生成简化版 fix-advice 文档仅说明缺少什么数据及用户补充指引。判定前提是相关 API 返回 200 但数据为空（非 4xx/5xx 错误）

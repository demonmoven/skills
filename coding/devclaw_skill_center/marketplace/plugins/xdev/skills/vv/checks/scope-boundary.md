## 审查要点

### 范围原则 (Scope Principles)

1. **原子性原则 (Atomicity)**
   - 一个 PR 应聚焦于**一个**独立的功能、修复或重构。
   - **禁止**混合多种目的的提交（例如：在修复 Bug A 时顺手重构了不相关的 B 模块，或修改了无关的基础设施配置）。
   - 跨模块修改 (Cross-Module Side Effects) 必须有强理由。

2. **一致性原则 (Consistency)**
   - 代码风格不仅要正确，还要与现有代码库保持一致。
   - 错误处理模式（`errorx` vs `fmt.Errorf`）、日志格式、项目结构应遵循既有惯例。
   - **不一致**本身就是一种范围越界（引入了异构性）。

### 基础范围检查

- 超出规格/计划范围的代码变更
- 与功能变更混合的无关重构
- 功能蔓延或过度设计
- 修改了本功能不应修改的文件

### 文件类型差异化判断

不同类型的文件变更有不同的评判标准：

1. **配置文件变更**
   - `go.mod`, `go.sum`: 新增依赖是否必要？是否引入了过重的依赖？
   - 配置 yaml/json: 变更是否在规格范围内？
   ```
   # 问题示例：为简单功能引入重量级依赖
   + require github.com/some-heavy-framework v1.0.0  // 只是为了用一个小功能
   ```

2. **共享工具类变更**
   - `utils/`, `common/`, `pkg/` 等共享代码的变更
   - 是否考虑了对其他模块的影响？
   - 是否应该新建专用工具而非修改共享代码？

3. **IDL/Proto 文件变更**
   - 接口定义变更是否在规格范围内？
   - 是否添加了规格未要求的字段或方法？

4. **数据库迁移文件**
   - 是否添加了规格未要求的表或字段？
   - 迁移脚本是否可逆？

### Fix Agent 修复副作用检测

在 E2E 迭代修复过程中，Fix Agent 容易产生以下副作用：

1. **过度修复**
   - 为修复一个测试失败，修改了不相关的文件或逻辑
   - 例：修复 API A 的问题时，意外修改了 API B 的行为
   ```
   # 问题示例：修复范围过大
   变更文件: api/handler_a.go, api/handler_b.go, api/handler_c.go
   实际问题: 只在 handler_a.go 中
   ```

2. **连锁修改**
   - 修改一处导致需要修改多处
   - 如果发现修复需要修改 5+ 个不相关文件，应该重新评估方向

3. **撤销之前的正确实现**
   - 新的修复是否意外撤销了之前迭代的正确修改？
   - 检查 git diff 是否有 `-` 行撤销了之前 `+` 行添加的逻辑

4. **过度设计**
   - 添加了规格未要求的抽象层
   - 添加了"以防万一"的配置选项
   - 过早优化

## 严重程度分级

> 通用四级定义见 `references/severity-scoring.md`。

| 级别 | 描述 | 示例 |
|------|------|------|
| **严重** | 变更明显超出范围，添加了规格未定义的功能或修改了不相关模块 | 规格只要求 CRUD，却添加导出功能；修改了与当前功能完全无关的模块（如在开发评估器时修改了用户认证逻辑）；撤销了之前迭代的正确修复 |
| **中等** | 变更可能超出范围，包含不必要的重构或改进 | 在功能修改的文件中进行大量代码重构；添加规格未要求的优化；引入不必要的依赖 |
| **轻微** | 变更略微超出范围，但影响有限 | 在修改的函数中添加额外日志；小范围的变量重命名；添加注释 |
| **提示** | 不确定是否是问题，或优先级很低的观察 | 基础设施脚本的小幅调整；自动生成代码的格式变化；开发工具配置变更 |

**注意:**
- 只报告你有合理置信度的问题
- 如果不确定某事是否是问题，将其标记为**提示**级别，并说明不确定的原因
- 提示级别用于：不确定是否合理、不确定是否是问题、优先级很低的观察

### 通过判定的额外条件

- **无 Fix Agent 严重副作用**: 未检测到"撤销正确实现"或"过度修复导致功能破坏"

不通过 (Fail) 的额外情况：
- 检测到"撤销正确实现"（新修复撤销了之前迭代的正确修改）
- 检测到"过度修复"导致其他功能受影响
- 添加了完全与规格无关的新功能

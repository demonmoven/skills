对于每个变更的文件：

5. 记录任何性能或一致性风险

## 审查要点

### 数据库性能陷阱

1. **N+1 查询问题**
   - **严禁**在循环中进行数据库查询或 RPC 调用
   - 应使用批量查询接口 (BatchGet / MGet)
   ```go
   // 严重问题：N+1 查询
   for _, id := range userIDs {
       user, _ := db.GetUser(id) // 每次循环一次 DB 调用
   }
   // 正确做法：批量查询
   users, _ := db.GetUsers(userIDs) // 一次 DB 调用
   ```

2. **索引意识**
   - 新增的查询条件 (`WHERE` 子句) 是否有对应的索引支持？
   - 是否对大表进行了全表扫描？
   - 模糊查询是否使用了前缀通配符 (`LIKE '%value'`) 导致索引失效？

3. **大对象加载**
   - 是否一次性加载了过多数据到内存（如 `SELECT *` 无 Limit）
   - 是否在内存中进行大数据的排序或过滤（应下推到 DB）

### 事务与锁粒度

1. **长事务风险**
   - **严禁**在数据库事务中进行 RPC 调用、HTTP 请求或复杂计算
   - 事务应仅包含必要的 DB 操作，保持短小快
   ```go
   // 严重问题：事务中包含 RPC
   tx := db.Begin()
   resp, err := remoteClient.Call() // RPC 可能超时，导致长事务锁定 DB
   ```

2. **锁粒度过大**
   - 是否锁住了整个大对象或长列表，而非单个条目
   - 锁持有的时间是否包含了 I/O 操作

### 分布式一致性

1. **幂等性 (Idempotency)**
   - 所有的核心写接口（支付、扣库存、创建订单）是否支持幂等？
   - 是否有唯一的 `idempotency_key` 或业务 ID 防重？
   - 重试机制下是否会导致数据重复写入？

2. **分布式事务/最终一致性**
   - 跨服务调用失败后，是否有数据补偿机制？
   - 是否存在本地事务提交成功但远程调用失败导致的数据不一致？
   - 是否需要使用事务消息或 Saga 模式？

3. **缓存一致性**
   - 更新数据时，缓存策略是否正确（Cache Aside Pattern：先更库，再删缓存）？
   - 是否存在并发更新导致的缓存脏读？

### 资源使用与稳定性

1. **连接池使用**：是否正确使用了连接池，而非每次请求新建连接？连接泄漏风险？
2. **内存分配**：是否频繁创建大对象导致 GC 压力？`bytes.Buffer` 或 Slice 是否复用？

## 严重程度分级

> 通用四级定义见 `references/severity-scoring.md`。

| 级别 | 示例 |
|------|------|
| **严重** | 核心路径 N+1 查询；事务中包含 RPC；写接口无幂等保护；死循环风险 |
| **中等** | 疑似缺失索引的查询；锁粒度过大；缓存更新策略存疑；未限制的大列表查询 |
| **轻微** | 可以使用更高效的 API；可以复用内存对象；日志过多影响性能 |
| **提示** | 建议添加索引但不确定表大小；建议使用缓存；关于架构设计的讨论 |

**注意**: 如果不确定某事是否是问题，将其标记为**提示**级别，并说明不确定的原因。

# 误区纠正（豆包-创作 agent 链路）

> 本文档列出**新人 / AI Coding 工具最容易归类错误**的 7 条典型混淆。每条给出"误区现象 + 纠正"。
>
> **使用方式**：当 brainstorm skill 在阶段一定位时遇到歧义，回到这里查；当 RD 写方案前对架构理解不确定时，回到这里查。

---

## 误区 1：以为 `creation_evaluation` 是独立仓库

**误区**：看到 `flow.agent.creation_evaluation` 是独立 PSM，以为是独立仓库。

**纠正**：
- `flow.agent.creation_evaluation` 是**独立 PSM**
- **但与 `flow.agent.creation` 共仓库** `creation_agent/`
- 子目录 `creation_agent/creation_evaluation/` 有自己的 main.go / handler / service
- 同一份 build.sh 产出**两个二进制**，部署时按 PSM 选启动入口
- `creation_agent/main.go` 第 42-45 行：`if isPSMCreationEvaluation() { creation_evaluation.Main() }`

**影响**：如果以为是两个仓库，会重复 clone / 漏改 / 混淆 owner。

---

## 误区 2：以为 Libra 是仓库内 SDK

**误区**：看到代码里 `LibraGet(...)`，以为是仓库内的 SDK 模块。

**纠正**：
- **Libra 是字节内部实验切流平台**（外部基础设施）
- 代码里只是引用**外部 SDK + 散落的常量定义**（如 `creation_access/constant/libra.go`）
- 实验配置 / 切流比例**在 Libra 平台**，不在仓库
- 所以"改 Libra 实验"的动作大部分**不需要改代码**，只需要改 Libra 平台

**影响**：如果以为要改代码，会写出多余的"硬编码切流比例"的方案。

---

## 误区 3：以为 `access` 是 C 端入口

**误区**：看到 `creation_access` 名字带 "access"，以为是 C 端流量入口。

**纠正**：
- **C 端用户直接打 `flow.agent.creation`**，不经过 access
- `creation_access` 6 个接口里 **5 个标注 `picasso 调用`**（仅 EvaluateImageTask 例外）
- 业务方原话："access 主要 for picasso 的适配"
- 所以"接入层"在豆包-创作链路里**等价于"Picasso 评测接入"**

**影响**：方案如果只改 access，C 端用户用不到该改动。详见 [`../../../locators/psm_locator.md`](../../../locators/psm_locator.md) §二、§三。

---

## 误区 4：以为 `agent_phase_26` 是替换老链路

**误区**：看到 `creation_agent/agent_phase_26/` 全新目录、`+16K 行` 改动，以为是把老 Plan-Act 链路重构掉了。

**纠正**：
- **agent_phase_26 是新 ReAct 全新增**（共存策略，不替换）
- 老 Plan-Act 链路在 `handler/phase3handle/` 完全保留
- `creation_agent/handler/handler.go` 顶部用 `option.SupportAgent26(ctx)` + query 标签 `2026_bh` **灰度切换**
- 在灰度 100% 之前，**两条链路都有真实流量**，必须双轨分析

**影响**：如果以为重构掉了，方案漏改老链路 → 灰度回退或未灰度的流量出 bug。详见 [`./5. 新老架构并存策略.md`](../B.%20Agent%20架构专栏/5.%20新老架构并存策略.md)。

## 误区 5：以为 SP 加载已经"统一收敛"

**误区**：看到 PRD § Agent 逻辑层 § SP 管理写了"SP 加载的整体优先级：Picasso > AB > TCC > Fornax"，以为本期已经收敛到一个统一入口。

**纠正**：
- PRD 是**设计意图**，diff 显示**实际未收敛**
- 当前 SP 加载散落在 **3 处**：
  - 旧：`internal/rpc/agent_util/sp.go::LoadSPWithDefault`
  - phase3：`internal/rpc/phase3/agent_runtime/sp_manager.go::SystemPromptManager`
  - 新：`agent_phase_26/agent/sp/agent_sp.go`
- `agent_phase_26/agent/sp/sp.md` 自述："当前**有意不考虑** bizID/tenantID"
- 这是**已知 regression**（详见 `Z.2 PRD vs 实现 Gap 表`）

**影响**：改 SP 必须三处都验证，不能假设统一。详见 [`../../../locators/sp_locator.md`](../../../locators/sp_locator.md)。

## 误区 6：以为 aigc 三件套是平行调用

**误区**：看到 `flow.aigc.{dag, management, tool}` 三个 PSM，以为 `creation_agent` 平行调用三个。

**纠正**：调用关系是**树形（扇形）**，不是平行：

```
creation_agent
   ↓ SyncInvokeTool / AsyncInvokeTool
flow.aigc.tool（网关）
   ├── 查 → flow.aigc.management（拿 DAG topic）
   └── 调 → flow.aigc.dag（执行 DAG）

flow.aigc.management
   └── 调 → flow.aigc.dag（执行 DAG，由 management 直接发起的场景）
```

- `creation_agent` **只直接调 `aigc_tool`**（见 `agent_phase_26/agent/runtime/tool/`）
- `aigc_tool` 内部去查 `aigc_management` 拿 DAG topic，再调 `aigc_dag` 真执行

**影响**：如果以为平行调用，会以为 `creation_agent` 直接调 management → 写出错位的 RPC 强弱依赖表。详见 [`../../../locators/psm_locator.md`](../../../locators/psm_locator.md) §五。

## 误区 7：以为 `_never_used_<hash>` 是乱码或残留 token

**误区**：看到模型输出里大量 `<function_never_used_51bce0c785ca2f68081bfa7d91973934=...>`，以为是模型 bug 或调试残留。

**纠正**：
- 这是 **模型独享 token 围栏**（特殊 token）
- 用于隔离工具调用与正文，避免内容污染
- 由 parser（`agent_phase_26/agent/runtime/think_stream_parser.go` / `content_stream_parser.go`）解析
- **不要尝试简化或重命名这个 token**，会破坏 ReAct 协议

**影响**：如果尝试"清理"会把 ReAct 协议解析逻辑搞坏。详见 [`../../../locators/tool_locator.md`](../../../locators/tool_locator.md) §五。

---

## 误区 8：把 ToolInfo 当成 thrift 接口而不是 JSON schema

**误区**：看到"改 Tool"时，以为要改 `alice_idl` 或 `idl` 的 thrift 文件然后重新生成代码。

**纠正**：
- Tool 的**真正 schema 是 JSON 文件**：`aigc_management/service/domain/ability/schema/<tool>.json`
- 改 schema **不需要重新生成 IDL 代码**
- IDL 里的 `ToolInfo` 是给 RPC 传输用的元数据**结构体**（仅本期从 map 简化为 ToolParamInfo 对象）
- 所以"加 / 改字段"的主战场在 JSON schema，不在 thrift

**影响**：如果搞错主战场，会去改 IDL 然后等不必要的代码生成 → 浪费时间。详见 [`../../../locators/tool_locator.md`](../../../locators/tool_locator.md) §五。

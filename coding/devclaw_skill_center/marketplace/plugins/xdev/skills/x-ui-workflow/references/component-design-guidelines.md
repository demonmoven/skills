# Component Design Guidelines

适用于以下命令生成 `component-design.md` 时统一遵循：
- `/design-from-figma`
- `/design-from-directory`

## 信息来源优先级

生成文档时，按以下优先级判断事实：

1. 真实实现代码
2. `summary.md`
3. `ui.md`
4. `ui.implement.xml`

如果信息冲突，必须以真实代码为准，不得为了“看起来更完整”而偏离实现。

## 文档开头要求

文档必须以以下标题开头：

```md
## UI 组件设计
```

在标题下方必须先说明两点语义：
- 将提案中的组件与下方 UI 组件进行关联
- 在代码实现时，将下方 UI 组件作为对应业务组件 UI 部分的参考

## 每个组件的最小结构

每个组件至少包含以下内容：

~~~md
### 1. <组件名> 组件

**参考实现**
- `apps/components-preview/src/design/...`

**UI 结构**
```text
<ASCII 框图>
```

**职责说明**
- 职责 1
- 职责 2
~~~

要求：
- 标题使用 `### <序号>. <组件名> 组件`
- `参考实现` 必须写真实文件路径
- `职责说明` 保持 1 到 3 条，聚焦 UI 组织与职责边界

## ASCII 结构图要求

- 必须放在代码块中
- 优先表达层级、左右布局、上下布局和主要内容块
- 不追求像素级精确，但必须与真实结构一致
- 命名使用业务语义，不要只写 `div`、`container`、`wrapper`

## 写作要求

- 覆盖页面组合层和业务组件层，不只写叶子组件
- 如果同一组件在多个文件中分拆，说明主入口文件与关键子组件关系
- 只描述 UI 结构和展示职责，不展开状态管理、接口请求等业务实现细节
- 若目录中存在预览文件，可以提到预览入口，但不能把预览文件当作实现源码

## 生成前自检

- [ ] 已重新读取真实代码文件
- [ ] 组件名、路径、层级与实现一致
- [ ] 文档以 `## UI 组件设计` 开头
- [ ] 每个组件都有 `参考实现`、ASCII 结构图和职责说明
- [ ] 没有凭空补充实现中不存在的结构

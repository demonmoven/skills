# Craft Stage 1: 用户动线提取

## 用户输入

```text
$ARGUMENTS
```

解析参数（按顺序）：
- `spec_dir`（必需）：SPEC 文档目录路径
- `idl_repo_path`（必需）：IDL 仓库本地路径，包含已变更的接口定义（Thrift/Protobuf 等）
- `output_dir`（可选）：输出目录。gan-fixloop 调用时会显式传入 `$OUTPUT_DIR/craft`（默认 `.costudio/craft`）；独立调用时默认为 `<spec_dir>/../craft_output/`

---

## 概述

本阶段负责从 SPEC 文档中提取用户动线（User Journey）：识别所有用户故事和验收场景，将每个场景转化为后端 API 调用序列，生成结构化的动线文档供后续测试生成阶段使用。

---

## 执行流程

### 1. 准备

- 确认 `spec_dir` 目录存在
- 确定 `output_dir`，创建目录（如不存在）
- 目标输出文件：`<output_dir>/user_journeys.md`

### 2. SPEC 文档 & IDL 探索

**必须在生成动线前完整阅读所有 SPEC 文档和 IDL 定义：**

1. 使用 Glob 或 Read 工具递归浏览 `spec_dir` 下的所有文件（包括子目录）
2. 重点阅读：API 契约文档、后端规格、数据模型、集成文档、PRD、验收标准
3. **阅读 IDL 仓库**：浏览 `idl_repo_path` 下的 IDL 文件（`.thrift`、`.proto` 等），提取：
   - 接口方法定义（方法名、请求/响应结构体）
   - 字段名、类型、是否必填（`required`/`optional`）
   - 枚举类型定义及其值
   - 数据结构（struct/message）及嵌套关系
4. 构建 API 接口清单表格（**必须先完成此步骤**，同时参考 SPEC 和 IDL）：

   | API路径 | HTTP方法 | 功能描述 | 动线编号（待填） |
   |---------|---------|---------|--------------|

   此表格作为覆盖度矩阵的基础，**每行对应一个 API 接口**。

### 3. 生成用户动线

为每条用户动线生成以下结构：

```markdown
## 动线 N: [动线名称]

### 前置条件
- [列出需要的前置数据和状态]

### API 调用序列

#### 步骤 1: [步骤描述]
- **方法**: POST/GET/PATCH/DELETE
- **路径**: /api/...
- **请求体**:
  ```json
  {...}
  ```
- **预期响应**:
  ```json
  {...}
  ```
- **断言**: [关键断言点]

#### 步骤 2: ...

### 预期结果
- [总结预期的最终状态]

### 清理步骤
- [列出数据清理操作，如 Delete 请求]
```

**覆盖范围要求：**
- SPEC 中描述的每个 API 接口（新增、变更）都应有对应动线
- 每个用户故事/验收场景都应有对应动线
- 关键接口需要覆盖异常场景（无效参数、缺失字段等）
- 如果 SPEC 涉及版本管理、调试/验证、批量操作、多类型等功能，也需要覆盖

**异步操作规则（如 SPEC 涉及异步 API）：**
- **轮询终止条件**：明确指定预期终态（如 `status == "completed"`）
- **轮询间隔**：指定合理的 polling interval（如 2 秒）
- **最大等待时间**：指定 timeout（如 60 秒）
- 在动线中明确标注异步步骤的等待逻辑，如：
  ```
  步骤 3: 轮询任务状态
  - 方法: GET /api/v1/tasks/{id}
  - 轮询条件: status != "completed" && status != "failed"
  - 间隔: 2 秒
  - 超时: 60 秒
  - 断言: status == "completed"
  ```

**动线数量原则：** 功能点越多、越复杂，动线数量越多。不要人为压缩动线数量。

### 4. 完成覆盖度矩阵

生成所有动线后：
1. 回填 API 接口清单表格中的「动线编号」列
2. 检查是否有任何 API 没有对应动线编号 → **如有，必须补充动线**
3. 在文档末尾附上完整的「功能点覆盖度矩阵」

### 5. 质量自检

在写入文件前，对照以下清单自检：
- [ ] 每条动线包含前置条件、API 调用序列、预期结果、清理步骤
- [ ] 每个 API 调用有明确的断言点
- [ ] 异步操作有轮询条件和超时设置
- [ ] 清理步骤能恢复测试环境到初始状态
- [ ] 动线间无隐式依赖（每条可独立执行）
- [ ] API 路径和参数与 SPEC 完全一致

有不满足的项 → 修复后再写入文件。

### 6. 将文档写入文件

使用 Write 工具将完整文档写入 `<output_dir>/user_journeys.md`。

**文档结构：**

```markdown
# 用户动线文档

## API 接口覆盖清单

| API路径 | HTTP方法 | 功能描述 | 对应动线编号 |
|---------|---------|---------|------------|
| ... | ... | ... | 动线 1, 动线 3 |

## 动线 1: ...
...

## 动线 N: ...
...

## 功能点覆盖度矩阵

| 功能点 | 覆盖状态 | 对应动线 |
|-------|---------|---------|
```

### 7. Review 与迭代（最多 5 轮）

**第 1 轮**：生成初始文档（如上）。

**第 2+ 轮（Review）**：

对照 SPEC 文档执行以下独立核查（**不得仅依赖已生成的覆盖矩阵**）：

| 检查项 | 要求 |
|-------|------|
| **完整性** | **独立重新提取**：重新阅读所有 SPEC 文档，独立提取一份新的 API 列表（**不参考已有的覆盖矩阵**），逐行比对新列表与已有动线，**发现遗漏必须补充** |
| **正确性** | API 路径、HTTP 方法、请求/响应字段与 SPEC 严格一致 |
| **可测性** | 每条动线有明确的断言点 |
| **独立性** | 每条动线可独立执行 |
| **清理步骤** | 每条动线包含数据清理（如 Delete 操作） |
| **范围** | 只包含 SPEC 范围内的场景 |

**Review 修复优先级**（当发现多个问题时，按此顺序处理）：
1. 遗漏的 API 接口（完整性优先）
2. API 路径/参数错误（正确性）
3. 缺失的断言点（可测性）
4. 缺失的清理步骤
5. 动线独立性问题

- 发现问题 → 直接修改 `user_journeys.md` 并继续下一轮
- 所有检查通过 → 在输出中写入 `CONVERGED`（收敛信号）

---

## 关键规则

- **先建清单，后写动线**：必须先构建 API 接口清单表格，再为每个接口生成动线
- **不得压缩覆盖范围**：表格中任何一行动线编号为空，必须补充动线
- **独立 Review**：Review 时必须重新从 SPEC 提取接口列表独立核查，不得依赖已有矩阵直接 CONVERGED
- **文件写入**：必须通过 Write 工具将文档写入文件，不要只在对话中输出

---

## 产出物

- `<output_dir>/user_journeys.md`：完整的用户动线文档

---

## 注意事项

- **不要**包含 SPEC 范围外的场景
- **不要**将多个动线合并为一条（每条动线对应一个独立的业务场景）
- API 路径、参数类型必须与 SPEC 和 IDL 严格一致，不要臆测或推断。当 SPEC 与 IDL 有出入时，以 IDL 为准（IDL 是代码生成的实际来源）
- 前置条件中的数据应在动线的第一步通过 API 创建，不依赖环境预置数据

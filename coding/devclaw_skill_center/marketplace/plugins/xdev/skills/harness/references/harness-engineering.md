# Harness Engineering 理念与三大支柱

## 核心发现

> **Agent 的表现上限不取决于模型本身，而取决于它工作的环境有多好。**

Harness Engineering（驾驭工程）是一套让 AI Agent 在代码仓库中高效、安全工作的工程实践体系。它不是关于选择哪个模型或提示词技巧，而是关于**如何准备你的代码仓库**，使 Agent 能够像一个资深开发者一样工作。

## 三大支柱

### 支柱一：Context Engineering（上下文工程）

**问题**：Agent 进入一个陌生仓库时，面对数万行代码和复杂的模块关系，往往不知道从哪里开始。

**解决方案**：通过分层文档体系实现"渐进式披露"（Progressive Disclosure），Agent 按需逐层深入获取上下文，而非一次性加载所有信息。

**文档层级**：

```
AGENTS.md (根)                  ← 项目总览、核心约束、文档索引
├── docs/AGENTS.md              ← 中层导航、文档体系索引
├── ARCHITECTURE.md             ← 架构鸟瞰、代码地图、不变量
├── src/module-a/AGENTS.md      ← 模块级上下文、本地约束
├── src/module-b/AGENTS.md      ← 模块级上下文、本地约束
└── docs/
    ├── reference/              ← 代码模式、集成点、运行时行为
    ├── guidance/               ← 调试手册、常见陷阱
    ├── rules/                  ← 黄金原则、不变量
    └── quality/                ← 技术债日志、知识缺口
```

**关键原则**：
- **给 Agent 一张地图，不是一本千页大辞典**——AGENTS.md 是知识导航，不是百科全书
- **命名但不链接**——鼓励 Agent 使用符号搜索能力，而非依赖可能过时的链接
- **只写不太会变的东西**——文档内容应聚焦于稳定的架构决策，而非频繁变动的实现细节

### 支柱二：Architecture Constraints（架构约束）

**问题**：Agent 善于生成代码，但容易违反项目中隐含的架构规则——比如"不要在 handler 层直接访问数据库"或"所有配置必须通过 TCC 下发"。

**解决方案**：将隐含的规则显式化为**不变量（Invariants）**，并通过自动化层级强制执行。

**不变量示例**：

```markdown
<!-- Architecture Invariant: handler 层禁止直接访问数据库 -->
所有数据访问必须通过 repository 层，handler 直接导入 dal 包是被禁止的。

<!-- Architecture Invariant: 配置来源唯一 -->
运行时配置只能通过 TCC 获取，禁止硬编码或环境变量覆盖。
```

**强制执行层级（从低到高）**：

| 层级 | 手段 | 适用场景 |
|------|------|----------|
| Level 0 | 文档声明 | 新约束、尚未被违反的规则 |
| Level 1 | Lint 规则 | 可通过静态分析检测的违规 |
| Level 2 | Pre-commit Hook | 需要在提交前拦截的问题 |
| Level 3 | CI Check | 需要完整构建/测试环境的检查 |

**升级规则（Promotion Rule）**：当同一不变量在文档层被违反 3 次以上，应将 enforcement 提升到下一层级。

### 支柱三：Garbage Collection（垃圾回收）

**问题**：Agent 生成的代码中可能包含占位符实现（`// TODO: implement`）、幻觉标记（引用不存在的包）、超长文件等质量问题。

**解决方案**：通过 **AI Guard Hooks** 在提交前自动拦截这些问题。

**AI Guard 检查项**：

| 检查 | 说明 |
|------|------|
| 占位符检测 | 拦截 `TODO: implement`、`FIXME`、`placeholder` 等标记 |
| 幻觉标记检测 | 检测引用不存在的模块、包或函数 |
| 文件长度检查 | 阻止超过阈值的文件（默认 500 行，可按语言配置） |
| 主分支保护 | 禁止直接提交到 main/master |
| 活跃计划检查 | 存在进行中的 ExecPlan 时提醒关注 |

## 核心信条

1. **适配优先，绝不照搬**——每个仓库都有自己的背景，harness 的配置必须根据实际情况调整
2. **先理解，再行动**——在做任何改动前，先深度理解仓库的技术栈、团队规范和现有实践
3. **尊重已有实践**——增强而非替换，harness 不会推翻项目已有的合理配置
4. **向用户解释"为什么"**——每个配置决策都应有清晰的理由
5. **增量演进**——文档和约束随项目发展持续更新，而非一次性产物

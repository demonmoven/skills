# 架构不变量编写指南

本文档指导 Agent 如何从代码分析中提取有意义的架构不变量（Architecture Invariants），用于 AGENTS.md、ARCHITECTURE.md 和 `docs/rules/invariants.md`。

## 什么是架构不变量

架构不变量是项目中 **刻意不做的事情** 或 **必须维持的性质**。它们的价值在于描述"缺席"——某种依赖关系的缺席、某种模式的缺席——光看代码很难发现，但一旦被打破会造成严重的架构腐化。

好的不变量回答这个问题：**如果一个新人（或 AI Agent）不知道这条规则，最可能犯什么错误？**

## 好的不变量 vs 坏的不变量

**好的（具体、可检测、描述"不做什么"）**：

- "model 层不依赖 view 层。model 中不应出现任何 UI 框架的 import。"
- "所有 API handler 必须通过 middleware 鉴权，handler 函数内禁止直接读取 cookie/token。"
- "生成代码目录 `biz/model/` 和 `biz/router/` 标注了 DO NOT EDIT，禁止手动修改。变更通过 IDL → 代码生成流程更新。"
- "数据库迁移脚本只允许 ALTER ADD，不允许 ALTER DROP 或 RENAME（需走单独审批流程）。"

**坏的（空泛、不可检测、描述"做什么"）**：

- "写好的代码" → 没有任何可执行性
- "保持代码整洁" → 没有判定标准
- "遵循最佳实践" → 太泛，哪些最佳实践？
- "做好测试" → 没有量化标准

## 从代码分析中提取不变量的方法

### 方法 1：检测分层边界

浏览目录结构，识别分层（如 model / service / handler / view）。然后检查：

- 下层是否有向上层的 import？如果没有，这就是一个不变量
- 是否有跨层直接调用（绕过中间层）？如果没有，记录下来

**模板**："[下层] 不依赖 [上层]。[下层] 中不应出现 [上层相关包] 的 import。"

### 方法 2：检测代码生成

搜索 `DO NOT EDIT`、`generated`、`auto-generated` 标记。识别生成工具和生成入口。

**模板**："[目录] 由 [工具] 生成，标注了 DO NOT EDIT，禁止手动修改。变更通过 [源文件] → [生成命令] 流程更新。"

### 方法 3：检测配置和状态边界

找到配置加载入口和状态存储。检查是否有明确的读/写职责划分。

**模板**："配置由 [入口函数] 统一加载，业务代码通过 [接口/context] 获取配置值，禁止在业务逻辑中直接读取配置文件或环境变量。"

### 方法 4：检测安全边界

找到认证/授权 middleware。检查是否所有外部入口都经过它。

**模板**："所有对外 API 必须经过 [middleware] 鉴权。handler 函数内禁止直接操作 token/cookie。"

### 方法 5：检测依赖方向

对于 monorepo 或多模块项目，检查 import graph。识别单向依赖。

**模板**："[模块A] 可以依赖 [模块B]，反之不可。[模块B] 中不应出现 [模块A] 的 import。"

### 方法 6：检测测试策略

查看测试目录结构和测试框架。检查是否有覆盖率门禁。

**模板**："新增业务代码必须有单元测试覆盖。覆盖率由 [脚本/CI] 检查，当前门禁为 [X]%。"

## 不变量的三个层级

### 仓库级不变量（放在根 AGENTS.md）

整个仓库所有代码都必须遵守的规则。例如：

- 文件长度上限
- 代码生成规则
- 分支保护策略
- 安全凭据规则

### 模块级不变量（放在模块 AGENTS.md 或 ARCHITECTURE.md）

特定模块内部的规则。例如：

- 该模块的依赖方向限制
- 该模块的 API 边界（哪些函数是对外的）
- 该模块的数据流方向

### 架构级不变量（放在 docs/rules/invariants.md）

跨模块的架构决策。例如：

- 模块间的调用关系（A → B → C，不允许 C → A）
- 数据存储的唯一事实来源原则
- 事件/消息传递的方向性

## 不变量的 Promotion Rule

当某条规则频繁被违反（出现在 Code Review 中 3+ 次），应将其提升：

    口头约定 → 写入文档 → 写入 lint 规则 → 写入 pre-commit hook → 写入 CI

每次提升都增加了强制力。目标是让机器而非人来执行检查。

## 输出格式

在文档中，不变量用加粗标注：

    **Architecture Invariant**: model 层不依赖 view 层。
    model/ 中不应出现任何 `views`、`templates`、`components` 的 import。

在 `docs/rules/invariants.md` 中使用结构化表格：

    | ID | 不变量 | 范围 | 检查方式 | 状态 |
    |---|---|---|---|---|
    | INV-001 | model 不依赖 view | 仓库级 | code review | 活跃 |
    | INV-002 | 生成代码禁止手改 | biz/model, biz/router | grep DO NOT EDIT | 活跃 |

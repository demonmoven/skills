# Combine Plan & Design

将 `component-design.md` 中的 UI 组件设计信息（参考实现、UI 结构图、职责说明）逐一嵌入到 `plan.md` 对应的实现阶段中，使开发者在实现某个阶段时无需跨文档查阅。

## 适用场景

- 项目中同时存在 `plan.md`（含分阶段实现计划）和 `component-design.md`（含 UI 组件设计）
- 两份文档的组件/阶段存在一一对应关系
- 目标是消除文档碎片，让每个实现阶段包含完整的上下文信息

## 执行流程

### 第一步：分析两份文档的结构

1. 完整读取 `component-design.md`，提取每个组件的三项信息：
   - **参考实现**：组件的文件路径
   - **UI 结构**：ASCII 格式的视觉布局图（`text` 代码块）
   - **职责说明**：组件核心职责的简要描述
2. 完整读取 `plan.md`，识别所有 `### 阶段 N: 组件名` 格式的实现阶段
3. 建立映射关系：将 `component-design.md` 中的每个组件与 `plan.md` 中的对应阶段关联

### 第二步：确定嵌入策略

对每个组件，判断其在 `plan.md` 中的归属：

- **有独立实现阶段的组件**（如业务特性组件）：嵌入到对应阶段的 `**Props 定义**` 之前
- **页面组合层组件**（如 XxxPage）：嵌入到 `## 组件分析` 章节的 `### 页面和组件入口` 中
- **无对应阶段的组件**（如 Store 等非 UI 阶段）：跳过，不涉及 UI 嵌入

### 第三步：逐个嵌入

对每个有对应关系的组件，在 `plan.md` 的目标位置插入以下内容块（保持这个顺序）：

```markdown
**参考实现**
- `<组件文件路径>`

**UI 结构**
\```text
<ASCII UI 结构图，原样复制>
\```

**职责说明**
- <职责描述1>
- <职责描述2>
- ...
```

插入位置规则：
- 在 `**Props 定义**:` 行之前插入
- 在组件的 `**实现路径**` 行之后插入
- 确保插入的内容块与上下文之间有空行分隔

### 第四步：更新文档结构说明

在 `plan.md` 的项目文档结构部分，更新说明以反映合并状态：

```markdown
├── plan.md              # 本文件（已整合 component-design.md 的 UI 组件设计）
├── component-design.md  # UI 组件设计（已合并至 plan.md 各实现阶段）
```

### 第五步：验证完整性

合并完成后，进行以下验证：

1. 统计 `plan.md` 中 `**UI 结构**` 出现的次数，应等于 `component-design.md` 中的组件总数
2. 统计 `**参考实现**` 和 `**职责说明**` 出现的次数，三者应一致
3. 检查所有实现阶段的标题是否完整（`### 阶段 N:` 格式连续递增）
4. 确保没有遗漏的组件（对照 component-design.md 的组件列表逐一核对）

## 嵌入后的阶段结构

每个实现阶段的信息排列顺序应为：

```
组件描述 → 组件层级/所属包/实现路径
→ 参考实现（新增）
→ UI 结构图（新增）
→ 职责说明（新增）
→ Props 定义 → 复用的基础组件 → 组件状态 → 验收场景
```

## 注意事项

- UI 结构图使用 `text` 代码块包裹，保留原始 ASCII 格式，不做任何修改
- 不删除 `component-design.md` 原文件，仅在 plan.md 中标注已合并
- 页面组合层组件（如 AIExperimentCreatePage）放在「组件分析」章节而非实现阶段中，因为它们通常在 User Story 集成阶段才实现，没有独立的组件实现阶段
- 如果 `plan.md` 中某个阶段不涉及 UI（如 Store、路由配置），则跳过，不插入 UI 设计信息

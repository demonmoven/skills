# Harness ExecPlan — 需求全生命周期管理

## 核心理念

> **计划是一等公民。** 复杂工作写成执行计划，附带进度和决策记录一起提交到仓库。
> — OpenAI Harness Engineering

ExecPlan 不只是"写个方案然后执行"，它覆盖一个需求**从模糊想法到代码合入**的完整生命周期。

## 生命周期全景

```
Phase 0   Phase 1    Phase 2     Phase 3      Phase 4        Phase 4.5    Phase 5      Phase 6      Phase 7
需求对齐 → 探索调研 → 方案撰写 → 方案Review → 开发与验证 → 独立审计 → 结果汇报 → 后续修复 → 代码提交
  ↑           ↑          ↑           │              ↑                        │           ↑
  └───────────┴──────────┴───────────┘              └────────────────────────┴───────────┘
           Review 可回退到任意前置阶段                       汇报/修复可循环多轮
```

不是每个任务都需要走完全部 8 个 Phase。按需裁剪：

| 任务类型 | 推荐 Phase |
|---------|-----------|
| 小型 bug 修复（<1h） | 不需要 ExecPlan |
| 中型功能（1-4h） | 0 → 2 → 3 → 4 → 7 |
| 大型功能/重构（1-3d） | 全部 Phase（含 4.5 审计） |
| 技术探索/POC | 0 → 1 → 2 → 3 → 5 |

## Agent 能力边界

ExecPlan 的编写必须考虑 Agent 的三个根本限制：

- **不知道先前上下文**：每次启动从零开始，ExecPlan 必须把所有前提、假设、决策理由全部写进去
- **无法从之前的 milestone 推断意图**：不能说"如前所述"，必须在每处重复声明
- **看不到外部文档**：不要指向外部链接，如果某个知识是必需的，用自己的话嵌入

## Phase 0: 需求对齐

在写任何方案之前，先确保理解用户真正想要什么。

**流程**：
1. **复述理解**：用自己的话重新描述用户的需求，让用户确认理解是否正确
2. **澄清歧义**：主动提出需要用户决策的关键问题（不超过 5 个），例如：
   - 这个功能面向谁？（终端用户 / 开发者 / Agent）
   - 优先级是什么？（先做 MVP 还是一步到位）
   - 有没有已知的约束？（性能要求 / 兼容性 / 依赖限制）
   - 已有哪些相关实现可以复用？
3. **确认边界**：明确列出"做什么"和"不做什么"
4. **记录到 ExecPlan**：对齐结果写入"目标与全局视角"和"上下文与方向"章节

**何时跳过**：用户已经给了非常明确的需求描述（含验收标准），可直接进入 Phase 1 或 2。

## Phase 1: 探索调研

用于存在重大技术未知数的任务。目标是产出**可运行的验证结果**和**明确的可行性结论**。

1. **读取仓库文档体系**：从 `AGENTS.md`（如有）开始，理解仓库结构和已有约束
2. 用里程碑组织 proof-of-concept 和原型
3. **读源码而非文档**：真正读目标库的实现代码，不只看 README
4. **深度调研，不浅尝辄止**：深入到足以判断可行性的程度
5. 将结论（行/不行/有条件可行）记录到 决策日志，附验证证据
6. 如结论支持继续，融入新知识更新后续规划

**何时跳过**：技术方案清晰、无重大未知数时可跳过。

## Phase 2: 方案撰写

创建完整的 ExecPlan 文档。

1. **记录 Git 基线**：`git rev-parse --abbrev-ref HEAD` + `git rev-parse HEAD`
2. **确认时区**：后续所有时间戳统一使用该时区
3. **按骨架模板填充**（见 [references/PLAN-TEMPLATE.md](references/PLAN-TEMPLATE.md)）
4. 深入研究源码，确保每个细节准确
5. 保存到计划目录（见下方"文件存放"）
6. 评估文档更新需求：是否涉及新模块/API/架构变更

**编写原则**：
- 完全自包含：一个零基础的新 Agent 仅凭 ExecPlan 就能完成全部实现
- 验收标准以用户可观察行为描述
- 文件路径使用仓库根目录相对路径
- 非日常术语首次出现时立即解释
- 散文为主，仅 进度追踪 章节用 checkbox

## Phase 3: 方案 Review

**主动暂停是硬性要求**。方案撰写完成后：

1. **停下来**，明确告知用户"计划已创建，请 review"
2. 向用户展示 **Review 摘要**（非全文，而是关键决策点的精简概览）：
   - 目标：一句话
   - 关键技术决策：列出需要用户拍板的 2-3 个点
   - 里程碑概览：数量 + 预估工作量
   - 风险点：已知的技术风险
   - 验收标准：核心指标
3. 等待用户反馈
4. **如果用户要求修改**：回到 Phase 2 修订，记录变更到 决策日志
5. **如果用户确认**：将 ExecPlan 从 `proposal/` 移到 `active/`，进入 Phase 4

**禁止在用户确认前擅自开始任何实现工作。**

## Phase 4: 开发与验证

按 ExecPlan 里程碑逐步实施。

1. 按里程碑顺序逐步推进，**不要停下来问用户"下一步做什么"**
2. **每完成一个里程碑，立即更新进度追踪**（与代码变更在同一轮完成）
3. 歧义时自主决策，记录到 决策日志
4. 发现意外时记录到 意外发现
5. 频繁提交代码（见 Phase 7 的提交策略）
6. 每个里程碑完成后运行对应的验收检查

**进度追踪实时更新是硬性要求**——它是中断恢复的唯一真实来源。

## Phase 4.5: 独立代码审计

所有功能里程碑完成后、结果汇报之前，触发独立代码审计。

详细流程见 [references/INDEPENDENT-AUDIT.md](references/INDEPENDENT-AUDIT.md)，核心要点：

1. **由不同于实现者的审查者盲审**（另一个 AI 模型、新会话的同模型、或人工）
2. **逐条验证审计发现**——审计工具的误判率很高，不经验证直接转发是不可接受的
3. **验证通过的真实 bug 在汇报前修复**，潜在改进记录为后续事项
4. 审计报告嵌入 ExecPlan 的 产物与备注

**可跳过的场景**：纯文档更新、<50 行的小修复。

## Phase 5: 结果汇报

所有里程碑完成且审计通过后，向用户提交结构化汇报：

```markdown
## 完成汇报

### 目标达成
- 原始目标：<一句话>
- 达成状态：✅ 完全达成 / ⚠️ 部分达成（说明缺口）/ ❌ 未达成（说明原因）

### 变更概览
- 新增文件：N 个
- 修改文件：N 个
- 删除文件：N 个
- 关键变更：<列出最重要的 3-5 个变更点>

### 验收结果
- 测试：<通过数/总数>，<覆盖率>
- 编译：<状态>
- Lint：<状态>

### 决策记录
<列出实施中做出的关键决策及理由>

### 已知风险/遗留
<如有未解决的问题或技术债，明确列出>

### 建议后续
<如需额外工作，列出建议的 follow-up 事项>
```

汇报后等待用户反馈。如果用户提出问题或要求修改，进入 Phase 6。

## Phase 6: 后续修复

处理汇报后的反馈、CI 失败、Review 意见等。

**触发条件**：
- 用户对汇报提出修改要求
- CI/测试在远端失败
- 代码 Review 收到反馈意见
- 发现回归问题

**流程**：
1. 在 ExecPlan 的 意外发现 或 决策日志 中记录新发现的问题
2. 评估影响范围：是局部修复还是需要回退设计决策
3. 如果是局部修复：直接修复 + 更新进度追踪
4. 如果需要改设计：回到 Phase 3 讨论，记录到 决策日志
5. 修复完成后重新运行验收检查
6. 更新 成果与复盘 章节

**循环退出条件**：用户确认所有反馈已处理 + 验收检查全部通过。

## Phase 7: 代码提交

将工作成果提交到版本控制。

**提交策略**：

| 策略 | 适用场景 |
|------|---------|
| 按里程碑提交 | 每个里程碑完成后立即 commit，消息引用里程碑编号 |
| 原子提交 | 所有里程碑完成后 squash 为一个语义完整的 commit |
| 混合 | 开发中按里程碑提交，合并前 squash |

**commit message 规范**：
- 格式跟随仓库已有的 commit 惯例（conventional commits / 自定义格式）
- 如果 ExecPlan 有编号，在 commit message 中引用
- body 中简述关键变更，不需要复述整个 ExecPlan

**PR 创建**（如需要）：
- 标题：简短描述核心变更
- 描述：引用 ExecPlan 路径 + 完成汇报的精简版
- 标签：按仓库惯例添加

**ExecPlan 归档**：
- PR 合并后（或用户确认完成后），将 ExecPlan 从 `active/` 移到 `completed/`
- ExecPlan 作为历史决策记录永久保留在仓库中

## 必需章节

每个 ExecPlan 必须包含以下章节（完整模板见 [references/PLAN-TEMPLATE.md](references/PLAN-TEMPLATE.md)）：

| 章节 | 职责 |
|------|------|
| 目标与全局视角 | 改完后用户能做什么之前做不了的事 |
| 进度追踪 | checkbox + 精确时间戳（唯一允许 checkbox 的章节） |
| 意外发现 | 观察 + 证据 |
| 决策日志 | 决策 + 理由 + 日期 |
| 成果与复盘 | 主要里程碑或完成时总结 |
| 上下文与方向 | 仓库当前状态，假设读者什么都不知道 |
| 工作计划 | 散文描述编辑和新增的顺序 |
| 具体步骤 | 精确命令 + 工作目录 + 预期输出 |
| 验证与验收 | 刚性量化指标，禁止"功能正常"等模糊描述 |
| 文档更新 | 列出需更新的文档，或声明"已评估，无需更新" |
| 幂等性与恢复 | 步骤可重复性和失败回滚路径 |
| 产物与备注 | 关键终端输出、diff、截图 |
| 接口与依赖 | 使用的库、类型签名 |

## 验收标准的刚性要求

**禁止模糊验收**。每个验收条件必须可自动化判定通过/失败：

- 测试通过率：`全部 PASS，0 skipped`
- 编译成功：`零错误`
- Lint 通过：`零告警`
- API 断言：`HTTP 200 + 预期 body`
- 覆盖率：`覆盖率脚本通过` 或 `新增代码覆盖率 ≥ N%`

**被 Skip 的测试视同失败**。发现 skip 时立即停止，向用户报告原因并请求决策。

## 里程碑规范

每个里程碑必须包含：
- **范围**：做什么
- **成果**：完成后存在什么之前不存在的
- **命令**：运行什么来验证
- **验收**：刚性量化指标

特殊里程碑类型：
- **原型里程碑**：标注"原型验证"，描述运行方法和"行/不行"的判断标准
- **文档更新里程碑**：所有功能里程碑之后，更新受影响的仓库文档
- **并行过渡**：大规模迁移中新旧路径共存，明确标注退役旧路径的里程碑

## 文件存放

ExecPlan 存放在仓库的计划目录中（常见为 `docs/plans/`、`docs/adr/`、`docs/exec-plans/`），按生命周期分阶段：

```
<plan_dir>/
├── proposal/   # 草案（待用户确认）
│   └── <YYYY-MM-DD>/
├── active/     # 进行中
│   └── <YYYY-MM-DD>/
└── completed/  # 已完成
    └── <YYYY-MM-DD>/
```

**首次使用时**：如果仓库没有计划目录，建议创建 `docs/plans/` 并在导航表中添加入口。

**Worktree 场景**：ExecPlan 存放在 worktree 的计划目录下，跟随代码变更一起提交。

## 修订纪律

1. **全面同步**：改了工作计划，就必须检查进度追踪、决策日志、具体步骤、验收标准是否都还准确
2. **底部追加修改说明**：`[YYYY-MM-DD HH:MM:SS±HH:MM] 修改说明：<描述>`
3. **保持自包含性**：修订后仍然满足"新手友好"标准
4. **记录为什么**：每个修订附带理由

## 配套技能衔接

| 场景 | 衔接技能 |
|------|---------|
| 开始前评估仓库 harness 成熟度 | `harness-analysis` |

| 发现架构级技术债需收敛 | `harness-debt-scan` |

## Gotchas

- **禁止跳过 Phase 3（Review）**。方案完成后必须暂停等确认
- **进度追踪不能攒批**。每完成一个 milestone 立即更新
- **时区不能混用**。所有时间戳统一一个时区
- **验证命令必须实际可运行**。集成测试不能标为"可独立运行"
- **不要创建带 Skip 的单测**。优先用 mock/stub
- **引用历史计划不替代自包含**。新计划必须完整嵌入必要上下文
- **结果汇报不是可选的**。Phase 5 是让用户知道发生了什么的关键环节
- **后续修复要记录**。Phase 6 的修复也要更新 ExecPlan，不能只改代码
- **文档更新是最后一个里程碑**。不能在中间态更新文档（内容可能还会变）
- **commit 策略要提前声明**。在 Phase 2 就决定好，不要到 Phase 7 才临时选择

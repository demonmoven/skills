## 一、一场激进的工程实验

过去五个月，OpenAI 内部有一支团队干了件很"极端"的事，他们从零开始做了一款内部产品，**一行代码都没有手动写过**。

这不是个玩具项目。产品已经被公司内部员工日常使用，也有一批外部 Alpha 测试用户。它跟任何正经产品一样，上线、部署、出 bug、打补丁，走完整的研发生命周期。唯一的区别在于：**所有代码**，业务逻辑、测试、CI 配置、文档、可观测性、内部工具，**全部由 Codex Agent 生成**。按他们自己的估算，效率大概是手写代码的 **10 倍**。

为什么要给自己施加这种约束？不是为了作秀，而是为了逼着自己回答一个根本问题：如果工程师的主要工作不再是"写代码"，而是**搭环境、说清楚要做什么、建好反馈闭环**让 Agent 去干活，那整件事会怎么变？

> **人来掌舵，Agent 来干活。**

这篇文章就是他们在这个过程中踩过的坑、发现的规律，以及如何把人类最稀缺的资源，**时间和注意力**，用在刀刃上。

## 二、一切从空仓库开始

2025 年 8 月底，团队往一个空仓库提交了第一笔代码。

仓库骨架，目录结构、CI 配置、代码格式规则、包管理、应用框架，都是用 Codex CLI（背后跑的是 GPT-5）照着一小套模板生成的。连那份指导 Agent 如何在仓库里干活的 `AGENTS.md`，本身也是 Codex 写的。

**没有任何人类预先写好的代码做垫底。** 这个仓库从第一天起就是 Agent 的作品。

五个月下来，成果如下：

| 指标 | 数据 |
|------|------|
| 代码总量 | ~**100 万行**（业务逻辑 + 基础设施 + 工具链 + 文档 + 内部工具） |
| 合并 PR 数 | ~**1,500 个** |
| 起步团队 | **3 人** |
| 当前团队 | **7 人** |
| 人均日产 PR | 平均 **3.5 个** |
| 内部用户 | 数百人，包括每天深度使用的核心用户 |

一个有意思的现象是，团队从 3 人扩到 7 人后，人均产出不降反**升**，更多的人意味着能覆盖更多的场景和工具建设，而 Agent 的执行能力随之被进一步释放。

整个过程中，**人类一行代码都没有直接写过**。这后来成了团队的铁律：**绝不手写代码**。

## 三、工程师在干什么？

不写代码不代表工程师闲着。恰恰相反，**一种全新的工程工作方式冒了出来，搭系统、建脚手架、找杠杆点**。

一开始进展比预期慢得多。不是 Codex 不行，而是**环境没准备好**，Agent 缺少干活需要的工具、抽象层和内部结构。团队很快意识到，他们最核心的工作其实是：**让 Agent 能干得动活**。

落到实操层面就是：深度优先地推进，把大目标拆成小模块（设计、编码、Review、测试等），让 Agent 一块一块搭起来，再用这些模块去解锁更大的任务。遇到失败时，答案几乎从来不是"让 Agent 再试一次"。既然活都得让 Codex 来干，工程师在卡壳时想的永远是同一个问题：

> **"差了什么能力？怎么让 Agent 既看得懂又执行得了？"**

日常交互几乎全靠 **Prompt**：工程师说清楚要做什么，启动 Agent，让它去开 PR。为了把一个 PR 推到可合并的状态，他们会让 Codex 先自己 Review 一遍、再请其他 Agent Review（本地和云端都有）、回应反馈、来回迭代，直到所有 Agent 审查者都满意，说白了就是一个 [Ralph Wiggum Loop](https://ghuntley.com/loop/)。Codex 直接调 `gh` CLI、本地脚本、仓库里预埋的 skills 来获取上下文，不需要人手动复制粘贴。

**人类可以 Review PR，但不是必须的。** 到后来，几乎全部 Review 都由 Agent 之间完成。

## 四、让 Agent “看得见”应用

代码产量上去之后，瓶颈很快转移到了**人类的 QA 能力**。既然人的时间和注意力才是硬约束，团队就想办法让 Agent 自己能“看见”更多东西，应用 UI、日志、监控指标，统统对 Codex 开放。

举几个例子：

- **每个 git worktree 独立启动一个应用实例**，这样 Codex 每做一个改动都能拉起一份独立的应用来测。
- **把 Chrome DevTools Protocol 接入 Agent 运行时**，配套做了 DOM 快照、截图、页面导航的技能模块。Codex 因此可以自己复现 bug、验证修复、直接理解 UI 上发生了什么。

![Codex 通过 Chrome DevTools 验证自己的工作](images/fig1_codex_chrome_devtools.png)
*Codex 驱动应用的流程：选一个目标 → 对触发 UI 路径前后做快照 → 通过 Chrome DevTools 观测运行时事件 → 应用修复并重启 → 循环验证直到问题消失。*

**可观测性**也做了同样的事。日志、指标、链路追踪通过一个临时的本地可观测性栈暴露给 Codex，每个 worktree 一套，用完即销毁。Agent 可以用 **LogQL** 查日志、用 **PromQL** 查指标。有了这些能力，类似“保证启动时间不超过 800ms”、“这四条关键用户路径里所有 span 都不能超过 2 秒”这种 Prompt 就变得可执行了。

![本地可观测性栈架构](images/fig2_observability_stack.svg)
*应用将日志、指标、追踪数据发给 Vector，Vector 分发到 Victoria Logs / Metrics / Traces，通过 LogQL / PromQL / TraceQL 查询。Codex 据此做诊断和推理，修代码、重启应用、跑工作负载、验证 UI，形成闭环。*

团队经常看到 Codex 单次运行在一个任务上连续干**六个多小时**，而且往往是在人类睡觉的时候。

## 五、仓库就是唯一“知识库”

如何管理上下文，是让 Agent 搞定大型复杂任务的头号难题。团队最早学到的教训只有一句话：

> **给 Codex 一张地图，别给它一本千页大辞典。**

他们试过把所有规则堆进一个大 [`AGENTS.md`](https://agents.md/)，毫不意外地翻了车：

- **上下文容量有限。** 一个巨大的指令文件会把任务本身、代码和相关文档挤出去，Agent 要么漏掉关键约束，要么跑偏去优化错误的东西。
- **什么都“重要”等于什么都不重要。** Agent 最后只是在局部做模式匹配，而不是有方向感地去导航。
- **文件秒速过时。** 一个大手册很快就变成过时规则的坟场。Agent 分不清哪些还有效，人类也懒得更新，它就这么悄悄变成了一颗定时炸弹。
- **没法自动校验。** 单个巨型文件既不好查覆盖率，也不好检查新鲜度和交叉引用，漂移在所难免。

所以他们换了玩法，**把 `AGENTS.md` 当目录用，而不是当百科全书用。**

仓库的知识体系住在一个结构化的 `docs/` 目录里，作为“唯一真相源”。`AGENTS.md` 只有大约 100 行，被注入上下文后充当地图角色，指向各处详细文档：

```
AGENTS.md
ARCHITECTURE.md
docs/
├── design-docs/
│   ├── index.md
│   ├── core-beliefs.md
│   └── ...
├── exec-plans/
│   ├── active/
│   ├── completed/
│   └── tech-debt-tracker.md
├── generated/
│   └── db-schema.md
├── product-specs/
│   ├── index.md
│   ├── new-user-onboarding.md
│   └── ...
├── references/
│   ├── design-system-reference-llms.txt
│   ├── nixpacks-llms.txt
│   ├── uv-llms.txt
│   └── ...
├── DESIGN.md
├── FRONTEND.md
├── PLANS.md
├── PRODUCT_SENSE.md
├── QUALITY_SCORE.md
├── RELIABILITY.md
└── SECURITY.md
```

设计文档有索引、有验证状态、有一组定义“Agent 优先”工作原则的核心理念。[架构文档](https://matklad.github.io/2021/02/06/ARCHITECTURE.md.html)画出了领域和包分层的顶层地图。质量文档给每个产品领域和架构层打分，持续追踪短板。

**计划（Plan）在这里是一等公民。** 小改动用临时轻量计划搞定，复杂工作则写成[执行计划](https://cookbook.openai.com/articles/codex_exec_plans)，附带进度和决策记录一起提交到仓库。进行中的计划、已完成的计划、已知的技术债务全部放在一起做版本管理，Agent 不需要去外部找任何上下文。

这种模式叫做 **Progressive Disclosure（渐进式披露）**：Agent 从一个小而稳定的入口出发，知道往哪深入找信息，而不是一开头就被灌一肚子东西。

这套机制用自动化手段保障执行力：专门的 linter 和 CI 任务负责验证知识库是否最新、交叉引用是否正确、结构是否规范。还有一个定期跑的“文档园丁” Agent 会自动扫描那些过时的、跟实际代码对不上的文档，然后自己提修复 PR。

## 六、Agent 读不到的信息，等于不存在

代码库不断膨胀的同时，Codex 做设计决策需要的背景知识也在不断变化。

因为仓库完全由 Agent 生成，所以它的首要优化目标是 **Codex 的可读性**，而不是人类工程师的阅读习惯。这跟你想让新来的同事尽快上手是一个道理，只不过“新同事”换成了 AI。

站在 Agent 的角度看事情就很简单：**运行时读不到的东西，就跟不存在一样。** Google Docs 里的讨论、Slack 里的对话、某个同事脑子里的想法，这些对 Agent 来说全都不可见。它能看到的只有仓库里版本化的东西：代码、Markdown、Schema、执行计划。

![Agent 知识的边界](images/fig3_agent_knowledge_limits.png)
*Codex 的知识被限定在它的上下文气泡里。Google Docs、Slack 消息、人类的隐性经验，它全都看不到。要让这些知识生效，唯一的办法就是以 Markdown 形式写进仓库。*

团队很快发现，他们得**持续不断地往仓库里灌入更多上下文**。那次 Slack 上讨论了半天、最终定下来的某个架构决策？如果不写进仓库，对 Agent 来说就好像从来没发生过，这跟三个月后新入职的员工对此一无所知，本质上是一回事。

给 Codex 更多上下文不是说随手丢一堆临时指令进去。关键在于**把正确的信息组织好、暴露出来**，让 Agent 能基于这些信息做推理。就像你给新队友讲产品逻辑、工程规范、甚至团队的 emoji 梗一样，Agent 知道得越多、产出就越对路。

这个思维框架帮团队理清了很多技术选型上的取舍：

- **优先选能在仓库里被完全理解的依赖和抽象。** 所谓“无聊技术”（boring technology）反而是首选，可组合、API 稳定、在训练集里出现得多，Agent 建模起来最顺手。
- **有时候自己造轮子比引三方库更划算。** 比如他们没引 `p-limit` 那类通用并发控制库，而是让 Agent 写了一个自研版本，深度集成 OpenTelemetry、100% 测试覆盖、行为完全可控。
- 把系统的更多部分拉到 Agent 能检阅、验证和修改的形态下，不光 Codex 受益，其他在同一个仓库干活的 Agent（比如 [Aardvark](https://openai.com/index/introducing-aardvark/)）也能借力。

## 七、用约束换速度：架构与“品味”

光靠文档管不住一个全 Agent 生成的代码库。团队的策略是：**守住不变量（invariants），不去管实现细节**。这样 Agent 能跑得快，又不会把地基拆了。

比如，他们规定 Codex 必须[在边界处做数据解析](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/)（parse, don't validate），但不管你具体怎么解析，模型自己选了 Zod，但这不是团队硬性要求的。

Agent 在[边界明确、结构可预测](https://bits.logic.inc/p/ai-is-forcing-us-to-write-good-code)的环境里最出活，所以团队从一开始就用了一个**很刚的架构模型**。每个业务领域拆成固定的层，层与层之间的依赖方向被严格管控，只允许特定的边。这些规则通过自定义 linter（当然也是 Codex 写的）和结构测试来机械化执行。

![分层领域架构](images/fig4_layered_architecture.png)
*在每个业务领域（比如 App Settings）内部，代码只能沿着固定方向依赖：Types → Config → Repo → Service → Runtime → UI。认证、连接器、遥测、Feature Flag 等横切关注点统一通过 Providers 接口进入。其余路径一律禁止，自动化拦截。*

**这种架构通常是百人团队的专利。但在 Agent 驱动的开发模式下，它是一个从第一天就得有的前提条件**，正是这些约束才让高速产出不至于变成灾难。

在具体执行层面，团队还维护着一小套“品味规范”：结构化日志、Schema 和类型的命名规则、文件大小限制、平台可靠性要求等等，全用自定义 linter 强制检查。linter 的报错信息也是精心设计的，**报错即指导**，Agent 看到错误就知道怎么改。

> 在人工为主的工作流里，这些规则可能显得事儿多。但交给 Agent 后，它们变成了乘数，写一条规则，全代码库同时生效。

与此同时，团队也很清楚**哪些地方需要管、哪些地方不需要管**。这和管理大型平台工程组织一个道理：核心边界集中管控，边界以内充分放权。依赖方向、正确性、可复现性你得死守，但在这些框框里面，Agent 怎么写随它。

产出的代码风格不一定合人类的口味，**但这无所谓**。只要结果正确、好维护、下次 Agent 来了还看得懂，就算达标。

人类的“品味”通过持续反馈注入系统：Review 评论、重构 PR、用户实际遇到的 bug，要么变成文档更新，要么直接编进工具链。文档兜不住的时候，就把规则升级成代码去强制执行。

## 八、产出太快，合并策略得跟着变

Codex 吞吐冲上去之后，很多传统工程规范反而**拖后腿**了。

这个仓库的合并门禁做得很轻。PR 生命周期很短。Flaky Test 通常靠后续的 PR 来修，不会无限卡在那里。在一个 Agent 产出速度远超人类注意力的系统里，**纠错很便宜，等待很昂贵**。

这种做法放在传统低频交付的团队里肯定不合适。但在这里，它往往是对的。

---

## 九、“Agent 生成”具体包括什么？

团队说“代码全是 Agent 写的”，这个“全”是字面意思，仓库里**什么都是**。

Agent 产出的东西包括：

- ✅ 产品代码和测试
- ✅ CI 配置和发布工具
- ✅ 内部开发者工具
- ✅ 文档和设计历史
- ✅ 评测 Harness
- ✅ Review 评论和回复
- ✅ 仓库自身的管理脚本
- ✅ 生产环境 Dashboard 配置文件

**人类始终在环里，只是工作在更高的抽象层上。** 排优先级、把用户反馈翻译成验收标准、验证最终结果。Agent 搞不定的时候，团队不是自己去写代码，而是去想“差了什么”，工具？约束？文档？然后把答案喂回仓库，**让 Codex 自己来写修复**。

Agent 直接用的就是标准开发工具链：拉 Review 反馈、行内回复、push 代码，很多时候直接自己 squash and merge。

## 十、自治水平在不断升级

随着测试、验证、Review、反馈处理、故障恢复等环节一个个被编码进系统，仓库最近跨过了一个标志性的门槛：**单个 Prompt 就能让 Codex 端到端交付一个完整功能。**

具体来说，给 Agent 一句话，它能自己跑完这整套流程：

1. 检查代码库当前状态
2. 复现用户上报的 bug
3. 录一段视频展示故障现象
4. 写出修复代码
5. 驱动应用验证修复
6. 再录一段视频展示修复效果
7. 开 Pull Request
8. 回应 Agent 和人类的 Review 意见
9. 检测并修复构建失败
10. 只有需要人来拍板的时候才上报
11. 合并代码

但要泼个冷水：这种能力**强依赖于该仓库的特定架构和工具体系**。换个仓库没做同等级别的基建投入，别指望直接复制，至少现在还不行。

## 十一、对抗熵增：代码的“垃圾回收”

**全自治也有全自治的麻烦。** Codex 会复制仓库里已有的模式，包括那些不够好的模式。时间一长，代码就会悄悄散架。

早期团队靠人工来收拾。每周五拿出**一整天**（工作时间的 20%）来清理 AI 产出的“脏活”（AI slop）。可想而知，这事没法持续。

后来他们想通了，转而把团队称之为**“黄金原则”**的东西直接编进仓库，再配合周期性的自动清理流程。这些原则是一组有态度的、可机械化执行的规则，目的是维持代码库对 Agent 的可读性和一致性。比如：

1. **优先用共享工具包，别每次手搓 helper**，把不变量收拢在一处
2. **别搞 YOLO 式数据探测**，要么在边界做校验，要么用类型化的 SDK，杜绝 Agent 在猜的数据结构上瞎建东西

团队设了固定节奏的后台 Codex 任务，专门扫描违规、更新质量评分、开重构 PR。这些 PR 大多数一分钟内就能看完，自动合并。

> **这就是代码的“垃圾回收”。** 技术债就像高利贷，每天还一点小钱远比攒到还不起了再爆发好得多。人类的品味只需要表达一次，之后工具链会在每一行代码上持续执行。坏模式当天就能发现和消灭，而不是在代码里静悄悄蔓延几周。

## 十二、还没想清楚的事

到目前为止，这套打法在 OpenAI 内部的落地和推广中跑得不错。为真实用户做真实产品，帮他们把投入校准在实际需求上，也逼着他们往长期可维护的方向走。

但仍然有几个大问号悬在那里：

- **一个全 Agent 生成的系统，架构一致性放到年的时间尺度下会怎样？**
- **人类的判断力在哪个环节杠杆最大？怎么把这种判断力编码下来让它生利息？**
- **模型能力还在涨，整套系统会往哪个方向演变？**

有一件事已经很清楚了：**做软件还是需要纪律的，只是纪律的着力点变了，从代码本身转到了脚手架上。** 保持代码库一致性的工具链、抽象机制、反馈闭环，正变得比代码写得好不好更重要。

> **现在最难的事情不是写代码，而是设计出合适的环境、反馈循环和控制系统**，让 Agent 能够大规模地构建和维护复杂可靠的软件。

Agent 正在接管软件生命周期中越来越大的份额。OpenAI 希望分享这些早期踩坑的经验，帮更多人想清楚精力应该**花在哪儿**，从而真正腾出手来，专注于构建产品本身。

## 十三、Martin Fowler 的冷思考：Harness 会变成什么？

OpenAI 这篇文章发出后，Martin Fowler 在他的[博客](https://martinfowler.com/articles/exploring-gen-ai/harness-engineering.html)上写了一篇很有分量的评论。他把 OpenAI 团队的做法拆解成三类 Harness 组件，并抛出了几个尖锐的问题。

### Harness 的三根支柱

Martin Fowler 把 OpenAI 描述的 Harness 拆成了三个方面：

| 支柱 | 内容 |
|------|------|
| **上下文工程** | 代码库内持续维护的知识体系，加上 Agent 对动态上下文（可观测性数据、浏览器导航等）的访问能力 |
| **架构约束** | 不只靠 LLM Agent 来监督，还有确定性的自定义 linter 和结构测试 |
| **“垃圾回收”** | 周期性运行的 Agent，扫描文档不一致和架构违规，对抗熵增和衰变 |

他特别注意到这套体系的**迭代性**：“当 Agent 遇到困难时，把它当作信号：找出缺了什么，工具、护栏、文档，然后反馈给仓库。”这不是一次性建好的东西，而是一个不断进化的系统。

### Harness 会成为未来的“服务模板”吗？

Martin Fowler 提出了一个前瞻性的想法：大多数组织其实只有两三套主力技术栈，不是每个应用都是独一无二的雪花。他想象了一个未来，**团队可以从一组预置的 Harness 中挑选，作为常见应用拓扑的起步模板**。

这类似于今天的 Service Template（黄金路径模板），帮团队快速新建服务。未来的 Harness 可能包含：自定义 linter、结构测试、基础的上下文知识文档、以及可观测性接入，团队拿来就能开工，再根据自己的业务逐渐定制。

但他也看到了潜在问题：跟 Service Template 一样，团队在使用过程中会积累经验并贡献回来，但其他团队往往难以同步这些更新。**Harness 会不会面临同样的分叉和同步难题？**

### 要获得 AI 的自治，运行时就得受约束

早期的 AI 编码炒作假设 LLM 会给我们无限的灵活性，任何语言、任何模式，LLM 都能搞定。但 Martin Fowler 指出，OpenAI 的实践严重挑战了这个假设：

> **要在 AI 生成的代码上获得信任和可靠性，就必须约束解空间**，特定的架构模式、强制的边界、标准化的结构。这意味着要放弃一些“什么都能生成”的灵活性，换来充满技术细节的规则和 Harness。

换句话说，**更多的 AI 自治 = 更严格的运行时约束**。这是一个反直觉但越来越被验证的等式。

### 技术栈会趋同吗？

Martin Fowler 还推测，当编码越来越不是“敲键盘”而是“引导生成”时，**AI 可能推动我们走向更少的技术栈选择**。原因很直接：

- 对人类好用的框架和 SDK，对 AI 同样好用
- 但开发者个人的口味偏好会变得不那么重要
- 接口上的小低效和小怪癖不再那么烦人，因为你不直接打交道了
- 团队可能会**优先选有现成好 Harness 的技术栈**，“AI 友好度”成为选型的新维度

这个逻辑不只适用于技术栈，也适用于代码库结构和拓扑，那些更容易用 Harness 管控的结构会胜出。

### 两个世界：AI 原生 vs AI 改造

如果我们真的掌握了好的 Harness 技术，能把 AI 自治拨到 9 档并对结果有信心，**哪些技术能用在既有应用上，哪些只对从零开始构建的 AI 原生应用有效？**

对老代码库来说，改造 Harness 的投入产出比是个大问题。AI 能加速改造过程，但那些非标准化、熵值极高的老系统，可能根本不值得改。Martin Fowler 打了个比方：这就像**在一个从来没跑过静态分析的代码库上第一次启用检查工具，然后被告警淹死**。

### 缺失的一块：功能性验证

Martin Fowler 指出 OpenAI 原文中有一个明显的缺口：所有描述的措施都聚焦于**长期的内部质量和可维护性**，但**没有谈功能正确性和行为验证**。Harness 如何确保 Agent 生成的代码不仅结构优雅、而且功能正确？这个问题留了一个待答的空白。

### 你今天的 Harness 是什么？

Martin Fowler 的结尾很实在：这个团队在 Harness 上投入了五个月，不是你能跳进去就立刻见效的事。但值得现在就开始反思：

- 你有 pre-commit hook 吗？里面跑的是什么？
- 你有没有想过自定义 linter？
- 你想对代码库施加什么架构约束？
- 你试过 ArchUnit 这类结构测试框架吗？

> 他们做的事情显然比“维护一堆 Markdown 规则文件”要复杂得多。Harness 的确定性部分需要大量工程投入。上下文工程不只是写知识库文档，更涉及重大的设计工作，**代码设计本身就是上下文的核心部分**。

## 总结：关键要点速览

| 要点 | 说明 |
|------|------|
| 零手写代码约束 | 倒逼团队构建让 Agent 高效工作的基础设施 |
| 工程师角色转变 | 从写代码的人变成搭环境、说清意图、建反馈循环的人 |
| 渐进式披露 | `AGENTS.md` 当目录用，知识按需层层展开 |
| 仓库即唯一真相源 | Agent 看不到的信息等于不存在，所有知识必须版本化入库 |
| Agent 可读性优先 | 代码库先为 Agent 优化，人的阅读体验次之 |
| 架构约束是加速器 | 刚性分层 + 自动化执行 = 高速产出不翻车 |
| 修比等便宜 | 高产出下纠错成本低，传统 merge gate 收益反转 |
| 垃圾回收式维护 | 持续小步清理技术债，品味编进工具链自动执行 |
| 自治水平在升级 | 从辅助写码到端到端交付，能力持续进化 |

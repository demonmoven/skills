# Harness 分析技能

使用这个 skill 时，你要回答的核心问题是：这个代码库是否为人和智能体提供了一个安全、可验证、低漂移的工程环境？

这不是通用代码评审 skill。它关注的不是单个实现好不好，而是围绕代码的工程系统是否足够成熟。

激活此 skill 后，**必须先完整阅读**以下参考文章，再开始正式分析：

- [references/openai-harness-engineering.md](references/openai-harness-engineering.md)

这一步不是可选项。该参考文章定义了本 skill 的分析视角和判断标准。

## 适用场景

当用户提出以下需求时，使用这个 skill：

- 分析某个仓库的 harness 现状
- 分析某个模块的 harness 成熟度
- 从 Harness Engineering 角度评估工程环境
- 围绕文档、观测、测试、lint、hook 做成熟度评分
- 输出 harness 差距清单
- 输出面向 Agent-first 工程的改进路线图

## 配套 Action 技能

分析完成后，差距清单中的建议动作可衔接以下技能直接执行：

| 差距维度 | 对应 Action 技能 | 职责 |
|---------|----------------|------|
| 文档体系（dim 2）评分 ≤ 3 | `harness-doc-init` | 建立分层 AGENTS.md + ARCHITECTURE.md + docs/ 索引 |
| 观测体系（dim 3）评分 ≤ 3 | `harness-obs-init` | 建立本地观测栈（结构化日志 + OTel trace + 基础设施） |
| Hook 护栏（dim 6）评分 ≤ 3 | `harness-hook-init` | 交互式生成 pre-commit 配置并安装验证 |
| 文档明显过时/死链 | `harness-doc-gardener` | 巡检文档新鲜度，修复失效路径和过时描述 |
| 存在结构性重复/模型分裂 | `harness-debt-scan` | 架构级技术债检测，产出收敛方案 |
| 复杂任务需要分阶段规划 | `harness-exec-plan` | 创建自包含的执行计划，支持中断恢复 |
| 知识散落在飞书文档中 | `harness-feishu-sync` | 读取飞书文档并转为 Markdown 写入仓库 |
| 服务无法本地运行/调试 | `harness-local-twin` | 分析内场服务依赖，给出本地化改造建议 |

在路线图中，应主动提示用户可调用对应技能：
- phase 0（建立入口）→ `harness-doc-init`（+ `harness-feishu-sync` 迁入飞书上的已有文档）
- phase 1（统一验证 / 本地可运行）→ `harness-local-twin`（分析依赖并规划本地化）
- phase 2（补本地护栏）→ `harness-hook-init`
- phase 3（强化真相层）→ `harness-doc-gardener`（巡检已有文档质量）
- phase 4（补观测闭环）→ `harness-obs-init`（建立本地观测栈）
- phase 5（治理漂移与熵增）→ `harness-debt-scan` + `harness-doc-gardener`（周期性运行）

## 默认分析维度

除非用户另行指定框架，否则默认分析以下六个维度：

1. 仓库或模块基本情况
2. 文档体系
3. 观测体系
4. 测试体系
5. lint 与静态检查体系
6. hook 与提交前护栏体系

如果是模块级分析，第 1 项应解释为“模块基本情况”。

## 核心原则

- 所有判断必须基于仓库证据。
- 在下结论前，先建立结构认知。
- 不要把零散工具误判成完整 harness。
- 每个维度都要区分优势、缺口和 Harness 视角评估。
- 结论要可执行，不要停留在抽象评价。
- 当“传统工程成熟度”和“Agent-first harness 成熟度”不一致时，要明确区分。

## 必须遵循的流程

### 0. 先读参考文章

在开始任何仓库或模块分析前，**必须先完整阅读**：

- [references/openai-harness-engineering.md](references/openai-harness-engineering.md)

要求：

- 不要跳过这一步
- 不要只看标题或摘要
- 不要在未读参考文章前直接开始打分或下结论
- 先用 `3-5` 条要点提炼出参考文章里的 harness 框架，再进入仓库分析

阅读目标：

- 明确 `Harness Engineering` 不是单纯的 Prompt Engineering
- 明确分析重点是“环境、约束、反馈闭环、知识沉淀、熵增治理”
- 明确参考文章只是分析视角来源，不能替代目标仓库证据

### 1. 先明确分析范围

先判断用户要的是：

- 仓库级分析
- 模块级分析
- 子系统级分析
- 多个范围的对比分析

不要混淆范围。一个仓库整体很弱，不代表某个子树也弱。

如果是模块级分析，必须额外做一件事：

- 先快速建立仓库级基线，再判断该模块是强于、弱于，还是仅仅复用了仓库级能力

### 2. 先读结构入口文件，再做判断

从所选范围最关键的入口文件开始读。

常见入口包括：

- `package.json`
- `pyproject.toml`、`go.mod`、`Cargo.toml`、`rush.json`、`pnpm-workspace.yaml`、`WORKSPACE` 等工作区或构建清单
- `README.md`
- `AGENTS.md`
- `CONTRIBUTING.md`
- `Makefile`、`Taskfile.yml`、`justfile` 等统一任务入口
- `specs/`、`adr/`、`rfcs/`、`docs/`、`design-docs/` 等规格或设计目录
- CI workflow 文件，如 `.github/workflows/`、GitLab CI、Buildkite、Jenkins 配置
- 根级或模块级验证脚本

先建立对以下内容的具体认知：

- 使用了哪些语言和包管理器
- 项目边界怎么划分
- build / test / typecheck 的入口在哪里
- 工程知识沉淀在哪些地方
- 质量门禁是如何执行的

### 3. 按维度收集证据

从文件、脚本、配置、文档中收集具体证据。

强证据包括：

- 实际存在且被使用的脚本
- 确实接入 CI 或本地流程的配置
- 指向真实路径、可执行命令的文档
- 代表当前真实行为的 spec
- 版本化且实际生效的 hook

弱证据包括：

- 占位模板
- 空 README
- 失效的绝对路径
- 从未被调用的脚本
- 存在但没有接入任何流程的质量工具

### 4. 按维度写分析

每个维度都应明确写出：

- 当前判断
- 优势
- 问题
- 它对 Harness Engineering 的意义

每个维度在下结论前，至少要有 `2` 个具体证据，优先使用：

- 文件路径
- 配置项
- 脚本入口
- CI 任务
- hook 文件

如果证据不足，不要直接下成熟度结论。

### 5. 先完成证据分析，再做评分

如果用户要求评分，使用 `1-5` 分：

- `1`：基本缺失
- `2`：有零散能力，但没有系统化
- `3`：已有部分体系，能覆盖部分工作流
- `4`：体系较强，能稳定支撑大部分开发活动
- `5`：范围内统一、自动化、可持续、Agent 友好

### 6. 最后一定要落到行动建议

一个好的 harness 报告不能停留在诊断。结尾至少要给出：

- 关键差距
- 优先级
- 最小高杠杆动作
- 分阶段路线图（如果有必要）

## 逐维检查清单

### 1. 仓库或模块基本情况

检查：

- 仓库或模块结构
- workspace 清单文件
- 语言和技术栈混合情况
- build、dev、typecheck、test 脚本
- 子项目数量和分布
- 是否存在清晰的入口让 Agent 快速上手

重点追问：

- Agent 能不能快速建立正确心智模型？
- 有没有一个明显的起点？
- 边界是清晰显式的，还是靠经验隐含的？

### 2. 文档体系

检查：

- `README.md`
- `AGENTS.md`
- `CONTRIBUTING.md`
- `docs/`
- `specs/` / `adr/` / `rfcs/`
- `specs/`
- `adr/`
- 模块局部 spec
- 贴近代码的设计文档

重点关注：

- 是否有仓库地图或模块地图
- 是只有 proposal，还是有当前真相层
- 是否存在过期路径、过期命令、占位内容
- 文档是否真的能帮助 Agent 知道“去哪改、怎么验”

强信号：

- 存在 current-state spec
- 文档和代码路径绑定清晰
- 复杂子系统附近有局部说明文档或局部指令

弱信号：

- 只有 proposal，没有当前真相层
- 根文档只是跳转提示
- 文档很多，但已经明显过期

### 3. 观测体系

检查：

- 日志抽象层
- telemetry / analytics 包装层
- 错误归一化机制
- 日志目录或排障入口
- 运行时调试工具
- 调试说明或 runbook

重点追问：

- Agent 能不能不靠猜测就观察运行态？
- 稳定信号和调试噪音有没有分离？
- 观测能力是服务开发闭环，还是只服务产品埋点？

特别注意：

- 大量 `console.log`
- 有 telemetry 代码但没有操作文档
- 运行态反馈存在于代码里，但没有进入真实工作流

### 4. 测试体系

检查：

- test 脚本
- 测试框架配置
- 测试文件分布
- CI 是否真的执行测试
- 仓库级和模块级验证入口
- 测试策略是否被文档化

重点追问：

- 改完代码后，是否容易知道该跑什么？
- 测试是 unit、integration、e2e 还是混合？
- changed-scope 验证链是否清晰？

强信号：

- 存在明确验证矩阵
- CI 有稳定测试门禁
- 改动类型到测试命令的映射清晰

弱信号：

- 测试存在但没有接入 CI
- 多种测试框架并存但没有指导文档
- 没有统一验证入口

### 5. Lint 与静态检查体系

检查：

- lint 脚本
- ESLint、Stylelint、OXlint、Biome、Clippy、Ruff、Mypy、golangci-lint 等工具
- 共享配置包
- 分层、依赖边界等结构性检查
- 静态检查是否进入 CI 或 hook

重点追问：

- 这些只是风格工具，还是工程护栏？
- 是否编码了结构性约束？
- 是否容易发现、容易执行？

强信号：

- 存在清晰 lint 入口
- 有架构约束类规则
- 自动在 CI 或 hook 中执行

弱信号：

- 有配置但没有 lint 命令
- 大量规则只是 advisory warning
- 检查链碎片化，未进入活跃流程

### 6. Hook 与提交前护栏体系

检查：

- `.husky/`
- `.pre-commit-config.yaml`
- `lint-staged`
- `prepare`
- `lefthook`
- `simple-git-hooks`、工作区生命周期 hooks 或等价机制
- `pre-commit` / `pre-push`

重点追问：

- 在 CI 之前，本地会拦住什么问题？
- 常见低级错误是否能在提交前暴露？
- hook 策略在目标范围内是否一致？

强信号：

- hook 版本化管理
- changed-file 校验存在
- 本地反馈链清晰

弱信号：

- 完全没有 hook
- 只有零散子项目 hook
- 质量门禁几乎全部后移到 CI

## 推荐输出结构

除非用户另有要求，默认按以下结构输出：

- 使用 Markdown 输出。
- 标题默认带编号，使用稳定的层级编号格式，例如 `## 1.`、`### 1.1`。

### 1. 结论摘要

- 一段总结性结论
- 一句对当前 harness 状态的定义
- 一个分维度总览表，至少包含 `维度 | 判断`

### 2. 分析范围

- 明确本次分析覆盖的是仓库级、模块级还是子系统级
- 列出默认分析维度
- 简要说明本次使用的 Harness 视角判断标准

### 3. 分维度分析

每个维度都包含：

- 判断
- 证据
- 优势
- 问题
- Harness 视角评估

### 4. 综合评估

包含：

- 当前成熟度画像
- 当前最强的部分
- 当前最弱的部分
- 与目标状态的主要差距

### 5. 成熟度评分

包含：

- 评分说明
- 分维度评分表
- 简要评分理由
- 必要时给出总体成熟度分数

### 6. 差距清单

按优先级分组：

- 高优先级
- 中优先级
- 低优先级

详细报告中，优先使用表格呈现差距，至少包含：

- 差距
- 当前表现
- 风险
- 建议动作
- 可用技能（如有配套 action 技能可直接执行，注明技能名）

### 7. 改进路线图

建议优先按阶段推进，例如：

- phase 0：建立入口 → `harness-doc-init`
- phase 1：统一验证
- phase 2：补本地护栏 → `harness-hook-init`
- phase 3：强化真相层与结构约束 → `harness-doc-gardener`（巡检并修复）
- phase 4：补观测闭环 → `harness-obs-init`（建立本地观测栈）
- phase 5：治理漂移与熵增 → `harness-debt-scan` + `harness-doc-gardener`（周期性）

跨阶段改动较大时，建议用 `harness-exec-plan` 为改进路线图中的单个 phase 创建详细执行计划。

当报告足够详细时，每个 phase 建议包含：

- 目标
- 建议动作（如有对应 action 技能，注明技能名）
- 建议产出
- 成功标志

### 8. 建议优先级总表

- 提炼最值得立刻做的 `3-5` 件事
- 说明这些动作为什么是高杠杆、低侵入或适合优先落地

### 9. 可选附录

- 当某个子树明显强于或弱于仓库根时，可追加模块级附录分析
- 模块级附录必须显式说明它与仓库级基线的关系

## 报告规则

- 尽量引用文件作为证据。
- 用具体证据替代泛泛评价。
- 不要因为看到少量工具就过度拔高成熟度。
- 如果某个子树明显强于仓库根，要明确说出来。
- 如果是模块级分析，必须说明它与仓库级基线的关系。
- 如果文档很丰富但明显陈旧，也要直说。
- 如果观测能力存在但噪音很大，就明确说“信噪比低”，而不是简单说“没有观测”。
- 仓库级分析默认应包含一个“维度总览表”，帮助读者先建立整体判断。
- 报告较长时，默认补一个“综合评估”章节，把分维度结论收束为整体画像。
- 差距清单在详细报告中默认优先使用表格，而不是纯 bullet list。
- 路线图在详细报告中默认补齐“目标 / 建议动作 / 建议产出 / 成功标志”。
- 优势列表中的每一项默认使用 `✅` 开头。
- 问题、缺口、风险或待改进项列表中的每一项默认使用 `❌` 开头。
- 警示、残余风险、开放问题、假设或需要用户特别注意的事项默认使用 `⚠️` 开头。
- `phase` 阶段标题及其阶段内任务列表默认不使用 emoji，保持中性路线图表达。

## 需要主动标记的反模式

发现以下情况时，应明确点名：

- 根级说明文件为空或只是模板
- 文档仍包含旧仓名或失效绝对路径
- 归档后的 spec 仍保留 `TBD`
- 活跃代码路径中存在大量调试 `console.log`
- 附近明明有共享 lint 配置，但目标本身没有 lint 命令
- hook 只存在于零散子项目中
- CI 只 build 某个目标，却不显式执行该目标自己的验证

## 交付标准

一个高质量结果应当帮助用户回答以下问题：

1. 这个目标当前到底属于哪种 harness 状态？
2. 它最强的地方在哪里？
3. 它最弱的地方在哪里？
4. 要实现稳定的 Agent 操作，还缺什么？
5. 哪些是最小但高杠杆的下一步动作？
6. 哪些差距可以通过配套技能（`harness-doc-init` / `harness-obs-init` / `harness-hook-init` / `harness-feishu-sync`）直接填补？

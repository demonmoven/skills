# 规格审阅（交互式）

由主 Agent 直接执行，与用户交互式校审修订功能规格说明书。

## 参数

- `FEATURE_NAME`（必需）：功能特性名称，用于定位 specs 目录

## 入参校验

读取并执行 `<skill_dir>/prompts/resolve_feature_name.md`，传入以下参数：
- `ACTION_TYPE = "other"`
- `ARG = {用户传入的参数}`

执行完成后获得 `FEATURE_NAME`。

推导内部变量：

```text
SPECS_DIR = docs/xdev/speckit/{FEATURE_NAME}
SPEC_DOC = {SPECS_DIR}/spec.md
```

继续校验：

1. `SPEC_DOC` 文件存在
   - 不存在 → 提示用户："`SPEC_DOC` 文件不存在：{路径}，请确认 spec.md 文件是否已生成"

全部校验通过后，进入执行阶段。

## 执行流程

### 1. 开场提示

向用户输出以下提示，进入审阅模式：

```
现在我来协助您对 Spec 文档进行校审修订。

请您仔细查阅 Spec 文档，尤其关注文档末尾的「假设与未知项」部分——其中可能有需要您确认或澄清的问题。

有任何修订要求都可以直接告诉我，我来帮您修改。审阅完毕后告诉我即可。
```

### 2. 交互式修改循环

> **Assumption 同步规则**：当用户的回答或确认涉及 Spec 文档末尾的假设（Assumption）或 `[NEEDS CLARIFICATION]` / `[待澄清]` 标记的问题时，必须同时执行以下操作：
> 1. 根据用户确认的内容，更新 `SPEC_DOC` 末尾假设区域中对应的条目（将假设替换为用户确认的结论，移除标记）
> 2. 同时更新 `SPEC_DOC` 正文中引用了该假设的相关章节内容（如功能性需求描述、用户故事等），确保正文与确认结论一致

用户会反复提出修改意见，每次收到用户的修改要求后：

1. **执行修改**：根据用户要求修改 `SPEC_DOC` 文件（注意遵守上方的 Assumption 同步规则）
2. **告知用户修改完成**：简要说明做了什么修改
3. **询问是否继续**：`还有其他需要修改的地方吗？`

> 用户可能继续提修改意见（重复上述 1-3），也可能表示审阅完毕（进入步骤 3）。

### 3. 完成审阅

用户表示审阅完毕后，输出完成确认：

```
规格审阅完毕！Spec 文档已按您的意见修订完成。

修订后的文档：{SPEC_DOC}
```

# 单 Phase 开发执行指令

## 输入文档

> **变量路径说明**：以下变量通过 system prompt 注入，值为绝对路径。

1. 任务文件：`{SPECS_DIR}/{TASK_PHASE}`
   - 当前 Phase 的 subtasks 文件，包含本次开发的任务列表、前置依赖文档引用和实现策略
   - TASK_PHASE 为当前阶段的任务文件名（如 `subtasks_1.md`、`subtasks_7.md`）
   - SPECS_DIR 为 specs 文档目录的绝对路径
2. Spec 文档：SPEC_DOC
   - 对需求的详细描述，也是功能实现的目标
3. Constitution：CONSTITUTION_DOC
   - 当前代码库上做需求的规约，所有的代码实现都必须**严格遵循**它
4. Data Model 文档：DATA_MODEL_DOC
   - 数据模型/存储层/约束规则等的设计
5. Contracts 文档：CONTRACTS_DOC
   - 对外暴露的 API 接口契约文档
6. Configuration 文档：CONFIGURATION_DOC
   - 系统/核心领域的配置设计
7. Integration 文档：INTEGRATION_DOC
   - 系统内部对外的集成方案（RPC 外调、外部 HTTP 服务等）
8. Plan 文档：PLAN_DOC
   - 技术实现方案
9. Research 文档：RESEARCH_DOC
   - 技术方案调研文档
10. Mining 文档：MINING_DOC
    - 隐性需求挖掘文档（差异化版，仅独特发现）
11. 代码仓库：当前工作目录即代码仓库根目录，代码开发在此目录下进行

## 输出

1. 更新后的任务文件：`{SPECS_DIR}/{TASK_PHASE}`（末尾追加"## 开发状态"章节）

## 续接开发检查

在开始开发前，**先检查** `{SPECS_DIR}/{TASK_PHASE}` 文件的当前状态：

1. 如果存在已标记为 `[X]` 的 task 和未标记 `[ ]` 的 task **混合存在**：
   → 说明这是**续接开发场景**（上次可能因阻塞中断了）

2. 如果文件末尾存在"## 开发状态"章节，且其中包含"❌ 未完成"和阻塞性问题：
   → 检查问题下方是否已有用户追加的回答
   → 如果有回答，结合回答内容继续开发

3. 在续接场景下，**务必重新检查当前 Phase 的所有 tasks**（即使是已经标记 `[X]` 的），确保它们在结合用户回答后仍然正确

4. 清除旧的"## 开发状态"章节内容（开发结束时会重新写入新的状态）

## 任务要求

1. 按照任务计划执行实现：
   - 分阶段执行：每次只执行当前 `{TASK_PHASE}` 中的任务，完成后直接退出
   - 遵循依赖关系：按顺序执行串行任务
   - 遵循 TDD 方法：在对应的实现任务前先执行测试任务
   - 基于文件的协调：影响到同一文件的任务必须顺序执行
   - 验证检查点：在结束当前开发阶段之前验证每个任务是否已完成

2. 代码实现执行规则：
   - 先进行设置：初始化项目结构、依赖和配置
   - 先测试再编码：如果需要为合约、实体和集成场景编写测试，则先写测试
   - 核心开发：实现模型、服务、CLI 命令、端点
   - 集成开发：数据库连接、中间件、日志、外部服务
   - 打磨与验证：单元测试、性能优化、文档

3. 进度跟踪和错误处理：
   - 在完成每项任务后报告进度
   - 串行任务失败则停止执行
   - 提供清晰的错误信息及调试上下文
   - **重要**：对已完成的任务，务必在任务文件中标记为 `[X]`，每完成一个任务后及时更新，不要在最后统一标记

4. 完成验证：
   - 确认当前实现阶段所有必需任务均已完成
   - 检查实现的功能是否符合原始规格
   - 验证测试已通过且覆盖率达到要求
   - 确认实现遵循技术方案

   **重要限制**：本次只完成 `{TASK_PHASE}` 的所有 task 开发，不允许进入下一阶段。

## 开发状态写入

在当前 Phase 开发结束前（无论成功还是阻塞），在 `{SPECS_DIR}/{TASK_PHASE}` 文件**末尾**追加"## 开发状态"章节。

> **写入时机**：只有确定要退出时（成功完成 or 遇到阻塞性问题），才写这个章节。开发过程中不要提前写。

### 场景 A：开发顺利完成

1. 在代码仓库执行 `git add -A && git commit && git push`
   - **commit message**：就是完整的"开发状态"里的内容（状态 + 总结）
2. 获取 commit hash：`git rev-parse HEAD`
3. 在 `{TASK_PHASE}` 文件末尾写入：

```markdown
## 开发状态

**状态**：✅ 已完成

**Commit**：{commit_hash}

**总结**：
- 完成了 xxx
- 实现了 yyy
- 测试通过情况 zzz
```

### 场景 B：遇到阻塞性问题需要用户回答

如果开发过程中遇到任何阻塞性问题——需要用户配合回答才能继续——则：

1. 不要 git commit（代码可能处于不完整状态）
2. 在 `{TASK_PHASE}` 文件末尾写入：

```markdown
## 开发状态

**状态**：❌ 未完成，需要用户协助回答问题

**已完成的开发**：
- [X] Task 1.1: xxx（精炼描述）
- [X] Task 1.2: yyy

**阻塞性问题**：
1. 问题一：xxx？
2. 问题二：yyy？

**待用户回答后继续**
```

## 退出输出

开发结束前的**最终输出**：将上面写入 `{TASK_PHASE}` 文件中"开发状态"章节的内容，以纯文本形式输出，作为本次执行的总结。

外层 Agent 会阅读这段文本来理解本次执行的结果（成功完成 / 阻塞需要提问 / 异常失败），不需要输出额外的结构化数据。

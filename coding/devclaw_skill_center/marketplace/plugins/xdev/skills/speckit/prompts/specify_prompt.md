# specify 指令（生成功能规格说明书）

> 根据 PRD 原始需求和 Spec 模板，生成 Spec 文档，并记录合理假设

## 输入文档

> **变量路径说明**：以下变量的实际路径值从 `var/.env` 文件中读取（由调用方传入 env 文件路径）。

1. PRD_DOC：需求描述文档（prd.md，包含用户需求描述及所有引用文档的完整展开内容），是功能实现的唯一输入源
2. SPEC_TEMPLATE_DOC：Spec 文档的结构模板，后续生成严格按照此模板结构填写

## 输出文档

1. SPEC_DOC：生成的功能规格说明书（最终包含假设推理内容）
2. SPEC_ASSUMPTION_DOC：Spec 假设推理文档（中间产物，与 SPEC_DOC 同目录下的 `spec-assumption.md`，合并到 SPEC_DOC 末尾后删除）

## 执行流程

### 步骤 1：提取关键信息

1. 首先向用户报告 MESSAGE 提示 "【当前状态】开始 >> [步骤1] 需求关键信息提取..."

2. 理解 Spec 模板文档（SPEC_TEMPLATE_DOC）的内容，后续的流程严格按照该模板结构进行填写

3. 读取 PRD 文档（PRD_DOC）内容，并从中提取 需求名称
   - **注意**：大多情况下为文档的标题，如果标题内容不明确或者过于笼统，比如 "Fornax需求"、"Fornax观测需求" 等，则从文档内容中分析出合理的需求名称
   - 需求名称要求：
     1. 简洁
     2. 最好是动名词格式，比如："新增用户认证"、"新增Trace手动回流" 等
     3. 其中动词一般为 增、删、查、改、优化、修复 等等带有明确的目的性

4. 从 PRD 文档的内容中提取关键概念
   - Actors: 用户 / 核心参与者 / 交付对象
   - Actions: Actors / System 的核心操作
   - Data: 关键数据实体 / 系统状态 等等
   - Constraints: 所有 Actions 限制条件 / Edge Cases / 成功标准(性能要求) 等等

5. 对于 PRD 文档中 不明确、不清晰 的点
    - 基于 上下文 以及 行业标准和管理 做出合理推断
    - 如果遇到下面任意一种情况就用 [NEEDS CLARIFICATION: 具体问题] 标记/记录：
      1. 做出的推断 **严重影响** 需求涉及的功能的范围、用户体验
      2. 该 不明确、不清晰 的点本身存在 多种合理解释 且 含义各不相同
      3. 根本无法做出合理推断 且 不存在合理的默认值
    - **最多标记/记录 3个 [NEEDS CLARIFICATION]**，超出3个的，直接做出合理推断，并将推断记录到 Spec 假设推理文档（SPEC_ASSUMPTION_DOC）的 "NEEDS CLARIFICATION - 合理假设" 章节中

    - [NEEDS CLARIFICATION]的优先级：需求功能范围 > 安全/隐私 > 用户体验 > 技术细节
    - 留下的 [NEEDS CLARIFICATION] 记录到 Spec 假设推理文档（SPEC_ASSUMPTION_DOC）的 "NEEDS CLARIFICATION - 待确认" 章节中
        - 对于留下的标记，按以下格式给予用户选项(按顺序编号问题（Q1、Q2、Q3最多 3 个）)
        ```markdown
        ## 问题 [N]：[主题]

        **上下文**：[引用相关 PRD 文档相关章节]

        **需要澄清的内容**：[来自 NEEDS CLARIFICATION 标记的具体问题]

        **建议**：

        - 选项 A: [第一个建议答案]
          - 说明：[这对需求功能意味着什么]
        - 选项 B: [第二个建议答案]
          - 说明：[这对需求功能意味着什么]
        - 选项 C: [第三个建议答案]
          - 说明：[这对需求功能意味着什么]

        [如有更多问题，请继续添加，总共最多3个]
        ```

6. 结合上面提取到的关键信息并结合 PRD 文档分析并提取出用户故事（User Stories）
   - **注意**：
     - 如果 User Stories 都缺失或者不明确，则要终止流程并 ERROR提示 "无实质的 User Stories，请先完善需求描述"
     - 按照 Spec 模板文档的要求，优先级的判定以及独立验收场景的定义要明确并符合User Stories的定义
     - 若在之前明确识别出明确的边界情况（Edge Cases），则也要在模板中填上

7. 进一步生成 功能性需求（Functional Requirements）
   - 每个需求(FR)必须可测试
   - 对于需求相关不明确的细节使用合理默认进行假设，并记录到 Spec 假设推理文档（SPEC_ASSUMPTION_DOC）中
     - 这部分假设追加到 "功能性需求 - 合理假设" 中
       - 若章节为创建，则先创建章节

8. 进一步识别出 关键实体（Key Entities），如果需求涉及到

9. 进一步识别出 成功标准（Success Criteria），如果需求涉及到
   - 所有成功标准(SC)必须可量化、可定性
   - SC的描述必须与技术实现细节无关，面向于非技术人员

10. 信息提取环节结束，向用户报告 MESSAGE 提示 "【当前状态】完成 >> [步骤1] 需求关键信息提取"

### 步骤 2：生成 Spec 文档

1. 首先向用户报告 MESSAGE 提示 "【当前状态】开始 >> [步骤2] 生成 Spec 文档..."

2. 根据之前提取的信息，按照 Spec 模板文档的结构和要求填写其内容(并替换其中的占位符)，并输出到 SPEC_DOC
   - **重要**：**不得** 擅自 增加/删除章节、改变章节顺序

3. 生成完毕后向用户报告 MESSAGE 提示 "【当前状态】完成 >> [步骤2] 生成 Spec 文档"

### 步骤 3：合并假设文档到 Spec 末尾并删除中间文件

将 Spec 假设推理文档（SPEC_ASSUMPTION_DOC，即 SPEC_DOC 同目录下的 `spec-assumption.md`）的内容直接追加到 SPEC_DOC 末尾，使最终的 Spec 文档包含所有假设记录：

1. 检查 SPEC_ASSUMPTION_DOC 文件是否存在且非空
2. 如果存在且非空，将其内容追加到 SPEC_DOC
3. 追加完成后，删除 SPEC_ASSUMPTION_DOC 文件（它是中间产物，已合并到 SPEC_DOC 中）
4. 如果不存在或为空，跳过此步骤（不报错）

## 退出输出

执行结束前的**最终输出**：以纯文本形式输出执行总结，外层 Agent 会阅读这段文本来判断执行结果。

### 成功时输出

```
✅ Spec 生成完成
- Spec 文档: SPEC_DOC
- 需求名称: {提取到的需求名称}
```

### 失败时输出

```
❌ Spec 生成失败
- 原因: {失败原因}
```

## 指南

### 纲领（General Guidelines）

- 聚焦用户需要什么（WHAT）以及为什么需要（WHY）
- 避免描述如何实现（HOW）（不涉及技术栈、API、代码结构等）
- 要面向业务相关方撰写，而不是面向开发/技术人员
- 不要在 Spec 文档中创建任何 checklist，这些信息已经被控制在其他文档中了

### 章节要求（Section Requirements）

- 必选章节（Mandatory）：必须按要求严格包含并完整填写
- 可选章节（Optional）：仅在需求涉及到时才包含，若不涉及则 **直接移除**，不要留为诸如 "N/A" 等记号

### AI 生成规范（For AI Generation）

0. **禁止向用户提问**：本流程在无头模式下运行，没有用户可以响应。所有不确定、不明确的事项一律基于上下文和行业惯例做出合理假设，并记录到 Spec 假设推理文档（SPEC_ASSUMPTION_DOC）中。**绝对不要**使用 AskUserQuestion 或任何交互式提问方式，否则会导致进程退出。
1. 做出合理推断：利用上下文、行业惯例和常见模式来补全缺失信息，并记录到 Spec 假设推理文档（SPEC_ASSUMPTION_DOC）中
2. 以测试者视角思考（Think like a tester）
    - 着重关注需求功能的描述是否满足 "可测试且无歧义"，否则不能通过相关的Spec质检
3. 关于 [NEEDS CLARIFICATION] 标记
   - 数量限制：最多 3 个，优先级为 功能范围 > 安全 / 隐私 > 用户体验 > 技术细节（超出3个的，直接做出合理推断，并将推断记录到 Spec 假设推理文档中）
   - 仅在以下关键决策点标记：
     - 该点会显著影响功能范围或用户体验
     - 该点本身存在多种合理解释且含义各不相同
     - 该点根本无法做出合理推断且不存在合理的默认值
   - **不需要**标记的示例（往往都存在行业标准做法，因此可直接采用）：
     - 数据持久化：采用该领域的行业标准做法
     - 性能目标：未明确说明时，采用标准 Web / 移动应用的用户期望
     - 错误处理：用户友好的提示 + 合理的兜底方案
     - 认证方式：Web 应用中常见的 session-based 或 OAuth2 等
     - 集成模式：未说明时，默认采用 RESTful

### 成功标准指南（Success Criteria Guidelines）

成功标准必须满足以下条件
1. 可衡量（Measurable）：包含明确指标（时间、百分比、数量、比率等）
2. 技术无关（Technology-agnostic）：不提及任何框架、语言、数据库或具体工具
3. 以用户为中心（User-focused）：从用户或业务结果角度描述，而不是系统内部实现
4. 可验证（Verifiable）：无需了解实现细节即可测试或验证

Good examples
- "用户可以在 3 分钟内完成结账流程"
- "系统可支持 10000 名用户并发量"
- "95% 的搜索请求在 1 秒内能返回结果"
- "商家任务完成率提升 40%"

Bad examples（往往过于偏技术实现）
- "API 响应时间低于 200ms"（过于技术化，应改为"用户几乎能立即看到结果"）
- "数据库可以处理 1000 TPS"（存在技术细节，应改为用户可感知的指标）
- "React 组件渲染高效"（涉及到了具体的技术框架）
- "Redis 缓存命中率高于 80%"（涉及到了具体的技术细节）

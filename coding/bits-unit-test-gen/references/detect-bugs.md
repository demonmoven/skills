# 单元测试缺陷挖掘

本文用于指导模型在单测生成前，从目标代码或变更代码中挖掘可供后续单测验证的真实缺陷。核心产物是 `BUG_MAP`：它是后续缺陷探测单测的唯一来源。

核心策略：**先放宽召回，尽量多提出疑点；再用严格过滤和降噪规则压掉误报。** 最终只输出降噪后的 `BUG_MAP`。

> **无需为通过 CI 卡口而排除缺陷**。缺陷探测用例会在最终检查 CI 卡口时排除，不会导致单测卡口无法通过。

## 1. 工作流

1. **确定范围**：只使用 `scope.md` 输出的 `scope_type`、`TARGETS`、`diff_context` 和 `fallback_notes`。不得要求上游提供完整 `diff_content`。
2. **广召回候选**：对 `TARGETS` 中每个目标函数，按本文定义的缺陷类型分类表逐类审查，从目标单元、diff hunk、同 diff 直接调用方/被调用方、代码注释、日志或错误处理中承认的异常行为中召回疑似缺陷。
3. **逐个闭环**：每个候选都要补齐触发路径、根因、错误结果、正确期望、归因范围和后续可验证条件。
4. **严格过滤**：按范围、证据、噪音逐层淘汰。
5. **输出 `BUG_MAP`**：只输出通过全部门禁的缺陷；没有缺陷时输出空数组。

## 2. 缺陷类型分类

以下分类表是整个缺陷挖掘流程的**唯一类型定义**。召回阶段必须按此表逐类审查，门禁和降噪阶段按分类引用。

| 分类 | 定义 | 典型信号 |
|------|------|---------|
| `logic_errors` | 条件判断、算术运算或分支选择存在客观逻辑错误，导致执行路径或计算结果与预期不符 | 条件取反、运算符误用、switch/if 分支遗漏或落入错误分支、布尔表达式短路逻辑错误、off-by-one 逻辑 |
| `boundary_errors` | 缺少对输入的必要约束检查，或边界条件处理不当，导致非法或异常数据进入业务链路产生错误结果 | 未校验 nil/空/越界/格式的 optional 字段直接使用、off-by-one、数组越界、可选字段未做 nil guard 直接解引用 |
| `error_handling` | error/异常被忽略、吞没或错误传播中断，导致调用方无法感知失败 | 未检查 err、catch 后静默继续、错误码被覆盖、错误返回格式不一致 |
| `business_gaps` | 函数实现与接口契约、IDL 定义、业务规约或调用方期望的语义不一致；或数据流中值的产出语义与消费位置期望不匹配，导致业务结果错误 | 返回格式不统一、字段缺失、错误码不符合约定、分页子集长度当全量计数、局部状态当全局状态、条件查询结果赋给无条件字段、聚合粒度错配、核心业务逻辑疏漏 |
| `security` | 存在可被利用的安全漏洞，导致数据泄露、权限绕过或注入攻击 | SQL/命令注入、XSS、路径穿越、硬编码密钥、未授权访问 |
| `resource` | 资源（内存、文件句柄、连接、goroutine 等）未正确释放或管理，导致泄漏或耗尽 | 未 close 的 fd/conn、defer 缺失、循环内累积分配未释放、context 泄漏 |
| `concurrency` | 并发/多线程场景下共享状态未正确保护，导致数据竞争或不确定行为 | 无锁读写共享变量、race condition、死锁、非线程安全容器并发访问 |
| `other` | 无法归入上述类型的其他缺陷 | - |

语言层可在 `assets/${LANG}/prompt.md` 中声明额外的分类，但不得删除或重定义上述基础分类。

## 3. 候选召回范围

1. 缺陷挖掘的唯一代码事实来源是本地当前 checkout 后的工作区源码，包括当前文件内容、staged/unstaged/untracked 变更对应的实际文件内容。
2. 候选来源应围绕当前代码尽量覆盖，宁可先召回再过滤。

有 diff 时：

- `bug_range` 必须与本次 diff hunk 相交，或位于本次 `untracked` 文件目标单元内，或根因必须来自同 diff 中的契约变化。
- 优先审查 `+` 行和它直接影响的上下文。
- 只要 `diff_context` 非空，就必须使用变更信息挖掘缺陷；即使用户仅指定文件、目录、包或模块，`TARGETS` 也已是显式范围与本地变更的交集。
- 必须基于 `diff_context.files[].mode`、`diff_context.files[].range` 和 `diff_context.files[].file_path` 获取真实变更：`cached` 使用 `git diff --cached -- <file_path>`，`unstaged` 使用 `git diff -- <file_path>`，`merge_base` / `endpoint` 使用对应 `range`，`untracked` 直接读取文件内容。
- `diff_context.files[].hunks` 只作为定位索引，不替代真实 hunk 或未跟踪文件内容；进入门禁前必须按文件读取局部变更。
- 每个进入门禁的候选都必须实际读取相关 hunk 或未跟踪文件内容，并在 `BUG_MAP.evidence` 中写清候选与变更的归因关系。
- 不得把未变更代码中的存量问题写入 `BUG_MAP`，除非本次 diff 改变了触发条件或调用契约。

> 不同语言特定缺陷挖掘模式，请查阅对应 `assets/${LANG}/prompt.md`中对应部分，补充语言相关信息
> - JS/TS：额外加载 `assets/javascript/references/defect-scoring.md`（严重性评分）和 `assets/javascript/references/defect-verifier.md`（3-Gate 置信度验证）
>
> **冲突解决规则**：当本文件的通用规则与 `assets/${LANG}/` 下的语言特定规则存在冲突时（如数量限制、严重性分级标准、降噪规则覆盖等），以语言特定规则为准。降噪规则覆盖的具体机制见 Section 6.3。

无 diff 时：

- 当 `scope_type=non_diff` 或 `diff_context=null` 时，只扫描 `TARGETS` 中的目标单元及其直接可验证调用链。
- `TARGETS[].source` 只说明范围来源，例如 `explicit`、`test_entry`、`untracked`；不得把来源字段当作额外扩大范围的理由。
- 可以报告存量真实缺陷，但必须与 `TARGETS` 中目标单元的实现或契约直接相关。
- 不得因为无 diff 自动输出空 `BUG_MAP`；无 diff 只限制搜索范围。


## 4. 理解业务规约

当 `biz_spec` 非空时，**必须**按其获取指令读取内容，尝试提取与当前 TARGETS 相关的段落。若读取后确认内容与目标函数无关或无法提取有效业务信息，可以忽略；但不允许未读取就跳过。

- **角色**：为准入门禁中的"正确期望"提供权威依据，并在降噪阶段辅助区分"语义猜测"与"有据矛盾"。
- **重点关注维度**：
  - 输入参数校验规则（必填、格式、范围、枚举值等）
  - 业务字段映射关系（字段对应、转换逻辑、默认值填充等）
  - 响应文案、报错信息和错误码定义
  - 数据模型实体关系（外键关联、级联行为、唯一性约束等）
  - 数据资源归属和权限控制（鉴权规则、资源隔离、越权访问防护等）
  - 性能和安全性要求（超时限制、并发约束、数据脱敏、注入防护等）
- **限制**：`biz_spec` 不替代代码事实。缺陷的 `evidence` 必须指向具体代码位置；必须存在代码实现与业务规约的可证明矛盾才能构成缺陷。


## 5. 缺陷准入门禁

候选进入 `BUG_MAP` 前必须同时满足：

| 门禁 | 要求 |
| --- | --- |
| 定位 | `bug_range` 指向最小连续代码范围 |
| 归因 | 有 diff 时与 hunk 或同 diff 契约变化相关；无 diff 时位于目标函数直接范围 |
| 触发路径 | 能说明正常业务输入或 mock 依赖如何执行到该代码 |
| 根因 | 能指出错误值、错误分支、错误状态或错误副作用如何产生 |
| 错误结果 | 会导致 Section 2 定义的缺陷分类中至少一种类型的错误 |
| 正确期望 | 写明正确结果、当前错误结果和后续可验证条件 |
| 降噪 | 未命中第 6 节降噪规则（含语言覆盖判断），或能用代码证据反驳过滤规则 |

对吞错、默认值成功返回、nil/zero 误用、部分结果继续使用等高误报候选，必须完成三段证明：

| 证明段 | 必须回答 |
| --- | --- |
| 被调用方失败语义 | 被调用方在什么正常输入或 mock 状态下返回 error、nil、zero 或部分结果 |
| 当前函数处理契约 | 被调用方返回 error、nil、zero 或部分结果时，当前函数是否承诺返回错误、非空结果、完整字段、幂等状态或可观测副作用 |
| 可观测坏结果 | 当前函数忽略或误用被调用方结果后，会在返回值、状态、副作用或上层调用处产生什么可观察的错误结果 |

任一证明段缺失时，不得进入 `BUG_MAP`；该疑点在本阶段直接过滤，不输出给后续阶段。


## 6. 高优先级降噪规则

以下类型默认过滤，除非能给出明确代码级反证。规则分为通用规则和语言可调整规则两层。

### 6.1 通用降噪规则（所有语言一律适用，不可被语言层覆盖）

- **不影响功能正确性**：性能、风格、命名、可读性、架构建议，无法证明造成错误返回值、状态、功能、数据、panic 或卡死。
- **仅凭语义猜测**：结论缺少调用方/被调用方契约、接口/IDL 契约或数据流证据，主要依赖函数名、变量名、注释推断产品意图。以下情形**不属于**语义猜测：
  - 函数实现与其签名语义直接矛盾（如声明动态目的但返回固定值）——属于代码级证据。
  - `biz_spec` 中明确定义了业务规则，且代码实现与该规则存在可证明矛盾——业务规约是正确行为的权威定义，与之矛盾属于代码级证据。
- **验证缺口反向证明不足**：现有覆盖不足、缺少用例或缺少校验，不等于代码有缺陷。注意："缺少外部测试覆盖"与"代码本身缺少其职责范围内的必要逻辑"是不同的；后者属于逻辑缺失，不适用本规则。
- **低置信兼容差异**：新旧行为不同但没有契约说明哪一个正确，且没有调用方错误结果。

### 6.2 语言可调整降噪规则（默认适用；语言层可声明覆盖）

以下规则包含默认行为，适用于未声明覆盖的语言。当 `assets/${LANG}/prompt.md` 对某规则声明了覆盖条件时，以语言层为准。

| # | 规则 | 默认行为 | 可覆盖维度 |
|---|------|----------|------------|
| A | **泛化防御建议** | 机械要求补 nil/null、长度、类型、default 分支 → 过滤；除非正常业务流会传入该值且违反声明行为 | 语言层可声明哪些防御检查在该语言中是真实缺陷信号 |
| B | **存量约定已覆盖** | 同类写法在存量代码中稳定存在且存量行为正确，或参数、配置、请求体已由上游校验 → 过滤 | 通用逻辑，语言层通常无需覆盖 |
| C | **责任不在本次变更** | 根因位于未变更 helper、SDK/框架 getter、基础设施默认行为，且当前 diff 没有误用证据 → 过滤 | 语言层可调整"基础设施默认行为"的具体范围 |
| D | **非关键副作用** | 日志、指标、缓存预热等失败被忽略 → 过滤；除非调用方明确依赖该副作用做重试、路由或分支决策 | 语言层可调整"非关键"的边界定义 |
| E | **服务边界转换** | 错误包装、错误码转换、默认值兼容属于既有边界契约 → 过滤；除非调用方依赖原始错误或字段 | 语言层可声明本规则不适用 |
| F | **框架托管契约** | 框架明确保证的行为不得反向怀疑 → 过滤 | 语言层应声明具体框架保证清单 |
| G | **不可稳定触发** | 只能靠竞态窗口、真实网络波动、外部服务状态、当前时间或随机数触发，无法用固定输入或可控依赖稳定构造 → 过滤 | 语言层可声明哪些异步/并发场景可通过 mock 或可控依赖稳定构造并值得报告 |

### 6.3 语言覆盖机制

语言层可在 `assets/${LANG}/prompt.md` 中声明降噪规则覆盖。覆盖格式为表格，包含规则编号、覆盖条件和覆盖后行为。

**执行顺序**：
1. 对每个候选缺陷，先检查 `assets/${LANG}/prompt.md` 是否对匹配的降噪规则有覆盖声明。
2. 若有覆盖声明且候选符合覆盖条件 → 跳过该降噪规则，候选保留（按覆盖后行为处理）。
3. 若无覆盖声明或候选不符合覆盖条件 → 适用 6.2 表中的默认过滤行为。

**关于"缺少业务闭环"**：该语义已完全由 Section 5 准入门禁的"触发路径 + 根因 + 错误结果 + 正确期望"四项要求覆盖。未通过门禁的候选在 Section 5 已被拦截，不再在降噪规则中重复检查。

### 6.4 补充规则

- 不得使用 commit message、MR 标题或提交描述作为缺陷过滤依据；缺陷的召回和过滤必须完全基于代码事实和变更内容本身，commit message 仅反映作者意图，不能用于否定代码中存在的真实缺陷。

## 7. 缺陷分级和数量预算

缺陷分级只用于排序，不替代门禁：

| Severity | 使用条件 |
| --- | --- |
| P0 | 较大隐患：稳定崩溃、数据丢失、置信度高的逻辑或数据流错误等。导致核心链路整体不可用、功能异常、无法交付 |
| P1 | 一定隐患：异常处理不当、轻微违反业务契约、边界场景保护不足等。虽不影响核心代码的运行但存在一定出错的风险 |
| P2 | 较小隐患：影响范围有限，出现概率低。如资源泄露、并发保护等风险 |

数量预算：

- 每个目标函数最多输出 2 条缺陷。
- 整个任务默认最多输出 4 条缺陷。
- 超预算时优先保留：P0/P1、直接位于 diff `+` 行、后续最容易构造稳定输入、错误结果最明确、覆盖不同文件和失败模式的候选。

多样性约束：

- 同一缺陷分类在整个任务中最多输出 2 条；超出时只保留证据最强的实例。
- 同一源文件中最多输出 3 条缺陷；超出时优先保留不同分类的候选。
- 如果全部候选都属于同一分类，必须重新审视是否在模板化套用，确认每条都有独立的触发路径和不同的错误结果。

### 7.1 Verifier 强制执行（输出 BUG_MAP 前）

BUG_MAP 中的每条缺陷在写入最终输出前，必须通过以下自检。该自检不可跳过。

对每条候选，回答：
1. **反面验证**：是否存在已知的 false-positive 模式匹配（参见语言层 `defect-scoring.md` / `defect-verifier.md` 的误报列表）？匹配则 DROP。
2. **证据自检**：如果一位不了解该代码的工程师只看 `evidence` 和 `expect_outcome` 字段，能否独立确认这是 bug？如果需要额外假设（"假设上游传入 null"、"假设用户快速点击"），则证据不充分，降级或 DROP。
3. **设计意图排除**：当前行为是否可能是有意为之（哨兵值、降级策略、兼容处理）？存在合理设计意图时 DROP。

若语言层声明了 3-Gate Verifier（如 JS/TS 的 `defect-verifier.md`），则本自检替换为语言层 Verifier 的完整流程。

## 8. 输出格式

完成缺陷分析阶段时，输出：

```json
{
  "BUG_MAP": [
    {
      "defect_type": "error_handling",
      "scenario": "[defect-probing] 被调用方返回错误时，目标函数应返回错误而不是成功",
      "description": "忽略被调用方错误会导致成功分支返回无效结果",
      "file_path": "path/to/file.go",
      "target_func": "FunctionName",
      "bug_range": "line 45-48",
      "evidence": "Line 45 ignores err from Load; 调用方会把返回结果当作成功响应处理",
      "expect_outcome": "correct outcome: return the Load error; current wrong outcome: nil error with zero result; verification: downstream should observe a non-nil error instead of a successful zero result",
      "severity": "P1"
    },
    {
      "defect_type": "business_gaps",
      "scenario": "[defect-probing] 用户注册接口未校验手机号格式，与业务规约要求不符",
      "description": "业务规约要求注册时手机号必须为 11 位数字且以 1 开头，但代码实现仅检查了非空，未做格式校验",
      "file_path": "pkg/user/register.go",
      "target_func": "RegisterUser",
      "bug_range": "line 34-38",
      "evidence": "Line 34-38 仅判断 phone == \"\" 即返回错误，未校验长度和前缀；业务规约 Section 3.2 明确定义：手机号必须匹配正则 ^1[3-9]\\d{9}$",
      "expect_outcome": "correct outcome: phone 不匹配 ^1[3-9]\\d{9}$ 时返回 InvalidPhoneFormat 错误码; current wrong outcome: 任意非空字符串均通过校验并写入数据库",
      "severity": "P1"
    }
  ]
}
```

字段约束：

- `defect_type`：必须为 Section 2 中定义的分类枚举值或语言层扩展的分类。
- `scenario`：必须以 `[defect-probing]` 开头，描述后续可验证的缺陷场景。
- `description`：一句话说明缺陷本质。
- `file_path`、`target_func`、`bug_range`：定位到最小责任代码。
- `evidence`：合并写清触发路径、根因、错误结果和 diff/范围归因；不要拆成多个审计字段。
- `expect_outcome`：写清正确结果、当前错误结果和后续可验证条件。
- `severity`：只能是 `P0`、`P1`、`P2`。

无缺陷时输出：

```json
{
  "BUG_MAP": []
}
```

当 `BUG_MAP` 为空时，必须在缺陷分析日志或调试输出中记录候选过滤摘要，包含候选位置、疑点、读取过的证据和过滤原因；该摘要不得作为后续缺陷探测单测的输入。

完成输出后，`BUG_MAP` 通过上下文传递给后续阶段（gen-verify-fix-loop、report）。

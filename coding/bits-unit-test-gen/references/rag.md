# RAG 知识检索协议

本文件定义 RAG（Retrieval-Augmented Generation）知识检索的使用规范。RAG 提供公共知识检索能力，包括框架用法、mock/断言写法示例、编译异常和测试运行异常的解决方案等通用知识。RAG 不包含特定仓库或项目的上下文。

## 使用场景

RAG 查询不是每个步骤的强制动作。只在以下两种场景下使用，且满足“只按需加载“的原则。即：当前上下文知识已足够时无需查询，不足时优先通过 RAG 获取知识，避免无头绪的自由探索浪费耗时和 token。

### 场景一：测试框架/库的用法和示例

涉及非编程语言原生或第三方测试框架、工具库或包时，优先通过 RAG 查询其 API、使用说明和代码示例。具体判断：

1. 涉及非原生或第三方测试框架、工具库或包（非语言标准测试库）。
2. 仓库已有测试代码无法提供完整所需的参考知识（采样的已有测试未覆盖当前需要的用法或模式）。

满足以上两个条件时，**建议优先查询 RAG** 补充相关知识。

### 场景二：编译或单测运行错误的修复

遇到难以解决的编译或运行时错误时，优先通过 RAG 查询解决方案以提升修复效率。具体判断：

- 常见且解决方案清晰直白的错误（如 import 缺失、拼写错误、语言 prompt 中已列举的常见问题）：直接修复，无需查询。
- 同一错误已尝试修复但仍然失败、或错误根因不直观时：**应查询 RAG 获取解决方案**，避免反复试错浪费 token 和时间。

查询时，`query` 应包含具体的错误信息，例如：`"go test 报错 mockey PatchConvey panic: convey need gomonkey open"` 或 `"Jest TypeError: Cannot read properties of undefined (reading 'mock') in ESM module"`。

## 调用方式

```bash
python3 ${SKILL_ROOT}/scripts/rag_query.py \
  --query "<自然语言描述需要的知识>" \
  --language "${LANG}" \
  --top-k 3
```

输出为 Markdown 格式，每条知识以 `### [序号] (score: 分数) 标题` 开头，多条结果之间以 `---` 分隔。示例：

```
### [1] (score: 0.83) 规范Go语言中泛型函数与方法的Mock实现

Generic Functions and Methods
Purpose
Mock generic functions/methods using MockGeneric...
Code
func main() {
    MockGeneric(FooGeneric[string]).Return("MOCKED!").Build()
    ...
}
Key Points
Prefer MockGeneric for generic functions/methods...

---

### [2] (score: 0.76) Go Table-Driven 测试与 mockey 结合的写法

...
```

- `score`：综合相关性得分（0-1），越高越相关，仅作为辅助参考。
- 查询无结果时输出 `RAG 查询无结果。`。
- 查询失败时错误信息输出到 stderr，脚本以非零退出码退出。



## 查询构造规范

### query 字段

`query` 必须是清晰、具体的自然语言描述，聚焦于当前需要解决的具体问题。尽量包含足够的信息和关键词，避免模糊或不明确的问题。
如果某次查询未返回有效知识，可以换一种问法重新查询（如调整关键词、换用同义表达、或从不同角度描述问题），同一问题最多尝试 3 次不同的 query。

好的 query 示例：

- `"Go mockey 如何 mock 接口类型的方法"`
- `"Jest 中 mock ES module 的 default export"`
- `"go test 报错 package xxx is not in std 的解决方案"`
- `"Python pytest 中如何 mock asyncio 协程"`

差的 query 示例：

- `"如何写单测"` — 太泛
- `"Go"` — 无具体问题
- `"帮我修复错误"` — 缺少错误信息

### language 字段

`language` 必须使用 `LANG` 的值，只能是：`go`、`python`、`java`、`javascript`、`kotlin`、`cpp`、`swift`、`rust`。

### top-k 字段

默认 `3`。当问题涉及多种可能方案时可提高至 `5`。

## 结果评估协议

RAG 返回 TopK 结果后，必须按以下流程评估：

1. **相关性筛选**：逐条检查每个结果的正文是否与当前具体问题直接相关。结合标题快速判断知识领域是否匹配。`score` 可作为辅助参考但不是唯一依据——低分结果可能仍然有用，高分结果可能与当前具体场景不相关。丢弃与当前上下文无关的结果。
2. **适配性验证**：相关结果中的代码示例或方案是否适用于当前项目的技术栈版本、框架版本和目录结构。
3. **冲突检查**：RAG 返回的知识是否与更高优先级的规则（用户指令 > 项目约定 > 已有测试风格 > 语言 prompt）冲突。冲突时以高优先级规则为准。
4. **综合采用**：只采用通过上述检查的结果，结合当前项目上下文进行适配，不得原样复制代码。

### 全部无关时的退回策略

当 RAG 返回的所有结果都与当前问题不相关时：

- 记录"RAG 查询未返回有效结果"。
- 退回自主处理：通过阅读项目代码、搜索文件、分析错误堆栈等方式自行解决。
- 不得因 RAG 无结果而跳过当前任务或降低处理质量，也不得强行使用不相关的 RAG 结果。

## 约束

- RAG 结果中的代码示例仅作为参考，必须根据目标项目的实际框架、目录结构和代码风格进行适配。
- RAG 查询超时或失败时，记录错误信息，退回自主处理，不得阻塞整体流程。

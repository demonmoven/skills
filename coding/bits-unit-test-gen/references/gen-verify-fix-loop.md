# 生成、验证、修复循环

本文件是单元测试生成阶段的强制执行协议。执行顺序固定为 `Loop-A 生成 -> Loop-B 验证 -> Loop-C 处置 -> Loop-D 收敛判断`。

`BUG_MAP` 是上游步骤输出的缺陷列表。本阶段必须为这些候选生成缺陷场景测试，用真实测试结果验证：

- 缺陷场景测试失败，且失败现象能稳定映射到对应 `BUG_MAP` 条目：该缺陷被实锤（即被验证成立），保留失败测试作为证据并输出缺陷。
- 缺陷场景测试通过：该 `BUG_MAP` 条目未被实锤，必须从本阶段缺陷输出中剔除。
- 失败无法映射到 `BUG_MAP`：不能新增缺陷，也不能把失败包装成已实锤缺陷；按测试问题修复，或以未收敛结束。
- 仅报告判定：当缺陷在 Loop-A 中经过充分分析后确认满足透出要求时（见 Loop-A 中的仅报告判定规则），标记为 `仅报告`，跳过后续验证和修复循环，直接进入报告阶段。

**本阶段的"成功"定义**：
- 常规单测（正常/边界/异常场景）：编译通过 + 运行通过 = 成功。
- 缺陷探测单测（BUG_MAP 场景）：编译通过 + 运行失败 + 失败现象稳定映射 BUG_MAP = 成功（缺陷被实锤）。

## 全局约束

- 只允许修改测试代码、测试配置、测试依赖和必要测试基础设施；**禁止**修改业务源码、被测函数、生产逻辑。
- 所有"通过 / 失败 / 已实锤 / 已剔除"结论必须来自真实测试执行结果。多轮修复后依然无法编译或执行时，必须记录环境或基础设施原因。
- 正常场景、边界场景、异常场景和 `BUG_MAP` 缺陷场景要分开记录；历史测试和新增测试要分开判断。
- 缺陷场景测试必须断言"修复后的正确行为"，禁止把当前实现的错误输出写成期望值。
- 禁止删除失败测试、注释关键断言、放宽断言、吞掉异常、用 mock 绕开被测逻辑来制造通过。
- 可以用 subagent 辅助生成测试代码，但测试命令必须由主 agent 执行。
- 在生成和修复过程中，若需要额外的框架用法、API 示例或错误解决方案（如无相关代码权限）等知识参考，使用 RAG 能力按需查询。使用方式和触发条件见 `${SKILL_ROOT}/references/rag.md`。
- **RAG 流程指令优先**：当通过 RAG 查询错误或异常的处理方式时，若 RAG 返回的结果要求改变主流程（如跳过当前目标的生成、运行或修复、要求用户介入等），其优先级高于本文件中的默认生成/修复逻辑。

## 输入与输出

输入：

- `TARGETS`：本次需要覆盖的目标函数集合。
- `BUG_MAP`：上游步骤输出的缺陷列表；为空时只生成正常测试，不生成缺陷探测用例。
- `LANG`：语言标识，以及语言 prompt 给出的测试命令、构建规范、目录约定。
- `biz_spec`（可选）：业务规约来源引用（含地址和获取指令），在处理具体 TARGET 时按其中的获取指令按需读取相关段落，辅助设计测试输入和预期值。若获取失败（权限、网络、工具不可用等），跳过即可，不阻塞流程。

输出：

- 新增或修改的测试文件、覆盖目标函数、用例目的。
- 每轮执行的测试命令、退出码、失败测试名和核心错误。
- 每个 `BUG_MAP` 条目的状态：`实锤` / `剔除` / `未收敛` / `仅报告`。未执行或无法判断的条目统一标记 `未收敛` ，并写原因。`仅报告` 条目在 Loop-A 阶段判定，未生成缺陷探测测试，结论基于静态分析的高置信证据。
- 最终结论：`全部通过` / `部分失败但已实锤 BUG_MAP 缺陷` / `未收敛` / `禁止修复`。

## Loop-A 生成单测

目标：为 `TARGETS` 生成最小且有意义的测试，覆盖正常路径、边界条件、异常路径；对 `BUG_MAP` 中每个候选缺陷生成独立缺陷场景测试。

执行要求：

- 复用项目既有测试框架、目录、mock、fixture 和断言风格；缺失时只补最小必要测试基础设施。
- 每个目标函数至少覆盖一个有效行为场景；不得只生成空壳测试。
- 对每个 `BUG_MAP` 条目，尝试构造能触发候选缺陷的输入，并通过静态分析推导正确期望值。
- 缺陷场景测试必须能回答"该候选是否成立"：失败则可能实锤，通过则剔除该候选。
- `BUG_MAP` 为空或目标不在 `BUG_MAP` 时，只生成应当通过的常规单测；不得临时发明缺陷场景。

### 仅报告判定规则

对 `BUG_MAP` 中的 P0 条目，如果经过分析后确认无法构造稳定的缺陷探测测试，可标记为 `仅报告`。标记时必须同时满足：

1. **severity 为 P0**：仅限 P0 缺陷。P1/P2 必须构造测试验证，或不输出。
2. **测试构造不可行或代价极高**：包括但不限于：
   - 触发条件依赖无法在单测中可控模拟的外部状态。
   - 并发窗口无法通过 mock/fixture 稳定复现。
   - 触发需要的系统环境超出单测能力范围。
   - 缺陷位于框架托管的入口/出口/中间件层，单测无法直接触达。
   - 需要构造的前置状态链过长且每一环都需要真实外部交互。

**偏好原则**：优先构造测试。即使满足上述条件，也应先尝试通过 mock、stub、依赖注入等手段构造测试。只有在分析后确信无法构造稳定、可靠的缺陷探测测试时，才标记仅报告。

标记 `仅报告` 的条目：
- 不生成缺陷场景测试，但仍应为其 `target_func` 生成常规功能测试（正常路径、边界条件）。
- 跳过 Loop-B/C/D 的验证和修复循环。
- 最终状态为 `仅报告`，输出时标注"静态分析发现，难以构造测试验证"。

进入 `Loop-B` 前必须落盘测试代码，并记录：

- 测试文件列表。
- 测试用例与 `TARGETS` 的覆盖关系。
- 缺陷场景测试与 `BUG_MAP` 条目的映射。

## Loop-B 验证单测

目标：按语言规范真实执行测试，优先运行本次改动相关的最小范围；最小范围通过后，再按项目规范决定是否扩大到文件、包或模块范围。

必须记录：

- 测试命令和退出码。
- 失败类型：`compile-error`、`test-infra-error`、`historical-test-failed`、`new-test-failed`、`all-pass`。
- 失败测试名和核心错误信息。

`all-pass` 后必须复核新增/修改测试：
- 对每个已执行且通过的缺陷场景测试，将对应 `BUG_MAP` 条目标记为 `剔除`，不得输出为缺陷。
- 若测试名、注释或断言说明承认”当前实现错误”，但断言仍按当前错误行为通过，视为未收敛。
- 若没有失败、没有上述异常，进入 `Loop-D`。

## Loop-C 处置失败

目标：只修复测试问题；稳定复现的 `BUG_MAP` 缺陷保留为失败证据。

按失败类型处理：

- `compile-error`：优先修复测试代码、测试依赖、测试配置或测试构建选项。若必须改业务源码才能编译，标记 `禁止修复`。
   - **依赖权限错误** 如果是因为缺失权限导致下载依赖失败，直接标记 `禁止修复`，禁止任何修复尝试，唯一允许的动作是提取依赖仓库地址（如 `code.byted.org/tikcast/agency_monorepo`），提示用户前往 `https://code.byted.org/<org>/<repo>` 申请访问权限。

- `test-infra-error`：优先修复 mock、fixture、环境变量、测试入口、超时等测试基础设施。若崩溃来自被测代码且能映射到 `BUG_MAP`，标记该缺陷 `实锤`。
- `historical-test-failed`：先判断是否由本次测试改动引起。若是历史测试稳定命中 `BUG_MAP`，标记 `实锤` 并保留失败；若是陈旧测试或 fixture 问题，可以修复测试。
- `new-test-failed`：先映射 `BUG_MAP`。能稳定映射则标记 `实锤` 并保留失败；不能映射时，若是断言、输入、mock 或环境准备错误，修复测试后回到 `Loop-B`；若疑似新业务缺陷，标记 `未收敛`，不得新增到 `BUG_MAP`。

处置结论只能是：

- 已修复测试问题，回到 `Loop-B`。
- 已实锤 `BUG_MAP` 缺陷，保留失败并进入 `Loop-D`。
- 无法在允许范围内修复，标记 `禁止修复` 并进入 `Loop-D`。
- 疑似新缺陷或原因不稳定，标记 `未收敛` 并进入 `Loop-D`。

## Loop-D 收敛判断

最多执行 3 轮。任一轮修改了测试代码、测试配置或测试依赖，都必须回到 `Loop-B` 重新验证。

`仅报告` 条目（在 Loop-A 中标记）不参与收敛判断。收敛状态仅基于非 `仅报告` 的 `BUG_MAP` 条目和常规测试来确定。

可结束状态：

1. `全部通过`
   - 目标范围内测试全部通过。
   - 没有未解释的历史失败。
   - 新增测试没有按当前错误行为断言。
   - `BUG_MAP` 中未失败的缺陷场景全部标记为 `剔除`。

2. `部分失败但已实锤 BUG_MAP 缺陷`
   - 存在失败测试。
   - 每个失败都稳定复现。
   - 每个失败都能映射到明确 `BUG_MAP` 条目。
   - 已说明失败不应被修成通过。

3. `未收敛`
   - 达到 3 轮仍无法稳定通过或稳定复现。
   - 失败现象变化，根因不稳定。
   - 疑似新业务缺陷但无法映射到 `BUG_MAP`。

4. `禁止修复`
   - 继续修复必须修改业务源码，或超出测试代码、测试配置、测试依赖范围。

### 更新 BUG_MAP 状态

循环结束后，将每个 `BUG_MAP` 条目的最终状态更新到上下文中的 `BUG_MAP`。对每个条目新增字段：

- `status`：最终状态，取值为 `confirmed`（实锤）/ `dismissed`（剔除）/ `inconclusive`（未收敛）/ `report_only`（仅报告）。
- `status_reason`：`report_only` 时填写无法构造测试的原因；`inconclusive` 时填写未收敛原因；其他状态可省略。

## 最终输出格式

| 结果 | 结论 | 用例输出 | 缺陷输出 | 建议 |
|:---|:---|:---|:---|:---|
| 全部通过 | `结论：全部通过，已完成 all-pass 复核。` | 输出全部已落盘且验证通过的用例 | 输出被剔除的 `BUG_MAP` 条目；不得输出为缺陷。`仅报告` 条目单独列出，标注"静态分析发现，难以构造测试验证" | 无 |
| 部分失败但已实锤 BUG_MAP 缺陷 | `结论：部分失败，但这些失败已实锤 BUG_MAP 缺陷。` | 输出全部已落盘用例，标注通过用例与缺陷证据用例 | 输出已实锤缺陷、失败测试映射、被剔除条目。`仅报告` 条目单独列出，标注"静态分析发现，难以构造测试验证" | 无 |
| 未收敛 | `结论：未收敛，需要人工介入。` | 输出已运行用例、失败用例和不可用原因 | 输出 `BUG_MAP` 缺陷；疑似新缺陷标记为复核项。`仅报告` 条目单独列出 | 输出下一步人工介入建议 |
| 禁止修复 | `结论：无法自动修复，需要人工介入。` | 输出全部已落盘用例、验证状态、失败类型、阻塞原因 | 输出 `BUG_MAP` 条目的 `实锤` / `剔除` / `未收敛` / `仅报告` 状态 | 输出禁止修复原因 |

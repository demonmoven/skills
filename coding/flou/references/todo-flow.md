# Todo-Flow 管理文件格式规范

## 一、核心设计理念

Todo-Flow 采用 **"多流程嵌套"** 模式管理研发流程，支持同时跟踪多个流程的状态。文件开头描述流程引用关系，后续依次记录每个流程的执行状态。

### 1.1 YAML Header（任务元信息）

每个 todo-flow 文件必须以 YAML header 开头，用于存储任务的基本元信息，便于 CLI 工具快速检索和展示。

**YAML Header 格式：**

```yaml
---
task-id: TASK-YYYYMMDD-{task-name}
session-id: session_YYYYMMDDHHMMSS_xxxxxxxx
summary: {任务摘要描述}
status: {任务状态}
create-time: YYYY-MM-DD HH:MM:SS
---
```

**字段说明：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| task-id | string | 是 | 用户可读任务标识，格式：TASK-YYYYMMDD-{task-name}；本地目录名仍使用它 |
| session-id | string | 是 | 本次 task init 生成的任务会话标识，格式：session_YYYYMMDDHHMMSS_xxxxxxxx；老任务没有该字段时按 default session 兼容 |
| summary | string | 是 | 任务摘要，简短描述任务目标 |
| status | string | 是 | 任务状态：执行中/已完成/已取消/阻塞 |
| create-time | string | 是 | 创建时间，格式：YYYY-MM-DD HH:MM:SS |

**示例：**

```yaml
---
task-id: TASK-20260316-user-auth
session-id: session_20260316103000_a1b2c3d4
summary: 实现用户认证功能
status: 执行中
create-time: 2026-03-16 10:30:00
---
```

### 1.2 多流程设计

一个 todo-flow 文件可以包含多个流程状态：

```
Flow 0: Flou 工作流程（始终存在）
├── Flow 1: 任务流程（在"执行"阶段启动）
│   ├── Flow 2: 子流程（可选）
│   └── ...
└── ...
```

**流程层级关系：**
- **Flow 0**：Flou 工作流程（初始化→澄清→执行→小结→归档），始终存在
- **Flow 1**：任务流程（SDD/TDD/多仓开发等），在"执行"阶段启动
- **Flow N**：子流程，按需启动

### 1.3 为什么需要多流程？

- **工作流程管理**：Flou 需要知道当前处于哪个交互阶段
- **任务流程跟踪**：用户任务有独立的执行流程
- **状态隔离**：不同流程的状态互不干扰
- **嵌套支持**：任务流程可以启动子流程

### 2.4 关键决策列表区

记录执行过程中影响方案、范围、验收或风险的关键决策，尤其是开发执行、测试反馈、Troubleshooting 后导致的方案变更。

```markdown
### 关键决策列表

| 时间 | 来源 | 决策 | 原因/依据 | 影响范围 | 关联文档 | 确认状态 |
|------|------|------|-----------|----------|----------|----------|
| 2026-03-08 11:20 | Troubleshooting | 将 Session 存储从内存改为 Redis | 压测发现多实例登录态不一致 | 数据模型、部署依赖、验收标准 | [design.md](./docs/design.md#方案变更记录), [requirement.md](./docs/requirement.md#方案变更影响) | 已确认 |
```

**更新要求：**
- 方案变更时必须新增或更新关键决策记录，不能只更新阶段 checkbox。
- 关联文档需同时指向 `./docs/design.md` 和 `./docs/requirement.md` 的相关段落。
- 未经用户确认但影响验收口径的决策，确认状态标记为“待确认”，并同步加入待确认事项。

## 四、流程状态规范

### 4.1 状态标识

| 标识 | 含义 |
|------|------|
| ✅ 完成 | 阶段已完成 |
| 🔄 进行中 | 阶段正在执行 |
| ⏳ 待执行 | 阶段尚未开始 |
| ❌ 阻塞 | 阶段遇到阻塞 |
| ⏸️ 暂停 | 阶段暂停执行 |

### 4.2 流程状态

| 状态 | 含义 |
|------|------|
| 待启动 | 流程已引用但未开始 |
| 执行中 | 流程正在执行 |
| 已完成 | 流程已完成所有阶段 |
| 已取消 | 流程被取消 |

### 4.3 流程切换规则

1. **子流程启动**：父流程进入"等待子流程"状态
2. **子流程完成**：父流程恢复执行
3. **流程切换**：更新"当前活跃流程"

## 五、门禁校验

### 5.1 门禁校验机制

研发流程各阶段设有门禁条件，需通过校验才能进入下一阶段。门禁校验使用 `sub-agent` 执行，通过对比 todo-flow 文件和日志文件来评估进度一致性。

### 5.2 使用 sub-agent 进行门禁校验

```bash
# 门禁校验命令
flou-cli sub-agent exec analyze "读取 todo-flow 文件 {todo-flow路径} 和日志文件 {log路径}，评估进度是否一致，给出下一步建议"
```

**示例：**

```bash
# 评估任务进度
flou-cli sub-agent exec analyze "读取 /path/to/.flou/tasks/TASK-20260317-user-auth/todo-flow.md 和 /path/to/.flou/logs/TASK-20260317-user-auth.jsonl，评估进度是否一致，给出下一步建议"
```

### 5.3 校验输出格式

sub-agent 会输出以下内容：

```markdown
## 进度评估

**todo-flow 当前状态**: {阶段} - {节点}
**日志记录最新状态**: {最后操作}

**一致性检查**:
| 检查项 | 状态 | 说明 |
|--------|------|------|
| 阶段匹配 | ✅/❌ | {说明} |
| 节点匹配 | ✅/❌ | {说明} |
| 时间一致性 | ✅/❌ | {说明} |

**结论**: 进度一致/存在差异

**下一步建议**: {具体建议}
```

### 5.4 门禁校验结果处理

- **通过**：更新 todo-flow 状态，进入下一阶段
- **不通过**：记录阻塞原因，待解决后重新校验
- **进度不一致**：根据日志修正 todo-flow 状态

### 5.5 门禁校验记录

在 todo-flow 中记录门禁校验结果：

```markdown
#### 需求分析
- [x] 理解需求目标
- [x] 明确验收标准
- [x] 记录需求文档
- [x] 门禁校验: ✅ 通过 (2026-03-08 10:10)

**门禁校验记录**: sub-agent 确认需求分析完成，可进入方案设计阶段
```

## 六、更新规范

### 6.1 更新时机

- 进入新阶段时
- 完成阶段任务时
- 启动子流程时
- 用户确认时
- 遇到阻塞时
- 门禁校验时
- 开发执行、测试反馈或 Troubleshooting 导致方案变更时

### 6.2 更新内容

1. 更新流程引用表的状态
2. 更新当前流程的阶段进度
3. 更新阶段详情的 checkbox
4. 更新"当前节点"和"下一步"
5. 添加待确认事项（如需要）
6. 记录门禁校验结果
7. 方案变更时更新“关键决策列表”，并关联 `./docs/design.md` 与 `./docs/requirement.md` 的同步修改段落

### 6.3 更新示例

```
# 更新前
**当前节点**: 方案设计 - 设计数据结构
**下一步**: 完成 User 模型设计

# 更新后
**当前节点**: 方案设计 - 技术方案评审
**下一步**: 等待用户确认方案
```

## 七、文档管理

### 7.1 文档引用规范

每个阶段完成后，必须在阶段详情中引用相关文档：

```markdown
#### 需求分析
- [x] 理解需求目标
- [x] 明确验收标准
- [x] 记录需求文档
- [x] **文档引用**: [requirement.md](./docs/requirement.md)
```

### 7.2 文档清单

在流程状态区末尾添加文档清单，汇总所有文档状态：

```markdown
### 文档清单

| 文档 | 状态 | 路径 |
|------|------|------|
| 需求调研文档 | ✅ 已完成 | [requirement.md](./docs/requirement.md) |
| 需求确认记录 | ✅ 已完成 | [requirement-confirm.md](./docs/requirement-confirm.md) |
| 技术方案文档 | 🔄 进行中 | [design.md](./docs/design.md) |
| 技术评审记录 | ⏳ 待创建 | [design-review.md](./docs/design-review.md) |
```

### 7.3 文档状态标识

| 标识 | 含义 |
|------|------|
| ✅ 已完成 | 文档已创建并通过审阅 |
| 🔄 进行中 | 文档正在编写或修改中 |
| ⏳ 待创建 | 文档尚未创建 |
| ❌ 需修改 | 文档需要修改后重新审阅 |

### 7.4 方案变更文档同步

开发任务中若实现方案被调整，必须保持三类记录一致：

1. `./docs/design.md`：记录调整后的设计、变更原因、影响范围。
2. `./docs/requirement.md`：记录对需求范围、验收标准、验证结果、风险识别的影响。
3. `todo-flow.md`：在“关键决策列表”中记录决策来源、依据、关联文档和确认状态。

Troubleshooting 触发的方案变更应额外写明运行事实（失败用例、接口响应、logid、错误栈等）和根因摘要。

## 八、最佳实践

### 8.1 流程层级控制

- 最多支持 3 层嵌套
- 每层流程职责清晰
- 避免过度嵌套

### 8.2 状态同步

- 子流程状态变更时，同步更新父流程
- 保持流程引用表的准确性
- 及时更新"当前活跃流程"

### 8.3 文件大小控制

- 阶段详情保持简洁
- 详细信息记录在独立文件
- 归档记录定期清理

### 8.4 文档驱动

- 每个关键阶段必须输出文档
- 文档必须经过用户审阅确认
- 在 todo-flow 中及时更新文档引用和状态
- 开发方案修改必须同步设计文档、需求调研文档和关键决策列表，保证小结/归档可追溯

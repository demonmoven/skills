# PRD 技术方案评论修订

## 概述

PRD 生成技术方案流程的可选后续阶段。目标是在保留原文档结构、章节和未受影响内容的前提下，根据评审评论修订已创建的飞书/Lark 技术方案。这是定向修订，不是重新生成。

## 硬性规则

- 不得重新生成或新建文档。必须在已有文档和已有结构上操作。
- 只做解决评论所需的最小修改。保留章节顺序、标题、表格、图和未触达段落。
- 评论没有要求修改的内容不得删除。
- 如果评论含糊、与其他评论冲突，或涉及高风险资金/账户流，不得猜测，必须先问用户。
- 全文一致性修改（MUST）：当评论指出某个设计点不合理时，不能只改评论锚定的那一处。必须在全文检索所有相同/等价的设计点（同一字段、账户、流程节点、规则、接口、配置、结论、图示、表格行等），并按评论意见统一修改所有命中处，避免"改一处、漏多处"导致文档自相矛盾。
- 不修改评论本身（MUST）：只修改文档正文内容，不得改写、删除、解决或回复评论线程本身（除非用户明确要求 reply/resolve）。评论锚定引用的原文可以按意见修改，但评论文本（reviewer 的话）与评论状态保持不动。

## 输入

- 目标文档：飞书/Lark `docx`/`doc` URL、知识库 URL 或 doc token。如果用户只说“最新技术方案”，复用上一轮 `prd-tech-design` 生成的文档链接。
- 可选：用户指定优先处理的评论或说明。若未指定，默认处理全部未解决评论。

## 工作流程

### 1. 定位文档并读取当前内容

- 如果输入是知识库 URL，先解析真实 `docx`/`doc` token。
- 使用 `lark-doc` skill 读取当前文档内容；可用时保留 block ID，方便精确编辑。

### 2. 收集评论

- 使用 `lark-drive` skill 读取未解决评论：
  - `lark-cli drive file.comments list --params '{"file_token":"<token>","file_type":"docx","is_solved":false}'`
  - 如果某条评论 `has_more=true`，使用 `drive file.comment.replys list` 拉取完整回复。
- 将每条评论映射到锚定的章节/block（使用引用文本、选中文本或 `anchor.block_id`）。
- 构建修订清单：`评论 -> 定位 -> 修改意图 -> 是否涉及资金流/账户 -> 同点全文命中清单 -> 处理方式`。
- For每条「设计不合理」类评论，先抽象出被否定的设计点（字段/账户/流程节点/规则/接口/配置/结论/图示），再全文检索所有相同或等价表述（正文、表格行、流程图/时序图节点、伪代码、改动点分析、待确认事项等），列出全部命中位置，作为本条评论的统一修改范围。

### 3. 确认高风险或含糊评论（必须）

- 如果评论不清楚、与其他评论矛盾，或会改变资金流、账户、结算路径、金额、时点等事实，必须停止并先问用户。
- 用户确认修改意图后才能继续。

### 4. 执行定向修改

- 使用 `lark-doc` skill 的 update/replace/insert 能力，只修改受影响 block。
- 按评论统一修改全部同点命中处：对每条评论，遍历第 2 步列出的同点全文命中清单，按同一意见修改所有命中位置（含表格、流程图/时序图、伪代码、改动点分析、待确认事项），不得只改锚定处。修改完成后做一次全文一致性回扫，确认无遗漏、无前后矛盾。
- 只改正文，不动评论：仅编辑文档正文 block，不改写/删除/解决评论本身。
- 当评论质疑技术事实时，必须重新使用 `llm-wiki-git query "<问题>"`，按 `Module/System -> Scenario -> PlatformCapability -> Application -> Data/Implementation -> Source -> RawRef` 检索 Wiki，并结合代码证据核验；修订正文中按 PRD/Wiki/历史方案/代码/推断/待确认等标签补充证据。
- 保持证据纪律：不得虚构 owner、日期、QPS 或 URL。
- 修改引入或变更资金流时，必须同时更新资金流分析和信息流分析；修改内部实现时，必须精确到代码逻辑（PSM/文件/函数/分支/配置 + 改动前后逻辑），复杂流程使用流程图/流程图 diff，不用伪代码；修改流程或配置时，同步更新流程图/时序图并标注 diff。
- 保持 `待确认事项` 准确：移除已被修订解决的项，补充评论新增的待确认项。

### 5. （可选）回复或解决评论

- 只有用户明确要求时，才使用 `lark-drive` skill 回复或解决评论。
- 默认不处理评论状态，由评审人自行解决；只报告每条评论对应的正文修改。

## 输出

返回：

- 同一个文档 URL/token（不变，不新建文档）。
- 修改日志：逐条评论说明改了什么、改在什么位置。必须列出该评论触发的所有同点修改位置，不只列锚定 block。
- 未处理评论及原因。
- 未解决 `待确认` 项，包括仍需用户或评审人决策的内容。

## 起草检查清单

- 业务目标尽量沿用 PRD 表述；技术目标从系统职责角度重写。
- 改动跨 PSM 或跨领域时，补充业务流程、系统时序和依赖图。使用 `prd-sequence-diagram` 生成时序/流程图，明确核心业务动作、参与方、分支和 diff 标记。
- 涉及资金流新增或修改时，必须同时填写「资金流分析」和「信息流分析」，不得只写其一。包含账户级流转、biz code、fund-driven type、来源到下游字段链路和证据。
- 使用 `prd-funds-flow-diagram` 生成资金流图，确保每个动作都识别主体、待结算户/现金户/垫资户等账户、借贷方向、金额来源、是否真实动账、biz code/fund type 和代码证据。
- 「系统内部实现分析」必须精确到代码逻辑变更：引用 PSM/文件/函数/分支/配置，并描述改动前后逻辑。逻辑复杂（新增分支、状态流转、账户决策、循环/并发、幂等、跨 PSM 编排）时，使用流程图/流程图 diff，不用伪代码。流程图必须突出资金流金额赋值和信息流字段改动。
- 改动影响流程或配置时，必须提供图形化变更 diff（时序/流程）：标注新增/修改/删除节点、调用、分支、配置，或提供变更前/后图和差异表。不要只给最终态全量图。
- RPC/HTTP/面向商户 API 或 IDL 字段变化时，必须写接口设计。
- 表、schema、索引或存储内容变化时，必须写数据模型设计。
- 新增或修改 MQ/event 流程时，必须写消息设计。
- 新增 Redis/本地缓存，或 key/TTL/淘汰策略变化时，必须写缓存设计。
- 风险章节不得留空。没有证据时写 `不涉及，原因：...` 或 `待确认：...`。
- 改动点分析必须先给「功能点 -> 仓库/接口/链路」映射表，再给「按类型分类的具体改动」表：每个功能点都要落到具体代码仓库（PSM/repo）、改动接口（RPC/HTTP/IDL）与受影响链路；每条具体改动按 接口/逻辑/配置/数据/消息/缓存/任务 分类，并带文件/函数/分支/配置级代码定位与新增/修改/无需改动/待确认结论。
- 技术方案必须保留功能点 ID、能力域和能力变化类型。每个确定性设计点都能追溯 `PRD 来源 -> 业务动作 -> 能力域 -> 功能点 ID -> 代码证据 -> 设计决策`。
- 只有 evidence table 中 `confirmed` 且有代码证据的 claim 可以作为确定性改动点；只有 Wiki/历史方案线索的内容进入待确认或风险。
- 计费/结算方案必须写清能力边界，以及明细生成、聚合/汇总、凭证/账务、资金操作、对账分别归属哪个 PSM。

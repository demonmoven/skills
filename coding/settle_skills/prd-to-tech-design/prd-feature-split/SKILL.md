# PRD 功能点拆分

## 概述

PRD 生成技术方案流程的第二阶段。该阶段不是纯 PRD 文本拆分，而是“需求理解后的系统现状调查 + 功能点拆分”阶段：先使用 `llm-wiki-git query "<问题>"` 作为子 skill 检索系统现状、能力边界和历史方案，再按 Wiki 线索回查代码/配置/接口，最后将需求拆成可驱动技术方案生成的功能点。

## 输入与本地产物

- 输入必须优先读取 `prd2tech/<需求目录>/prd-understand.md`。如果该文件经过用户微调，以微调后的内容作为功能拆分事实输入。
- 功能拆分必须消费 `prd-understand.md` 中的「业务场景模型」和「业务动作候选」。如果旧文件没有这些章节，先从业务流程与规则中补齐动作列表，再继续。
- 本阶段必须把 `llm-wiki-git query "<问题>"` 作为子 skill 使用，按 `Module/System -> Scenario -> PlatformCapability -> Application -> Data/Implementation -> Source -> RawRef` 先检索现有能力、系统边界、历史方案、候选 PSM 和代码阅读路径。不得在未检索 Wiki/现状的情况下直接产出正式功能点拆分。
- 本阶段必须进行必要的代码/配置/接口检索，用来把 Wiki 线索校正为当前仓库事实。Wiki 是线索和阅读路径，代码/配置/IDL 是最终事实。
- 输出必须写入两个本地产物：
  - `prd2tech/<需求目录>/investigation.md`：Wiki 命中、Source/raw 证据、系统现状、代码/配置/接口初步证据、未知项、需代码确认清单。
  - `prd2tech/<需求目录>/prd-feature-split.md`：基于 `investigation.md` 的正式功能点拆分。
- 如果用户要求“基于功能点拆分结果微调后重跑”，必须优先读取已有 `prd-feature-split.md`，保留用户调整后的功能点、边界、结论和备注，只重算后续调查、绘图和技术方案生成。
- 不要把多个 PRD 的功能点拆分写到同一个目录；每个需求一个 `prd2tech/<需求目录>/` 子目录。

## 必须使用 llm-wiki-git 子 skill

本阶段必须先执行知识库查询，再做功能点拆分：

1. 读取 `prd-understand.md` 中的需求摘要、范围、待确认问题和资金流阻塞结论。
2. 对每个非阻塞待确认问题，先用 `llm-wiki-git query "<问题>"` 查询现有能力、历史方案、应用职责和 Source/raw 证据；能通过 Wiki/Source/代码低成本确认的，不要先问用户。
3. 查询问题必须围绕 PRD/功能点/待确认问题组织，包含场景、业务动作、资金/账户疑问、接口/字段/PSM 线索，并明确希望区分 `已有能力复用`、`本次需要增强`、`本次需要新增`、`无需改动` 或 `待确认`。
4. 语义检索路径必须遵循 `Module/System -> Scenario -> PlatformCapability -> Application -> Data/Implementation -> Source -> RawRef`。落地读取时可从 `REGISTRY` 和注册分册定位文件，但不得用临时关键词搜索替代 `llm-wiki-git query` 的完整路径。
5. 查询后必须结合代码/配置/接口做初步核验，至少定位候选仓库、入口接口、关键配置/XML/IDL/常量/函数。若涉及 `settle_center`，还必须运行 `settle-center-recognition`。
6. 调查必须以功能点 ID 为主键组织证据。若功能点 ID 尚未最终确定，先基于业务动作生成临时 ID（F001...），再在功能点矩阵中固化。
7. 输出 `investigation.md`，作为功能点拆分的依据。`prd-feature-split.md` 必须引用或声明其依赖 `investigation.md`。

`investigation.md` 必须包含：

- 实际执行的 `llm-wiki-git query "<问题>"` 查询问题列表。
- 按 `Module/System -> Scenario -> PlatformCapability -> Application -> Data/Implementation -> Source -> RawRef` 组织的检索路径和命中情况。
- 命中的场景/能力/应用/映射。
- 相关历史方案和可复用决策。
- 候选 PSM/仓库。
- Source/raw 证据列表。
- Wiki 推导出的假设和未知项。
- 代码/配置/接口初步核验证据。
- 按功能点 ID 输出的 evidence table。
- 建议的代码检索关键词。
- 明确的 `需代码确认` 清单。
- 对每个待确认问题的处理结论：`Wiki/代码已确认`、`仍需用户确认`、`保留待确认但不阻塞` 或 `资金流待确认（阻塞）`。

Evidence table 格式：

| 功能点 ID | Claim | Wiki 线索 | 代码证据 | 验证状态 | 置信度 | 是否可进入技术方案 | 说明 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| F001 |  | 页面/Source/历史方案 | repo/path/file.go:function 或 XML/IDL/配置/表 | confirmed/contradicted/not_found/pending | high/medium/low | yes/no |  |

- `confirmed` 且有代码证据的改动点才可以进入技术方案的确定性改动。
- `pending`、`not_found` 或只有 Wiki 线索的项只能进入 `待确认事项`、`风险` 或 `调查不足`，不得包装成最终方案。
- 如果 Wiki 与代码冲突，以代码为准，并在说明中记录冲突。

## 核心拆分模型

功能点拆分不是把 PRD 段落改写成列表，而是把 `prd-understand.md` 中的业务事实翻译成系统能力变化。按以下路径拆分：

```text
结构化 PRD 理解
  -> 业务场景
  -> 业务动作
  -> 能力域
  -> 系统能力功能点
  -> Wiki/代码调查任务
```

本阶段不得直接编造代码改造结论。输出是后续 Wiki 检索、代码调查和技术方案生成的路线图：系统可能需要哪些能力、能力是新增/扩展/复用/编排/配置/兼容/观测/补偿、哪些事实必须由代码验证。

## 能力域

将每个业务动作映射到一个或多个能力域：

| 能力域 | 说明 |
| --- | --- |
| 接入能力 | RPC/HTTP/API/消息入口、IDL 字段、请求响应模型 |
| 准入校验能力 | 商户、订单、场景、状态、权限、风控/合规校验 |
| 规则决策能力 | 账户选择、路由选择、策略判断、命中条件 |
| 金额计算能力 | 金额拆分、费用计算、币种、税费、优惠/补差 |
| 流程编排能力 | 状态机、BP/XML/workflow、任务流、执行阶段 |
| 资金处理能力 | 资金明细、记账、转账、退款、结算、汇总/凭证边界 |
| 数据持久化能力 | 表、字段、索引、状态、幂等记录、审计记录 |
| 下游集成能力 | RPC/MQ/HTTP 调用、回调、离线产出 |
| 配置灰度能力 | TCC、白名单、规则配置、开关、发布灰度 |
| 查询运营能力 | 查询接口、运营后台、对账/报表、客服可见信息 |
| 异常补偿能力 | 重试、冲正、补偿任务、人工处理、幂等恢复 |
| 可观测能力 | 日志、指标、报警、trace、资损核对 |

## 能力变化类型

每个功能点必须标记能力变化类型：

| 类型 | 含义 |
| --- | --- |
| 新增能力 | 当前系统没有，需要新增完整能力 |
| 扩展能力 | 当前已有类似能力，需要新增分支、参数、规则或账户/金额口径 |
| 复用能力 | 当前已有能力可直接复用，只需接入或配置 |
| 编排能力 | 底层能力不变，调整流程顺序、条件、依赖或阶段 |
| 配置能力 | 通过配置、规则、白名单、开关控制 |
| 兼容能力 | 为老接口、老数据、老流量、上下游发布顺序保留行为 |
| 观测能力 | 增加日志、指标、报警、资损核对 |
| 补偿能力 | 增加失败、重试、冲正、人工处理或恢复机制 |

如果 `llm-wiki-git` 查询没有直接命中需求专题，也必须记录“未直接命中”，并继续利用系统/能力/应用/历史 Source 的现状信息作为拆分依据；不得因为关键词未命中就跳过 Wiki 阶段。

## 拆分规则

- 按业务能力和实现归属拆分，不按 PRD 段落顺序机械拆分。
- 先从 `prd-understand.md` 的「业务场景模型」和「业务动作候选」抽取业务动作，再映射能力域；如果理解文件没有该表，先从业务流程与规则中补齐动作列表。
- 拆分必须基于 `investigation.md` 中的系统现状和代码初步证据，不能只基于 PRD 原文。
- 查询/只读能力与写入/状态变更能力分开。
- 同步请求链路、异步任务链路、消息/回调链路、离线/对账链路分开。
- 计费/结算需求中，计价/计费、分账、结算明细生成、周期汇总、凭证/账务、退款/退结算、通知、对账应分开分析。
- 每个功能点必须标记能力变化类型，并给出 `已有能力复用`、`本次需要增强`、`本次需要新增`、`无需改动` 或 `待确认` 结论。
- 一个 PRD 规则影响多个能力域时必须拆开，例如“指定账户退款”通常至少拆为接入识别、准入校验、账户决策、金额计算、资金明细生成、流程编排、灰度配置。
- 多个 PRD 规则落到同一系统能力时可以合并，例如商户白名单和订单场景限制可合并为准入校验能力。
- 涉及资金方向、账户、金额口径、结算时点、是否真实动账的内容必须单独拆成资金/账户相关功能点，不能隐藏在“流程改造”里。
- 灰度、幂等、补偿、监控、查询/运营可见性如果影响落地或风险控制，应拆成独立能力点。
- 每个功能点必须带调查任务，且调查任务要能直接驱动 Wiki 检索和代码搜索。
- 对每个功能点给出结论依据：PRD 事实、Wiki/Source 线索、代码/配置/接口证据、用户确认或待确认项。

## 资金流阻塞门禁（必须）

功能拆分经常会暴露 PRD 未明确说明的资金/账户影响。当某个功能点的资金流影响既重要又不确定时，必须先用 `llm-wiki-git query "<问题>"` 和代码/配置/接口检索尝试确认现状；检索后仍不确定且会影响账户/路径/金额/时点/是否动账时，必须停止并先向用户确认，不能继续方案设计。

- 如果错误理解会改变借贷账户、退款/退结算路径、付款方/收款方、会计主体、金额/币种、结算时点或是否真实动账，则属于阻塞问题。
- 在 `结论` 列标记 `资金流待确认（阻塞）`，列出候选理解，并使用 `AskUserQuestion` 或直接阻塞式提问获取用户明确决策。
- 存在阻塞资金流问题时，可以输出 `investigation.md` 和草稿拆分，但不得输出“可进入方案生成”的最终功能矩阵。用户确认后再更新 `prd-understand.md`、`investigation.md` 和 `prd-feature-split.md`。
- 低风险不确定点可以保留为 `待确认`，并带明确假设继续。

## settle_center 识别门禁（必须）

如果 PRD 或 Wiki/代码检索结果表明任一功能点涉及 `settle_center`（结算、退结算、分账、独立结算、补差、账户决策，或 PSM `caijing.bytepay.settle_center`），在写该功能点改动分析前必须先运行 `settle-center-recognition` skill。使用其输出填充 `候选 PSM`、`触发场景`、`输入/条件`、资金流和信息流列：

- 端内/端外商户判断，以及准确入口接口。
- 命中的 `conf/mapping/**` `<condition>` 和最终执行的 `conf/product/**` XML 流程。

不得仅凭 LLM Wiki 或名称相似性断定 XML 流程；执行流程由 conf/mapping 条件决定，并以代码/配置确认为准。

## 改动点定位（必须）

每个功能点都必须从功能点推进到具体代码目标。不要停留在候选 PSM，需要识别受影响仓库、改动接口和调用链路，再按类型拆分具体改动。该结果用于最终技术方案的「改动点分析」。

与功能点矩阵同时产出以下定位表。若当前只有 Wiki 线索而代码证据不足，可暂填 `待定位/待确认`，但必须在 `investigation.md` 的 `需代码确认` 清单中列出；进入最终方案前必须用代码证据确认：

| 功能点 | 改动仓库（PSM/repo） | 改动接口（RPC/HTTP/IDL 方法） | 受影响链路（入口->编排->下游->持久化/消息） | 涉及改动类型 | 结论 |
| --- | --- | --- | --- | --- | --- |
|  | 待定位 | 待定位 | 待分析 | 接口/逻辑/配置/数据/消息/缓存/任务 | 待确认 |

- 改动类型至少覆盖：接口（RPC/HTTP/IDL）、业务逻辑、配置（conf/mapping/XML/tcc/开关）、数据（表/索引/字段）、消息（MQ/事件）、缓存、任务（定时/异步）。
- 一个功能点可能命中多个仓库或多种改动类型；分别列出，不要合并。
- 这是定位清单，不是最终方案结论：仓库/接口/链路必须由代码/配置/IDL 证据确认后才可作为最终改动点。
- 功能点 ID 必须与「业务动作到能力域映射」和「功能点矩阵」保持一致，后续 investigation 和技术方案都以该 ID 追踪证据。

## 输出

输出写入 `prd2tech/<需求目录>/prd-feature-split.md`，文件必须包含：

- 前置 Wiki/代码调查摘要（引用 `investigation.md`）。
- 业务动作到能力域映射。
- 功能点矩阵。
- 调查任务清单。
- 改动点定位表（功能点 -> 仓库/接口/链路/改动类型）。
- 候选业务链路。
- 候选系统调用链路。
- 候选资金流。
- 候选信息流。
- Wiki/代码检索关键词。
- 候选 PSM/仓库。

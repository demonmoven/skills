# PRD 需求理解

## 概述

PRD 生成技术方案流程的第一阶段。目标是产出结构化需求摘要，并识别是否存在必须先确认的阻塞问题。

## 工作流程

1. 准备工作目录。
   - 在当前工作目录下创建或复用 `prd2tech/<需求目录>/`。
   - `<需求目录>` 优先使用 PRD 标题或项目名生成可读短名；无法确定时使用文档 token、需求编号或时间戳兜底。
   - 如果目录中已有 `prd-understand.md`，且用户表达“基于本地结果微调/重跑/继续”，优先读取该文件作为当前需求理解输入，不要用旧 PRD 解析结果覆盖用户修改。

2. 读取 PRD 输入。
   - 飞书/Lark 知识库 URL 需要先解析 wiki token，再读取真实对象 token。
   - 飞书/Lark 文档使用 `lark-doc` skill，必要时使用用户身份读取。
   - 飞书/Lark PRD 必须同时读取文档评论和回复：使用 `lark-drive` 的 comments list/reply 能力获取未解决评论；如需求结论可能受已解决评论影响，按上下文读取相关已解决评论。
   - 本地文件若附带评论导出、评审意见或用户补充说明，也必须作为 PRD 输入一起读取。
   - 本地文件直接读取。

3. 合并正文和评论，形成 PRD 最终结论。
   - PRD 正文和评论/回复共同作为需求理解输入，不得只读正文。
   - 如果评论与正文内容冲突，以评论/回复中的最新明确结论为准。
   - 如果多条评论互相冲突，或评论表述含糊且会影响正确设计，必须列为待确认；涉及资金流则进入资金流阻塞门禁。
   - 已被评论明确否定的正文表述，不得作为产品事实进入需求摘要；可以在“正文与评论冲突处理”中记录为被覆盖项。
   - 产品原文、评论结论、技术推断必须分开，不要把推断写成产品事实。

4. 提取结构化需求摘要和可拆分需求模型。
   - PRD 标题、负责人（如有）、关联文档、目标用户/参与方。
   - 业务背景和目标。
   - 范围内/范围外边界。
   - 核心业务场景、触发条件、参与方、入口和预期结果。
   - 可抽取的业务动作，例如受理、校验、决策、计算、生成明细、编排、执行、持久化、通知、查询、灰度、补偿。
   - 状态变化、资金/账户影响、信息流、接口、消息、数据/存储、上线约束和非功能要求。
   - 对每个受评论影响的结论，标明来源是正文、评论或正文+评论一致。
   - 本阶段不要直接给技术改造点或代码方案，只输出后续功能拆分需要的业务事实和待验证假设。

5. 判断是否需要提问。
   - 只有缺失信息会阻塞正确设计时才提问。
   - 能从 PRD、LLM Wiki 或代码中低成本确认的事实，不要先问用户。
   - 每轮问题尽量不超过 5 个，并按决策影响分组。
   - 如果用户要求先继续，必须带明确假设和 `待确认` 标记。

6. 写入本地阶段产物。
   - 必须将需求理解结果写入 `prd2tech/<需求目录>/prd-understand.md`。
   - 写入后再进入功能点拆分阶段。
   - 如果是重跑且用户已经微调该文件，只更新需要重算的内容，不要丢失用户补充的事实、约束、待确认结论和备注。

## 资金流阻塞门禁（必须）

有些资金流不确定点不能仅标为 `待确认` 后继续。当资金流问题既重要又不确定时，必须停止后续阶段并先询问用户。

- 如果错误理解会改变借贷账户、退款/结算路径、付款方/收款方、会计主体、金额/币种、结算时点或是否真实动账，则属于阻塞问题。
- 出现阻塞问题时，不得继续功能拆分或方案设计。必须显式标注 `资金流待确认（阻塞）`，列出候选理解，等待用户明确决策。
- 使用 `AskUserQuestion` 或直接提出阻塞问题，避免流程静默推进。
- 非资金类、且不满足阻塞标准的问题，可以带明确假设继续，并标注 `待确认`。

## 澄清门禁

以下信息缺失且会阻塞正确设计时，需要先提问：

- 业务场景不清：触发方式、产品入口、商户/用户/订单类型。
- 范围边界不清：地区、渠道、支付方式、商户类型、结算类型、业务线。
- 成功标准缺失：预期产物、状态变化、时效、SLA、对账或风控目标。
- 资金/会计行为不清：借贷账户、退款路径、结算时点、付款方/收款方、会计主体、是否真实动账。
- 集成目标缺失：上下游系统、API、消息 topic、回调、离线表或配置负责人。
- 兼容/灰度约束缺失：影响存量流量、字段、存储、消息或规则时必须明确。

## 输出

输出：写入 `prd2tech/<需求目录>/prd-understand.md`，并在对话中简要说明文件路径、是否存在阻塞问题、是否可以进入功能点拆分。

如果存在 `资金流待确认（阻塞）`，必须优先报告并停止后续流程，直到用户确认。

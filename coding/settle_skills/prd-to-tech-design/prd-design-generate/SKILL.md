# PRD 技术方案生成

## 概述

PRD 生成技术方案流程的最终阶段。将结构化调查结果整理成中文技术方案，并创建飞书/Lark 文档。

## 必读参考

- 读取 `../prd-tech-design/references/tech-design-template.md` 获取章节模板。
- 创建飞书文档前读取 `../prd-tech-design/references/feishu-delivery.md`。
- 读取当前需求目录 `prd2tech/<需求目录>/` 下的阶段产物：`prd-understand.md`、`prd-feature-split.md`、`investigation.md`。如果用户微调过前两阶段文件，以本地文件内容为准。
- 技术方案必须消费 `prd-feature-split.md` 中的业务动作到能力域映射、功能点 ID、能力变化类型和调查任务，以及 `investigation.md` 中按功能点 ID 组织的 evidence table。
- 起草包含业务流程图或系统时序分析的章节前，先使用 `prd-sequence-diagram`。
- 起草 `资金流分析` 前，先使用 `prd-funds-flow-diagram`，并用其字段链路输出生成配套 `信息流分析`。
- 创建或编辑 Lark 文档时使用 `lark-doc` skill。

## 起草规则

- 默认输出中文。
- 先起草 Markdown，再由 Markdown 创建飞书/Lark 文档。
- 仍有假设时必须包含 `待确认事项`。
- 证据引用使用简洁标签：PRD、Wiki、历史方案、代码、推断、待确认。
- 每个技术改造点必须带 `代码` 证据（文件/函数/分支/配置）。Wiki/历史方案可以补充背景，但不能替代代码证据。不得输出仅由 Wiki 阅读推导出的改动点。
- 每个确定性改动点必须能追溯：`PRD 来源 -> 业务动作 -> 能力域 -> 功能点 ID -> 代码证据 -> 设计决策`。如果某个改动无法串起这条链路，只能写入 `待确认事项` 或 `风险`。
- 从 `investigation.md` 的 evidence table 读取 `是否可进入技术方案`。只有 `yes` 且有代码证据的 claim 可以作为确定性实现结论；`pending/not_found/只有 Wiki 线索` 的 claim 不得写成已确定设计。
- 不虚构负责人、排期、QPS、容量、监控 URL 或评审人，缺失时标记 `待补充`。
- 计费/结算方案中，要区分产品流、系统调用链、资金/账务流、信息/数据流。
- 绘图子 skill 的输出是正式设计内容，不是附录。时序图写入 `业务流程分析` / `业务流程系统时序分析`，资金流图写入 `资金流分析`，并配套 `信息流分析`。
- 技术方案草稿必须写入 `prd2tech/<需求目录>/tech-design.md`，再基于该文件创建飞书/Lark 文档。
- 如果是重跑流程，必须先说明从哪些本地阶段产物恢复，并只重算受影响的后续内容；不要覆盖用户已经微调的 `prd-understand.md` 和 `prd-feature-split.md`。

## 强制细节规则

- 资金流与信息流配套（资金流改动/新增时）：当本次设计涉及资金流的改动或新增，必须按模板同时填充「资金流分析」与「信息流分析」两个小节，不得只填其一。资金流标注账户流转/记账方向/biz code/资金驱动类型的差异；信息流描述关键字段从来源 -> 决策/派生 -> 持久化 -> 下游的链路及新增/变更字段兼容性。
- 时序图子 skill 必须调用：当本次设计涉及业务流程、系统调用、BP/XML 编排、异步消息、配置路由或判断分支时，先使用 `prd-sequence-diagram` 生成时序图。图中必须明确核心业务动作 action、参与方 participant、判断逻辑分支、同步/异步边界、异常/补偿分支，并用 `+`/`~`/`-` 标注本次新增/修改/删除。
- 资金流图子 skill 必须调用：当 PRD 或代码涉及资金移动、记账/明细生成、账户决策、退款/结算/扣费、汇总/凭证、机构记账或任意账户影响时，先使用 `prd-funds-flow-diagram` 生成资金流图。图和表必须明确主体、待结算户/现金户/垫资户/手续费户/机构户等账户、借贷方向、金额来源、是否真实动账、biz code/fund type，并按动作说明不同主体在该动作下的资金变化。
- 系统内部实现分析精确到代码逻辑：「业务流程系统内部实现分析」必须定位到 PSM/文件/函数/关键分支或配置项，说明改动前后逻辑差异；逻辑复杂（新增分支、状态流转、账户决策、循环/并发、幂等处理、跨 PSM 编排）时，不用伪代码展示，必须使用流程图/流程图 diff 描述目标逻辑，并标注新增/修改/删除节点。
- 复杂流程图重点表达资金流金额赋值和信息流改动：资金流节点必须标注金额字段来源、赋值公式、币种、账户借贷方向、biz code/fund type；信息流节点必须标注来源字段 -> 决策/派生字段 -> 持久化字段 -> 下游传递字段，以及新增/变更字段的兼容性。
- 流程/配置改动给出图的 diff：当设计涉及流程或配置的改动时，必须给出流程图或时序图的「改动 diff」——在图上标注新增（+）/修改（~）/删除（-）的节点、调用、分支、配置项，或并排给出变更前/变更后两张图并附差异说明表；不要只给一张最终态全量图。
- 改动点分析按功能点驱动并分类列出：「改动点分析」必须先给出「功能点 -> 改动仓库（PSM/repo）-> 改动接口（RPC/HTTP/IDL）-> 受影响链路（入口->编排->下游->持久化/消息）」的映射表，再给出「按类型分类的具体改动」表（接口/业务逻辑/配置/数据/消息/缓存/任务）。每个功能点都要落到具体代码仓库与接口/链路；每条具体改动带文件/函数/分支/配置级代码定位与新增/修改/无需改动/待确认结论，纯 wiki 推断不得作为改动点。
- 功能点章节必须先展示「业务动作 -> 能力域 -> 功能点」映射，保留功能点 ID 和能力变化类型。后续系统实现、接口、数据、消息、风险、测试章节都应引用该功能点 ID，避免按仓库聚合后丢失需求来源。
- 对 `复用能力/无需改动` 的功能点，也要说明复用的现有代码证据；如果没有代码证据，只能标记 `待确认`。
- settle_center XML 流程编排改动给出完整可落地 XML（MUST/）：当改动涉及 settle_center（结算中心）的 conf/product 或 conf/mapping XML 流程编排（新增/修改流程、action、mapping 条件等）时，改动点分析必须给出完整的目标 XML 编排片段，而不是文字描述。至少包含：① 新增/修改的 `<action>` 完整属性（`name`、`actionType`、`assignFundOrder`、`executePhase`、`async`、`index` 等）；② 控制流条件（`<if test=...>`、`<product condition=...>`、mapping `<condition>` 表达式）；③ action 之间的依赖关系（`assignFundOrder` 指向的上游 action 名）与执行阶段（consult/confirm）；④ 在现有 XML 中的插入位置（参照已有同类流程文件）。需对照已存在的同类产品流程作为模板，并标注新增（+）/修改（~）/删除（-）。
- settle_center 同步受理 + 异步驱动资金流编排（MUST）：如果新增/修改的 settle_center XML 资金流 action 属于“同步受理、异步驱动”链路（例如 accept 阶段 `flowType=RPC_*_ACCEPT*`，execute 阶段 `flowType=RPC_*_EXECUTE_ASYNC`），则同步受理 XML 中也必须编排对应资金流的 consult 阶段，异步 execute XML 中再编排 confirm 阶段。不得只在 execute XML 中新增 confirm。设计时必须参考同类既有流程：`general_settle_refund_accept.xml` 在同步受理阶段先执行 `*_FUND_GEN` + `*_FUND_DRIVEN executePhase="consult"`，`general_refund_execute.xml` 在异步执行阶段复用 consult 结果并执行 `*_FUND_DRIVEN executePhase="confirm"`。目标 XML 需同时给出 accept/execute 两段片段，明确 consult action 与 confirm action 的 `assignFundOrder` 依赖。

## 设计自检门禁

起草 `tech-design.md` 前先自检，不通过则补调查或降级为待确认，不要硬写方案：

| 检查项 | 通过标准 |
| --- | --- |
| 功能点追踪 | 每个确定性改动点都有功能点 ID、业务动作、能力域和 PRD 来源 |
| 代码证据 | 每个确定性改动点都有文件/函数/IDL/XML/配置/表/常量证据 |
| Wiki 边界 | Wiki 只作为线索或背景，没有替代代码证据 |
| 资金流 | 账户、金额、时点、是否真实动账不确定时已阻塞或标为待确认 |
| 能力变化 | 每个功能点已标记新增/扩展/复用/编排/配置/兼容/观测/补偿 |
| 章节覆盖 | 接口、逻辑、配置、数据、消息、缓存、任务、风险、测试按影响范围覆盖 |

## 飞书交付

- 默认创建飞书文档，除非用户明确说不需要。
- 标题默认使用 `<PRD/项目名>技术方案`，除非用户指定标题。
- `lark-cli docs +create --markdown @file` 或当前 CLI 支持的等价参数需要当前目录下的相对路径；先把草稿写入 `prd2tech/<需求目录>/tech-design.md`，或切到该需求目录再执行。
- 如果创建被 keychain、权限或授权阻塞，保留本地 Markdown 草稿，并报告阻塞原因和路径。

## 输出

返回飞书文档 URL/token、保留的本地 Markdown 路径、简要覆盖范围，以及未解决的 `待确认` 项。

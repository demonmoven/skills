# 计费/结算需求改动系统判断

本 Skill 用于判断一个需求文档、需求描述或飞书需求链接需要改动哪些计费/结算系统/PSM。

本 Skill 不内置任何系统职责、关键词映射或链路判断。所有候选系统、职责边界、上下游、需求评估提示和判断依据，必须来自 Git-only LLM Wiki 知识库，尤其是：

```text
wiki/applications/
```

不得仅凭模型常识、通用支付/结算经验或本地业务代码仓库做 PSM 归因判断。

---

## 核心原则

1. **先确认知识库，再做判断**
   - 必须确认 `llm-wiki-git` skill 可用。
   - 必须识别 Git-only LLM Wiki 仓库。
   - 必须读取仓库内 `AGENTS.md`、`wiki/registry/REGISTRY.md` 和相关 `REGISTRY-*` 分册。

2. **候选系统来自知识库**
   - 候选系统应从 `wiki/registry/REGISTRY-Applications.md` 和 `wiki/applications/` 中发现。
   - 若用户或知识库限定了候选系统范围，则按该范围判断。
   - 若知识库未收录某系统的 Application 文档，不得凭空补全职责。

3. **Application 文档优先**
   - 本 Skill 的目标是判断改动系统/PSM，因此涉及 PSM 判断时，必须优先读取 `wiki/applications/`。
   - Application 文档是 PSM 职责判断的一手索引入口。

4. **需求文档重点看改动点、功能和方案**
   - 需求文档通常是飞书文档。
   - 如果用户输入需求文档链接，必须读取文档正文。
   - 判断改动系统时，优先分析：用户 prompt 中的改动点、范围、排除项；需求文档中的改动点 / 改动范围 / 影响范围；需求文档中的功能说明 / 产品方案 / 技术方案 / 实现方案。

5. **用户 prompt 与需求文档冲突时先确认**
   - 如果用户补充说明与需求文档存在明确冲突，不得直接裁决。
   - 必须暂停并让用户确认以哪个范围为准。

6. **先判定需求域，再收敛 PSM**
   - 判断 PSM 前必须先判定需求域，且默认输出的需求域只能在 `计费` / `结算` 中二选一。
   - 即使需求同时关联计费和结算，也必须按主要改动职责二选一归入 `计费` 或 `结算`，不得默认输出“混合”或“待确认”作为需求域。
   - 计费需求默认只输出计费相关系统；结算需求默认只输出结算相关系统。

7. **关联方不等于改动方**
   - 出现在资金流、上下游影响、协助联调、历史链路、数据消费方、账单展示方、账户参与方中的系统，不默认列为需要改动。
   - 只有同时满足以下条件，才能列为“需要改动”：需求文档的改动点 / 功能方案明确描述该系统职责范围内发生变化；知识库 Application 或 Source 能支撑该系统对该类变化负有主责。

8. **settle_faas 特殊规则**
   - 计费/结算领域的部分消息经 `settle_faas` 转发。
   - 即使需求域是计费/收费，只要改动点涉及接收、过滤、转发计费结算 MQ 消息，区分消息类型，新增/调整 topic，或 FaaS 触发入口，必须额外评估 `settle_faas` 的 Application/Source 中 MQ 消息处理逻辑。
   - 若知识库证据显示该消息入口或转发逻辑属于 `settle_faas`，应将 `settle_faas` 列为协同改动 PSM。

9. **证据不足不强判**
   - 没有证据时写“待确认”或“未检索到直接证据”。
   - 不能为了给答案而用经验补全。

10. **不直接读本地业务代码仓库**
    - 本 Skill 只读 LLM Wiki 仓库和必要的飞书原文。
    - 不读取业务代码仓库来判断系统归属。
    - 如果知识库未收录代码细节，只能写“待代码仓库核实”。

11. **自动推进只读检索**
    - 只读检索流程默认自动执行。
    - 不要中途询问“是否继续 / 是否读取 / 是否推进”。
    - 仅当知识库无法识别、`llm-wiki-git` 不可用、飞书认证失败、需求对象不足以识别，或用户 prompt 与需求文档存在明确冲突时，才停下询问。

## 前置检查

### 1. 检查 `llm-wiki-git` skill 是否可用

本 Skill 的判断依据来自 Git-only LLM Wiki，因此执行前必须确认 `llm-wiki-git` skill已安装且可用。

若不可用，停止执行并提示用户安装或启用 `llm-wiki-git`。

安装地址：
    
    https://code.byted.org/bytepay/settle_skill/tree/feature/ai_native/llm-wiki-git?ref_type=heads

规则：

- 未确认 `llm-wiki-git` 可用时，不得直接做 PSM 归因判断。
- 不得用模型常识、业务经验或本地代码搜索替代知识库判断。
- 如果 `llm-wiki-git` 缺失，应输出：`BLOCKED: llm-wiki-git 未安装或不可用`。

### 2. 识别 Git-only LLM Wiki 仓库

本 Skill 依赖计费/结算 Git-only LLM Wiki 知识库。仓库路径不得硬编码为某台机器的绝对路径，必须按以下顺序识别。

识别优先级：

1. 用户本次请求明确指定的知识库路径。
2. 当前对话上下文已确认的知识库路径。
3. 环境变量指定路径，依次检查：

```text
BYTEPAY_LLM_WIKI_REPO
CHARGE_SETTLE_LLM_WIKI_REPO
LLM_WIKI_REPO
```

4. 默认候选知识库路径，按顺序尝试：

```text
~/charge_settle_llm_wiki/
~/bytepay/charge_settle_llm_wiki/
~/code.byted.org/bytepay/charge_settle_llm_wiki/
```

识别条件：候选目录必须同时满足：

```text
raw/
wiki/registry/
wiki/INDEX.md 或 wiki/registry/REGISTRY.md
```

规则：

- 不做全盘扫描。
- 不得把业务代码仓库误识别为知识库仓库。
- 找到知识库后，必须先读取仓库内 `AGENTS.md` 与 `wiki/registry/REGISTRY.md`。
- 若无法识别知识库，停止执行并要求用户提供知识库路径；不得继续输出确认版 PSM 改动判断。

### 3. 读取仓库规则

识别知识库仓库后，必须优先读取：

```text
AGENTS.md
```

若存在该文件，必须遵守其中关于 raw 分类、Source 分类、Application 命名、PSM 归属、证据纪律、新增/更新阈值、query/import/ingest/lint 行为等规则。

仓库 `AGENTS.md` 中的规则优先于本 Skill 的通用流程。

### 4. 检查 `lark-cli` 是否可用

需求文档通常是飞书文档，且 raw 原文回查也可能需要读取飞书文档。因此在读取飞书文档前，必须检查 `lark-cli` 是否可用。

Step 1：检查 lark-cli

```bash
which lark-cli
```

如果 `lark-cli` 不存在，尝试安装：

```bash
npm install -g @larksuite/cli
```

安装完成后再次执行：

```bash
which lark-cli
```

如果仍不可用，停止读取飞书文档，并提示用户处理本地 `lark-cli` 安装问题。

Step 2：检查认证状态

```bash
lark-cli auth status
```

如果未认证，提示用户运行：

```bash
! lark-cli auth login
```

规则：

- 未安装 `lark-cli` 时，可以尝试自动安装。
- 未认证时，不要代替用户执行交互式登录；必须提示用户运行 `! lark-cli auth login`。
- `lark-cli` 不可用或未认证时，不得声称已读取飞书原文。
- 若飞书文档无法读取，只能基于用户粘贴内容或已存在知识库摘要做低置信度判断，并标记阻塞/待确认。
- 只有在需要读取飞书需求文档或 raw 飞书原文时，才执行 `lark-cli` 检查。

## 需求输入解析规则

需求输入可能包含用户 prompt 中的文字说明、飞书需求文档链接、用户粘贴的需求正文、用户补充的范围约束/排除项/判断重点。必须同时分析用户 prompt 和需求文档正文。

### 用户补充 Prompt 解析规则

当用户同时提供需求文档链接和额外 prompt / 文字说明时，必须同时分析飞书需求文档正文和用户本次输入中的额外 prompt。

从用户 prompt 中重点抽取：改动点、本次只看、重点关注、只涉及、不涉及、排除、忽略、以这个为准、新方案、旧方案不用看、新增、修改、删除、下线、迁移、切流、灰度、回滚、接口、字段、配置、MQ、定时任务、回调、同步、补偿、审批、工单、计费、收费、退费、结算、分账、核销、账单、报账。

处理规则：

1. 如果用户 prompt 明确给出了改动点，应将其作为 PSM 判断的首要输入之一。
2. 如果用户 prompt 只是泛泛提问，没有额外改动点，则仍以需求文档中的“改动点 / 功能 / 方案”章节为主。
3. 如果用户 prompt 与需求文档内容存在明确冲突，必须进入冲突确认流程。

### 需求文档读取规则

需求文档通常是飞书文档或飞书 Wiki 链接。若用户输入包含飞书需求文档链接，必须先只读读取文档正文，再进行系统/PSM 改动判断。

读取方式优先使用：

```bash
lark-cli docs +fetch --as user --doc <DOC_ID>
```

备用方式：

```bash
bytedcli --json feishu docs fetch-doc <URL_OR_DOC_TOKEN>
```

若飞书读取失败，应提示用户完成认证或提供文档内容，不得仅凭链接标题判断。

### 重点关注：改动点相关章节

读取需求文档后，必须优先定位并分析文档中的“改动点”相关章节，包括但不限于：改动点、改动范围、需求改动点、系统改动点、技术改动点、涉及系统、影响范围、改造点、方案改动、本期改动、研发改动点、接口改动、字段改动、配置改动、数据改动、定时任务改动、MQ 改动、上下游改动。

处理规则：

1. 如果文档中存在“改动点”相关章节，必须以该章节内容作为 PSM 判断的首要需求输入。
2. 如果背景/目标/需求描述和改动点存在差异，以改动点部分判断实际需要改哪些系统。
3. 不得只根据需求标题判断改动系统。

### 重点关注：功能 / 方案相关章节

很多需求文档不会显式写“改动点”，而是将实际改造内容写在功能说明或方案章节中。因此必须重点读取并解析功能 / 方案相关章节。

需要重点关注的章节标题包括但不限于：功能说明、功能需求、需求功能、功能点、产品功能、产品方案、业务方案、技术方案、实现方案、详细方案、设计方案、系统方案、流程设计、流程说明、业务流程、交互流程、处理流程、接口方案、接口设计、字段设计、数据方案、数据设计、配置方案、规则配置、规则说明、计费方案、结算方案、分账方案、收费方案、退费方案、对账方案、账单方案、任务方案、定时任务方案、MQ 方案、消息方案、回调方案、异常处理、补偿方案、灰度方案、上线方案。

处理规则：

1. 如果文档中存在功能 / 方案相关章节，必须把这些章节作为 PSM 判断的核心输入之一。
2. 重点从功能 / 方案章节中抽取新增或变更的业务流程、系统交互、接口、字段、配置、数据对象、MQ/定时任务/回调、计费/收费/退费/结算/分账/核销/账单/对账/报账逻辑。
3. 如果“改动点”章节缺失，但功能 / 方案章节明确描述了系统变化，应基于功能 / 方案章节形成改动系统判断。
4. 如果功能 / 方案章节只是业务目标描述，没有明确系统变化，应标记：`待确认：功能/方案章节未明确系统改动点。`
5. 不要把功能 / 方案章节中的业务目标直接等同于系统改动；必须结合 Application 职责证据判断。

### 需求输入解析优先级

当用户同时提供飞书需求文档和额外 prompt 时，按以下顺序解析：

1. 用户 prompt 中明确指定的改动点、范围、排除项、判断重点
2. 需求文档中的改动点 / 改动范围 / 影响范围
3. 需求文档中的功能说明 / 功能需求 / 功能点
4. 需求文档中的产品方案 / 业务方案
5. 需求文档中的技术方案 / 实现方案 / 系统方案
6. 需求文档中的接口 / 字段 / 数据 / 配置 / MQ / 定时任务 / 回调相关章节
7. 需求文档中的验收标准 / 上线范围 / 灰度方案
8. 需求文档中的背景 / 目标 / 价值说明

如果用户 prompt 与需求文档冲突，必须进入冲突确认流程。

## 用户 prompt 与需求文档冲突处理

当用户同时提供需求文档和额外 prompt 时，必须检查二者是否存在明确冲突。

明确冲突包括：改动范围冲突、系统范围冲突、方案版本冲突、改动动作冲突、上线范围冲突。

如果发现用户 prompt 和需求文档存在明确冲突：

1. 不得直接选择其中一方作为准则。
2. 不得继续输出确认版 PSM 改动判断。
3. 必须暂停并向用户确认。
4. 确认问题必须列出冲突点，并让用户选择以用户 prompt 为准、以需求文档为准、按用户指定的合并/裁剪范围为准。

只有用户确认后，才能继续做 PSM 改动判断。

## 候选系统发现

本 Skill 不在自身说明中内置候选系统清单或职责说明。候选系统必须从知识库中发现。

候选系统发现顺序：

1. 读取 `wiki/registry/REGISTRY-Applications.md`。
2. 从注册表中提取所有 Application 页面。
3. 读取与计费/结算模块、需求关键词或用户指定范围相关的 Application 页面。
4. 如果用户明确要求只在若干系统中判断，则候选系统以用户限定范围为准，但仍必须读取对应 Application 文档确认职责。
5. 如果知识库中存在横向职责边界 Source，例如系统梳理、职责边界、系统对比类文档，可作为候选系统发现和边界判断的辅助证据；但不能替代 Application 文档。

规则：

- 不得把未在知识库 Application/Source 中出现的系统写成确认版改动系统。
- 若需求可能涉及知识库外系统，只能列为“外部依赖 / 待确认”。
- 若 Application 文档缺失，应标记该系统职责证据不足。

## PSM 判断证据优先级

判断某个 PSM 是否需要改动时，证据优先级如下：

1. `wiki/applications/<system>.md`
2. `wiki/sources/**`
3. `wiki/modules/**`
4. `wiki/platform-capabilities/**`
5. `wiki/maps/**`
6. `raw/**` 及必要时飞书原文

Application 文档中应重点读取 Summary、核心职责、主要能力、上下游与边界、非职责边界、需求评估提示、证据来源。

若 Application 页面与 Source/raw 冲突，应标记“来源冲突”，并回查更原始的 Source/raw 或飞书原文。

## 默认查询顺序

1. 读取 `AGENTS.md`、`wiki/registry/REGISTRY.md`、`wiki/registry/REGISTRY-Applications.md`。
2. 从 `REGISTRY-Applications.md` 定位用户明确提到、与需求关键词匹配、横向职责边界 Source 中提到、与计费/结算 Module 相关的 Application 页面。
3. 从 `REGISTRY-Sources-*` 中搜索系统梳理、职责边界、系统对比、系统白皮书、日常分享中的系统说明、架构说明等横向职责边界 Source。
4. 根据需求关键词补充读取 `REGISTRY-Sources-日常分享.md`、`REGISTRY-Sources-系统白皮书.md`、`REGISTRY-Sources-技术方案.md`、`REGISTRY-Sources-需求文档.md`、`REGISTRY-Sources-ADR决策.md`、`REGISTRY-Modules.md`、`REGISTRY-PlatformCapabilities.md`、`REGISTRY-Maps.md`。
5. 当 Source 摘要不足以支撑字段、接口、状态机、资金流、费用项、费率、结算周期、单据状态、配置开关、数据表、MQ topic、Timer、TCC、PSM 交互细节等事实时，回查 raw / 飞书原文。

## 判断流程

1. **读取并解析需求输入**：如果用户输入是飞书需求文档链接，先读取飞书正文。从用户 prompt 和需求文档中提取标题、用户补充范围/改动点/排除项、需求摘要、背景、目标、改动点、功能/方案、接口/字段/配置/数据/任务/MQ/回调、明确提到的系统/PSM/上下游、验收标准/上线范围。
2. **检查用户 prompt 与需求文档是否冲突**：如果存在明确冲突，暂停并请求用户确认。
3. **读取候选 Application 文档**：基于 `REGISTRY-Applications.md` 发现候选 Application，并读取相关 Application 文档。
4. **读取横向职责边界 Source**：如果知识库中存在系统梳理、职责边界、系统对比类 Source，应读取它们作为辅助判断材料。
5. **读取需求相关 Source**：补充读取与需求关键词、场景、接口、字段、任务、配置相关的 Source 或 Map。
6. **先判定需求域，再收敛 PSM**：需求域默认只能是 `计费` 或 `结算` 二选一；若同时关联两域，按主要改动职责归类。按需求域收敛候选 PSM，不因资金流、上下游、历史链路或联调验证中出现某系统就列为需要改动。
7. **额外检查 settle_faas**：如果需求涉及接收/过滤/转发计费结算 MQ 消息、消息类型区分、topic、FaaS Timer、事件触发或下游 RPC 编排，必须读取 `settle_faas` Application/Source 并判断是否需要协同改动。
8. **形成判断**：只输出明确需要改动的 PSM；若存在不确定项，简要列入待确认。

---

## 默认输出策略

默认情况下，本 Skill 只输出两部分，且顺序固定：

1. 需求域
2. 改动涉及的 PSM / Application

默认输出格式：

```md
需求域：<计费 | 结算>

改动涉及的 PSM：

- `<psm_1>`
- `<psm_2>`
```

默认不要输出主改/协同、待确认、完整判断表、每个系统排除理由、大段证据清单、详细关键词映射、完整需求内容提取表或说明性文字。

只有当用户质疑、追问、要求依据、要求说明为什么、要求列出待确认/不改系统/主改协同/详细判断表时，才补充这些内容。

### 详细输出触发条件

当用户明确要求详细分析、给依据、给证据、给判断表、说明为什么、哪些系统不需要改、输出完整评估，或用户对默认结论提出疑问时，再输出完整结构：需求关键内容提取、判断表、主改/协同/不改/待确认、需求关键词命中、系统级证据、排除理由、不确定性。

---

## 输出要求

默认输出要求：

1. 默认第一行必须输出 `需求域：<计费 | 结算>`，且只能二选一。
2. 默认第二部分只输出 `改动涉及的 PSM` 列表。
3. 默认不输出主改/协同、待确认、证据、解释、排除理由、完整判断表或其他说明。
4. 只有用户质疑或追问时，才补充主改/协同、待确认、证据路径、判断依据、排除理由和不确定性。
5. 不输出知识库外系统为确认版改动系统。

详细输出要求：

当用户要求详细说明或提出疑问时，必须补充需求关键内容提取、判断表、主改/协同/不改/待确认、证据路径、关键词命中、排除理由、不确定性。

## 证据分级

- **A 级**：`wiki/applications/` 下的 Application/PSM 文档。
- **B 级**：`wiki/sources/` 下的 Source 摘要，以及通过 raw 回查到的飞书原文。
- **C 级**：`wiki/modules/`、`wiki/platform-capabilities/`、`wiki/maps/`。
- **D 级**：知识库中记录的实现线索，例如接口、字段、表、topic、Timer、TCC、配置。
- **E 级**：飞书补充检索结果；若与 Git-only 知识库冲突，必须说明冲突。

优先使用高等级证据。低等级证据不得覆盖高等级证据。

## 最终自检

默认输出前必须检查：

1. 是否确认 `llm-wiki-git` 可用。
2. 是否识别到 Git-only LLM Wiki 仓库。
3. 是否读取仓库 `AGENTS.md`。
4. 是否在需要读取飞书时检查 `lark-cli` 可用性和认证状态。
5. 是否读取 `REGISTRY.md` 和 `REGISTRY-Applications.md`。
6. 是否读取候选 Application 页面。
7. 是否优先依据 Application 文档判断 PSM 职责。
8. 是否分析了用户 prompt 中的改动点、范围约束和排除项。
9. 是否重点分析了需求文档中的改动点、功能/方案章节。
10. 如果用户 prompt 与需求文档存在明确冲突，是否已暂停并请求用户确认。
11. 是否先判定需求域并按需求域收敛 PSM。
12. 默认输出的需求域是否只在 `计费` / `结算` 中二选一。
13. 是否针对 MQ/FaaS/Timer 类改动额外检查 `settle_faas`。
14. 默认输出是否只包含需求域和改动涉及的 PSM，而非主改/协同、待确认、证据、解释或冗长完整表格。

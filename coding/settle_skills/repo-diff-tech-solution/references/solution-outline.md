# 技术方案文档结构

根据「多仓库分支 diff + PRD」生成技术方案时的章节骨架与写作要点。用 `lark-doc` skill 撰写 `.lark.md` 时按此组织，图表用 `![preview](...)` 嵌入到对应章节。

## 章节编号规范

**所有一级、二级章节标题统一加编号**，风格更规范、便于引用：

- 一级章节用 `1.`、`2.`、`3.` …（如 `## 1. 背景 / 需求说明`）。
- 二级章节用父级序号 + 点 + 子序号（如 `### 3.1 模块变更`、`### 3.2 接口变更`）。
- 「首屏摘要（TL;DR）」是文档开头的 callout，不参与编号。
- 编号从「背景 / 需求说明」开始连续递增；若某章节（如接口文档）无实际内容而省略，后续章节序号顺延，保持连续不跳号。

## 首屏摘要（TL;DR）

文档开头放一个 callout 摘要，包含：本方案对应的需求范围、涉及的仓库数量与分支、核心改动一句话结论、主要风险/影响提示。

## 1. 背景 / 需求说明

- 来源于 `prd_content`，提炼需求要解决的问题、目标、关键场景。
- 明确本次技术方案覆盖的范围与不覆盖的范围。
- 建议放**架构图**：展示本次变更触及的系统/服务/模块全景。

## 2. 变更范围概述

- 用表格列出涉及的仓库：仓库、对比分支、base 分支、变更文件数、增删行数（数据来自 `diff_summary.json` / `diff_summary.md`）。
- 一段话概述整体改动方向，以及多仓库之间如何联动。

## 3. 核心改动分析

按「模块 / 接口 / 数据结构」三个维度组织（每个维度作为一个二级章节，可按仓库再细分）：

- **3.1 模块变更**：新增/修改/删除了哪些模块、职责，对应满足 PRD 的哪条需求。
- **3.2 接口变更**：接口/RPC/路由的签名、入参、返回、错误码变化；标明是否破坏兼容。接口名、方法名等标识逐字保留，不缩写。（此处是**概览性**说明，字段级明细放到「接口文档」章节。）
- **3.3 数据结构变更**：表结构、DTO、配置、存储格式的变化；是否需要数据迁移。
- 建议放**流程图**：新增或变化的业务处理流程 / 核心链路；放**时序图**：关键交互（尤其跨仓库/跨服务）的调用时序。

## 4. 接口文档

从 diff 中识别涉及 **HTTP handler / RPC handler / API 接口** 的变更（典型信号：路由注册、gin/hertz/kite handler、thrift/protobuf service 方法、IDL 定义、Controller/Endpoint、请求/响应结构体 struct/DTO 变化），为每个受影响接口生成一份接口文档。**入参/出参/示例的事实依据来自 diff 中的 IDL/handler/struct/注解**，不可凭空编造字段；无法从 diff 推断的字段如实标注「diff 中未体现」。

每个接口按如下结构撰写（可用小标题 + 表格）：

- **接口名称、路由 / 方法**：接口业务名 + HTTP 路由与方法（`POST /api/v1/xxx`）或 RPC 服务方法名（`ChargeService.CalcFee`）。
- **入参说明**（表格）：字段名 | 类型 | 是否必填 | 说明。
- **出参说明**（表格）：字段名 | 类型 | 说明。
- **请求 / 响应示例**：JSON 代码块，给出典型请求体与响应体。
- **变更内容重点突出**：在字段说明或独立「本次变更」小节中，用标注区分改动类型——
  - ✨ 新增字段
  - ⚠️ 修改字段（类型/含义/是否必填/默认值变化）
  - ❌ 删除字段
  并一句话说明每处改动的原因（对应 PRD 的哪条需求 / 哪处代码）。

若本次 diff 未涉及任何对外接口变更，可省略本章节（后续章节序号顺延），并在「核心改动分析」中说明本次为纯内部逻辑/数据改动。

## 5. 影响分析

- **依赖影响**：受影响的上下游服务、调用方、SDK 使用方。
- **风险**：兼容性、数据迁移、性能、回滚风险；每条风险给出应对/缓解措施。
- 若 PRD 与实际代码改动存在不一致，在此如实标注差异与建议。

## 6. 工作量及排期

基于 diff 改动规模（文件数、增删行、接口/数据结构复杂度）与仓库依赖关系，给出**有依据**的工作量拆解与排期，包含两个二级章节。工时不可随意填写，需与「变更范围概述」的统计对得上；负责人从 MR author / commit author（或 Bits 需求创建人）提取，**不可编造具体人名**，无法确定时写「待指派」。

- **6.1 改动点分析**：按仓库把核心改动点拆成表格（每个仓库的核心改动点单独一行，改动点多时可拆多行），列：所属系统 | 改动点 | 负责人 | 研发估时。
  - *所属系统*：仓库名 / 服务名。
  - *改动点*：该行对应的具体改动（如「新增 BANK_CHANNEL_CODE_TYPE 计费维度」），来自 diff 分析。
  - *负责人*：从该仓库 MR author / commit author 提取；未知写「待指派」。
  - *研发估时*：单位人日，结合改动规模粗估（如小改动 0.5~1 人日、中等 2~3 人日、大改动 5+ 人日），并保证与实际 diff 规模匹配。
- **6.2 项目成员及排期**：给出两张表——
  - **分系统估时**：列 模块 | 接口人 | 耗时/排期 | 日期。按仓库/模块分行，*日期从当前日期（执行时的真实日期）按工作日顺推*，要求有明确检查点（起止日）。
  - **里程碑节点**：列 里程碑 | 时间段。必须包含节点：开发 / 联调 / 提测 / BOE测试 / PPE测试 / 上线 / 开实验 / 数据回收，各节点时间段从当前日期按工作日顺推填写，前后衔接、不重叠矛盾。

> **排期日期计算**：以执行当天的真实日期为起点，按**工作日**顺推（跳过周末）。执行前用 `truetime` skill（或等效方式）确认「今天」的准确日期，再据此推算各节点起止日，避免用示例里的旧日期。工时之和应与 6.1 的研发估时大致自洽。

## 7. 验证与灰度

给出可落地的上线保障方案，包含三个二级章节：

- **7.1 三板斧（可有效监控 / 可灰度 / 可应急）**：
  - *可有效监控*：本次变更需重点观察的监控指标（QPS/耗时/成功率/错误码/关键业务指标）与告警配置；结合改动内容给出应观察哪些新增或受影响的指标。
  - *可灰度*：灰度策略（按流量比例 / 白名单 / 机房 / 特定渠道等），灰度开关或配置位（若 diff 中存在特性开关/TCC/配置项则引用其名），以及灰度放量步骤。
  - *可应急*：应急回滚方案——代码回滚方式、开关关闭方式、数据回滚/补偿方式；明确回滚耗时与影响面。
- **7.2 发布顺序**：列出各代码仓库、DML（数据库变更）、配置变更等的发布先后顺序，**结合实际仓库依赖关系给出合理排序并说明理由**。一般原则（按实际情况调整）：先做向后兼容的 DDL/DML → 再发被依赖的底层服务 / 公共 SDK → 再发上层调用方服务 → 最后打开配置/灰度开关；下线字段则顺序相反。用有序列表或表格呈现。
- **7.3 发布清单（CheckList）**：把发布顺序拆成可勾选步骤，用表格呈现，每步包含：步骤 | 执行人 | 操作内容 | 预期结果 | 回滚条件。执行人默认可用需求创建人 / 各仓库改动作者，无法确定时写「待指派」。

## 写作要点

- 结论、数字、影响判断要有依据（来自 diff 或 PRD），避免空泛描述。
- 每个实质性小节尽量配一个可视锚点（表格 / callout / 画板图）。
- 遵循 `lark-doc` skill 对 design-doc 类文档的写作与格式规范。

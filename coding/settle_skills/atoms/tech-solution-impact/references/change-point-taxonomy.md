# 变更点分类与报告规范

技术方案里描述的「变更」大多是自然语言，而影响面图谱（`impact_index.json`）只认三类可查询对象：
**DB 字段、DB 表、配置项**。解析的核心任务，就是把方案文字里的变更点归一到这三类可查询目标，
其余类型（Proto/接口、枚举/常量、离线数据集）标注出来交人工评估。

## 一、可自动查询的变更点

| 类型 | 图谱 key | 方案里的典型写法 | 解析规则 |
|------|----------|------------------|----------|
| DB 字段 | `db:<表>.<列>` | "新增 `channel_code` 字段"、"`table.col` 加列" | 点分形式直接命中；裸列名（如 `channel_code`）会**展开为所有含该列的表**（一个列名可能落在多张表） |
| DB 表 | `db:<表>` | "新增表 `xxx`"、"`xxx` 表结构调整" | 表名命中后聚合该表下所有被使用字段的入口 |
| 配置项 | `cfg:<KEY>` | "TCC 新增 `XXX_CONFIG`"、"配置 `KEY` 调整" | 大写下划线 key 命中 `cfg:` 索引 |

**为什么用「图谱字典命中」做主过滤**：图谱是对支付/结算多仓库静态分析的产物，其中的表名/列名/配置 key
就是这个域里真实存在的对象。方案文字里凡是能命中字典、且邻近出现「新增/变更/调整/删除/字段/维度」等
变更信号词的标识符，几乎都是真实的变更或波及对象。这样在不依赖大模型的情况下就能得到高精度候选。

**裸列名展开的意义**：方案常只写"新增 channel_code"，不写落在哪张表。一个列名在支付/结算域可能出现在
多张表，逐表查询才能得到完整影响面，避免漏掉某个仓库的入口。

## 二、无法自动查询的变更点（标注 + 人工评估）

图谱只建模了「入口 → 方法 → DB/配置」的链路，以下类型查不到入口，解析器会单独列出：

- **Proto / 接口字段变更**：接口新增字段的影响，通常等价于其背后读写的 DB 字段影响面——优先在方案里找到该接口对应的落库字段，按 DB 字段查询。
- **枚举 / 常量变更**：如"新增银行渠道枚举"。若枚举值最终落到某个 DB 列（如 `channel_code`），就按该列查询；纯前端/展示枚举无后端影响面。
- **离线数据集 / Hive 表**：如 `caijing_pay.dwd_xxx`。这类库.表不在在线服务图谱内，解析器归入 `unresolved_hints`，报告里提示人工评估离线链路。

处理原则：**能落到 DB 字段/表/配置的，就转成对应查询；落不到的，如实标注为人工排查项**，不要臆造入口。

## 三、解析产物结构（extract_change_points.py 输出）

```json
{
  "doc": "方案文件路径",
  "change_points": [
    {"raw": "channel_code", "type": "field",
     "resolved_targets": ["bytepay_settle_order.channel_code", ...],
     "signal": true, "occurrences": 6, "entry_hint": 101,
     "evidence": ["...新增 channel_code 字段..."]}
  ],
  "review_candidates": [ ... ],
  "unresolved_hints": [ ... ]
}
```

`entry_hint` 是倒排索引里各目标入口数之和，用于粗排；真实去重后的入口数在聚合阶段给出。

## 四、聚合报告结构（analyze_impact.py 输出）

聚合结果 JSON（`--out-json`）与报告正文（`--out-md`）包含四个核心板块，最终飞书文档按此组织：

1. **概览摘要**：变更点数、去重后受影响入口总数、涉及仓库数、P0/P1/P2 分布。
2. **跨仓库风险汇总**：被多个仓库共享读写的表（`shared_by`）。这是最易漏改的高危项——改一张共享表的字段，所有共享方仓库的入口都要同步评估回归。
3. **变更点 → 受影响入口映射**：每个变更点命中的去重入口数、涉及仓库、是否跨仓共享。
4. **回归建议优先级**：入口按「被多少个变更点命中 + 是否落在跨仓共享表 + 入口类型」排序：
   - **P0**：被 ≥3 个变更点命中，或跨仓共享表上被 ≥2 个变更点命中 → 核心链路，必须优先回归。
   - **P1**：被 ≥2 个变更点命中，或落在跨仓共享表 → 重点回归。
   - **P2**：仅被单个变更点命中 → 常规回归。

## 五、结果解读注意

- **入口 = 可触达功能面**：Kitex RPC 是上游/前端能直接调的接口，MQ 是消息驱动功能。入口越多、跨 PSM 越多，辐射越广。
- **查不到入口 ≠ 没风险**：可能是纯内部使用、经未建模路径访问、或图谱未覆盖，必要时人工确认。
- **图谱是某次构建的快照**：若近期代码结构大改，需先由 `code_graph_system` 流水线重建图谱再查，否则结果滞后。
- **调用链举证**：需要"为什么这个入口会受影响"的证据链时，用同目录 `impact_query.py <目标>`（默认带调用链）单独查证。

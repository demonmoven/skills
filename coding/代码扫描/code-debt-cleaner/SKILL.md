# Code-Debt-Cleaner 🧹

## 描述

Code-Debt-Cleaner 是一个代码债务每日治理工具，帮助你从「定期大扫除」转变为「每日扫地」。支持多种问题类型，自动随机选择问题类型和扫描目录，避免重复劳动，优先发现和修复容易处理的问题，自动创建分支、提交、推送。
**微型 PR 原则**：每次最多修复 10 个问题，保持改动小而可控

建议配合定时任务触发使用，实现代码债务的持续治理。

### 使用场景

当用户出现以下情况时触发此技能：

- 用户请求清理代码债务，clean code debt
- 用户说"使用CodeDebtCleaner技能清理代码债务"

## 工作流程

1. **prepare.sh**：随机选择问题类型和目录，输出 JSON 包含 `all_selected_types`、`tool_types`、`llm_types`、`directories`
2. **scout.sh**：扫描 tool 类型的问题，接受 `-t`（类型）和 `-d`（目录）参数，输出 JSON
3. **技能逻辑**：根据 prepare.sh 的结果，有 `tool_types` 就调用 scout.sh，有 `llm_types` 就直接用 LLM 分析

### 随机化策略

- **问题类型**：从 35 种类型中随机选择 2-4 个，自动分离 tool 和 llm 类型
- **目录**：优先选择深度 2-4 的具体子目录，随机选择 1-3 个，排除隐藏目录

## 重构策略

| 重构手法                                                   | 定义                                                          | 核心思路                                                     | 识别信号                                                                                   | 适用场景                                                         |
| ------------------------------------------------------ | ----------------------------------------------------------- | -------------------------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| **Extract Method**                                     | 把一段可以独立表达意图的代码，从原函数中提取出来                                    | 给行为命名，从"怎么做"变成"在做什么"                                     | 函数里有几段不同逻辑、某段代码需要加注释才能看懂                                                               | 业务流程函数太长、if/for/while 嵌套逻辑过多                                 |
| **Introduce Explaining Variable**                      | 把复杂表达式的结果放进命名清晰的临时变量                                        | 给表达式加"语义标签"，帮助理解                                         | if 条件很长充满布尔组合、数学/金额/时间计算复杂                                                             | 复杂条件表达式、复杂业务规则计算、校验/计费/权限逻辑                                  |
| **Split Temporary Variable**                           | 如果一个变量被赋予多个不同含义，就拆成多个                                       | 一个变量只能代表一个概念，避免语义混乱                                      | 一个变量被多次赋值且每次意义不同、变量名很泛                                                                 | 长函数中间计算步骤多、财务/订单/库存多阶段数据处理                                   |
| **Replace Temp with Query**                            | 把临时变量所保存的表达式提炼成查询函数                                         | 把逻辑从局部状态提升为对象能力，便于后续重构                                   | 某个临时变量由复杂表达式计算得到、该值在函数中被多次使用                                                           | 函数内部计算逻辑较复杂、某计算结果具有命名价值                                      |
| **Remove Assignments to Parameters**                   | 不要直接修改传入参数，使用新的局部变量承接                                       | 参数应该表示"输入"，而不是"可随意改写的工作变量"                               | 方法参数进入函数后马上被重新赋值、读代码时分不清原始值和修改后值                                                       | 字符串拼接、金额修正、时间偏移等处理逻辑、旧代码把参数当临时变量用                            |
| **Inline Temp**                                        | 如果某个临时变量只是保存一个简单表达式的结果，直接用表达式替换它                            | 减少局部状态，让代码更紧凑                                            | 临时变量只被使用一次、变量名没有提供更强语义、赋值语句非常简单                                                        | 清理多余中间变量、为 Extract Method 做准备                                |
| **Inline Method**                                      | 如果一个函数体和函数名一样清楚，把函数调用替换为函数本体                                | 减少不必要的间接层，让代码更直接                                         | 函数体只有一两行且函数名没提供额外语义、读代码时频繁跳转                                                           | 过度封装、为了"形式上的优雅"拆出太多无意义小函数                                    |
| **Replace Method with Method Object**                  | 当一个函数过长且充满局部变量时，把这个函数变成一个对象                                 | 让局部变量变成对象字段，为进一步拆分创造条件                                   | 一个函数又长又复杂、局部变量很多且彼此依赖强、Extract Method 一做就要传很多参数                                        | 复杂计费/评分/推荐/规则计算、大型转换逻辑                                       |
| **Substitute Algorithm**                               | 将一个函数内部的算法整体替换成更清晰、更简单或更高效的实现                               | 在保证行为一致的前提下，直接用更好的算法替换                                   | 某函数逻辑正确但特别难懂、旧算法是历史遗留补丁叠出来的、已有更简单标准化的实现                                                | 排序/过滤/聚合/匹配/计费/校验规则重写、"能跑但没人敢动"的核心函数                         |
| **Move Method**                                        | 如果一个函数更多地使用另一个类的数据或行为，就把它搬到更合适的类中                           | 让函数待在最了解它所操作数据的对象那里                                      | 一个方法频繁调用另一个对象的 getter、方法内部主要操作的是别的类的数据                                                 | DTO/Entity/VO 上挂了很多外部逻辑、Service 里塞了过多与领域对象强相关的计算             |
| **Move Field**                                         | 如果一个字段被另一个类更多地使用，或者从语义上更属于另一个类，就把它搬过去                       | 字段应该属于真正拥有它、解释它、维护它的对象                                   | 某字段的 getter 被另一个类频繁调用、当前类几乎不使用该字段                                                      | 领域对象拆分不清、聚合边界设计不合理、一些状态字段被"顺手挂在某类上"                          |
| **Extract Class**                                      | 如果一个类承担了过多职责，就从中提炼出一个新类，把相关字段和方法搬过去                         | 拆职责，把经常一起变化、一起使用的一组字段/方法抽成独立类                            | 一个类字段很多方法很多、类里存在明显的"子主题"、某些字段和方法总是一起出现                                                 | God Object/巨型类、领域模型和展示逻辑揉在一起、配置/状态/统计/校验等不同职责混合              |
| **Inline Class**                                       | 如果一个类几乎没有独立职责，存在感很弱，反而增加理解成本，就把它并回使用它的类中                    | 保留没有形成真正抽象的类只会增加跳转和维护成本，该合并时就合并                          | 某个类很小几乎没行为、它的所有方法都只是简单委托、使用者必须频繁穿透这个类才能干正事                                             | 过度设计后的"空壳类"、历史遗留拆分失败、某类原本有意义但演进后已经失去独立价值                     |
| **Hide Delegate**                                      | 如果客户端需要通过一个对象去访问另一个委托对象的成员，可以在中间对象上提供转发方法                   | 客户端知道的内部结构越多，耦合就越强，把结构细节藏起来                              | 调用方频繁写出 obj.getX().getY() 这样的链式访问、客户端需要知道过多内部结构                                        | 领域对象对外暴露太多内部导航、Service/Facade 希望收敛对下游对象的访问                   |
| **Remove Middle Man**                                  | 如果一个类只是简单地把请求转发给另一个类，没有提供真正价值，就让客户端直接调用目标对象                 | 中间层只有在真的提供了抽象/隔离/约束/聚合价值时才值得存在                           | 某个类的大量方法都只是 return delegate.xxx()、客户端调用中间层并没有获得更好的语义                                   | 过度封装、历史遗留 facade/wrapper 已失效、某类曾有职责但后来退化成传话筒                 |
| **Introduce Foreign Method**                           | 当你需要为一个外部类增加功能，但又不能修改它本身时，在当前客户类中增加一个以该对象为参数的辅助函数           | 以较低成本补足能力，先在自己的代码里增加一个"外加函数"                             | 你反复写某段针对外部类的操作逻辑、很想给某个库类"加个方法"、修改原类不现实或不安全                                             | 标准库类型扩展、第三方 SDK 对象辅助处理、日期/金额/字符串/集合等外部对象增强逻辑                 |
| **Introduce Local Extension**                          | 当你需要多次扩展某个无法修改的外部类时，建立一个本地扩展类，以子类或包装类形式为它增加行为               | 把扩展能力集中管理，而不是散落在各处                                       | 针对同一个外部类写了很多辅助函数、业务代码中到处都是同类包装逻辑、某个第三方类型在系统里被高频使用且原生能力不足                               | 对日期时间/金额/地址/字符串等常用类型做业务增强、对第三方返回对象做统一封装                      |
| **Self Encapsulate Field**                             | 让类内部访问自己的字段时，也统一通过 getter/setter，而不是直接访问字段                  | 给字段套上一层可控入口，为未来改造留出扩展点                                   | 某字段目前是直接访问但未来可能变成计算属性、子类可能需要改写字段访问逻辑、你准备对字段做更多封装或迁移                                    | 继承体系中字段访问逻辑可能变化、需要为字段访问插入校验/缓存/懒加载、为 Move Field 做铺垫          |
| **Replace Data Value with Object**                     | 如果一个数据项不仅仅是原始值，还带有行为、规则或语义，就把它从基本值升级为对象                     | 把原始值升级为有语义的对象，提升领域建模表达力                                  | 某个字符串/数字在多个地方有重复处理逻辑、某字段有专门的格式/校验/规则、你总在写 parse/format/validate                        | 金额/手机号/邮箱/身份证/地址/订单号/区间/比例等、代码中反复处理同一类原始值                    |

## 通用约束

- **小步重构**：每次最多修复 5 个问题，保持 PR 微型化，避免大规模改动
- 必须先扫描，再修复，再验证，顺序不能乱
- **充分利用 LLM 能力**：尽可能多的任务交给 LLM 处理，包括代码分析、修复方案生成、重构等
- **只在必要时询问**：仅在高风险、不确定的情况下才等待用户确认
- **保持功能不变**：所有重构都必须保证功能等价，改善代码质量，不改变外部行为
- **测试护航**：修复前后确保测试通过，验证失败必须立即回滚所有修改
- **始终展示 diff**：展示修改内容让用户知道发生了什么
- 不要自动推送到远程，必须等用户确认

## 执行流程

### 1. 准备

1. 检查当前目录是否有 go.mod 文件
2. 运行 `bash resources/prepare.sh` 随机选择类型和目录
   - 日志行以 `[LOG]` 开头，展示给用户
   - 提取不以 `[LOG]` 开头的 JSON 结果
3. 解析 JSON 结果：
   - `tool_types`：需要用工具处理的类型
   - `llm_types`：需要用 LLM 处理的类型
   - `directories`：随机选择的目录

### 2. 安装工具

根据 `tool_types` 按需安装：

- 如果为空，跳过安装工具
- 如果包含除 duplicated\_code 外的其他类型 → 检查并安装 golangci-lint
  - 检查 golangci-lint 是否可用：`command -v golangci-lint`
  - 如果不可用，运行：`go install github.com/golangci/golangci-lint/cmd/golangci-lint@latest`
- 如果包含 duplicated\_code → 检查并安装 dupl
  - 检查 dupl 是否可用：`command -v dupl`
  - 如果不可用，运行：`go install github.com/mibk/dupl@latest`

### 3. 扫描问题

- **有 llm\_types**：在随机选择的 `directories` 中用 LLM 分析代码坏味道
- **有 tool\_types**：运行 `bash resources/scout.sh -t <tool_types> -d <directories>`
- 合并所有找到的问题

### 4. 选择问题

- 如果没有找到问题，告知用户并结束
- 如果找到问题，必须优先从 `prepare.sh` 随机选择的问题类型中选择问题实例来修复
- 按优先顺序选择 3-5 个可修复的问题（跳过自动生成的文件）
- 向用户展示找到的问题和选择的问题，等待确认

### 5. 修复问题

对选中的每个问题：

1. 读取文件内容
2. 执行类型对应的处理方式
3. **主动生成修复/重构方案**：
   - 识别需要修复的位置
   - 生成修复/重构后的完整代码
   - 确保保持原有功能不变
4. 向用户展示修复前后的对比（diff）
5. 简要说明修复/重构思路
6. **等待用户确认**：
   - 如果用户确认，保存修复后的代码
   - 如果用户不确认，建议用户手动修复或放弃此问题

### 6. 验证

**⚠️ 关键：必须完整验证整个项目，不能只验证修改的包！**

1. **先检查 Git 状态**：确保只修改了必要的文件
2. **运行完整编译（必须）**：
   - **禁止**只编译修改的包（如 `go build ./pkg/xxx`）
   - **必须**运行 `go build ./...` 编译整个项目
   - 如果编译失败，回滚所有修改，告知用户详细错误信息并结束
3. **运行静态检查**：使用 golangci-lint 检查是否有新的问题被引入
4. **运行测试**：`go test ./...` 确保测试通过，可选。如果测试时间过长可以跳过，但要告知用户；如果测试失败，回滚修改，告知用户错误信息并结束

### 7. GitOps 操作

1. 检查 Git 状态，确保当前工作区干净（除了我们刚做的修改）
2. 运行 `bash resources/gitops.sh create-branch [选项]` 创建新分支
3. 运行 `bash resources/gitops.sh commit [选项]` 提交修改
4. 询问用户是否要推送到远程仓库
5. 如果用户确认推送，运行 `bash resources/gitops.sh push`
6. 告知用户推送成功，可以创建 PR/MR 了

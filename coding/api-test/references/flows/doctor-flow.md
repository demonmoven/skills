# 测试结果诊断流程

用于在 `test-flow.md` 的 `4.1 测试结果分析诊断` 中，对接口测试执行结果进行结构化总结、证据链分析和根因诊断。

## 摘要

接口测试结果诊断的关键，不是把测试断言做得更复杂，而是把 `接口契约`、`请求与响应`、`运行环境`、`日志链路`、`代码变化` 组织成一条统一证据链，最终输出一份精简、可执行、带置信度说明的诊断结论。是在测试完成后回答以下问题：

- 这次失败更像是哪一层的问题
- 当前结论是基于哪些证据得出的
- 哪些证据还缺失，导致不能强行定案
- 用户下一步最值得做的动作是什么

## 适用时机

在完成一次 HTTP 或 RPC 接口测试后，若需要进入结果分析诊断阶段，使用本文件。典型场景包括：

- 测试失败后，需要快速归因
- 已获取 `logid`，希望基于测试结果和上下文继续做深度诊断
- 用户提供了 `logid`、测试链接、`PSM` 或接口名，希望直接做排障

## 核心思想

### 1. 诊断本质上是证据拼装

不要把一次失败简单理解为“接口失败了”。真正需要判断的是失败属于哪一层。至少需要围绕以下五类证据做交叉验证：

1. 现象证据：测试结果、状态码、业务码、断言失败点、请求与响应摘要
2. 结构证据：IDL、接口定义、字段规范、版本信息
3. 变化证据：代码分支、MR Diff、提交、最近发布变更
4. 现场证据：`logid`、日志片段、Trace、关键异常
5. 环境证据：`<VRegion>`、`<ENV>`、`<CLUSTER>`、`<VDC>`、实例状态

只要关键证据缺失，就不能把猜测写成确定结论。

### 2. 先分类，再下钻

先判断这次更像是请求参数问题、契约问题、环境问题还是服务端问题，再决定优先查看哪类证据。不要一开始就陷入日志细节。

### 3. 拒绝单证据定案

不能只凭一条错误日志、一个 HTTP 5xx、一个 Diff hunk 或一个 BAM 版本页面，就下最终结论。高置信度结论至少需要两类核心证据交叉验证。

### 4. 结论必须服务下一步动作

诊断结论不是为了“解释得像”，而是为了指导后续修复、补测、重试或转交。每次输出都必须包含下一步建议。

## 最小输入契约

优先采用渐进式输入，不要一开始要求用户提供过多上下文。

### 最低可用输入

- `<VRegion>` + `logid`
- 或 `<VRegion>` + `<psm>`
- 或 `<VRegion>` + `报错信息`

### 标准输入

- `<VRegion>` + `<psm> + logid`
- `或 <VRegion>` + `<psm> + 报错信息`
- 或 `<VRegion>` + `<psm> + 报错信息 + Logid`+ 接口名

### 可自动补全的信息

在已有上下文足够时，应尽量自动补全以下信息，而不是全部依赖用户手工提供：

- 请求方法与接口名
- 请求参数和响应摘要
- `HTTP status`、`biz_status_code`、`duration`
- 是否存在 `logid`
- 当前环境、泳道、集群、实例信息
- 是否涉及 BAM / Codebase IDL 分支
- 是否存在 Mock、染色、场景化规则

## 标准流程

### Step A：构建诊断上下文

先整理本次诊断的基础上下文：

- `interface_context`：`<psm>`、接口名、协议、方法签名
- `test_context`：请求参数、响应结果、状态码、耗时、断言表现
- `env_context`：`<VRegion>`、`<ENV>`、`<CLUSTER>`、`<VDC>`、`<IPport>`
- `log_context`：`logid`、关键日志、Trace、错误关键词
- `code_context`：相关分支、IDL 分支、最近变更、是否有 Mock

若存在缺失项，应明确标记，不得虚构。

### Step B：先输出结果摘要

无论成功或失败，默认先给出测试结果摘要，而不是直接进入深度分析：

- 接口是否调用成功
- 命中的环境或地址
- 状态码、业务码、响应耗时
- 是否获取到 `logid`
- 关键响应字段或关键错误信息
- 当前可见的初步判断

### Step C：确认是否继续深度分析

测试结果分析默认跳过。只有当用户明确要求继续分析时，才进入深度诊断。

建议使用明确问法：

`是否需要我基于本次测试结果、上下文和已有证据继续做接口测试结果分析与诊断？`

处理规则：

- 用户明确不需要：停留在结果摘要层
- 用户明确需要：进入下一步
- 若缺少 `logid`、环境信息、接口定义或其他关键证据：明确数据缺口，但仍可基于现有信息继续做低置信度诊断

### Step D：执行结果分析

测试结果分析统一使用本文件定义的证据链诊断流程完成，不再依赖 `analyze-result` 命令。

执行时按以下顺序组织证据：

1. 先读取测试结果中的原始现象证据：
   - 请求参数
   - 响应状态码与业务码
   - 响应体关键字段
   - 错误信息
   - 耗时
2. 再补充结构证据与环境证据：
   - 接口定义与 IDL 分支
   - `<VRegion>`、`<ENV>`、`<CLUSTER>`、`<VDC>`、`<IPport>`
   - 是否存在 Mock、染色、场景化规则
3. 若已有 `logid`、关键日志、Trace 或人工提供的现场信息，将其作为补充证据使用；没有则如实说明缺失
4. 按 `根因分类框架` 完成归类，并按 `推荐报告结构` 组织输出

若当前证据不足以支持高置信度结论，应明确降级为 `medium` 或 `low` 置信度，不得为了完整性强行定案。

### Step E：归类、降噪、给建议

在摘要和分析结果基础上，完成三件事：

1. 给出根因分类
2. 给出最强证据摘要
3. 给出下一步动作建议，并说明是否值得立即重试

## BAM / IDL 一致性诊断原则

### 关键原则

`测试请求侧使用的 IDL Version`，不等于 `运行时实例真实编译使用的 IDL 版本`。

因此，在涉及 IDL、字段不一致、结构不兼容等问题时，不能只看测试页面选择的 BAM 版本，就写“契约一致”。

### 必须区分两侧事实

1. 请求侧 IDL：本次测试请求究竟按哪个 BAM 版本，或哪个 Codebase 分支 / commit 来构造请求与解析 schema
2. 运行时侧 IDL：目标实例当前部署版本，对应的运行时代码实际使用了哪个 IDL 版本
3. 一致性结论：只有两侧都能回到同一条可追溯版本链时，才可以判定为真实一致

### 一致性结论分档

涉及 BAM / IDL 一致性时，统一使用以下四档结论：

- `confirmed_match`：请求侧版本与运行时反查出的编译 IDL 版本同源且可追溯
- `confirmed_mismatch`：两边版本明确不同
- `weak_match`：两边看起来相近，但缺少运行时闭环证据
- `unverifiable`：只能拿到测试侧版本，无法反查运行时实际编译 IDL 版本

只有 `confirmed_match` 才能表达“真实一致”。

### 当前 skill 中的落地要求

当你只能拿到 BAM 页面版本、`get-service-idl-setting` 结果或分支信息时：

- 可以说明“请求侧 schema 使用了什么”
- 不可以自动上升为“运行时契约一致”
- 若缺少运行时侧证据，应明确降级为 `weak_match` 或 `unverifiable`

## 根因分类框架

诊断归类时，优先归到一级分类之一并给出标准枚举值。完整的 10 类根因（枚举值 / 典型信号 / 建议动作）见 [doctor-reference.md](../refs/doctor-reference.md#根因分类框架)。

## 诊断约束

### 1. 失败必须分层

失败用例必须优先区分请求、Mock、环境、通信、IDL、代码、配置、数据、依赖问题，不允许只写“调用失败”。

### 2. 日志只是证据之一

日志可以帮助缩小范围，但不能只凭单条 error 日志就直接判定服务缺陷。

### 3. BOE / PPE 优先查环境侧

在 BOE / PPE 等测试环境中，若请求失败，应优先检查：

- 环境名称是否正确
- 集群、实例是否存在
- 流量是否命中目标泳道
- Mesh、路由、权限是否正常

### 4. 契约问题优先查结构侧

若响应字段缺失、类型不符、解析失败，应优先检查：

- 必填字段
- 字段类型
- 枚举值
- 响应结构
- IDL 分支与版本一致性

### 5. 代码问题尽量定位到代码位置

若诊断倾向服务端代码异常，应尽量给到：

- 关键方法
- 关键文件
- 关键日志片段
- 必要时给出关联变更线索

### 6. 报告必须精简

输出应突出：

- 结论
- 证据
- 根因分类
- 动作建议

不要平铺原始长日志或大量无关上下文。

## 推荐报告结构

每次输出尽量遵循统一的 7 段结构：一句话结论、根因分类、证据摘要、关键日志/诊断结论、修复或补测建议、是否建议重新执行测试、置信度与数据缺口。各段的具体要求见 [doctor-reference.md](../refs/doctor-reference.md#推荐报告结构)。

## 输出模板

按场景选用模板，模板正文见 [doctor-reference.md](../refs/doctor-reference.md#输出模板)：

- 模板一（结果摘要版）：仅输出结果摘要，或用户未要求深度分析时使用。
- 模板二（综合诊断版）：已完成 doctor 证据链诊断且具备较完整证据时使用。

## 禁止事项

- 禁止把猜测包装成确定根因
- 禁止在缺少关键证据时伪造现场结论或强行补全事实
- 禁止把“测试页选择的 IDL 版本”直接等同于“运行时真实编译 IDL 版本”
- 禁止只引用一条日志就断定服务代码有缺陷
- 禁止调用 `analyze-result` 作为本 Skill 的测试结果分析主路径
- 禁止在生产环境相关场景中，忽略写操作和数据污染风险

# Harness Doc Gardener — 文档新鲜度巡检与修复

## 核心理念

> **文档兜不住的时候，就变成定时炸弹。**
> Agent 分不清哪些还有效，人类也懒得更新，它就这么悄悄变成了误导源。

本技能定期巡检仓库文档体系，检测与实际代码不一致的内容，产出修复清单或直接提交修复。

## 检测维度

| 维度 | 检测内容 | 严重度 |
|------|---------|--------|
| 路径有效性 | 文档中引用的文件/目录路径是否实际存在 | 高 |
| 命令可执行性 | 文档中列出的命令在对应目录能否执行 | 高 |
| 目录结构一致性 | 文档中的 tree 展示是否与实际目录匹配 | 中 |
| 交叉引用完整性 | 文档间相对路径引用是否指向真实文件 | 高 |
| 导航表覆盖度 | AGENTS.md 导航表是否遗漏了新增的重要文件 | 中 |
| 术语一致性 | 文档中的项目名/模块名是否与代码一致（检测历史遗留旧名） | 低 |
| 描述准确性 | 模块职责描述是否仍然准确（需要理解代码语义） | 低 |

## 执行流程

### Step 1: 确定巡检范围

- **全量巡检**：扫描仓库所有 `.md` 文件
- **增量巡检**：只扫描自上次巡检以来有代码变更的模块对应的文档
- **指定范围**：用户指定某个文档或目录

询问用户选择模式。增量巡检需要一个基准点（commit hash 或日期）。

**增量巡检操作方法**：
1. 确定基准点：`git log --oneline -20` 选择上次巡检的 commit
2. 获取变更文件列表：`git diff --name-only <base>..HEAD`
3. 从变更文件反推受影响的模块目录
4. 只扫描受影响模块对应的 AGENTS.md + ARCHITECTURE.md + 相关 docs/
5. 同时检查新增但未被任何文档引用的 `.md` 文件

### Step 2: 收集文档清单

扫描仓库，列出所有待检文档：
- `AGENTS.md`（根 + 所有模块级）
- `ARCHITECTURE.md`
- `README.md`
- `docs/**/*.md`
- 其他 `.md` 文件

### Step 3: 逐文件巡检

对每个文档执行以下检查：

#### 3.1 路径有效性检查

从文档中提取所有文件/目录路径引用：
- Markdown 链接：`[text](path)`
- 代码块中的路径：`src/xxx/yyy.ts`、`pkg/xxx/`
- 反引号内的路径：`` `path/to/file` ``

对每个提取的路径，验证是否实际存在：
```bash
test -e "<resolved_path>" || echo "DEAD: <path> in <doc>:<line>"
```

#### 3.2 命令可执行性检查

从文档中提取 bash 代码块中的命令，验证：
- 命令所依赖的工具是否存在（`which <tool>`）
- 如果命令含 `cd <dir>`，该目录是否存在
- package.json scripts 中引用的 script name 是否存在

注意：不实际执行命令（可能有副作用），只检查前置条件。

#### 3.3a 目录树详尽度判断

文档中的目录树不需要列出每个文件，但应遵循以下原则：

- **必须列出**：所有一级子目录、所有代表独立职责的文件（如按业务域拆分的 Go 文件）
- **可以省略**：测试文件（`*_test.go`、`*.test.ts`）、生成文件、临时文件
- **判断标准**：如果一个新开发者看到目录树后，对"这个目录里有什么能力"的理解与实际偏差超过 30%，说明目录树需要更新
- **数量阈值**：如果实际文件数超过文档列出数的 2 倍，标记为"目录树严重过时"

#### 3.3 目录结构一致性

如果文档包含 tree 格式的目录展示（```text ... ```），对比实际目录：
- 文档中列出但实际不存在的条目 → 标记为"已删除"
- 实际存在但文档未列出的重要条目 → 标记为"缺失"

"重要"的判断：非 `.`、非 `node_modules`/`vendor`/`dist`/`__pycache__` 等忽略目录。

#### 3.4 交叉引用完整性

检查文档间的相对路径引用：
- `../docs/reference/xxx.md` → 解析为绝对路径后验证存在性
- 导航表中每一行的路径 → 验证存在性

#### 3.5 导航表覆盖度

对比根 AGENTS.md 的知识导航表与实际存在的文档：
- `docs/reference/` 下有新文件但导航表未收录 → 标记为"未索引"
- `docs/guidance/` 下有新文件但导航表未收录 → 标记为"未索引"
- 模块目录下有新的 AGENTS.md 但根导航未引用 → 标记为"未索引"

#### 3.6 术语一致性

搜索文档中是否残留已废弃的项目名/模块名/概念名：
- 需要用户提供"旧名 → 新名"映射（或从 git log 中推断）
- 如果无映射，跳过此检查

### Step 4: 产出报告

```markdown
## 文档巡检报告

### 巡检范围
- 模式：全量 / 增量（基准：<commit>）
- 扫描文件数：N
- 扫描时间：<timestamp>

### 问题汇总

| 严重度 | 数量 | 示例 |
|--------|------|------|
| 高（路径失效/引用断裂） | N | `backend/AGENTS.md:42` 引用不存在的 `pkg/cache/` |
| 中（目录过时/未索引） | N | `docs/reference/new-api.md` 未加入导航表 |
| 低（术语/描述过时） | N | 仍使用旧名 "OpenClaw" |

### 详细问题列表

#### [HIGH] 路径失效
| 文档 | 行号 | 引用路径 | 状态 |
|------|------|---------|------|
| `AGENTS.md` | 42 | `docs/reference/old-api.md` | 文件不存在（已删除？） |

#### [MED] 目录结构过时
| 文档 | 实际变更 |
|------|---------|
| `backend/AGENTS.md` | 目录树缺少 `pkg/newpkg/`（3 天前新增） |

#### [MED] 未索引文档
| 文件 | 应加入 |
|------|--------|
| `docs/reference/new-feature-api.md` | 根 AGENTS.md 导航表 + docs/AGENTS.md |

### 建议修复
（按严重度排序的具体修复动作列表）
```

### Step 5: 自动修复（征求确认）

对于可机械修复的问题，询问用户是否自动修复：

**可自动修复**：
- 导航表补充新增文档条目
- 目录树更新（基于实际 `ls` 结果重新生成）
- 交叉引用路径更正（如果能推断正确路径）
- 术语替换（旧名 → 新名）

**需要人工判断**：
- 引用的文件已删除 — 是删除引用还是恢复文件？
- 模块职责描述已过时 — 需要理解新的职责才能重写
- 命令已变更 — 需要确认新命令是什么

自动修复前展示 diff 预览，确认后执行。

## 使用模式

### 手动触发

用户在开发过程中随时调用，检查文档是否跟上了代码变更。

### 周期性巡检（推荐）

建议在以下时机触发：
- 每周一次全量巡检
- 每次大 feature 合并后增量巡检
- 每次文档体系刷新后验证巡检

### CI 集成（可选）

可作为 CI 步骤运行路径有效性和交叉引用检查（纯静态，无需代码理解）：
示例：检查所有 markdown 中的相对路径引用

```bash
find . -name "*.md" -exec grep -oP '\[.*?\]\(((?!http)[^)]+)\)' {} + | \
  while read match; do
    : "解析并验证路径..."
  done
```

## Gotchas

- **不要把所有 TODO/WIP 标记当问题报**。文档中明确标注"待补充"的部分是有意为之
- **增量巡检比全量更实用**。全量首次跑完建立基线后，日常用增量即可
- **目录树检查要排除生成产物**。`dist/`、`node_modules/`、`vendor/`、`__pycache__` 等不应出现在目录树中
- **"未索引"不一定是问题**。有些内部草稿文档不需要加入导航表
- **路径大小写在 macOS 上可能掩盖问题**。macOS 文件系统默认不区分大小写，但 Linux CI 会报错
- **自动修复要保守**。宁可列出待修复清单让用户确认，不要静默修改语义不确定的内容
